# JVM

> **一句话定位**：JVM（Java Virtual Machine，Java 虚拟机）是一台「软件模拟出来的计算机」，它负责把编译器产出的、与平台无关的 `.class` 字节码翻译成本地机器指令，并统一管理内存的分配与回收（垃圾回收 GC）。一句话说清它解决什么问题：**它把「一次编译、到处运行」变成现实，让 Java 程序员彻底告别手写 `malloc/free` 和操心平台差异。**

---

## 基础篇

基础篇从「JVM 是什么、内存长什么样、对象怎么创建」三条主线入手，把这台虚拟机的骨架搭起来。后面高级篇、原理篇的所有内容（类加载、GC、锁升级、JIT）都是在这套骨架上生长出来的。

### 一、JDK / JRE / JVM 三者关系与跨平台原理

#### 1. 背景：为什么需要 JVM

早期的 C/C++ 程序要「一次编译、多次编译」：同一份源码，在 Windows 上要编译一次生成 `.exe`，在 Linux 上要再编译一次生成 ELF 可执行文件，换个平台（甚至换个芯片架构 x86/ARM）就得重来。因为编译出来的机器码是**和 CPU 指令集、操作系统 ABI 强绑定**的。

Java 团队给出的解法是「**加一层**」：不直接编译成某个平台的机器码，而是编译成一种**中间的、与平台无关的字节码**（`.class`），再让每个平台各自装一个「翻译官」——JVM——在运行期把字节码翻译成本地机器码。这一层就是 JVM。

#### 2. 定义：三者的包含关系

| 名称 | 全称 | 核心职责 | 包含关系 |
| --- | --- | --- | --- |
| JVM | Java Virtual Machine | 执行字节码、管理内存、垃圾回收 | 最底层，只管「运行」 |
| JRE | Java Runtime Environment | 提供 Java 程序运行环境 | = JVM + 核心类库（rt.jar 等） |
| JDK | Java Development Kit | 开发工具包 | = JRE + 编译工具 `javac`、`javap`、`jar` 等 |

用一句话记忆：**JDK 是给开发者用的（含编译），JRE 是给运行者用的，JVM 是真正干活的**。

```
┌─────────────────────────────── JDK ───────────────────────────────┐
│  ┌───────────────────────── JRE ──────────────────────────┐       │
│  │  核心类库(rt.jar / jmods)                                │       │
│  │  ┌──────────────────── JVM ─────────────────────┐       │       │
│  │  │  类加载器 / 运行时数据区 / 执行引擎 / GC       │       │       │
│  │  └──────────────────────────────────────────────┘       │       │
│  └──────────────────────────────────────────────────────────┘       │
│  开发工具: javac(编译) / javap(反编译) / jar / jshell / jdb ...      │
└─────────────────────────────────────────────────────────────────────┘
```

#### 3. 跨平台原理：编译 + 解释的混合执行

Java 程序的执行链路是：

```
Hello.java --(javac 编译)--> Hello.class(字节码) --(JVM 解释/编译)--> 本地机器码
      [平台无关]                    [平台无关]                [平台相关]
```

- **前端（编译期）**：`javac` 把 `.java` 编译成 `.class`，这个字节码是**平台无关**的，一套字节码可以在任何装了 JVM 的机器上跑。
- **后端（运行期）**：各平台的 JVM 负责把同一份字节码翻译成自己平台的机器码，这一步是**平台相关**的，所以才需要每个平台各有一个 JVM 实现（Oracle HotSpot、OpenJ9、GraalVM 等）。

现代 JVM 不是纯「解释器」，而是「**解释器 + 即时编译器（JIT）混合执行**」：先解释执行快速启动，再把热点代码（反复执行的方法）编译成本地机器码缓存起来，之后直接跑机器码，性能逼近 C/C++。这一块在 [原理篇 JIT](#十六jit-即时编译) 展开。

::: tip 💡 面试题：Java 为什么能跨平台？
**结论**：靠 JVM 这一抽象层。**原因**：源码只编译成平台无关的字节码，跨平台差异由各平台 JVM 各自承担。**展开**：`.class` 字节码与 CPU/OS 无关，同一份字节码拿到 Windows/Linux/macOS 上的 JVM 都能执行；代价是运行期多一次「字节码 → 机器码」的翻译，这也就是 JVM 存在 JIT 优化的原因。
:::

### 二、JVM 运行时数据区（内存模型）

这是 JVM 面试的「重中之重」，几乎每一场 JVM 面试都会从这里开场。JVM 启动一个进程后，把系统分配给它的一大块内存，按用途切分成若干**运行时数据区**。先看全景图：

```
┌──────────────────────────── JVM 运行时数据区 ────────────────────────────┐
│                                                                            │
│  ┌─────────────── 线程私有(随线程生灭, 各线程一份) ───────────────┐         │
│  │  程序计数器(PC)   虚拟机栈(Java Stack)   本地方法栈(Native Stack) │         │
│  └────────────────────────────────────────────────────────────────┘         │
│                                                                            │
│  ┌─────────────── 线程共享(进程级, GC 主战场) ────────────────────┐         │
│  │              堆(Heap)          方法区/元空间(Metaspace)          │         │
│  │         ┌──────┐ ┌──────┐       存放类元信息/常量池/静态变量       │         │
│  │         │新生代│ │老年代│                                        │         │
│  │         └──────┘ └──────┘                                        │         │
│  └────────────────────────────────────────────────────────────────┘         │
│  运行时常量池(JDK8 后移入堆)   直接内存(堆外, NIO 使用)                       │
└────────────────────────────────────────────────────────────────────────────┘
```

#### 1. 程序计数器（PC Register）

- **背景/定义**：CPU 在多线程下靠「时间片轮转」来回切换线程，线程被切走再切回来时，必须记得自己上次执行到哪一条指令，否则就乱套了。程序计数器就是**当前线程所执行字节码的行号指示器**。
- **特性**：
  - 每个线程**独立一份**，是唯一一个 JVM 规范里**不会抛任何 `OutOfMemoryError` 的区域**。
  - 如果线程正在执行 Java 方法，PC 记录的是正在执行的**字节码指令地址**；如果执行的是 `native` 方法，PC 值为 `undefined`（未定义）。
- **小结**：它是「线程切回现场」的锚点，体积极小但必不可少。

#### 2. 虚拟机栈（Java Stack）

- **背景/定义**：Java 方法调用的本质是「入栈出栈」。每个方法被执行时，JVM 都会同步创建一个**栈帧（Stack Frame）**压入虚拟机栈，方法执行结束（正常返回或抛异常）栈帧弹出销毁。虚拟机栈描述的是**Java 方法执行的内存模型**。
- **栈帧的完整结构**：

```
┌──────────────── 栈帧(Stack Frame) ────────────────┐
│  局部变量表(Local Variables)                        │  ← 存放方法参数 + 局部变量, 以「变量槽 slot」为单位
│  操作数栈(Operand Stack)                            │  ← 计算过程的「草稿纸」, 字节码指令在这里操作
│  动态链接(Dynamic Linking)                          │  ← 指向运行时常量池中该方法的引用, 支持多态
│  方法返回地址(Return Address)                       │  ← 记录调用方下一条指令位置
│  附加信息                                            │  ← 调试/异常表等信息
└─────────────────────────────────────────────────────┘
```

- **局部变量表**：以 `slot`（变量槽）为最小单位，`long`/`double` 占 2 个 slot，其余占 1 个。**复用机制**：某个 slot 对应的变量作用域结束后，该 slot 可被复用，所以一个方法里局部变量多不一定栈就大。
- **操作数栈**：字节码指令的「中间结果缓冲区」。比如 `a + b`，会先把 `a`、`b` 压栈，`iadd` 指令弹出两个数相加再把结果压回去。
- **异常**：如果线程请求的栈深度超过允许深度，抛 `StackOverflowError`（典型：无终止条件的递归）；如果栈可以动态扩展但扩展时内存不足，抛 `OutOfMemoryError`。

```java
public class StackDemo {
    static int depth = 0;

    // 演示 StackOverflowError：无限递归, 栈帧不断入栈直到栈空间耗尽
    static void recursive() {
        depth++;
        recursive(); // 每递归一次压入一个新栈帧
    }

    public static void main(String[] args) {
        try {
            recursive();
        } catch (StackOverflowError e) {
            // 默认栈深度约 1 万层(受 -Xss 影响)
            System.out.println("栈溢出, 当前深度 = " + depth);
        }
    }
}
```

#### 3. 本地方法栈（Native Method Stack）

- **定义**：与虚拟机栈作用类似，区别只在于它为 `native` 方法（用 C/C++ 写的、`native` 关键字声明的方法，如 `Thread.start0()`、`System.arraycopy()`）服务。
- **HotSpot 实现**：HotSpot 虚拟机把**本地方法栈和虚拟机栈合并**了，直接用一套栈，所以日常开发中几乎不用单独区分它。
- **小结**：面试时一句话带过即可，重点记住「虚拟机栈管 Java 方法，本地方法栈管 native 方法，HotSpot 里二者合一」。

#### 4. 堆（Heap）

- **背景/定义**：堆是 JVM 管理的**最大的一块内存**，存放**几乎所有对象实例和数组**。它是所有线程共享的，也是**垃圾回收的主战场**，所以常被称为「GC 堆」。
- **分代结构**（现代主流收集器都基于分代假设设计）：

```
┌──────────────────────────────── 堆(Heap) ────────────────────────────────┐
│  ┌────────────────── 新生代(Young Generation) ──────────────────┐  老年代 │
│  │  Eden区(伊甸园)  │  Survivor0(from)  │  Survivor1(to)  │  Old  │
│  │  默认 8          :  1                :  1              │       │
│  └────────────────────────────────────────────────────────────┘       │
│      新对象出生地       GC 存活对象来回搬运的两个半区        熬过多次 GC 的对象 │
└──────────────────────────────────────────────────────────────────────────┘
```

  - **新生代**：新对象默认在 Eden 区分配。Eden : S0 : S1 默认比例 **8:1:1**（可用 `-XX:SurvivorRatio=8` 调整）。每次 Minor GC 后，Eden 和 from 区存活的对象被复制到 to 区（from/to 角色互换）。
  - **老年代**：存放长期存活的对象、大对象。
- **异常**：堆内存不足时抛 `OutOfMemoryError: Java heap space`。
- **小结**：堆的设计核心是「**分代假设**」——大部分对象朝生夕死，少数对象长命百岁；按存活时间分代，才能用不同算法分别高效回收（详见 [垃圾回收算法](#七垃圾回收gc基础)）。

#### 5. 方法区 / 元空间（Method Area / Metaspace）

- **背景/定义**：方法区用于存放**已被虚拟机加载的类元信息**：类的结构（字段、方法、构造器）、运行时常量池、静态变量、方法字节码、即时编译后的代码等。
- **演进**：这是面试高频点。JDK7 及以前，方法区由「**永久代（PermGen）**」实现，属于堆的一部分；**JDK8 起彻底移除永久代，改用「元空间（Metaspace）」**，直接使用**本地内存（堆外内存）**。
- **为什么要从永久代移到元空间**：
  1. 永久代有固定大小上限（默认约 80MB 左右），动态加载类多时容易 `PermGen OOM`；元空间默认只受本地内存限制，几乎不会因为类太多而 OOM。
  2. 永久代属于堆，参与堆 GC，而类的卸载条件苛刻，导致回收效率低；元空间独立于堆，与堆 GC 解耦。
- **异常**：元空间不足时抛 `OutOfMemoryError: Metaspace`（常因 CGLIB 动态代理大量生成类、或频繁加载类而触发）。

#### 6. 运行时常量池（Runtime Constant Pool）

- **定义**：`.class` 文件里有一个「常量池（Constant Pool Table）」，类加载后其中的内容进入方法区的**运行时常量池**。它存两类东西：**字面量**（字符串、`final` 常量值）和**符号引用**（类/字段/方法的全限定名、描述符）。
- **重要演进（高频陷阱）**：**JDK7 起，字符串常量池和静态变量从永久代移到了堆中**；JDK8 运行时常量池也随方法区整体迁到了元空间。所以「运行时常量池在哪」这个问题的答案随版本不同，面试要答出「JDK8 后常量池随元空间、字符串常量池在堆里」。
- `String.intern()` 操作的对象就是字符串常量池（详见 [原理篇字符串常量池](#十五字符串常量池与-intern)）。

#### 7. 直接内存（Direct Memory）

- **定义**：不属于 JVM 运行时数据区，但被频繁使用——它是**堆外内存**，通过 `NIO` 的 `ByteBuffer.allocateDirect()` 分配，使用 `Unsafe` 底层实现。
- **意义**：避免数据在 Java 堆和本地堆之间的来回拷贝，显著提升 IO 性能（零拷贝）。
- **异常**：直接内存不足时抛 `OutOfMemoryError: Direct buffer memory`，受 `-XX:MaxDirectMemorySize` 控制（默认等于 `-Xmx`）。

#### 8. 内存区域异常总结表

| 区域 | 线程归属 | 存什么 | 可能异常 | 是否 GC |
| --- | --- | --- | --- | --- |
| 程序计数器 | 私有 | 字节码行号 | 无 | 否 |
| 虚拟机栈 | 私有 | 栈帧（局部变量表、操作数栈等） | `StackOverflowError` / OOM | 否 |
| 本地方法栈 | 私有 | native 方法栈帧 | 同上 | 否 |
| 堆 | 共享 | 对象实例、数组 | `OOM: Java heap space` | **是（主战场）** |
| 方法区/元空间 | 共享 | 类元信息、常量池、静态变量 | `OOM: Metaspace` | 参与类卸载 |
| 运行时常量池 | 共享 | 字面量、符号引用 | 随所在区 | 否 |
| 直接内存 | 堆外 | NIO 缓冲区 | `OOM: Direct buffer memory` | 否 |

::: tip 💡 面试题：JVM 内存区域中哪些会发生 OOM，哪些不会？
**结论**：堆和方法区/元空间、直接内存会 OOM；虚拟机栈/本地方法栈主要抛 `StackOverflowError`（也可能 OOM）；程序计数器是唯一不抛任何异常的区域。**原因**：堆和元空间大小受配置硬限制，栈的异常主要是「深度」问题而非「容量」问题。**展开**：答题时先按「线程私有 / 共享」二分，再逐个点名异常类型，就能显得结构清晰。
:::

### 三、对象创建过程（new 一个对象发生了什么）

「new 一个对象发生了什么」是 JVM 面试的经典连环问，通常会一路追问到内存分配方式、并发安全、内存布局、锁升级。我们把它彻底拆开。

#### 1. 完整流程（六步）

```
new Object()
    │
    ▼
① 类加载检查   常量池定位符号引用 → 若类未加载/未初始化, 先触发类加载(见高级篇)
    │
    ▼
② 分配内存    在堆上划出一块大小固定的内存(指针碰撞 或 空闲列表)
    │
    ▼
③ 初始化零值  把这块内存全部清零, 保证实例字段不赋值也能拿到默认值(0/null/false)
    │
    ▼
④ 设置对象头  写入 Mark Word(哈希码/GC年龄/锁状态) + 类型指针
    │
    ▼
⑤ 执行 <init> 调用构造方法, 按程序员意图初始化字段、执行构造代码块
    │
    ▼
⑥ 返回引用    把对象在堆中的地址压回操作数栈, 赋给引用变量
```

#### 2. 内存分配方式：指针碰撞 vs 空闲列表

第②步在堆上划内存，选哪种方式取决于**堆是否规整**：

| 分配方式 | 适用堆状态 | 原理 | 对应收集器 |
| --- | --- | --- | --- |
| 指针碰撞（Bump the Pointer） | 堆规整（无碎片） | 已用内存和空闲内存中间有个指针，分配就指针往后挪一段 | 复制、标记-整理（Serial、ParNew、G1） |
| 空闲列表（Free List） | 堆不规整（有碎片） | JVM 维护一张空闲块列表，从里面找到一块足够大的分出去 | 标记-清除（CMS） |

#### 3. 并发分配安全：CAS + 重试 / TLAB

对象分配是极其频繁的操作，多线程同时 `new` 时可能撞在同一块内存上。两种解法：

1. **CAS + 失败重试**：对分配动作做乐观锁，失败就重试（保证原子性，但高并发下自旋开销大）。
2. **TLAB（Thread Local Allocation Buffer，本地线程分配缓冲）**：给每个线程在 Eden 区**预先划分一小块私有缓冲区**，线程在自己的 TLAB 里分配对象（无锁、极快）；TLAB 用完才走 CAS 申请新缓冲区。默认开启（`-XX:+UseTLAB`）。

#### 4. 对象在内存中的布局

对象在堆里的内存布局分三块：

```
┌──────────────────────── 对象内存布局 ────────────────────────┐
│  对象头(Header)  │  实例数据(Instance Data)  │  对齐填充(Padding) │
│  ┌─────────────┐ │                           │                     │
│  │ Mark Word   │ │  父类+子类声明的字段        │  补齐到 8 字节的     │
│  │ 类型指针     │ │  (同字段顺序受分配策略影响)  │  整数倍(方便对齐)    │
│  │ (数组加长度)  │ │                           │                     │
│  └─────────────┘ │                           │                     │
└───────────────────────────────────────────────────────────────┘
```

- **对象头**：分两部分。
  - **Mark Word（标记字）**：存哈希码、GC 分代年龄、锁状态标志、偏向线程 ID 等，它**随锁状态动态复用**（详见 [原理篇 Mark Word](#十一mark-word-字节级内存布局与锁升级)）。
  - **类型指针（Klass Pointer）**：指向方法区里该类的元数据，JVM 据此知道「这个对象是哪个类的实例」。（开启压缩指针后占 4 字节，默认 64 位下压缩。）
  - 如果是数组，对象头里还会多一段记录**数组长度**。
- **实例数据**：对象真正存的有效字段信息，包括从父类继承来的字段。字段排列顺序受「字段分配策略」影响（HotSpot 默认顺序：long/double、int/float、short/char、byte/boolean、引用类型，同类字段放一起以省填充）。
- **对齐填充**：HotSpot 要求对象起始地址是 **8 字节的整数倍**，所以对象大小不是 8 的倍数时用 padding 补齐。它只起占位作用，没有实际语义。

#### 5. 对象访问定位：句柄 vs 直接指针

JVM 拿到栈上的 `reference` 引用后，怎么找到堆里的对象？两种主流方式：

| 方式 | 结构 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 句柄池 | 栈引用 → 句柄池 →（对象指针 + 类型指针） | 对象被移动（GC 整理）时只需改句柄里的指针，引用不变，稳定 | 多一次间接寻址，慢 |
| 直接指针（HotSpot 采用） | 栈引用 → 直接指向对象 | 速度快（少一次定位），吞吐高 | GC 移动对象时要改引用本身 |

HotSpot 采用**直接指针**，这解释了为什么对象头里要放「类型指针」——因为引用直接指向对象，对象内部必须自带「我是哪个类型」的信息。

### 五、类加载机制（完整生命周期）

#### 1. 类加载的七个阶段

一个类从被加载到卸载，完整生命周期：

```
┌────────────────────────────── 类加载生命周期 ──────────────────────────────┐
│                                                                            │
│  加载 ──▶ 验证 ──▶ 准备 ──▶ 解析 ──▶ 初始化 ──▶ 使用 ──▶ 卸载             │
│  Loading  Verification Preparation Resolution Initialization               │
│                                                                            │
│  └──────── 连接(Linking) ────────┘        └─ 执行期按需进行(可懒加载) ─┘    │
│                                                                            │
└────────────────────────────────────────────────────────────────────────────┘
```

> 注意：**加载、验证、准备、初始化、卸载**这五个阶段的顺序是确定的（必须按此顺序开始），但**解析**阶段比较特殊——它在某些情况下可以在初始化之后才开始（这是为了支持 Java 的「动态绑定/晚期绑定」）。因此上图「连接」里只有验证和准备严格在初始化之前。

#### 2. 各阶段详解

| 阶段 | 做什么 | 关键点 |
| --- | --- | --- |
| 加载 | ① 通过全限定名获取二进制字节流；② 把静态结构转为方法区运行时数据；③ 在堆中生成 `java.lang.Class` 对象作为入口 | 获取字节流的来源极灵活：class 文件、jar 包、网络、动态代理生成，这也是自定义类加载器的切入点 |
| 验证 | 校验字节码合法性：文件格式、元数据、字节码、符号引用四类校验 | 保护 JVM 安全，防止恶意字节码破坏虚拟机 |
| 准备 | 为**静态变量**（`static`）分配内存并赋**默认零值** | `static int a = 10` 此时 `a` 仍是 0（不是 10！高频陷阱） |
| 解析 | 把常量池中的**符号引用**替换为**直接引用** | 符号引用是字面量（如 `"java/lang/String"`），直接引用是指针/句柄/偏移量 |
| 初始化 | 执行 `<clinit>`：为静态变量赋程序员指定的初值、执行静态代码块 | 真正执行「类构造器」，此时 `a` 才变成 10 |

#### 3. `<clinit>` 与 `<init>` 的区别（高频）

| | `<clinit>`（类构造器） | `<init>`（实例构造器） |
| --- | --- | --- |
| 触发时机 | 类初始化阶段 | 每次 `new` 对象时 |
| 内容来源 | 静态变量赋值 + 静态代码块，按**源码顺序**合并 | 构造方法 + 实例变量赋值 + 实例代码块 |
| 执行次数 | 每个类**只执行一次**（且加锁，线程安全） | 每创建一个对象执行一次 |
| 注意 | 接口的 `<clinit>` 只有在用到其常量时才执行 | 子类 `<init>` 会先隐式调用父类 `<init>` |

```java
public class ClinitDemo {
    static {
        // 静态代码块会在 <clinit> 中执行, 只跑一次
        System.out.println("static block");
    }
    {
        // 实例代码块会在 <init> 中执行, 每 new 一次跑一次, 且先于构造方法体
        System.out.println("instance block");
    }
    public ClinitDemo() {
        System.out.println("constructor");
    }
    public static void main(String[] args) {
        new ClinitDemo(); // 先 static block(类初始化), 再 instance block + constructor
        new ClinitDemo(); // static block 不再执行, 只跑 instance block + constructor
    }
}
```

#### 4. 类加载时机：主动引用 vs 被动引用

只有「**主动引用**」才会触发类的初始化，共 6 种场景（前 4 个最常见）：

1. 遇到 `new`、`getstatic`、`putstatic`、`invokestatic` 这四条字节码指令（即 `new` 对象、读写静态字段、调用静态方法）。
2. 使用 `java.lang.reflect` 反射调用。
3. 初始化子类时，若父类未初始化，先触发父类初始化。
4. 虚拟机启动时指定的主类（含 `main` 方法的类）会被初始化。
5. JDK7 动态语言支持（`MethodHandle`）。
6. JDK8 接口默认方法。

「被动引用」**不会**触发初始化，典型三类，面试常考：

```java
class Parent {
    static int a = 1;
    static final int CONST = 100; // 编译期常量, 会在常量池里被「常量传播」直接内联
    static { System.out.println("Parent init"); }
}
class Child extends Parent {
    static { System.out.println("Child init"); }
}

public class PassiveRefDemo {
    public static void main(String[] args) {
        // ① 通过子类引用父类静态字段, 只会初始化父类, 不初始化子类
        System.out.println(Child.a);      // 输出 Parent init, 没有 Child init

        // ② 通过数组定义引用类, 不会触发该类初始化
        Child[] arr = new Child[10];      // 不会输出任何 init

        // ③ 引用编译期常量, 不会触发初始化(常量已在编译期进常量池)
        System.out.println(Parent.CONST); // 不会输出 Parent init
    }
}
```

### 六、双亲委派模型

#### 1. 类加载器的层次结构

自 JDK9 模块化后，类加载器仍是这套三层 + 自定义：

```
┌─────────────────────────────────────────────────────────────┐
│  启动类加载器 BootstrapClassLoader (C++实现, 不是 ClassLoader 子类) │
│    └─ 加载 <JAVA_HOME>/lib 下的核心类: java.lang.*, java.util.*    │
│  平台类加载器 PlatformClassLoader (JDK9前叫扩展类加载器 ExtClassLoader) │
│    └─ 加载 <JAVA_HOME>/lib/ext 或 jdk 平台模块                      │
│  应用程序类加载器 AppClassLoader                                  │
│    └─ 加载 classpath 上用户写的类                                  │
│  自定义类加载器 (继承 ClassLoader, 重写 findClass)                  │
└─────────────────────────────────────────────────────────────┘
```

> 注意：JDK8 里中间那层叫「扩展类加载器 ExtClassLoader」，JDK9 起改叫「平台类加载器 PlatformClassLoader」，答题时说明版本差异是加分项。

#### 2. 双亲委派的工作流程

一个类加载器收到加载请求后，**先不自己加载，而是逐级向上委派给父加载器**；只有当父加载器无法加载时，才尝试自己加载。核心逻辑在 `ClassLoader.loadClass()`：

```java
protected Class<?> loadClass(String name, boolean resolve) throws ClassNotFoundException {
    synchronized (getClassLoadingLock(name)) {
        // ① 先查缓存: 自己是否已经加载过, 避免重复加载同一个类
        Class<?> c = findLoadedClass(name);
        if (c == null) {
            try {
                // ② 有父加载器就委派给父加载器(递归向上, 这就是「委派」)
                if (parent != null) {
                    c = parent.loadClass(name, false);
                } else {
                    // ③ 没有父加载器(顶到 Bootstrap), 交给启动类加载器
                    c = findBootstrapClassOrNull(name);
                }
            } catch (ClassNotFoundException e) {
                // 父加载器加载不到, 继续往下走自己加载
            }
            // ④ 父加载器都加载不了, 才调用 findClass 自己加载
            if (c == null) {
                c = findClass(name); // 自定义类加载器通常只重写这个方法
            }
        }
        if (resolve) {
            resolveClass(c);
        }
        return c;
    }
}
```

流程示意：

```
请求加载 java.lang.String
        │
        ▼
   AppClassLoader  ──委派──▶ PlatformClassLoader  ──委派──▶ BootstrapClassLoader
                                                              │ 找到, 直接返回
                                                              ▼
                                                         (加载成功, 不再向下)
请求加载 自定义 com.foo.User
        │
        ▼
   AppClassLoader ──▶ Platform ──▶ Bootstrap(找不到)
                                        │ 逐级回退
        ◀────────────────────────────────┘
        ▼
   AppClassLoader 自己加载 classpath 里的 com.foo.User
```

#### 3. 为什么要双亲委派

**防止核心类库被篡改，保证 Java 类型体系的安全与唯一**。设想：如果允许「谁先收到谁先加载」，黑客可以自己写一个 `java.lang.String` 塞进 classpath，替换掉 JDK 的 `String`，轻则程序行为异常，重则植入恶意代码。双亲委派让核心类**永远优先由 Bootstrap 加载**，用户写的假 `String` 永远不会生效。

另一个原因是**避免类的重复加载**：同一个类被不同的类加载器各加载一份，会产生两个「相等却不同」的 Class 对象，破坏 `equals`/`instanceof` 的语义。

::: tip 💡 面试题：双亲委派模型的作用是什么？
**结论**：保证核心类库的唯一性和安全性，防止用户自定义同名类替换 JDK 核心类。**原因**：通过「先委派父加载器、父加载不了才自己加载」的顺序，让核心类永远优先由顶层加载器加载。**展开**：同时它也避免了类的重复加载——JVM 判断「两个类是否相同」的标准是「全限定名 + 类加载器」两者都相同，若同名类被不同加载器各加载一份，就会出现两个语义冲突的类。
:::

#### 4. 如何打破双亲委派（进阶）

双亲委派不是铁律，有几处经典「破坏」场景，面试问「什么时候打破双亲委派」时答这几个：

| 场景 | 为什么打破 | 实现方式 |
| --- | --- | --- |
| JDBC（SPI 机制） | 接口在核心库（Bootstrap 加载），实现类在厂商 jar（App 加载），核心库要反向加载第三方实现 | `Thread.currentThread().getContextClassLoader()` 线程上下文类加载器 |
| Tomcat 容器 | 每个 Web 应用隔离（各自加载自己的类），又共享容器类 | 自定义 `WebappClassLoader`，先自己加载再委派 |
| 热部署/热替换 | 需要动态加载、卸载类而不重启 JVM | 自定义类加载器，定期销毁旧加载器重建 |
| OSGi 模块化 | 模块间类隔离与动态导入导出 | 网状类加载器结构 |

### 七、垃圾回收（GC）基础

GC 是 JVM 面试的绝对核心，分为三层递进：**怎么判断垃圾 → 怎么回收垃圾（算法）→ 用什么回收（收集器）**。本节讲前两层。

#### 1. 如何判断对象可回收

**（1）引用计数法（已被淘汰）**

- 思路：每个对象维护一个计数器，被引用 +1，引用失效 -1，计数器为 0 即可回收。
- 缺点：**无法解决循环引用**——A 引用 B、B 引用 A，二者计数永远不为 0，但外界已无法访问，造成内存泄漏。
- 结论：JVM **不采用**此方法。

**（2）可达性分析算法（JVM 采用）**

- 思路：从一组被称为 **GC Roots** 的根对象出发，沿引用链（Reference Chain）向下搜索，搜索走过的路径叫「引用链」；能被搜到的对象是**存活**的，搜索不到的对象（即使相互引用）判定为**可回收**。

```
        GC Roots
       ╱    │    ╲
      ▼     ▼     ▼
    obj1  obj2  obj3 ──▶ obj4 ──▶ obj5
     │           │
     ▼           ▼
    obj6       obj7 ◀──▶ obj8   (obj7 和 obj8 互相引用, 但都不可达 → 判为垃圾)
```

- **GC Roots 包括哪些**（高频，务必背全）：
  1. 虚拟机栈（栈帧局部变量表）中引用的对象；
  2. 方法区静态属性引用的对象；
  3. 方法区常量引用的对象（如字符串常量池里的引用）；
  4. 本地方法栈中 JNI（native 方法）引用的对象；
  5. Java 虚拟机内部的引用（基本类型对应的 Class 对象、常驻的异常对象、系统类加载器）；
  6. 所有被 `synchronized` 持有的对象；
  7. 反映 JVM 内部情况的 JMXBean、回调等。

::: tip 💡 面试题：JVM 如何判断对象可回收？
**结论**：可达性分析算法——从 GC Roots 出发沿引用链搜索，不可达的对象判为垃圾。**原因**：引用计数法无法处理循环引用，可达性分析天然免疫循环引用。**展开**：即使两个对象互相引用，只要它们都不在 GC Roots 的引用链上，依然会被回收，这解决了引用计数法的致命缺陷。
:::

#### 2. Java 的四种引用类型

光有可达性分析还不够，Java 提供了四种引用强度，让程序能更精细地控制对象的生命周期：

| 引用类型 | 强度 | 回收时机 | 典型用途 |
| --- | --- | --- | --- |
| 强引用（Strong） | 最强 | 只要引用在，永不回收 | 普通 `Object o = new Object()` |
| 软引用（Soft） | 次强 | 内存不足时才回收 | 缓存、图片缓存 |
| 弱引用（Weak） | 较弱 | 下次 GC 无论内存是否够都回收 | `WeakHashMap`、ThreadLocal |
| 虚引用（Phantom） | 最弱 | 无法通过它获取对象，仅用于对象回收通知 | 管理直接内存的回收（`DirectByteBuffer` 的 Cleaner） |

```java
import java.lang.ref.*;

public class ReferenceDemo {
    public static void main(String[] args) {
        // 软引用: 内存充足时不回收, 适合做缓存
        SoftReference<byte[]> soft = new SoftReference<>(new byte[1024 * 1024]);
        // 弱引用: 下次 GC 就会被回收
        WeakReference<Object> weak = new WeakReference<>(new Object());
        // 虚引用: get() 永远返回 null, 必须配合 ReferenceQueue 使用
        PhantomReference<Object> phantom = new PhantomReference<>(new Object(), new ReferenceQueue<>());

        System.gc(); // 建议 JVM 执行 GC(不保证立即执行)
        System.out.println("weak 回收后: " + weak.get());   // 通常为 null
    }
}
```

#### 3. 垃圾回收算法（四大算法 + ASCII 图）

| 算法 | 核心思想 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 标记-清除（Mark-Sweep） | 先标记存活对象，再统一清除未标记对象 | 简单、无需移动对象 | ①产生内存碎片 ②两遍扫描效率不高 |
| 复制（Copying） | 内存分两块，存活对象复制到另一块，整块清空 | 无碎片、速度快（只需复制存活对象） | 浪费一半空间、存活对象多时复制成本高 |
| 标记-整理（Mark-Compact） | 标记后让存活对象向一端移动，清理边界外内存 | 无碎片、内存连续 | 移动对象需 STW、开销大 |
| 分代收集（Generational） | 按对象存活时间分代，不同代用不同算法 | 综合最优、实际主流 | 实现复杂 |

**标记-清除**：

```
回收前: [A] [·] [B] [·] [C] [·]     (· 表示垃圾)
标记:   [A] [x] [B] [x] [C] [x]     (A/B/C 存活)
清除:   [A] [ ] [B] [ ] [C] [ ]     → 产生内存碎片
```

**复制算法**：

```
┌─────────┬─────────┐         ┌─────────┬─────────┐
│  存活    │  空闲    │  GC 后  │  空闲    │  存活    │  (两块互换角色)
│ [A][B][C]│         │   ──▶  │         │[A][B][C] │
└─────────┴─────────┘         └─────────┴─────────┘
```

**标记-整理**：

```
回收前: [A] [·] [B] [·] [C] [·]
整理后: [A] [B] [C] [ ] [ ] [ ]   (存活对象向一端移动, 内存连续无碎片)
```

#### 4. 分代收集理论（实际落地）

现代 JVM 几乎都采用「分代」：**新生代对象朝生夕死用复制算法，老年代对象存活久用标记-整理/标记-清除**。新生代的复制算法有「优化版」——因为 98% 的对象活不过第一轮 GC，所以**不用 1:1 分两块**，而是按 **Eden:S0:S1 = 8:1:1** 分三块：

```
新生代(复制算法)每次 Minor GC 流程:
  Eden + S0(from) 的存活对象  ──复制──▶  S1(to)
  然后 Eden 和 S0 整块清空
  下一次 GC 时 S0/S1 角色互换(S1 变 from, S0 变 to)
  幸存对象「年龄」+1, 熬到 15 岁晋升老年代
```

::: tip 💡 面试题：新生代为什么用复制算法，老年代为什么不用？
**结论**：新生代大部分对象朝生夕死，每次存活对象少，复制成本低且无碎片；老年代存活率高，用复制会浪费一半空间且频繁搬运。**原因**：算法选择本质是按「对象存活率」来权衡。**展开**：分代收集理论建立在「弱分代假说」（绝大多数对象朝生夕死）和「强分代假说」（熬过多次 GC 的对象更难消亡）之上，两条假说决定了新生代用复制、老年代用标记-整理。
:::

### 八、垃圾收集器（GC Collector）

垃圾收集器是「算法」的具体实现，是面试最爱问的一环。按作用区域分代记忆：

#### 1. 收集器全景与组合

```
┌────────────────────── 新生代收集器 ──────────────────────┐   ┌──── 老年代收集器 ────┐
│  Serial   ParNew   Parallel Scavenge                     │   │  Serial Old          │
└──────────────────────────────────────────────────────────┘   │  Parallel Old        │
                                                               │  CMS                 │
┌──────────────────────── 整堆收集器(不分代或弱分代) ───────────────────────────────┐
│  G1(Garbage First)   ZGC   Shenandoah                                          │
└──────────────────────────────────────────────────────────────────────────────────┘
```

常见组合（JDK8 时代）：

- **Serial + Serial Old**：单线程，客户端/小内存场景。
- **ParNew + CMS**：经典的低延迟组合，JDK8 之前互联网主流。
- **Parallel Scavenge + Parallel Old**：吞吐量优先，**JDK8 默认**。

#### 2. 各收集器详解

| 收集器 | 作用代 | 算法 | 线程 | 核心特点 | 适用场景 |
| --- | --- | --- | --- | --- | --- |
| Serial | 新生代 | 复制 | 单线程 | 简单高效，GC 全程 STW | 客户端、单核、小内存 |
| ParNew | 新生代 | 复制 | 多线程 | Serial 的多线程版，唯一能与 CMS 搭配的新生代收集器 | 配合 CMS |
| Parallel Scavenge | 新生代 | 复制 | 多线程 | **吞吐量优先**，可自适应调节（`-XX:+UseAdaptiveSizePolicy`） | 后台批处理、计算密集 |
| Serial Old | 老年代 | 标记-整理 | 单线程 | 老年代版 Serial | 客户端 |
| Parallel Old | 老年代 | 标记-整理 | 多线程 | 吞吐量优先，JDK8 默认搭档 | 配合 Parallel Scavenge |
| CMS | 老年代 | 标记-清除 | 并发 | **最短停顿优先**，并发标记 | 互联网 B/S 系统（JDK8 前） |
| G1 | 整堆 | 分区+复制 | 并发 | **可预测停顿**，JDK9 默认 | 大堆（≥6-8G）、对停顿敏感 |
| ZGC | 整堆 | 染色指针+复制 | 并发 | 停顿 <10ms，可支持 TB 级堆 | 超大堆、极低延迟 |

#### 3. CMS 详解（高频）

CMS（Concurrent Mark Sweep）是**以最短停顿为目标的老年代收集器**，把 GC 过程拆成四步，只在其中两步需要 STW：

```
① 初始标记(STW, 极快)    标记 GC Roots 直接关联的对象
② 并发标记(与用户线程并发) 从 GC Roots 出发遍历整个对象图
③ 重新标记(STW)           修正并发标记期间因用户线程运行而变动的记录
④ 并发清除(与用户线程并发) 清除未标记对象
```

- **优点**：并发标记、并发清除，停顿短。
- **缺点（高频）**：
  1. **产生内存碎片**（标记-清除算法固有），碎片多了会导致「并发模式失败」，触发 Full GC（退化为 Serial Old）。
  2. **对 CPU 敏感**：并发阶段占用一部分 CPU，抢占用户线程资源。
  3. **浮动垃圾**：并发清除期间用户线程又产生的新垃圾，只能等下一轮回收。

#### 4. G1 详解（JDK9 默认，重点）

G1 把整个堆划分为**大小相等的多个 Region（默认 2048 个）**，每个 Region 可扮演 Eden、Survivor 或 Old 角色，不再要求新生代/老年代物理连续：

```
┌──── G1 堆(划分为等大 Region) ────────────────────────┐
│ [E] [E] [S] [O] [E] [H] [O] [E] [S] [O] [O] [E] ... │
│  E=Eden  S=Survivor  O=Old  H=Humongous(大对象专用)   │
└──────────────────────────────────────────────────────┘
  垃圾最多的 Region ──▶ 优先回收(故称 Garbage First)
```

- **核心思想**：不再「整堆一起回收」，而是维护一个**回收优先级列表**，每次在用户设定的停顿时间内，**优先回收「回收收益最大」（垃圾最多）的 Region**，从而做到「可预测的停顿时间」（`-XX:MaxGCPauseMillis=200`）。
- **跨 Region 引用**：用 **Remembered Set（记忆集）** 记录「谁引用了我」，避免全堆扫描。
- **回收过程**：初始标记 → 并发标记 → 最终标记 → 筛选回收（复制存活对象到空 Region）。
- **为什么 JDK9 把它设为默认**：G1 在停顿时间与吞吐量之间取得了更好平衡，且能处理超大堆，兼顾了低延迟与可维护性。

#### 5. 各版本默认收集器

| JDK 版本 | 默认新生代 | 默认老年代 | 默认整堆 |
| --- | --- | --- | --- |
| JDK6/7 | Parallel Scavenge | Parallel Old | - |
| JDK8 | Parallel Scavenge | Parallel Old | - |
| JDK9+ | - | - | **G1** |
| JDK15+（实验）| - | - | ZGC（低延迟备选） |

::: tip 💡 面试题：JDK8 和 JDK9 的默认垃圾收集器分别是什么？
**结论**：JDK8 默认 Parallel Scavenge + Parallel Old（吞吐量优先），JDK9 起默认 G1。**原因**：JDK8 时代服务器普遍追求吞吐量，JDK9 起应用规模变大、对停顿更敏感，G1 可预测停顿更契合。**展开**：可以用 `java -XX:+PrintCommandLineFlags -version` 查看当前 JVM 实际使用的收集器，这是面试和排障都常用的命令。
:::

#### 6. 收集器选择建议

- 单机/小内存/客户端：`Serial + Serial Old`。
- 后台批处理、计算密集、无交互：`Parallel Scavenge + Parallel Old`。
- 互联网应用、要求低停顿：`G1`（大堆首选）或 `CMS`（JDK8 前）。
- 超大堆 + 极低延迟：`ZGC`。

#### 6. 调优的一般思路

1. **明确目标**：优先吞吐量还是优先低停顿？（决定了选 Parallel 还是 G1/CMS）
2. **确定堆大小**：`-Xms = -Xmx`，堆不超过物理内存的 1/2~2/3，给 OS 和其他进程留余量。
3. **调新生代**：对象创建频繁的业务适当调大 `-Xmn`，减少对象过早进老年代。
4. **观察日志**：`-Xlog:gc*` 或 `jstat` 观察 Minor GC 频率和 Full GC 次数，Full GC 频繁是大问题。
5. **定位问题**：Full GC 频繁常见原因——元空间过小、大对象频繁进老年代、内存泄漏。
6. **验证**：压测对比调参前后吞吐量、停顿、GC 次数，避免凭感觉调参。

### 十、GC 完整机制：三色标记法与漏标问题

CMS 和 G1 的「并发标记」阶段，都不是简单的一次遍历，而是基于**三色标记法（Tri-color Marking）**，并且要处理并发场景下的「漏标」问题。这是 JVM 进阶面试的硬核考点。

#### 1. 三色标记法

把对象按标记进度染成三种颜色：

| 颜色 | 含义 |
| --- | --- |
| 白色 | 尚未被访问，GC 结束后白色对象即垃圾（不可达） |
| 灰色 | 自身已被访问，但其引用的子对象尚未全部访问完（正在遍历其出边） |
| 黑色 | 自身及其全部引用对象都已被访问 |

```
初始状态: 全部对象为白色
   GC Roots ──▶ 标记为灰色

遍历过程(核心循环):
   从灰色集合取一个对象 A
   把 A 直接引用的白色对象 B 都标记为灰色
   把 A 标记为黑色
   重复, 直到灰色集合为空

结束: 白色对象 = 垃圾, 黑色对象 = 存活
```

```
示例对象图:  A ──▶ B ──▶ C
             A ──▶ D
遍历:
  A 灰 → 遍历 A: B灰 D灰, A黑 → 遍历 B: C灰, B黑 → 遍历 C: C黑 → 遍历 D: D黑
最终: A/B/C/D 全黑(存活), 其余白色(垃圾)
```

#### 2. 并发标记的「漏标」问题

三色标记原本要求**在标记过程中对象引用关系不变**。但并发标记是和用户线程**同时运行**的，用户线程可能一边改引用一边被标记，导致两种错误：

- **多标（浮动垃圾）**：本应回收的对象被误标为存活。这会导致本次 GC 少回收一点垃圾，属于「可以接受」的错误，最多留到下一轮回收。
- **漏标（对象消失）**：**本应存活的对象被误判为垃圾回收掉了**。这是致命错误，会导致程序崩溃。

漏标发生的条件（必须**同时满足**两个条件，Wilson 1994）：

```
条件①: 一个黑色对象 A 新增了对白色对象 C 的引用
        (即: 赋值器插入了一条从黑到白的引用)
条件②: 删除或破坏了从灰色对象 B 到 C 的全部引用路径
        (即: C 唯一的「灰色上游」被切断, C 从图里「消失」了)
```

```
漏标示意:
        ┌─── A(黑) ──────┐  (条件①: A 新增引用 C)
        │                ▼
   B(灰)───(原引用被删)──▶ C(白)
   (条件②: B 对 C 的引用被删除)

结果: C 变成「黑色对象引用、但无灰色对象指向它」的孤儿 → 被当作垃圾回收 → 错误!
```

#### 3. 两种解决方案：增量更新 vs SATB

解决漏标的思路就是「破坏上面两个条件之一」：

| 方案 | 破坏哪个条件 | 做法 | 代表收集器 |
| --- | --- | --- | --- |
| 增量更新（Incremental Update） | 破坏条件① | 当黑色对象新增对白色对象的引用时，把**黑色对象重新标记为灰色**，让它在后续重新扫描一遍其出边 | CMS |
| 原始快照（SATB，Snapshot At The Beginning） | 破坏条件② | 记录「初始快照」，当灰色对象对白色对象的引用被删除时，把这个**被删除的引用记录下来**，视为存活，最后重新处理 | G1 |

- **增量更新**：核心是「**黑色对象插入新引用时，把它变回灰色**」，重新遍历它引用的对象，防止漏掉 C。
- **SATB**：核心是「**被删除的引用也当作存活**」，通过写屏障把「旧的引用值」记到 SATB 队列里，标记结束时统一处理这些旧引用，保证 C 不会被漏掉（代价是可能产生一点浮动垃圾，但绝对安全）。

#### 4. 写屏障（Write Barrier）

无论是增量更新还是 SATB，都依赖一个底层机制——**写屏障**。写屏障可以理解为「在对象引用赋值前后插入的一小段额外代码」，用来拦截引用变更事件：

```java
// 伪代码: 引用赋值 field = newValue 会被写屏障拦截
// 前置写屏障(Pre-Write Barrier): 在赋值前执行, SATB 用它记录「旧值」
// 后置写屏障(Post-Write Barrier): 在赋值后执行, 增量更新用它记录「新插入的引用」
```

::: tip 💡 面试题：G1 怎么解决并发标记的漏标问题？
**结论**：用 SATB（原始快照）——把标记开始时被删除的引用也当作存活，配合写屏障记录。**原因**：SATB 破坏的是「漏标条件②」，从根上保证灰色对象指向的旧引用不会被切断。**展开**：SATB 因为保留了「可能已死」的对象，会多产生一些浮动垃圾，但换来的是并发标记的绝对安全，这是 G1 在正确性与性能之间的取舍。
:::

### 十一、Mark Word 字节级内存布局与锁升级

Mark Word 是理解 `synchronized` 锁升级和 GC 分代年龄的**字节级基石**。它只有 8 字节（64 位 JVM，未开启压缩时），却在不同锁状态下**复用同一个存储空间**去存完全不同的数据。

#### 1. 64 位 Mark Word 布局

以 64 位 JVM（无锁状态，前 25 位存哈希码）为例，Mark Word 的内容随锁状态变化：

```
┌──────────────────────── Mark Word(64 bit) ──────────────────────────┐
│                                                                      │
│ 无锁(可偏向):  [unused:25][hashcode:31][unused:1][age:4][biased:1][01] │
│ 偏向锁:        [threadId:54]                [epoch:2][unused:1][age:4][biased:1][01] │
│ 轻量级锁:      [指向栈中锁记录的指针:62]                              [00] │
│ 重量级锁:      [指向 monitor 的指针:62]                              [10] │
│ GC 标记:      [空]                                                   [11] │
│                                                                      │
│  低 2 位 lock 标志: 01=无锁/偏向, 00=轻量级, 10=重量级, 11=GC 标记       │
└──────────────────────────────────────────────────────────────────────┘
```

关键字段解读：

- **lock 标志位（低 2 位）**：锁状态的核心判定位。
- **biased 标志位**：`1` 表示偏向锁，`0` 表示无锁。
- **age（4 位）**：GC 分代年龄，最大值 15（`1111`），这就是 `-XX:MaxTenuringThreshold` 默认 15 的由来——**4 个 bit 最多只能表示 0~15**。
- **hashcode（31 位）**：对象的哈希码（`identityHashCode`），一旦计算过就「固定」在 Mark Word 里。注意：**偏向锁状态下没地方存 hashcode**，所以对象一旦计算过 hashcode 或调过 `wait/notify`，就无法进入偏向锁。
- **threadId（54 位）**：偏向锁记录的持有线程 ID。
- **ptr_to_lock_record / ptr_to_monitor**：轻量级锁指向栈帧中的锁记录，重量级锁指向 ObjectMonitor。

#### 2. 锁升级的完整流程

`synchronized` 从 JDK1.6 起加入了锁升级机制（偏向锁 → 轻量级锁 → 重量级锁），避免每次加锁都直接申请重量级锁（重量级锁要操作系统的 mutex，代价高）：

```
                 synchronized 锁升级流程
                          │
                          ▼
             ┌──────── 无锁状态(01) ────────┐
             │ 首个线程尝试加锁                 │
             ▼                                │ 同一线程再次进入(重入)
        ┌─ 偏向锁(01+biased=1) ◀──────────────┘
        │ 把线程 ID 写入 Mark Word, 之后该线程进出锁只需比对 threadId, 几乎零开销
        │
        │ 发生竞争(另一线程也要锁)
        ▼
        ┌─ 轻量级锁(00) ── 通过 CAS 把 Mark Word 替换为「指向栈帧锁记录的指针」
        │ 竞争线程自旋等待(自适应自旋), 认为锁很快释放
        │
        │ 自旋失败/竞争激烈
        ▼
        ┌─ 重量级锁(10) ── 通过操作系统 mutex, 未抢到锁的线程进入阻塞(挂起)
        │ 由 ObjectMonitor 管理, 涉及用户态↔内核态切换, 成本最高
        ▼
```

- **偏向锁**：核心思想「锁总是被同一个线程获取」。第一次获取时把线程 ID 写进 Mark Word，之后该线程进出锁**只需比较 threadId，不用 CAS**，开销极小。适合**没有竞争、单线程反复加锁**的场景。JDK15 起偏向锁被默认禁用并逐步废弃（现代应用竞争普遍，偏向锁收益低还拖慢撤销）。
- **轻量级锁**：当出现第二个线程竞争，偏向锁撤销升级为轻量级锁。它基于「**CAS + 自旋**」，认为锁很快释放，竞争线程先忙等（自旋）而不是直接阻塞。适合**竞争不激烈、持锁时间短**的场景。
- **重量级锁**：自旋仍抢不到，升级为重量级锁，未抢到的线程**进入阻塞队列挂起**（不再占 CPU），等待被唤醒。涉及系统调用、线程切换，成本最高，但线程多时不浪费 CPU。

::: tip 💡 面试题：synchronized 的锁升级过程？
**结论**：无锁 → 偏向锁 → 轻量级锁（自旋）→ 重量级锁（阻塞），逐步升级且**不会降级**。**原因**：权衡「加锁开销」和「等待开销」——竞争弱时用廉价的 CAS/自旋，竞争强时才动用昂贵的系统互斥锁。**展开**：偏向锁靠「比对 threadId」省掉 CAS；轻量级锁靠「CAS + 自旋」省掉线程切换；重量级锁靠「阻塞挂起」省掉空转 CPU，三者各有所长。
:::

### 十二、对象晋升与 GC 触发机制

#### 1. 对象从新生代晋升老年代的规则

年轻对象默认在 Eden 区分配，经历 GC 后按以下规则「晋升」到老年代：

1. **年龄晋升（默认规则）**：对象每熬过一次 Minor GC，分代年龄 +1，年龄达到阈值（默认 **15**，`-XX:MaxTenuringThreshold` 控制）就晋升老年代。
2. **大对象直接进老年代**：超过 `-XX:PretenureSizeThreshold` 的对象（如大数组）直接在老年代分配，避免在新生代反复复制。
3. **动态年龄判断**：Survivor 区中，**相同年龄的所有对象大小之和**超过 Survivor 空间的一半时，**年龄 ≥ 该年龄**的对象直接晋升（不一定要等到 15 岁）。

```
晋升路径:
  new 对象 ──▶ Eden
                │ Minor GC 存活
                ▼
          Survivor(from/to) 来回复制, 年龄+1
                │ 年龄到 15 / 动态年龄达标 / 大对象
                ▼
            老年代(Old)
```

#### 2. Minor GC / Major GC / Full GC 的区别与触发

| 类型 | 作用范围 | 触发条件 | 特点 |
| --- | --- | --- | --- |
| Minor GC（Young GC） | 只回收新生代 | Eden 区满 | 频繁、快、通常伴随短 STW |
| Major GC（Old GC） | 只回收老年代 | 老年代空间不足 | 通常伴随 Full GC，单独出现少 |
| Full GC | 回收整个堆 + 方法区 | 见下方 | 慢、STW 长、应尽量避免 |

**Full GC 常见触发条件**（高频）：

1. `System.gc()` 显式建议（不一定触发，但可能）。
2. 老年代空间不足（晋升对象放不下）。
3. 元空间（Metaspace）不足（动态加载类过多）。
4. 晋升担保失败：Minor GC 后 Survivor 放不下存活对象，需老年代兜底，老年代也不够就 Full GC。
5. CMS 的「并发模式失败」（碎片过多，无法分配大对象）。

::: tip 💡 面试题：Minor GC 和 Full GC 的区别？
**结论**：Minor GC 只回收新生代、快而频繁；Full GC 回收整堆 + 方法区、慢且 STW 长。**原因**：作用范围和采用算法不同——新生代用复制算法（存活对象少、快），老年代用标记-整理/清除（对象多、慢）。**展开**：生产环境要重点关注 Full GC 次数，Full GC 频繁往往意味着内存泄漏、元空间过小或大对象过多，是性能问题的信号灯。
:::

### 十三、Stop The World 与安全点 / 安全区域

#### 1. 为什么会有 STW

GC 的「可达性分析」需要从一个**稳定快照**出发遍历引用链。如果分析过程中业务线程还在不停修改引用，分析结果就会错乱（正是上面三色标记讲的漏标问题）。所以 JVM 必须在**安全点**让所有业务线程暂停，GC 完成后恢复。这个「暂停所有业务线程」就叫 **STW（Stop The World）**。

**为什么可达性分析一定要 STW**：可以类比「给一栋楼做人口普查，但普查员一边数、住户一边搬家」，永远数不准。所以必须让所有人「原地不动」再数。

#### 2. 安全点（Safepoint）

JVM **不可能在任何一条指令处都停顿**（否则成本极高），只能在特定的「安全点」停顿。安全点是**当前线程状态一致、可以安全暂停执行 GC 的位置**，典型位置：

- 方法调用（`invoke*`）前后；
- 循环跳转处（循环的边界）；
- 异常跳转处。

线程响应安全点请求的方式：

- **抢先式中断**（旧式）：GC 直接强制所有线程暂停，若线程不在安全点就恢复它跑到安全点。几乎不用了。
- **主动式中断**（现代 JVM）：GC 设置一个标志位，各线程运行到安全点时**主动检查标志**，发现需要 GC 就主动挂起自己。避免指令级打断的代价。

```
线程: ... 执行字节码 ... ──▶ 到达安全点 ──▶ 检查「是否要 GC」──▶ 是 ──▶ 挂起等待 GC 完成
                            (方法调用/循环边界)   (轮询 poll)
```

#### 3. 安全区域（Safe Region）

安全点解决不了「线程正在 `sleep` / `blocked`」这种**长时间不执行字节码**的情况（它到不了安全点）。于是引入「安全区域」：指一段代码片段中，**引用关系不会发生变化**，GC 在这段区域内是安全的。

- 线程进入安全区域时标记自己，GC 无需等待它；
- 线程要离开安全区域时，需检查 GC 是否已完成，未完成就继续等待。

### 十四、逃逸分析与栈上分配

#### 1. 逃逸分析（Escape Analysis）

「逃逸」指对象是否**被方法之外的地方引用**。逃逸分析就是在编译期分析对象的**动态作用域**：

- **不逃逸**：对象只在本方法内创建、使用、销毁，方法外无人能访问到它。
- **方法逃逸**：对象被作为返回值返回，或被传参给其他方法。
- **线程逃逸**：对象被赋值给类变量、实例变量等，可被其他线程访问。

#### 2. 逃逸分析带来的三大优化

| 优化 | 做法 | 收益 |
| --- | --- | --- |
| 栈上分配（Stack Allocation） | 不逃逸的对象直接分配在**栈帧**里，随方法结束自动销毁 | 免去堆分配 + GC 回收，大幅减负 |
| 标量替换（Scalar Replacement） | 把对象「拆开」成它的成员变量，直接在栈/寄存器上作为局部变量使用 | 对象头、引用都不需要了，省内存、免寻址 |
| 锁消除（Lock Elimination） | 不逃逸对象上的 `synchronized` 直接去掉 | 去掉无意义的加锁开销 |

```java
public class EscapeDemo {
    // 不逃逸: point 只在本方法内使用, 可能被「栈上分配」或「标量替换」
    public static int sum() {
        Point point = new Point(1, 2); // Point 不逃逸, 可能被标量替换为 x=1, y=2 两个局部变量
        return point.x + point.y;
    }

    // 逃逸: 对象作为返回值返回, 方法外还能访问 → 必须分配在堆上
    public static Point create() {
        return new Point(1, 2);
    }
}

class Point {
    int x, y;
    Point(int x, int y) { this.x = x; this.y = y; }
}
```

> 说明：逃逸分析默认开启（JDK6u23 起，`-XX:+DoEscapeAnalysis`），但**并非所有不逃逸对象都一定栈上分配**——它需要经过逃逸分析判定，且受即时编译器的实现影响。这是「优化手段」而非「语言规定」，所以不能当成「Java 对象可以存在栈上」的死规则，答题时要说明这是 JIT 的优化。

::: tip 💡 面试题：对象一定分配在堆上吗？
**结论**：不一定——经过逃逸分析，不逃逸的对象可能被「栈上分配」或「标量替换」，免于进入堆。**原因**：JIT 编译时若发现对象只在方法内使用，就没必要为它付出堆分配和 GC 的代价。**展开**：这是 JIT 的运行时优化而非语言层面规定，是否生效取决于逃逸分析结果，所以「对象一定在堆上」这句话在高级面试里是会被纠正的。
:::

### 十五、字符串常量池与 intern

#### 1. 字符串常量池（String Pool）

字符串是 Java 里使用最频繁的对象，为了复用，JVM 维护了一个**字符串常量池**（本质是一张 HashTable）。用双引号 `"..."` 创建字符串字面量时，会先查池：池里有就直接复用，没有才新建并放入池。

```java
public class StringPoolDemo {
    public static void main(String[] args) {
        String s1 = "hello";        // ① 常量池没有 "hello", 创建并放入池, 返回池中引用
        String s2 = "hello";        // ② 池里已有 "hello", 直接复用同一个引用
        String s3 = new String("hello"); // ③ new 强制在堆上新建对象, 与池中的不是同一个
        String s4 = s3.intern();    // ④ intern(): 若池中已有相等字符串则返回池中引用

        System.out.println(s1 == s2); // true  (都指向池中同一个对象)
        System.out.println(s1 == s3); // false (s3 是堆上新对象)
        System.out.println(s1 == s4); // true  (intern 返回池中引用)
    }
}
```

#### 2. `intern()` 的规则与版本差异（高频）

`String.intern()` 的作用：**把字符串放入常量池（若池中已有等价字符串则返回池中引用）**。但它在不同 JDK 版本的**行为不同**，这是经典陷阱题：

| JDK 版本 | 字符串常量池位置 | `intern()` 行为 |
| --- | --- | --- |
| JDK6 及以前 | 永久代（PermGen） | 池中无则**复制一份**到池（永久代），返回池中副本引用 |
| JDK7 及以后 | 堆（Heap） | 池中无则**把堆中对象的引用直接登记进池**（不再复制），返回该堆对象引用 |

JDK7 的改动带来的经典现象（面试常考）：

```java
public class InternDiff {
    public static void main(String[] args) {
        String s = new String("a") + new String("b"); // 堆上新建 "ab"(不在常量池)
        String s2 = s.intern();  // JDK7+: 把 s 这个堆对象的引用放进常量池, 返回 s 本身
        String s3 = "ab";        // 字面量 "ab", 池中已有 s 的引用, 直接复用 s
        // JDK7+ 结果: s == s2 == s3 全为 true
        // JDK6  结果: intern 复制了一份到永久代, s != s2, s2 == s3
        System.out.println(s == s2); // JDK7+: true, JDK6: false
        System.out.println(s2 == s3); // 都是 true
    }
}
```

#### 3. 为什么 JDK7 要移动字符串常量池

因为**永久代空间有限且 GC 不积极**，大量字符串（尤其 `intern()` 滥用）容易把永久代撑爆，导致 `PermGen OOM`。移到堆后，字符串和普通对象一样受堆 GC 管理，回收更及时。这也是 JDK8 进一步把整个方法区迁到元空间的伏笔。

### 十六、JIT 即时编译

#### 1. 解释执行 vs 编译执行

JVM 的执行引擎有两种模式：

| 模式 | 原理 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 解释执行 | 逐条把字节码翻译成机器码执行 | 启动快、无需编译等待 | 反复翻译热点代码，运行慢 |
| 编译执行（JIT） | 把「热点代码」整体编译成本地机器码缓存 | 运行快（直接跑机器码） | 编译有开销、启动略慢 |

现代 JVM 采用「**解释器 + JIT 混合执行**」：先用解释器快速启动，同时 JIT 在后台监控，发现「热点代码」（反复执行的方法或循环）就编译成机器码，之后直接执行机器码，性能大幅提升。

#### 2. 热点探测方式

如何判断一段代码是「热点」？两种方式（HotSpot 用的是第二种）：

1. **基于采样（Sample）**：定时检查各线程栈顶方法，出现次数多的就是热点。简单但不精确。
2. **基于计数器（HotSpot 采用）**：为每个方法/循环维护计数器，达到阈值就触发编译。又分：
   - **方法调用计数器**：方法被调用次数超过阈值（C1:1500 次，C2:10000 次，受 `-XX:CompileThreshold` 影响）。
   - **回边计数器**：循环体执行次数（for/while 循环）。

#### 3. 两种即时编译器（C1 / C2）与分层编译

HotSpot 内置两个即时编译器：

| 编译器 | 全称 | 定位 | 特点 |
| --- | --- | --- | --- |
| C1（Client） | Client Compiler | 客户端/快速启动 | 编译快、优化浅，启动速度快 |
| C2（Server） | Server Compiler | 服务端/峰值性能 | 编译慢、优化激进，长期性能好 |

**分层编译（Tiered Compilation，JDK8 默认开启）**结合两者优点：

```
第 0 层: 解释执行(纯解释器)
第 1 层: C1 编译, 无 profiling(简单编译, 快速)
第 2 层: C1 编译, 带 profiling(收集运行期统计信息, 为 C2 预热)
第 3 层: C1 编译, 完整 profiling
第 4 层: C2 编译(最激进优化, 峰值性能)

热点代码从 0 层逐步升到 4 层, 兼顾「启动快」和「峰值快」
```

```
代码执行路径示意:
  字节码 ──▶ 解释器(第0层) ──▶ 热点? ──▶ C1 编译(1~3层) ──▶ 更热? ──▶ C2 编译(第4层)
```

::: tip 💡 面试题：JIT 是什么？为什么要有解释器和编译器两种执行方式？
**结论**：JIT 是即时编译器，把热点字节码编译成本地机器码缓存，提升运行速度；保留解释器是为了启动快。**原因**：解释器启动快但运行慢，编译器启动慢但运行快，二者结合（分层编译）才能同时兼顾启动和峰值性能。**展开**：这就是「混合执行」——先解释、后编译，C1 快速编译做预热、C2 深度优化冲性能。
:::

### 十七、内存泄漏与 OOM 排查实战

#### 1. 内存泄漏 vs 内存溢出

- **内存溢出（OOM，OutOfMemoryError）**：JVM 内存确实不够用了，直接报错崩溃。
- **内存泄漏（Memory Leak）**：对象已经没用了，但**仍被 GC Roots 引用着**，无法回收，长期累积最终导致 OOM。泄漏是 OOM 的最常见原因之一。

#### 2. 排查三步法

```
① 看现象: 报 OutOfMemoryError, 先区分类型
     Java heap space(堆溢出) / Metaspace(元空间) / Direct buffer memory(直接内存)
② 抓现场: 启动加 -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=./heap.hprof
③ 分析:  用 MAT/VisualVM/JProfiler 打开 .hprof
     → 看「占内存最大的对象」(Dominator Tree)
     → 看「GC Roots 引用链」(Path to GC Roots)
     → 定位是谁一直持有引用没释放
```

#### 3. 常见内存泄漏场景（高频）

| 场景 | 泄漏原因 | 修复方式 |
| --- | --- | --- |
| 静态集合不断 `add` | 静态集合（`static List/Map`）生命周期 = 应用生命周期，只加不删 | 用弱引用集合或定期清理 |
| `ThreadLocal` 未 `remove` | 线程池线程复用，`ThreadLocal` 的值一直挂在 Thread 上 | 用完 `finally { threadLocal.remove(); }` |
| IO/连接未关闭 | 流、`Connection`、`Statement` 未关，占用堆外/资源 | try-with-resources 自动关闭 |
| 监听器未注销 | 注册了监听器/回调但未移除，被持有 | 成对 `add/remove` 监听器 |
| 内部类持有外部引用 | 非静态内部类隐式持有外部类引用 | 改静态内部类或显式置 null |

```java
// 典型泄漏: ThreadLocal 未清理
public class ThreadLocalLeak {
    private static final ThreadLocal<byte[]> LOCAL = new ThreadLocal<>();

    public void process() {
        // ThreadLocal 的值绑定在线程上, 线程池线程复用会导致该值长期存活
        LOCAL.set(new byte[10 * 1024 * 1024]); // 10MB
        // 业务处理...
        // 忘记 LOCAL.remove()  → 每个线程都残留 10MB → 泄漏
    }

    // 正确姿势:
    public void processFixed() {
        try {
            LOCAL.set(new byte[10 * 1024 * 1024]);
            // 业务处理...
        } finally {
            LOCAL.remove(); // 关键: 用完后必须移除, 否则线程池复用时值一直挂着
        }
    }
}
```

#### 4. 一个真实排查案例的思路

> 现象：线上服务运行几小时后频繁 Full GC，最终 `OOM: Java heap space`。
> 排查：`jstat -gcutil` 看老年代占用率持续上升（GC 后仍不下降，说明有对象回收不掉）；`jmap -dump` 抓堆快照；MAT 打开后看到 `Dominator Tree` 顶部是一个 `ConcurrentHashMap`，往下一层是大量 `User` 对象；`Path to GC Roots` 显示它被一个 `static` 字段引用。
> 结论：静态缓存 `Map` 只 `put` 不 `remove`，用户对象越来越多导致泄漏。
> 修复：给缓存加容量上限（LRU 淘汰）或改弱引用。

## 面试常问

1. **JVM 内存区域有哪些？** 结论：堆、方法区/元空间、虚拟机栈、本地方法栈、程序计数器（外加运行时常量池、直接内存）。展开：堆和方法区线程共享（GC 主战场），栈和 PC 线程私有；堆存对象、方法区存类元信息、栈存方法调用的栈帧、PC 存字节码行号。

2. **对象什么时候进入老年代？** 结论：三种情况——年龄晋升（默认 15 岁）、大对象直接分配、动态年龄判断达标。展开：年龄存在 Mark Word 的 4 位字段里，所以上限是 15；大对象由 `-XX:PretenureSizeThreshold` 控制；动态年龄指 Survivor 中同年龄对象总大小超一半即晋升。

3. **双亲委派机制是什么，为什么要它？** 结论：类加载器收到请求先委派父加载器，父加载不了才自己加载。展开：目的是防止核心类被篡改、避免类重复加载；JDBC（SPI）、Tomcat 会打破它，靠线程上下文类加载器实现反向加载。

4. **如何判断对象可以回收？** 结论：可达性分析，从 GC Roots 出发不可达的对象判为垃圾。展开：JVM 不用引用计数（无法解决循环引用）；GC Roots 包括栈引用、静态字段、常量池、JNI 引用、synchronized 持有的对象等。

5. **Minor GC 和 Full GC 的区别？** 结论：Minor GC 只回收新生代、快而频繁；Full GC 回收整堆 + 方法区、慢且 STW 长。展开：新生代用复制算法、老年代用标记-整理/清除；Full GC 频繁通常意味着泄漏或配置不当，是重点排查信号。

6. **synchronized 的锁升级过程？** 结论：无锁 → 偏向锁 → 轻量级锁（CAS+自旋）→ 重量级锁（阻塞），只升不降。展开：偏向锁靠比对 threadId、轻量级锁靠自旋、重量级锁靠系统 mutex；Mark Word 的低 2 位 lock 标志记录了当前锁状态。

7. **Java 为什么能跨平台？** 结论：靠 JVM 抽象层——源码编译成平台无关字节码，各平台 JVM 翻译成本地机器码。展开：代价是运行期多一次翻译，所以有 JIT 优化热点代码；各平台各有一个 JVM 实现（HotSpot/OpenJ9 等）。

8. **JDK8 默认垃圾收集器是什么？JDK9 呢？** 结论：JDK8 默认 Parallel Scavenge + Parallel Old（吞吐优先），JDK9 起默认 G1（可预测停顿）。展开：G1 把堆分成等大 Region、优先回收垃圾最多的 Region；可用 `java -XX:+PrintCommandLineFlags -version` 验证。
