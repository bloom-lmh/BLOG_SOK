# Java 代理

> 一句话定位：给一个类/接口找个「替身」站在前面接调用，在不动原业务代码的前提下，把公共逻辑（事务、日志、鉴权）统一塞进替身里。你要学会的是——**亲手实现它**，并彻底搞懂 JDK 那几个怪参数。

## 基础篇

### 1. 代理解决什么问题

业务对象只负责自己的事，但有另一类「横切逻辑」想在它前后跑：开事务、记日志、验权限。直接写进业务方法就是到处重复，不写又没入口。

代理把它拆开：业务写在真实对象里，共同逻辑写在代理里，**调用者的手指落在代理上**：

```text
调用者 → 代理对象 → 真实对象
            │
            ├── 方法执行前：开启事务
            └── 方法执行后：提交/回滚
```

先看这套代码，后面全部围绕它展开：

```java
public interface UserService {          // ① 接口
    void save(String name);
}

public class UserServiceImpl implements UserService {   // ② 真实对象
    @Override
    public void save(String name) {
        System.out.println("保存用户：" + name);
    }
}
```

### 2. 静态代理 —— 把套路亲手写一遍

动手实现从静态代理开始。原理就一句话：**代理类和真实类实现同一个接口，代理持有真实类，转发时顺手加逻辑**。

```java
public class UserServiceProxy implements UserService {   // 和真实类同接口

    private final UserService target;                     // 持有真实对象

    public UserServiceProxy(UserService target) {
        this.target = target;
    }

    @Override
    public void save(String name) {
        System.out.println("开启事务");                     // 增强：方法前
        target.save(name);                                 // 转发给真实对象
        System.out.println("提交事务");                     // 增强：方法后
    }
}
```

```java
UserService service = new UserServiceProxy(new UserServiceImpl());
service.save("BLOOM_LMH");
// 输出：开启事务 / 保存用户：BLOOM_LMH / 提交事务
```

这就是代理的完整套路，任何代理都逃不出这三个动作：**同接口 → 持有目标 → 转发（±增强）**。

直觉通了，缺点的出路也明显了：每加一个类就要手写一个 Proxy —— 让 JVM 自动生成这个 Proxy，就是动态代理。

### 3. JDK 动态代理 —— 让 JVM 替你造代理类

不写 `UserServiceProxy` 这个类了，运行期让 JVM 现生成一个「实现 UserService 的类」，调用全部转发给一个统一处理器。

#### 3.1 核心 API 只有两个

| API | 干的活 | 类比到静态代理 |
| --- | --- | --- |
| `Proxy.newProxyInstance(...)` | 造出一个代理对象 | 等于 `new UserServiceProxy(target)` |
| `InvocationHandler` | 统一处理所有方法调用 | 等于 Proxy 类里那个 `save()` 方法体 |

#### 3.2 三步实现

```java
// 第一步：写 handler —— 一个接口，一个方法 invoke()
InvocationHandler handler = (proxy, method, args) -> {
    System.out.println("开启事务");               // 方法前
    Object result = method.invoke(target, args);   // 转发给真实对象（target 是外面的 UserServiceImpl）
    System.out.println("提交事务");               // 方法后
    return result;                                 // 把返回值还给调用者
};

// 第二步：把三个参数喂给 Proxy，造出代理对象
UserService proxy = (UserService) Proxy.newProxyInstance(
        UserService.class.getClassLoader(),   // 参数① 类加载器
        new Class<?>[]{UserService.class},    // 参数② 接口数组
        handler                                // 参数③ 处理器
);

// 第三步：像用真实对象一样用它
proxy.save("BLOOM_LMH");   // 输出：开启事务 / 保存用户：BLOOM_LMH / 提交事务
```

**你写代理只需要构造 handler 和凑齐三个参数**。每走一步搞清楚一个参数为什么存在，JDK 代理就不再是黑魔法。

#### 3.3 `newProxyInstance` 的三个参数 —— 为什么这么怪

```java
public static Object newProxyInstance(
        ClassLoader loader,        // ①
        Class<?>[] interfaces,     // ②
        InvocationHandler h)       // ③
```

原生代码里你从没见过「造个类还被要求指定类加载器」——因为代理类不是源码文件，是 JVM 在**内存里动态生成**的。一个类要被 JVM 承认（能 new、能 instanceof），必须先被某个 ClassLoader 加载。这三个参数就是回答「凭空造出来的类，用什么身份活下来」：

| 参数 | 传什么 | 为什么必须传 | 传错会怎样 |
| --- | --- | --- | --- |
| ① `loader` | 接口的 `getClassLoader()` | 代理类必须和接口**同加载器加载**。JVM 里「同一个类」由「全限定名 + 加载器」共同决定——换一个加载器，`UserService` 会被当成两个不同的类型，代理对象 `instanceof UserService` 直接 false | 乱传一个加载器 → 类型对不上，强转抛 `ClassCastException` |
| ② `interfaces` | 接口数组 | 动态生成的类得有一个「身份」。Java 单继承，生成类已经 `extends Proxy`（见 §4），所以**只能靠实现接口**来获得目标类型。数组 = 能同时实现多个接口 | 传 `null` 或空数组 → `IllegalArgumentException`；传的不是接口 → 同样报错 |
| ③ `handler` | InvocationHandler 实例 | 代理对象有了类型、能被加载，但**方法被调后得有人处理**。handler 就是那个人——没有它代理是空壳 | 传 `null` → 造出来的代理一调方法就空指针 |

> 理解 ① 的关键：**类 = 全限定名 + 加载器**。这也回答了「为什么不直接用 `Proxy.class.getClassLoader()`」——必须用**接口自己的**加载器，让代理类落在能看到该接口的那层里。

#### 3.4 `invoke` 的三个参数 —— 最容易被绕晕的地方

```java
Object invoke(Object proxy, Method method, Object[] args) throws Throwable
//            ↑①         ↑②              ↑③
//            返回值     被调的方法        实参
```

调用 `proxy.findByName("张三", 20)` 时，JVM 把这三个东西塞给你：

| 参数 | 内容 | 为什么有你用它 |
| --- | --- | --- |
| ① `proxy` | 当前这个代理对象 | 框架告诉你「你现在站在谁前面」。web 场景常用的真实用法：有需要就把代理对象本身返回/挂到别处（比如 Feign 把代理暴露出去当 HttpClient）。**永远不要做** `method.invoke(proxy, args)` —— 见 3.5 |
| ② `method` | `Method` 反射对象（`findByName`） | 静态语言里，**方法不是你名字调的函数，是一等对象**。你要按方法名/返回类型/参数列表去分发，全靠它：`method.getName()`、`method.getDeclaringClass()` |
| ③ `args` | 实参数组（`["张三", 20]`） | 转发给真实对象要用到它。注意：**无参方法时是 `null`，不是空数组**（JDK 的坑，见 3.5） |

**method + args 是转发的手脚**：`method.invoke(target, args)` 这一行等于「找到 target 上对应的那个方法，把 args 传进去执行」。

```text
proxy.findByName("张三", 20)
        ↓
invoke(proxy=代理对象, method=findByName, args=["张三", 20])
        ↓
method.invoke(target, args)      →  target.findByName("张三", 20)  // 真实方法执行
        ↓
invoke 返回 "张三#20" —— 调用者拿到结果
```

#### 3.5 两个最容易当场写错的细节

**① `method.invoke(proxy, args)` = 无限递归**

`proxy` 传进 invoke 的是**代理对象**，再对它 invoke，又会进代理、又进 invoke……直到 `StackOverflowError`：

```java
Object result = method.invoke(proxy, args);   // ❌ proxy 是代理 → 再进 invoke → 死循环
Object result = method.invoke(target, args);  // ✅ target 是真实对象 → 只执行一次
```

有个真实世界提示：相同思路做 AOP 时，「同类方法自调用」跳过代理、事务失效，就是因为它绕开了 proxy 这层直接点了真实对象（见 [Spring](/learn_backend/java/基础/Spring)）。

**② args 可能是 null，先判空**

```java
if (args != null) {
    for (Object arg : args) { System.out.println(arg); }   // 手动遍历前先判空
}
Object result = method.invoke(target, args);   // 这行没事：invoke 自身把 null 当空数组
```

## 高级篇

### 4. 生成的代理类长什么样

JDK 在内存里生成了一个类，**你真能看到它**——调 `System.getProperties().put("jdk.proxy.ProxyGenerator.saveGeneratedFiles", "true")` 后去 `com/sun/proxy/` 翻。它的结构近似：

```java
// 仅用于理解，不是真实源码
public class $Proxy0 extends Proxy implements UserService {   // 继承 Proxy + 实现接口

    private static Method m1 = ...;   // 编译时展开：方法信息在首次调用前查好，缓存

    public $Proxy0(InvocationHandler h) {
        super(h);                       // Proxy 里留着 handler
    }

    @Override
    public void save(String name) {
        try {
            super.h.invoke(this, m1, new Object[]{name});   // 全部转发给 handler
        } catch (Throwable e) { throw ...; }
    }
}
```

三个值得记住的细节：

1. **`extends Proxy`** —— 所以只能靠「实现接口」拿身份，这就是参数②必须是接口数组的根源。
2. **`Method` 被提前缓存成静态字段** —— 每个方法只查一次反射信息，之后复用。
3. **调用就是一行** `h.invoke(this, 方法, 实参)` —— 和 3.4 的三个参数完全对上：`this` 就是 invoke 里的 `proxy`。

### 5. JDK 动态代理 vs CGLIB

| 对比 | JDK 动态代理 | CGLIB |
| --- | --- | --- |
| 原理 | 生成**接口实现类** | 生成**目标类的子类**并覆写方法 |
| 要求 | 必须有接口 | 不需要接口 |
| 能增强什么 | 接口里声明的方法 | 非 `final` 的普通方法 |
| 致命短板 | 无接口不行 | `final` 类和 `final` 方法无法覆写 |
| 使用处 | MyBatis Mapper、OpenFeign | Spring AOP 的兜底 |

```text
JDK:   $Proxy0  implements UserService
CGLIB: UserServiceImplProxy extends UserServiceImpl   ← 靠继承覆写拦截
```

最终取舍一句记清：**有接口 JDK 自带的就够了；没有接口（或要代理类）才用 CGLIB 继承生成子类**。Spring Boot 2.x 起默认 `spring.aop.proxy-target-class=true`，一律走 CGLIB；MyBatis Mapper 天生是接口，走 JDK 代理。

### 6. 常见应用

| 技术 | 代理做了什么 |
| --- | --- |
| Spring AOP | invocation 在方法前后塞日志、鉴权、性能统计 |
| `@Transactional` | 方法前开事务，成功后提交，异常时回滚 |
| MyBatis Mapper | 「无 real target」型代理：invoke 里把接口方法翻译成 SQL 执行（读方法名、namespace、参数定位 MappedStatement） |
| OpenFeign | 同样无 target：invoke 里把方法翻译成 HTTP 请求 |
| 延迟加载 | 首次 getXxx() 触发时才查关联数据 |

注意两类代理的分工：

- **有真实 target**（Spring AOP、事务）→ `method.invoke(target, args)` 转发增强
- **没有 target**（MyBatis、Feign 的接口）→ invoke 里**不让 method.invoke**，而是自产自销：翻译成 SQL / HTTP

## 面试常问

- **Q：JDK 动态代理的原理？** 运行期 JVM 生成一个实现指定接口、且继承 `Proxy` 的类；对象上任何方法调用都转发给 `InvocationHandler.invoke(proxy, method, args)`，由它统一处理（转发给真实对象增强，或直接翻译成 SQL/HTTP）。

- **Q：为什么必须传 classLoader？** 动态生成的类在内存里没有字节码文件，JVM 要认它必须先由某个 ClassLoader 加载；必须和接口同加载器，否则同名的 `UserService` 在 JVM 视角是两个类，代理对象 `instanceof` 不过去。

- **Q：为什么参数②要求接口而不能是类？** 生成的代理类已经 `extends Proxy`，Java 单继承，没法再继承目标类，接口是唯一能让运行时对象具备「目标类型」身份的途径。所以要代理没有接口的类只能靠 CGLIB 生成子类。

- **Q：invoke 里 `method.invoke(proxy, args)` 会怎样？** 无限递归：proxy 是代理对象，再 invoke 又会进 handler，循环到 StackOverflow。有真实 target 必须 `method.invoke(target, args)`。

- **Q：为什么 Spring 事务在同类里自调用会失效？** 事务切面在代理对象上，`this.xxx()` 直接调的是真实对象自己，绕过了代理层，事务拦截器根本没进来。

- **Q：JDK 代理和 CGLIB 怎么选 / Spring 默认用哪个？** JDK：生成接口实现类，要求接口；CGLIB：生成子类覆写方法，不能碰 final。Spring Boot 2.x 默认 proxy-target-class=true 一律 CGLIB。
