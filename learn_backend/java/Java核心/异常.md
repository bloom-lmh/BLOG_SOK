# 异常

> 一句话定位：异常（Exception）是 Java 处理「运行时错误」的机制——把「出错」这件事从正常的业务逻辑里剥离出来，用 `throw` 抛出、`try-catch` 捕获、沿调用栈向上传播，让错误处理集中、可追踪，而不是靠「返回错误码 + 到处 if 判断」这种易遗漏、难维护的方式。

---

## 基础篇

### 1. 异常体系全景：Throwable 家族

Java 里所有「能抛出去的东西」都继承 `Throwable`，往下分两支：

```
Throwable（可抛出）
├── Error（错误）           ← 严重问题，程序无法处理，不该 catch
│   ├── OutOfMemoryError    内存溢出
│   ├── StackOverflowError  栈溢出（递归太深）
│   └── NoClassDefFoundError 类找不到
└── Exception（异常）        ← 程序应该处理的
    ├── RuntimeException（非受检异常）  ← 编译器不强制处理
    │   ├── NullPointerException
    │   ├── IndexOutOfBoundsException
    │   ├── ArithmeticException
    │   └── ClassCastException
    └── 其他 Exception（受检异常）       ← 编译器强制处理
        ├── IOException
        ├── SQLException
        └── FileNotFoundException
```

**三个关键区分**：

| 类型 | 谁 | 能否/该不该处理 |
|---|---|---|
| `Error` | JVM 层面的严重错误 | **不该 catch**——OOM、栈溢出程序已经废了，catch 了也没用 |
| 受检异常（Checked） | 编译期强制 | **必须处理**——要么 `try-catch`，要么 `throws` 声明，否则编译不过 |
| 非受检异常（Unchecked） | `RuntimeException` 及其子类 | **不强制**——编译器不管，通常代表「编程 bug」 |

### 2. 受检异常 vs 非受检异常（面试必考）

这是 Java 独有的设计，别的语言（C#、Go）基本没有「受检异常」：

```java
// 受检异常：IOException 必须处理，否则编译报错
public void readFile() {
    FileInputStream in = new FileInputStream("a.txt");  // 编译器报错：未处理 IOException
}

// 两种处理方式二选一：
// 方式 1：try-catch 就地处理
public void readFile() {
    try {
        FileInputStream in = new FileInputStream("a.txt");
    } catch (IOException e) {
        e.printStackTrace();
    }
}

// 方式 2：throws 声明，把异常甩给调用方
public void readFile() throws IOException {
    FileInputStream in = new FileInputStream("a.txt");
}
```

```java
// 非受检异常：NPE 是 RuntimeException，编译器不管，能通过编译，运行才炸
public int getLen(String s) {
    return s.length();   // s 为 null 时抛 NPE，编译器不提示
}
```

::: tip 💡 面试题：受检异常和非受检异常的区别？各自用在什么场景？
**一句话**：受检异常（`Exception` 的子类）编译器强制你 `try-catch` 或 `throws`，用于「调用方必须知道并能处理」的可恢复错误（如 IO 失败、SQL 失败）；非受检异常（`RuntimeException`）编译器不管，用于「编程 bug」（如 NPE、越界）——这类错误不该靠 catch 掩盖，而应该改代码修 bug。见 [Java集合](/learn_backend/java/Java核心/Java集合) 相关面试题里「fail-fast」会抛 `ConcurrentModificationException`。
:::

### 3. throw vs throws：一字之差，完全不同

| | `throw` | `throws` |
|---|---|---|
| 位置 | 方法**体内** | 方法**声明**上 |
| 作用 | **抛出**一个异常对象 | **声明**本方法可能抛哪些异常 |
| 语法 | `throw new BizException(...)` | `void foo() throws IOException` |
| 一次能 | 抛一个 | 声明多个，逗号分隔 |

```java
public void check(int age) throws BizException {   // throws：声明可能抛 BizException
    if (age < 0) {
        throw new BizException(400, "年龄非法");    // throw：真的抛出一个异常对象
    }
}
```

### 4. try-catch-finally 的执行顺序

```java
try {
    // 可能出错的代码
} catch (BizException e) {   // 精确匹配优先
    // 处理业务异常
} catch (Exception e) {       // 兜底
    // 处理其他异常
} finally {
    // 无论是否异常，都会执行（除非 System.exit / 断电）
}
```

**两个关键规则**：

1. **catch 顺序**：子类异常在前、父类在后。`catch (Exception)` 放前面会把所有异常都吞了，后面的 catch 变成「不可达代码」直接编译报错。
2. **finally 必执行**：即使 try 里 `return`、catch 里 `return`，finally 也会在 return 前执行。常用于释放资源（关流、关连接）。

### 5. 项目里的自定义异常：BizException

Day01 定义了 `BizException`，它是业务异常的基石：

```java
// 为什么继承 RuntimeException：非受检异常，业务代码 throw 时不用强制 try-catch 或 throws
public class BizException extends RuntimeException {
    private final Integer code;

    public BizException(ErrorCode errorCode) {
        super(errorCode.getMessage());   // 把 message 传给父类，getMessage() 能拿到
        this.code = errorCode.getCode();
    }

    public Integer getCode() { return code; }
}
```

为什么不用 `Exception`（受检）而用 `RuntimeException`：

| 用 `Exception`（受检） | 用 `RuntimeException`（非受检，本项目） |
|---|---|
| 每个 `throw new BizException` 的地方都要 `throws` 声明或 catch | 想抛就抛，不用层层声明 |
| 方法签名被污染，一路 `throws BizException` | 方法签名干净，异常统一交给全局处理器 |
| 强制调用方处理 | 靠 `GlobalExceptionHandler` 统一兜底 |

**关键**：业务异常不该「到处 try-catch」，而应该「抛出来，交给全局异常处理器统一转成 JSON 返回」。这就是 Day01 里 `GlobalExceptionHandler` 存在的意义。

## 高级篇

### 6. 异常链（cause）：保留原始异常

捕获一个异常后，想换成另一个异常抛出去，但又不想丢掉原始异常的信息，用「异常链」：

```java
try {
    // 解析 JSON 失败
} catch (JsonParseException e) {
    // 包装成业务异常，但把原始异常作为 cause 传进去
    throw new BizException(400, "参数格式错误").initCause(e);
    // 或者用带 cause 的构造器：new BizException("参数错误", e)
}
```

这样排查问题时，能顺着 `getCause()` 一路挖到最原始的根因，而不是只看到一个笼统的「参数错误」。

### 7. try-with-resources：自动关闭资源

传统的关闭资源要写在 finally 里，又臭又长还容易漏：

```java
// 传统写法：finally 里手动 close，容易漏
FileInputStream in = null;
try {
    in = new FileInputStream("a.txt");
} catch (IOException e) {
    // ...
} finally {
    if (in != null) {
        try { in.close(); } catch (IOException e) { /* ... */ }
    }
}
```

`try-with-resources` 自动关闭（Java 7+）：

```java
// 资源对象声明在 try 括号里，用完自动 close，不用写 finally
try (FileInputStream in = new FileInputStream("a.txt");
     BufferedReader reader = new BufferedReader(new InputStreamReader(in))) {
    String line = reader.readLine();
} catch (IOException e) {
    // ...
}
```

原理：括号里的资源必须实现 **`AutoCloseable`** 接口（JDK 7 引入），try 块结束后 JVM 自动调用 `close()`。这是「声明式资源管理」，比手写 finally 更安全（不会漏关）。

::: tip 💡 面试题：try-with-resources 的原理？
**一句话**：编译器在编译时把 `try (资源)` 自动展开成「try-finally + close()」的代码，资源对象必须实现 `AutoCloseable` 接口，try 块结束后（无论正常还是异常）自动调用 `close()`。它解决的是「手动关资源容易漏、finally 里套 try 又臭又长」的问题。
:::

### 8. 全局异常处理：@RestControllerAdvice

Day01 的 `GlobalExceptionHandler` 是业务异常的统一出口：

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    // 精确匹配：业务异常走这里
    @ExceptionHandler(BizException.class)
    public Result<Void> handleBiz(BizException e) {
        return Result.fail(e.getCode(), e.getMessage());
    }

    // 兜底：其他异常统一 500，不把堆栈暴露给前端
    @ExceptionHandler(Exception.class)
    public Result<Void> handleOther(Exception e) {
        return Result.fail(ErrorCode.SYSTEM_ERROR.getCode(), ErrorCode.SYSTEM_ERROR.getMessage());
    }
}
```

好处：**Controller 里不用写任何 try-catch**，异常「往上抛」，由这个切面统一拦截、统一转成 JSON。这是「异常处理集中化」——比每个接口自己 try-catch 干净得多。

## 原理篇

### 9. 异常的底层：抛出时发生了什么

`throw new Exception("msg")` 时，JVM 做了两件事：

1. **创建异常对象**：在堆上 new 一个异常实例，存下 message。
2. **填充栈轨迹（stack trace）**：调用 `Throwable.fillInStackTrace()`，把「从线程起点到 throw 这一行」的**每一层方法调用信息**（类名、方法名、文件、行号）记录下来。

所以 `e.printStackTrace()` 能打印出完整调用链：

```
java.lang.NullPointerException: Cannot invoke "String.length()"
    at com.mall.user.UserService.getLen(UserService.java:42)
    at com.mall.user.UserController.query(UserController.java:18)
    at java.base/jdk.internal.reflect.NativeMethodAccessorImpl.invoke0(Native Method)
    ...
```

### 10. 异常的性能开销

面试常问「异常为什么慢」：

| 开销点 | 说明 |
|---|---|
| **填充栈轨迹** | `fillInStackTrace()` 要遍历整个调用栈，是最贵的操作 |
| **栈轨迹的创建** | 每 new 一个异常都要记录一长串调用信息 |

所以两个工程原则：

1. **不要用异常控制正常业务流程**——异常只用于「真正的错误」，正常分支该用 if 判断就用 if。用 `throw` 代替 `if` 做流程控制是反模式。
2. **栈轨迹可以省**——极高频场景可重写 `fillInStackTrace()` 返回 this（跳过栈填充），但会失去调用链信息，一般不用。

### 11. 为什么 Java 要「受检异常」这种设计？

受检异常是 Java 备受争议的设计，理解它的动机和代价是加分项：

- **动机**：强制调用方「显式处理可恢复的错误」，避免开发者漏掉 IO 失败、SQL 失败这些关键错误。
- **代价/争议**：导致方法签名被 `throws` 污染，调用链每一层都要「声明或处理」，代码啰嗦。C#、Go 等后续语言都放弃了受检异常，改用「错误值」或「全部非受检」。

**业界共识**：受检异常适合「调用方必须知道且能恢复」的少数场景；业务逻辑里大量自定义异常应该用**非受检异常**（`RuntimeException`），配合全局处理器统一兜底——这正是本项目 `BizException` 的选择。

## 面试常问

- **Q：异常体系？** `Throwable` → `Error`（不该 catch）+ `Exception`（该处理）；`Exception` 下分受检异常和非受检异常（`RuntimeException`）。

- **Q：受检 vs 非受检？** 受检异常编译器强制处理（IO/SQL），非受检异常不强制（NPE/越界），代表编程 bug。

- **Q：throw vs throws？** `throw` 在方法体内抛异常对象，`throws` 在方法声明上声明可能抛的异常。

- **Q：catch 顺序有要求吗？** 子类在前、父类在后，否则父类 catch 吞掉所有异常，后面的变成不可达代码编译报错。

- **Q：finally 一定会执行吗？** 几乎一定（除 `System.exit` / 进程崩溃 / 断电）。即使 try 里 return，finally 也在 return 前执行。

- **Q：finally 里 return 有什么坑？** finally 里的 return 会**覆盖** try/catch 里的 return 值，导致方法返回值异常，属反模式。

- **Q：自定义异常用 Exception 还是 RuntimeException？** 业务异常用 `RuntimeException`（非受检，不污染签名），靠全局异常处理器统一兜底。

- **Q：try-with-resources 原理？** 编译器展开成 try-finally + `AutoCloseable.close()`，自动关资源。

- **Q：异常为什么慢？** `fillInStackTrace()` 遍历调用栈填充栈轨迹开销大；别用异常做流程控制。

- **Q：为什么全局异常处理器能拦截所有 Controller 异常？** `@RestControllerAdvice` 是 AOP 切面，拦截异常后按 `@ExceptionHandler` 类型匹配处理。
