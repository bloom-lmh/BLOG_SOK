# 并发编程

> 一句话定位：并发编程解决的是「**多个线程同时访问共享数据时，如何保证结果正确、不出脏数据、不产生性能瓶颈**」这一核心问题；它是理解 JVM 内存模型、锁机制、线程池、`ConcurrentHashMap` 等高频考点的地基，也是写出高性能后端服务（接口、MQ、缓存、任务调度）的必备能力。

> 阅读本文前建议先了解 [JVM](/learn_backend/java/Java核心/JVM) 的内存区域划分（并发问题的本质是「主内存与工作内存」的同步问题）；文中的 `ConcurrentHashMap` 与 [Java集合](/learn_backend/java/Java核心/Java集合) 的 HashMap 演进强相关，建议对照阅读。

## 基础篇

### 一、为什么会有并发问题（并发三要素）

在进入任何工具之前，先建立一个总框架：**并发编程里所有「诡异 bug」，本质都逃不出下面三个要素**。后面学的 `synchronized`、`volatile`、`CAS`、`Lock`、线程池，都是在解决这三个问题中的某一个或某几个。

| 要素 | 含义 | 一句话解释 | 典型问题 | 解决手段 |
| --- | --- | --- | --- | --- |
| 原子性 | 一个操作要么全部执行完，要么完全不执行，中途不被别的线程打断 | 「不可再分的整体」 | `i++` 其实是「读-改-写」三步，多线程下会互相覆盖 | `synchronized`、`Lock`、`AtomicInteger` |
| 可见性 | 一个线程修改了共享变量，其他线程能立刻看到最新值 | 「改了别人马上看得见」 | CPU 缓存导致线程 A 改了值，线程 B 一直读旧值 | `volatile`、`synchronized`、`Lock` |
| 有序性 | 程序按代码书写顺序执行，不被编译器/CPU 重排打乱 | 「先写的先发生」 | 指令重排序导致拿到「半初始化对象」 | `volatile`、`happens-before` 规则 |

**背景**：为什么会有这三个问题？根源在于现代计算机追求性能，引入了三级缓存（CPU 寄存器 → L1/L2/L3 缓存 → 主内存）和指令重排序。每个 CPU 核心有自己的缓存，线程 A 改了变量可能只写进自己的缓存还没刷回主内存，线程 B 读到的就是旧值——这就是可见性问题。而 `i++` 这种看似一句的代码，编译成字节码后是 `getfield → iconst_1 → iadd → putfield` 多条指令，中途被切走就丢更新——这就是原子性问题。

```java
// 原子性问题演示：i++ 不是原子操作
public class AtomicDemo {
    private static int count = 0;

    public static void main(String[] args) throws InterruptedException {
        // 开 1000 个线程，每个线程对 count 自增 1000 次
        Thread[] threads = new Thread[1000];
        for (int i = 0; i < 1000; i++) {
            threads[i] = new Thread(() -> {
                for (int j = 0; j < 1000; j++) {
                    count++; // 为什么不是 100 万？因为 count++ 是「读-改-写」三步，多线程互相覆盖
                }
            });
            threads[i].start();
        }
        for (Thread t : threads) {
            t.join(); // join 保证所有线程跑完再打印
        }
        // 期望 1000000，实际几乎每次都会少——这就是原子性被破坏
        System.out.println("count = " + count);
    }
}
```

**小结**：三要素是「病名」，后面每个工具是「药」。记忆口诀——**原子性用锁/CAS，可见性用 volatile，有序性用 volatile/锁**。

::: tip 💡 面试题：`i++` 为什么线程不安全？
`i++` 不是原子操作，它对应「读值、加 1、写回」三步，多线程下两个线程可能同时读到旧值，各自加 1 后写回，结果只加了一次（丢更新）。结论：需要 `synchronized`、`Lock` 或 `AtomicInteger` 保证原子性。
:::

### 二、进程、线程与并发、并行的区别

这是最容易被问懵的一组基础概念，先理清关系。

**进程**：操作系统进行「资源分配」和「调度」的基本单位，是一个程序的运行实例，拥有独立的内存空间（堆、方法区等）。

**线程**：进程内部的一个执行单元，是 CPU「调度」的基本单位。一个进程至少有一个线程（main 线程），同一进程内的线程**共享进程的堆和方法区**，但**各自有独立的栈和程序计数器**。

**并发 vs 并行**：

```
并发（Concurrent）：单核 CPU，多个任务「交替执行」
   时间轴：   [A]  [B]  [A]  [B]  [A]  →  看起来同时，其实是快速切换

并行（Parallel）：多核 CPU，多个任务「同时执行」
   时间轴：   [A]  [A]  [A]  [A]  [A]
              [B]  [B]  [B]  [B]  [B]  →  真正的同时
```

一句话：**并发是逻辑上的同时（宏观并行、微观串行），并行是物理上的同时（多核真并行）**。

| 对比项 | 进程 | 线程 |
| --- | --- | --- |
| 资源 | 独立内存空间 | 共享进程内存 |
| 通信 | 进程间通信（IPC、管道、Socket） | 共享变量、锁 |
| 创建/切换开销 | 大 | 小 |
| 崩溃影响 | 一个进程崩溃不影响其他进程 | 一个线程崩溃可能导致整个进程崩溃 |
| 经典类比 | 一座独立的工厂 | 工厂里的工人 |

::: tip 💡 面试题：进程和线程的区别？
进程是资源分配的最小单位，线程是 CPU 调度的最小单位；进程之间内存隔离，线程之间共享内存。原因是线程共享进程地址空间使得通信更快、切换开销更小，但也带来了需要加锁的并发问题。
:::

### 三、创建线程的几种方式

JDK 里「创建线程」本质只有一种——`new Thread()`，但「定义任务」的方式有多种，面试常问「有几种方式」，标准答案是 **3 + 1 种**（前三种是定义任务，第四种是推荐的线程池方式）。

**背景**：`Thread` 类实现了 `Runnable` 接口，`run()` 方法是线程要执行的任务。不同的方式本质区别是「把任务写在哪个地方」。

#### 方式一：继承 Thread 类

```java
class MyThread extends Thread {
    @Override
    public void run() {  // 重写 run()，线程启动后自动执行这里
        System.out.println(Thread.currentThread().getName() + " 执行中");
    }
}

// 使用
MyThread t = new MyThread();
t.start(); // 为什么必须调 start() 而不是 run()？见下方面试题
```

**缺点**：Java 是单继承，继承了 `Thread` 就不能继承别的类，扩展性差；任务和线程耦合在一起。

#### 方式二：实现 Runnable 接口（推荐）

```java
class MyTask implements Runnable {
    @Override
    public void run() {
        System.out.println(Thread.currentThread().getName() + " 任务执行");
    }
}

// 使用：任务与线程解耦，同一个任务可以丢给多个线程跑
MyTask task = new MyTask();
new Thread(task, "线程A").start(); // 为什么传 task？Thread 内部会调用 task.run()
new Thread(task, "线程B").start();
```

**优点**：任务（`Runnable`）和线程（`Thread`）分离，任务可复用、可被线程池复用，是首选方式。

#### 方式三：实现 Callable 接口（能拿返回值、能抛异常）

`Runnable` 的 `run()` 没有返回值也不能抛受检异常，`Callable` 弥补了这个缺陷。

```java
import java.util.concurrent.*;

class MyCallable implements Callable<String> {
    @Override
    public String call() throws Exception { // 注意：有返回值，且能抛异常
        Thread.sleep(1000); // 模拟耗时计算
        return "计算结果";
    }
}

public class CallableDemo {
    public static void main(String[] args) throws Exception {
        // FutureTask 是 Callable 和 Runnable 之间的「桥梁」，实现了 RunnableFuture 接口
        // 为什么需要它？因为 Thread 只接受 Runnable，FutureTask 实现了 Runnable 才能丢给 Thread
        FutureTask<String> futureTask = new FutureTask<>(new MyCallable());
        new Thread(futureTask).start();

        // get() 会阻塞直到任务执行完拿到结果（也能传超时时间 get(1, TimeUnit.SECONDS)）
        String result = futureTask.get();
        System.out.println("拿到结果：" + result);

        // 线程池也接受 Callable，返回 Future（更常用，见线程池章节）
    }
}
```

#### 方式四：线程池（实际项目唯一推荐）

生产环境几乎不会手动 `new Thread`，而是用线程池复用线程、控制并发数（详见高级篇「线程池」章节）。

| 方式 | 返回值 | 抛异常 | 推荐度 | 适用场景 |
| --- | --- | --- | --- | --- |
| 继承 Thread | 无 | 不能抛受检异常 | 低 | 几乎不用 |
| 实现 Runnable | 无 | 不能抛受检异常 | 高 | 无返回值的任务 |
| 实现 Callable | 有 | 能抛受检异常 | 高 | 需要返回值的任务 |
| 线程池 + Runnable/Callable | 可有 | 可抛 | 最高 | 生产环境统一方式 |

**小结**：`Thread` 是「线程」的抽象，`Runnable`/`Callable` 是「任务」的抽象，`FutureTask`/`Future` 是「结果」的抽象，三者解耦是并发 API 设计的精髓。

::: tip 💡 面试题：为什么调 `start()` 能启动线程，直接调 `run()` 不行？
`start()` 会调用 native 方法真正创建一个操作系统级别的线程，再由新线程去回调 `run()`；而直接调 `run()` 只是当前线程里的一次普通方法调用，不会产生新线程，也就没有并发效果。结论：多线程必须用 `start()`。
:::

::: tip 💡 面试题：`Callable` 和 `Runnable` 的区别？
`Runnable` 的 `run()` 无返回值、不能抛受检异常；`Callable` 的 `call()` 有返回值、能抛异常，配合 `FutureTask`/`Future` 可以拿到执行结果。原因是二者定位不同：`Runnable` 只管「跑」，`Callable` 负责「跑完给结果」。
:::

### 四、线程的生命周期与状态转换

Java 线程有 **6 个状态**（注意：这是 Java 层面的 `Thread.State` 枚举，不是操作系统线程状态），面试必考状态转换图。

**状态定义（背景）**：线程从创建到销毁，经历一系列状态。理解状态转换是理解 `wait`/`notify`、`park`、锁阻塞这些机制的基础。

```
                    ┌─────────────────────────────┐
                    │                              │
      start()       ▼                              │
  NEW ──────► RUNNABLE ───────► TERMINATED         │
              │   ▲  ▲                             │
              │   │  │ 获得锁 / notify / unpark     │
 获取锁失败   │   │  │                             │
              ▼   │  │                             │
           BLOCKED │  │                             │
                   │  │                             │
         wait/join/│park ─────────────► WAITING     │
         sleep(time) ─────────────────► TIMED_WAITING
```

| 状态 | 说明 | 进入方式 | 退出方式 |
| --- | --- | --- | --- |
| NEW（新建） | 线程对象已创建，还没调 `start()` | `new Thread()` | 调 `start()` |
| RUNNABLE（可运行） | 就绪 + 运行两种的统称，可能正在跑也可能在等 CPU 时间片 | `start()` 后 | —— |
| BLOCKED（阻塞） | 没抢到 `synchronized` 锁，被挡在锁外 | 竞争锁失败 | 抢到锁 |
| WAITING（无限等待） | 无限期等待，必须被别的线程显式唤醒 | `wait()`、`join()`、`LockSupport.park()` | `notify`/`notifyAll`、`unpark` |
| TIMED_WAITING（限时等待） | 限时等待，时间到了自动醒 | `sleep(time)`、`wait(time)`、`join(time)` | 超时或提前被唤醒 |
| TERMINATED（终止） | 线程执行完毕或异常退出 | `run()` 返回 / 抛异常 | —— |

**三个易混状态辨析（高频陷阱）**：

1. **BLOCKED vs WAITING**：`BLOCKED` 是「被动」等锁（锁被别人占着）；`WAITING` 是「主动」等待（调用了 `wait()` 等，主动让出 CPU）。
2. **RUNNABLE 为什么包含「就绪」和「运行」**：Java 层面拿不到操作系统「就绪/运行」的精确状态，所以统一归为 `RUNNABLE`。
3. **`sleep` 后线程处于 TIMED_WAITING**，不是 BLOCKED——很多人搞混。

```java
// 状态观察示例：用一个线程打印另一个线程的状态
public class StateDemo {
    public static void main(String[] args) throws InterruptedException {
        Object lock = new Object();
        Thread t = new Thread(() -> {
            synchronized (lock) {
                try {
                    Thread.sleep(5000); // 为什么用 sleep 而不是 wait？sleep 不释放锁，这里想让 main 观察到 TIMED_WAITING
                } catch (InterruptedException e) {
                    e.printStackTrace();
                }
            }
        });
        System.out.println("创建后: " + t.getState()); // NEW
        t.start();
        Thread.sleep(500);
        System.out.println("启动后: " + t.getState()); // TIMED_WAITING（sleep 中）
        t.join(); // 等 t 结束
        System.out.println("结束后: " + t.getState()); // TERMINATED
    }
}
```

**小结**：记住一句话——**`sleep` 不释放锁，`wait` 释放锁**，这是理解状态转换的关键锚点。

::: tip 💡 面试题：`sleep()` 和 `wait()` 的区别？
`sleep` 是 `Thread` 的静态方法，不释放锁，时间到自动醒；`wait` 是 `Object` 的方法，会释放锁，必须靠 `notify`/`notifyAll` 唤醒，且必须在 `synchronized` 块内调用。结论：`sleep` 抱着锁睡，`wait` 让出锁睡。
:::

### 五、Thread 常用方法与线程控制

线程控制方法很多，逐个过一遍，重点是 `join`、`yield`、`interrupt`、`daemon`。

| 方法 | 归属 | 作用 | 是否释放锁 | 使用场景 |
| --- | --- | --- | --- | --- |
| `sleep(long)` | Thread（静态） | 让当前线程休眠指定毫秒 | 否 | 限流、模拟耗时 |
| `join()` | Thread（实例） | 当前线程等待目标线程执行完再继续 | 是（内部用 `wait`） | 等子线程结果 |
| `yield()` | Thread（静态） | 让出 CPU，从运行态回就绪态，让同优先级线程有机会执行 | 否 | 极少用，只是「建议」 |
| `interrupt()` | Thread（实例） | 给线程发中断信号，设置中断标志位 | —— | 优雅停止线程 |
| `setDaemon(true)` | Thread（实例） | 设为守护线程 | —— | 后台清理、监控 |
| `isAlive()` | Thread（实例） | 线程是否还活着 | —— | 判断线程状态 |

#### join 详解（等子线程）

```java
public class JoinDemo {
    public static void main(String[] args) throws InterruptedException {
        Thread t = new Thread(() -> {
            try {
                Thread.sleep(2000);
            } catch (InterruptedException e) {
                e.printStackTrace();
            }
            System.out.println("子线程执行完");
        });
        t.start();
        t.join(); // 为什么 main 要 join？join 让 main 阻塞等待 t 执行完，否则 main 可能先打印「全部结束」
        System.out.println("全部结束");
    }
}
```

`join()` 的底层原理就是 `wait()`：调 `t.join()` 会让当前线程（main）进入 WAITING，等 `t` 执行完（JVM 会在线程结束时调用 `notifyAll`）再唤醒 main。

#### interrupt 与线程中断（优雅停止线程）

停止线程不能靠已废弃的 `stop()`（会直接杀死线程、破坏数据一致性），要用「中断标志位 + 协作」的方式。

```java
public class InterruptDemo {
    public static void main(String[] args) throws InterruptedException {
        Thread t = new Thread(() -> {
            while (!Thread.currentThread().isInterrupted()) { // 为什么检查中断标志？这是协作式停止：线程自己决定何时停，安全
                System.out.println("工作中...");
                try {
                    Thread.sleep(500); // sleep 会响应中断并抛异常
                } catch (InterruptedException e) {
                    // 为什么这里要再次 interrupt？捕获中断异常后中断标志会被清除，需要手动恢复
                    Thread.currentThread().interrupt();
                    break;
                }
            }
            System.out.println("线程已优雅退出");
        });
        t.start();
        Thread.sleep(2000);
        t.interrupt(); // 发中断信号，不是强制杀线程，只是打个「停止」招呼
    }
}
```

**小结**：线程控制的核心思想是「协作式」——`join` 等结果、`interrupt` 打信号、`daemon` 分主从，而不是暴力 `stop`。

::: tip 💡 面试题：如何优雅地停止一个线程？
用 `interrupt()` 设置中断标志 + 线程内部通过 `isInterrupted()` 检查并主动退出，而不是用已废弃的 `stop()`。原因：`stop()` 会立即终止线程，可能让共享数据处于不一致状态，违背线程安全的初衷。
:::

## 高级篇

### 六、synchronized 关键字（最基础的锁）

`synchronized` 是 Java 内置锁，也是最常用的同步手段。JDK 6 之后做了大量优化（锁升级），性能已不输 `Lock`，日常优先用它。

**背景**：多个线程访问共享资源需要「互斥」——同一时刻只允许一个线程进入临界区，`synchronized` 就是实现互斥的关键字。

#### 三种使用形式与锁的对象

```java
public class SyncDemo {
    private final Object lock = new Object(); // 专用锁对象，比锁 this 更清晰、更安全
    private static int count = 0;

    // 形式一：锁代码块（锁任意对象）—— 最灵活，推荐
    public void method() {
        synchronized (lock) {   // 锁的是 lock 对象，两个线程必须用同一个 lock 才互斥
            count++;
        }
    }

    // 形式二：锁实例方法（锁 this）
    public synchronized void method2() { } // 等价于 synchronized(this){...}

    // 形式三：锁静态方法（锁 Class 对象，全局唯一）
    public static synchronized void method3() { } // 等价于 synchronized(SyncDemo.class){...}
}
```

**关键结论：锁的是「对象」而不是「代码块」**。两个线程只有在竞争**同一个锁对象**时才会互斥。实例方法的锁是 `this`，静态方法的锁是 `Class` 对象——所以实例方法和静态方法之间不互斥。

#### 锁升级过程（JDK 6 后核心优化，面试必问）

JDK 6 之前 `synchronized` 直接是重量级锁（挂起线程、切换用户态/内核态，开销大）。JDK 6 引入了「锁升级」机制，让锁在有竞争时才逐步变重：

```
无锁 ──► 偏向锁 ──► 轻量级锁(CAS 自旋) ──► 重量级锁(挂起线程)
          (单线程)     (多线程交替、无竞争)   (竞争激烈)
```

| 锁状态 | 触发条件 | 加锁方式 | 开销 |
| --- | --- | --- | --- |
| 无锁 | 无竞争 | 不加锁 | 零 |
| 偏向锁 | 只有一个线程反复进入 | 对象头记录线程 ID，重入直接放行 | 极低 |
| 轻量级锁 | 多线程交替执行、无真正竞争 | CAS 自旋尝试获取 | 低（消耗 CPU 但不挂线程） |
| 重量级锁 | 竞争激烈、自旋失败 | 操作系统互斥量，没抢到挂起 | 高（用户态/内核态切换） |

**锁升级是单向的，只会升级不会降级**（偏向锁撤销会回到无锁是特殊情况，但整体趋势是向上）。

```java
// 锁升级示意：从偏向到轻量到重量，取决于竞争程度，无需程序员干预
public class LockUpgrade {
    public static void main(String[] args) {
        Object lock = new Object();
        // 线程 A 反复进入 → 偏向锁，记录线程 ID，几乎零开销
        // 线程 A、B 交替进入 → 轻量级锁，CAS 自旋
        // 线程 A、B、C 激烈竞争 → 重量级锁，挂起线程交给 OS
        synchronized (lock) {
            // 临界区
        }
    }
}
```

**小结**：`synchronized` 用对象头里的 Mark Word 记录锁状态，能自动完成「偏向 → 轻量 → 重量」升级，日常无脑用即可。

::: tip 💡 面试题：synchronized 底层是怎么实现的？
靠对象头 Mark Word 记录锁状态，锁升级路径是「偏向锁 → 轻量级锁（CAS 自旋）→ 重量级锁」；重量级锁基于字节码的 `monitorenter`/`monitorexit` 指令实现。结论：它是 JVM 层面的内置锁，无需手动释放。
:::

::: tip 💡 面试题：synchronized 锁的是什么？
锁的是「对象」（对象头 Mark Word），不是代码。实例方法锁 `this`，静态方法锁 `Class` 对象，代码块锁括号里的对象。结论：两个线程锁同一对象才互斥，锁不同对象不互斥。
:::

### 七、volatile 关键字（可见性 + 有序性）

`volatile` 是轻量级同步机制，只解决「可见性」和「有序性」，**不解决原子性**——这是它和 `synchronized` 最本质的区别。

**背景**：前面说过 CPU 有缓存、编译器会重排指令，导致一个线程改了共享变量，另一个线程读不到、或读到半成品。`volatile` 就是专门治这两点的。

#### 作用一：保证可见性

```java
public class VolatileVisibility {
    // 为什么必须加 volatile？不加的话，worker 线程可能一直从自己 CPU 缓存读旧值，看不到 main 的修改
    private static volatile boolean flag = false;

    public static void main(String[] args) throws InterruptedException {
        new Thread(() -> {
            while (!flag) { // 读 volatile 变量每次都强制从主内存读，能看到 main 的修改
                // 空转等待
            }
            System.out.println("worker 感知到 flag 变化，退出");
        }).start();

        Thread.sleep(1000);
        flag = true; // 写 volatile 变量会立刻刷回主内存
    }
}
```

#### 作用二：禁止指令重排序（内存屏障）

CPU 和编译器为了性能会重排指令，但重排不能改变「单线程」的语义，多线程下就可能出问题。`volatile` 通过「内存屏障」禁止特定重排：

```
内存屏障（Memory Barrier）是 CPU 指令，volatile 读写前后会插入屏障：
  写操作：...普通写 → StoreStore屏障 → volatile写 → StoreLoad屏障
  读操作：volatile读 → LoadLoad屏障 → LoadStore屏障 → ...普通读

  效果：volatile 写之前的所有操作，都不能重排到写之后
       volatile 读之后的所有操作，都不能重排到读之前
```

**经典应用：双重检查锁（DCL）单例**——这是 volatile 最有名的用武之地：

```java
public class Singleton {
    // 为什么必须加 volatile？
    // new Singleton() 不是原子操作，拆成三步：1.分配内存 2.初始化对象 3.把引用赋值给 instance
    // 2 和 3 可能被重排，导致其他线程拿到「分配了内存但还没初始化」的半成品对象
    private static volatile Singleton instance;

    private Singleton() { }

    public static Singleton getInstance() {
        if (instance == null) {                    // 第一次检查：为什么？避免每次调用都加锁，性能优化
            synchronized (Singleton.class) {       // 加锁保证只有一个线程能创建
                if (instance == null) {            // 第二次检查：为什么？防止多个线程都通过了第一次检查后重复创建
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}
```

**volatile 不保证原子性**（高频考点）：

```java
public class VolatileNoAtomic {
    private static volatile int count = 0; // volatile 了，但 count++ 仍然线程不安全

    public static void main(String[] args) throws InterruptedException {
        Thread[] ts = new Thread[100];
        for (int i = 0; i < 100; i++) {
            ts[i] = new Thread(() -> {
                for (int j = 0; j < 1000; j++) {
                    count++; // 为什么还是错？count++ 是「读-改-写」复合操作，volatile 管不了中途被打断
                }
            });
            ts[i].start();
        }
        for (Thread t : ts) t.join();
        System.out.println("count = " + count); // 期望 100000，实际会少
    }
}
```

**小结**：`volatile` 是「轻量级」的，只做两件事——保证可见性、禁止重排；它不阻塞线程，但也不保证复合操作的原子性。

::: tip 💡 面试题：volatile 能保证原子性吗？
不能。`volatile` 只保证可见性和有序性；`i++` 这种「读-改-写」复合操作，即使变量用 `volatile` 修饰，多线程下仍会丢失更新。结论：需要原子性时用 `AtomicInteger` 或加锁。
:::

::: tip 💡 面试题：synchronized 和 volatile 的区别？
`synchronized` 保证原子性 + 可见性 + 有序性，会阻塞线程，重量级；`volatile` 只保证可见性 + 有序性，不保证原子性，不阻塞，轻量级。结论：需要互斥/原子操作用 `synchronized`，只需要标志位可见性用 `volatile`。
:::

### 八、CAS 与原子类

CAS（Compare And Swap，比较并交换）是「无锁并发」的基石，`AtomicInteger` 等原子类底层全靠它。

**背景**：加锁有开销（挂起、切换线程），能否不加锁也能保证 `i++` 原子？CAS 用「乐观」思路：先算，再一次性「比较 + 写入」，CPU 用一条原子指令保证这一步不被打断。

#### CAS 的核心思想

```
CAS 的伪代码（底层是 CPU 原子指令 cmpxchg）：
   compareAndSet(预期值 expect, 新值 update):
       读取内存当前值 current
       if (current == expect):   // 没被别人改过
           内存 = update          // 才写入
           return true
       else:
           return false          // 被别人改了，放弃本次

   对应 Unsafe 类方法：compareAndSwapInt(对象, 字段偏移量, 预期值, 新值)
```

#### 原子类使用

```java
import java.util.concurrent.atomic.*;

public class AtomicDemo {
    public static void main(String[] args) throws InterruptedException {
        AtomicInteger count = new AtomicInteger(0);
        Thread[] ts = new Thread[100];
        for (int i = 0; i < 100; i++) {
            ts[i] = new Thread(() -> {
                for (int j = 0; j < 1000; j++) {
                    count.incrementAndGet(); // 为什么线程安全？底层是 CAS 自旋，失败就重试直到成功
                }
            });
            ts[i].start();
        }
        for (Thread t : ts) t.join();
        System.out.println("count = " + count.get()); // 稳定输出 100000

        // compareAndSet：只有当当前值是 0 才改成 1，返回是否成功
        boolean ok = count.compareAndSet(100000, 100001);
        System.out.println("CAS 成功: " + ok + ", 新值: " + count.get());
    }
}
```

#### 常用原子类一览

| 原子类 | 作用 | 使用场景 |
| --- | --- | --- |
| `AtomicInteger` | 原子 int | 计数器、序号生成 |
| `AtomicLong` | 原子 long | 大计数 |
| `AtomicBoolean` | 原子 boolean | 一次性开关、幂等标志 |
| `AtomicReference<T>` | 原子引用 | 原子更新对象引用 |
| `AtomicStampedReference<T>` | 带版本号的原子引用 | 解决 ABA 问题 |
| `AtomicIntegerArray` | 原子 int 数组 | 数组元素原子更新 |
| `LongAdder` | 高并发累加（分段累加） | 高并发统计，比 AtomicLong 吞吐高 |

#### CAS 的两大问题

1. **ABA 问题**：值从 A 变 B 又变回 A，CAS 误以为「没变过」，可能产生逻辑错误（如栈顶元素被换了两次）。

```java
// ABA 问题演示：值从 1 → 2 → 1，CAS 以为一直是 1
AtomicInteger atomic = new AtomicInteger(1);
// 线程 A 读到 1，准备 CAS(1, 3)
// 线程 B 先把 1 改成 2，又改回 1
atomic.compareAndSet(1, 2);
atomic.compareAndSet(2, 1);
// 线程 A 此时 CAS(1, 3) 仍会成功，但它没意识到中间发生过变化 —— 这就是 ABA

// 解决方案：加版本号，AtomicStampedReference
AtomicStampedReference<Integer> ref = new AtomicStampedReference<>(1, 0); // (值, 版本号)
int[] stamp = new int[1];
int oldValue = ref.get(stamp);          // 读值和版本号
ref.compareAndSet(oldValue, 3, stamp[0], stamp[0] + 1); // 值和版本号都要匹配才成功
```

2. **自旋开销**：CAS 失败会一直自旋重试，高竞争下大量线程空转浪费 CPU。这也是为什么 `synchronized` 竞争激烈时会升级成重量级锁（挂起线程省 CPU）。

**小结**：CAS 是「乐观锁」思想——先做，失败了再重试；而 `synchronized` 是「悲观锁」——先锁住再做。CAS 无阻塞、高并发读多写少时性能极好，但写竞争激烈时自旋反而浪费 CPU。

::: tip 💡 面试题：什么是 CAS？它有什么优缺点？
CAS 是「比较并交换」，通过 CPU 原子指令实现无锁更新，是 `AtomicInteger` 的底层。优点是无锁、不阻塞、性能高；缺点是存在 ABA 问题和高竞争下的自旋开销。结论：读多写少场景用 CAS，写竞争激烈用锁。
:::

::: tip 💡 面试题：如何解决 CAS 的 ABA 问题？
用带版本号的 `AtomicStampedReference`，每次更新同时递增版本号，CAS 时「值 + 版本号」都要匹配才成功。原因：版本号记录了「变过几次」，即使值回到 A，版本号不同也能发现中间变过。
:::

### 九、Lock 接口与 ReentrantLock

`Lock` 是 JDK 5 引入的显式锁接口，`ReentrantLock` 是其最常用的实现，可以理解为 `synchronized` 的「功能增强版」。底层依赖 AQS（AbstractQueuedSynchronizer，见原理篇）。

**背景**：`synchronized` 虽然够用，但有几个硬伤——不能尝试获取锁（要么阻塞要么拿到）、不能中断、不能限时等待、不能公平。`Lock` 补齐了这些能力。

#### synchronized vs ReentrantLock

| 对比项 | synchronized | ReentrantLock |
| --- | --- | --- |
| 加锁方式 | 关键字，自动加锁/解锁 | `lock()` / `unlock()` 手动管理 |
| 释放时机 | 代码块结束或异常自动释放 | 必须在 `finally` 里手动 `unlock()` |
| 公平性 | 非公平 | 构造器可指定公平/非公平 |
| 可中断 | 不可中断 | `lockInterruptibly()` 可中断 |
| 限时等待 | 不支持 | `tryLock(timeout, unit)` |
| 尝试获取 | 不支持 | `tryLock()` 立即返回 |
| 条件变量 | 单个 `wait`/`notify` 队列 | 多个 `Condition`，可精准唤醒 |
| 性能 | JDK6 优化后接近 | 略优 |

#### 基本用法与「必须 finally 释放」

```java
import java.util.concurrent.locks.ReentrantLock;

public class LockDemo {
    private final ReentrantLock lock = new ReentrantLock();
    private int count = 0;

    public void increment() {
        lock.lock(); // 加锁
        try {
            count++; // 临界区
        } finally {
            lock.unlock(); // 为什么必须在 finally？防止业务抛异常后锁永远不释放，导致其他线程死等
        }
    }
}
```

#### 可重入性（Reentrant 的含义）

同一个线程可以重复获取自己已经持有的锁，不会死锁——这是 `ReentrantLock` 名字的由来，`synchronized` 也是可重入的。

```java
public class ReentrantDemo {
    private final ReentrantLock lock = new ReentrantLock();

    public void outer() {
        lock.lock();
        try {
            System.out.println("外层方法拿到锁");
            inner(); // 为什么不会死锁？同一个线程重入，AQS 的 state 会从 1 变 2，只记录重入次数
        } finally {
            lock.unlock(); // state 2 -> 1
        }
    }

    public void inner() {
        lock.lock();      // state 1 -> 2（重入成功）
        try {
            System.out.println("内层方法再次拿到锁");
        } finally {
            lock.unlock(); // state 2 -> 1
        }
    }
}
```

#### 公平锁与非公平锁

```java
// 公平锁：线程按排队顺序获取锁，避免「饥饿」但吞吐低
ReentrantLock fair = new ReentrantLock(true);
// 非公平锁（默认）：新来的线程可以先「插队」抢锁，吞吐高但可能饥饿
ReentrantLock unfair = new ReentrantLock(false);
```

#### Condition：精准唤醒

`synchronized` 只能 `notifyAll` 唤醒所有等待线程，`Condition` 可以按条件分组，只唤醒某一类线程（典型场景：生产者消费者、有界队列）。

```java
import java.util.concurrent.locks.*;

public class ConditionDemo {
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notFull = lock.newCondition();  // 队列不满的信号
    private final Condition notEmpty = lock.newCondition(); // 队列不空的信号
    private final Object[] queue = new Object[10];
    private int size = 0;

    public void put(Object item) throws InterruptedException {
        lock.lock();
        try {
            while (size == queue.length) {
                notFull.await(); // 队列满，等待「不满」信号（为什么用 while？防止虚假唤醒）
            }
            queue[size++] = item;
            notEmpty.signal(); // 放入后唤醒一个等待「不空」的消费者
        } finally {
            lock.unlock();
        }
    }

    public Object take() throws InterruptedException {
        lock.lock();
        try {
            while (size == 0) {
                notEmpty.await();
            }
            Object item = queue[--size];
            notFull.signal();
            return item;
        } finally {
            lock.unlock();
        }
    }
}
```

**小结**：能用 `synchronized` 就用它（简单、自动释放），需要「可中断、超时、公平、多条件」时才上 `ReentrantLock`。

::: tip 💡 面试题：synchronized 和 ReentrantLock 怎么选？
能用 `synchronized` 就优先用它（写法简单、JVM 自动优化、自动释放锁）；需要可中断、超时获取、公平锁、多个条件变量这些特性时才用 `ReentrantLock`。结论：默认 synchronized，特殊需求 ReentrantLock。
:::

::: tip 💡 面试题：什么是可重入锁？
一个线程已经持有了锁，再次进入这把锁保护的代码时能直接通过，不会自己把自己锁死。`synchronized` 和 `ReentrantLock` 都是可重入的。原因：内部记录了持有线程和重入次数（AQS 的 state 计数）。
:::

### 十、线程池 ThreadPoolExecutor（面试最高频）

线程池是并发编程里「项目 + 面试」双料最高频知识点。核心是 `ThreadPoolExecutor` 的 **7 个参数 + 执行流程 + 拒绝策略**。

**背景**：频繁 `new Thread` 有三大问题——创建/销毁线程开销大、线程数量失控导致 OOM、缺乏统一管理。线程池通过「复用线程 + 任务队列」解决这三个问题。

#### 7 个核心参数

```java
import java.util.concurrent.*;

public class ThreadPoolDemo {
    public static void main(String[] args) {
        ThreadPoolExecutor pool = new ThreadPoolExecutor(
            2,                            // 1. corePoolSize：核心线程数，常驻不销毁（即使空闲也保留）
            5,                            // 2. maximumPoolSize：最大线程数 = 核心 + 非核心
            60,                           // 3. keepAliveTime：非核心线程空闲多久被销毁
            TimeUnit.SECONDS,             // 4. unit：上面时间的单位
            new ArrayBlockingQueue<>(10), // 5. workQueue：任务队列，核心线程忙时任务在这里排队
            Executors.defaultThreadFactory(), // 6. threadFactory：线程工厂，给线程起名、设优先级
            new ThreadPoolExecutor.AbortPolicy() // 7. handler：拒绝策略，队列满且线程满时的处理方式
        );

        // 提交任务（execute 提交 Runnable，submit 提交 Callable 能拿返回值）
        pool.execute(() -> System.out.println(Thread.currentThread().getName() + " 执行任务"));
        pool.shutdown(); // 优雅关闭：不再接新任务，等已提交任务执行完
    }
}
```

#### 执行流程（必背）

```
提交任务
   │
   ▼
 线程数 < corePoolSize ？ ──是──► 直接新建核心线程执行任务
   │否
   ▼
 任务队列满了吗？ ──没满──► 任务入队等待（核心线程空闲时取出执行）
   │满了
   ▼
 线程数 < maximumPoolSize ？ ──是──► 新建非核心线程执行任务
   │否
   ▼
 触发拒绝策略（handler）
```

一句话背法：**先核心线程 → 再任务队列 → 再非核心线程 → 最后拒绝**。

#### 四种拒绝策略

| 策略 | 行为 | 使用场景 |
| --- | --- | --- |
| `AbortPolicy`（默认） | 抛 `RejectedExecutionException` | 需要感知「扛不住」的场景 |
| `CallerRunsPolicy` | 交给提交任务的线程自己执行 | 温和削峰，不丢任务 |
| `DiscardPolicy` | 静默丢弃新任务 | 允许丢任务的场景（如日志） |
| `DiscardOldestPolicy` | 丢弃队列最旧任务再尝试提交 | 优先保新任务 |

#### 常用线程池工厂方法（及为什么被禁用）

| 工厂方法 | 底层 | 问题 |
| --- | --- | --- |
| `newFixedThreadPool(n)` | 固定线程数 + `LinkedBlockingQueue` | 队列无界，堆积可能 OOM |
| `newSingleThreadExecutor()` | 单线程 + `LinkedBlockingQueue` | 队列无界，可能 OOM |
| `newCachedThreadPool()` | 动态线程 + `SynchronousQueue` | 线程数无上限，可能 OOM |
| `newScheduledThreadPool(n)` | 定时任务 | 线程数无上限，可能 OOM |

```java
// 阿里规范禁止 Executors 工厂方法，必须手动 new ThreadPoolExecutor
// 为什么？newFixedThreadPool 的队列是 Integer.MAX_VALUE 的无界队列，任务积压时内存会被打爆
// 正确姿势：显式指定队列容量和最大线程数，让线程池「可控」
ThreadPoolExecutor pool = new ThreadPoolExecutor(
    10, 20, 60, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(100),  // 有界队列，最多排队 100 个，超了就拒绝
    new ThreadPoolExecutor.CallerRunsPolicy() // 拒绝时让调用线程自己跑，平滑降级
);
```

#### 线程数怎么配置（经验公式）

```
CPU 密集型（计算为主，几乎不等待）：
    线程数 = CPU 核心数 + 1   （线程多了反而因切换降低吞吐）

IO 密集型（大量网络/磁盘等待）：
    线程数 = CPU 核心数 * 2    （等待时 CPU 空闲，可以多开线程压榨）
    或 = CPU 核心数 / (1 - 阻塞系数)，阻塞系数通常取 0.8~0.9

   CPU 核心数获取：Runtime.getRuntime().availableProcessors()
```

**小结**：线程池把「线程」和「任务」解耦——线程是稀缺资源要复用，任务是排队处理。7 参数、执行流程、拒绝策略、禁用 Executors 是四个必考点。

::: tip 💡 面试题：为什么不推荐用 `Executors.newFixedThreadPool()` 等工厂方法？
因为它们内部默认使用 `LinkedBlockingQueue`（无界队列）或线程数无上限，任务堆积时会导致 OOM。结论：应该手动 `new ThreadPoolExecutor` 并显式指定有界队列、最大线程数和拒绝策略。
:::

::: tip 💡 面试题：线程池核心线程会销毁吗？
默认不会。核心线程即使空闲也常驻，除非设置了 `allowCoreThreadTimeOut(true)`。原因是核心线程是为「快速响应」预留的，避免任务到来时再花时间创建线程。
:::

### 十一、线程协作工具

除了锁，JUC 还提供了一批「线程间协调」的工具，解决「等 N 个完成」「限流」「互相等」等编排问题。

#### CountDownLatch（等 N 个线程完成，计数器）

**场景**：主线程要等所有子任务都执行完才能汇总结果（如等所有分片查询完再合并）。

```java
import java.util.concurrent.*;

public class CountDownLatchDemo {
    public static void main(String[] args) throws InterruptedException {
        int taskCount = 3;
        CountDownLatch latch = new CountDownLatch(taskCount); // 计数器初始为 3

        for (int i = 0; i < taskCount; i++) {
            new Thread(() -> {
                // 模拟子任务执行
                System.out.println(Thread.currentThread().getName() + " 完成任务");
                latch.countDown(); // 为什么每完成一个减 1？计数归零时 await 的线程才被唤醒
            }).start();
        }

        latch.await(); // 主线程阻塞，直到计数归零
        System.out.println("所有子任务完成，主线程继续汇总");
    }
}
```

#### CyclicBarrier（N 个线程互相等，可复用）

**场景**：多个线程分阶段执行，每一阶段都要「人到齐」才能进入下一阶段（如多人游戏匹配、多线程计算分步对齐）。

```java
import java.util.concurrent.*;

public class CyclicBarrierDemo {
    public static void main(String[] args) {
        int parties = 3;
        CyclicBarrier barrier = new CyclicBarrier(parties, () ->
            System.out.println("本轮人到齐，出发！") // 最后一个到达的线程触发这个回调
        );

        for (int i = 0; i < parties; i++) {
            new Thread(() -> {
                try {
                    System.out.println(Thread.currentThread().getName() + " 到达栅栏，等待");
                    barrier.await(); // 为什么等待？必须凑齐 parties 个线程才一起放行
                    System.out.println(Thread.currentThread().getName() + " 通过栅栏");
                } catch (Exception e) {
                    e.printStackTrace();
                }
            }).start();
        }
    }
}
```

**CountDownLatch vs CyclicBarrier**（高频对比）：

| 对比项 | CountDownLatch | CyclicBarrier |
| --- | --- | --- |
| 核心逻辑 | 一个（或多个）线程「等待」其他 N 个线程 | N 个线程「互相等待」 |
| 计数 | 只能减，归零即结束 | 归零后自动重置，可复用 |
| 可否复用 | 不可复用 | 可复用 |
| 回调 | 无 | 可设「人到齐」回调 |

#### Semaphore（信号量，限流）

**场景**：限制同一时刻最多 N 个线程访问某资源（数据库连接池、接口限流）。

```java
import java.util.concurrent.*;

public class SemaphoreDemo {
    public static void main(String[] args) {
        Semaphore semaphore = new Semaphore(3); // 最多 3 个许可

        for (int i = 0; i < 10; i++) {
            new Thread(() -> {
                try {
                    semaphore.acquire(); // 获取许可，没有则阻塞（为什么？保证并发数不超过 3）
                    System.out.println(Thread.currentThread().getName() + " 获取许可，处理中");
                    Thread.sleep(1000);
                    semaphore.release(); // 释放许可，让其他线程获取
                } catch (InterruptedException e) {
                    e.printStackTrace();
                }
            }).start();
        }
    }
}
```

#### Exchanger（两线程交换数据）

```java
// 场景：两个线程分别生产数据，在约定点交换结果（如流水线交接）
Exchanger<String> exchanger = new Exchanger<>();
new Thread(() -> {
    try {
        String received = exchanger.exchange("线程A的数据");
        System.out.println("A 收到：" + received);
    } catch (InterruptedException e) { }
}).start();
new Thread(() -> {
    try {
        String received = exchanger.exchange("线程B的数据");
        System.out.println("B 收到：" + received);
    } catch (InterruptedException e) { }
}).start();
```

#### CompletableFuture（异步编排，现代主流）

JDK 8 引入，用「声明式」方式编排多个异步任务，替代回调地狱，是当前后端最主流的异步工具。

```java
import java.util.concurrent.*;

public class CompletableFutureDemo {
    public static void main(String[] args) throws Exception {
        // 异步执行，supplyAsync 用默认线程池，返回有结果的 Future
        CompletableFuture<String> future = CompletableFuture.supplyAsync(() -> {
            return "查询用户"; // 模拟第一步
        }).thenApply(user -> {       // thenApply：依赖上一步结果做转换
            return user + " → 查询订单";
        }).thenApply(order -> {
            return order + " → 计算结果";
        }).exceptionally(e -> {      // exceptionally：异常兜底
            return "出错降级";
        });

        System.out.println(future.get()); // 阻塞拿最终结果

        // 两个任务并行再合并（thenCombine）
        CompletableFuture<Integer> f1 = CompletableFuture.supplyAsync(() -> 1);
        CompletableFuture<Integer> f2 = CompletableFuture.supplyAsync(() -> 2);
        CompletableFuture<Integer> sum = f1.thenCombine(f2, Integer::sum);
        System.out.println("合并结果：" + sum.get());
    }
}
```

**小结**：编排「一个等 N 个」用 `CountDownLatch`，「N 个互相等」用 `CyclicBarrier`，「限流」用 `Semaphore`，「复杂异步编排」用 `CompletableFuture`。

::: tip 💡 面试题：CountDownLatch 和 CyclicBarrier 的区别？
CountDownLatch 是一个或多个线程等待另外 N 个线程，计数器只能减、不能复用；CyclicBarrier 是 N 个线程互相等待，计数归零后自动重置、可复用。结论：一个「主等从」，一个「互相等」。
:::

### 十二、ThreadLocal（线程私有变量）

`ThreadLocal` 让每个线程拥有自己独立的变量副本，线程之间互不干扰，是「用空间换线程安全」的典型。

**背景**：共享变量要加锁（有性能开销），有没有办法「每个线程各用各的」避免共享？`ThreadLocal` 就是这个思路——变量归线程私有，天然无竞争。

#### 基本用法

```java
public class ThreadLocalDemo {
    // 为什么用 ThreadLocal？SimpleDateFormat 不是线程安全的，多个线程共享会出错
    // 给每个线程一份独立的 SimpleDateFormat，就避免了加锁或每次 new
    private static final ThreadLocal<SimpleDateFormat> LOCAL =
        ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd"));

    public static String format(Date date) {
        return LOCAL.get().format(date); // get() 拿到当前线程自己的副本
    }
}
```

#### 使用场景

| 场景 | 说明 |
| --- | --- |
| 日期格式化 | `SimpleDateFormat` 非线程安全，每线程一份 |
| 数据库连接 | 每个线程独立持有自己的 `Connection` |
| 用户上下文 | Spring 里存当前登录用户信息（`RequestContextHolder`） |
| 事务管理 | Spring 事务资源绑定到当前线程 |
| 链路追踪 | 分布式链路 ID 贯穿当前线程 |

#### 关键方法

```java
ThreadLocal<String> local = new ThreadLocal<>();
local.set("value");   // 给当前线程存值
String v = local.get(); // 取当前线程的值
local.remove();        // 为什么必须 remove？防止线程复用（线程池）时残留旧值 + 内存泄漏
```

#### 为什么容易内存泄漏（原理铺垫，详见原理篇）

`ThreadLocal` 内部用 `ThreadLocalMap` 存值，`Map` 的 key 是弱引用（`ThreadLocal` 对象本身），value 是强引用。当 `ThreadLocal` 对象被 GC 后，key 变 null，但 value 还挂在 `Thread` 上，线程池的线程又长期存活，value 就永远无法回收——这就是内存泄漏。

```java
// 正确使用姿势：用完必须 remove（finally 保证）
try {
    local.set(new byte[1024 * 1024]); // 假设存大对象
    // 使用
} finally {
    local.remove(); // 为什么放 finally？业务抛异常也要保证清理，避免泄漏
}
```

**小结**：`ThreadLocal` 用「线程私有副本」换取无锁并发，但代价是要手动 `remove` 防止泄漏；Spring 的 `@Transactional`、用户上下文都靠它实现。

::: tip 💡 面试题：ThreadLocal 为什么会内存泄漏？
`ThreadLocalMap` 的 key 是弱引用会被 GC 回收，但 value 是强引用，且线程池线程长期存活，导致 value 无法回收。结论：用完必须手动 `remove()`。原因是 key 被回收后 value 成了「无主强引用」，只能靠 remove 主动清理。
:::

::: tip 💡 面试题：ThreadLocal 的实现原理？
每个 `Thread` 内部持有一个 `ThreadLocalMap`，key 是 `ThreadLocal` 对象（弱引用），value 是线程自己的副本。`get/set` 时先取当前线程的 Map，再以 `ThreadLocal` 为 key 取值。结论：变量真正存在线程自己的 Map 里，所以天然线程隔离。
:::

## 原理篇

### 十三、JMM 内存模型与 happens-before 规则

JMM（Java Memory Model，Java 内存模型）是并发编程的「宪法」，它规定了多线程环境下变量的访问规则，是所有可见性、有序性问题的根源。

**背景**：物理上有 CPU 缓存，Java 抽象出「主内存 + 工作内存」模型来统一描述。它是「抽象」的，不是真实的内存分区。

#### 主内存与工作内存

```
                    ┌──────────────────────────────┐
                    │        主内存（Main Memory）    │
                    │   存放所有共享变量（对象、字段） │
                    └──────────────────────────────┘
                        ▲ 读(load)      ▲ 写(store)
                        │               │
        ┌───────────────┴───┐   ┌───────┴───────────────┐
        │  线程 A 工作内存    │   │   线程 B 工作内存       │
        │  (线程私有副本)     │   │   (线程私有副本)        │
        └───────────────────┘   └───────────────────────┘

   规则：所有变量都存在主内存，每个线程有自己的工作内存（CPU 缓存抽象）
        线程不能直接操作主内存，必须先拷贝到工作内存，改完再刷回
        → 这就是「可见性问题」的根源：A 改了还没刷回，B 读的是旧值
```

#### 八大原子操作（JMM 定义的内存交互协议）

JMM 定义了 8 种原子操作，描述线程和主内存之间如何交换数据：

| 操作 | 作用 | 作用对象 |
| --- | --- | --- |
| `lock` | 把主内存变量标记为某线程独占 | 主内存 |
| `unlock` | 解除独占标记 | 主内存 |
| `read` | 把主内存变量的值读到工作内存 | 主内存 → 工作内存 |
| `load` | 把 `read` 读到的值放入工作内存的变量副本 | 工作内存 |
| `use` | 把工作内存变量值传给执行引擎 | 工作内存 |
| `assign` | 把执行引擎的值赋给工作内存变量 | 工作内存 |
| `store` | 把工作内存变量值传回主内存 | 工作内存 → 主内存 |
| `write` | 把 `store` 传回的值写入主内存变量 | 主内存 |

读写顺序固定为：**read→load**（读主内存）、**use→assign**（执行引擎使用）、**store→write**（写回主内存），这三对操作必须成对出现——但因为中间间隔，就产生了可见性问题。

#### happens-before 规则（判断并发是否安全的依据）

如果操作 A happens-before 操作 B，那么 **A 的结果对 B 可见，且 A 在 B 之前执行**。这是判断代码是否线程安全的金标准。核心规则：

| 规则 | 内容 | 理解 |
| --- | --- | --- |
| 程序顺序规则 | 同一线程内，前面的操作 happens-before 后面的操作 | 单线程按顺序执行 |
| 监视器锁规则 | 一个锁的 `unlock` 先行发生于后面对同一锁的 `lock` | 解锁后其他线程才能看到改动 |
| volatile 规则 | 对 volatile 变量的写，先行发生于后面对它的读 | 写 volatile 刷主内存，读强制读主内存 |
| 传递性 | A hb B，B hb C，则 A hb C | 可见性可以传递 |
| start() 规则 | 主线程 `start()` 先行发生于子线程的任意操作 | 子线程能看到 start 前的改动 |
| join() 规则 | 子线程全部操作先行发生于 `join()` 返回 | join 返回后能看到子线程结果 |
| 线程中断规则 | `interrupt()` 先行发生于检测到中断 | 中断标志的可见性 |
| 对象终结规则 | 对象初始化先行发生于 `finalize()` | 构造先于终结 |

```java
// happens-before 实战理解
public class HappensBeforeDemo {
    private static int value = 0;
    private static volatile boolean flag = false;

    public static void main(String[] args) {
        // 线程 A
        new Thread(() -> {
            value = 42;    // 普通写
            flag = true;   // volatile 写（为什么放最后？靠 volatile 写建立 happens-before 屏障）
        }).start();

        // 线程 B
        new Thread(() -> {
            if (flag) {    // volatile 读
                // 根据 volatile 规则 + 程序顺序规则 + 传递性：
                // flag=true 的写 hb flag 的读，value=42 的写 hb flag=true 的写
                // 所以这里一定能读到 value=42（不需要给 value 加 volatile）
                System.out.println("value = " + value);
            }
        }).start();
    }
}
```

**小结**：JMM 是「约定」，happens-before 是「判据」。写并发代码时，靠 `synchronized`、`volatile`、`Lock` 主动建立 happens-before 关系，就能保证正确性。

::: tip 💡 面试题：什么是 happens-before 规则？
它是一组判断「两个操作之间是否有可见性和顺序性保证」的规则，A happens-before B 意味着 A 的结果对 B 可见且 A 先执行。原因：编译器/CPU 会重排指令，只有满足 happens-before 才能保证多线程下结果正确。
:::

### 十四、AQS 原理（AbstractQueuedSynchronizer）

AQS 是 JUC 的「地基」，`ReentrantLock`、`Semaphore`、`CountDownLatch`、`ReentrantReadWriteLock` 底层全都基于它。理解 AQS 就理解了整个 JUC 锁体系。

**背景**：各种锁/同步器都需要「维护同步状态 + 管理等待队列」，与其各自实现，不如抽象成统一框架——AQS 就是这个框架。

#### 核心结构：state + CLH 队列

```
AQS 两大核心：
1. state（int 类型，volatile 修饰）—— 同步状态
   - 独占锁：state = 0 未锁，= 1 已锁，可重入时每次重入 +1
   - 共享锁：state 表示剩余许可数（Semaphore）或未完成任务数（CountDownLatch）

2. CLH 队列（双向链表）—— 没抢到锁的线程排队的地方
   每个节点 Node 记录：线程引用 + 等待状态(waitStatus) + 前驱 + 后继

        head(哨兵) → Node1(线程B) → Node2(线程C) → tail
                        ↑waitStatus=SIGNAL
```

**AQS 的模板方法模式**：AQS 定义好「入队、出队、阻塞、唤醒」的通用逻辑，把「怎么算获取成功、怎么算释放」留给子类实现（`tryAcquire` / `tryRelease` 等）。这就是为什么不同锁能共用一套队列。

#### 独占锁加锁流程（以 ReentrantLock 为例）

```
线程调用 lock()
    │
    ▼
 tryAcquire(1)：CAS 尝试把 state 从 0 改成 1
    │
    ├─ 成功 ──► 获取锁，把「独占线程」设为自己，返回
    │
    └─ 失败 ──► 进入 acquireQueued 流程：
          1. 把自己包装成 Node，用 CAS 入队（加到 tail）
          2. 判断前驱是不是 head，是就再 tryAcquire 一次（可能前一个刚释放）
          3. 失败则 LockSupport.park() 挂起自己
          4. 被唤醒后继续从步骤 2 循环（这就是「自旋 + 阻塞」的协作）
```

```java
// ReentrantLock 非公平锁 tryAcquire 核心逻辑（JDK 8 简化）
final boolean nonfairTryAcquire(int acquires) {
    final Thread current = Thread.currentThread();
    int c = getState(); // 读 state（volatile）
    if (c == 0) {
        // state=0 说明没人持有，CAS 抢锁（非公平：新来的可以直接抢，不用排队）
        if (compareAndSetState(0, acquires)) {
            setExclusiveOwnerThread(current); // 记录独占线程为自己
            return true;
        }
    } else if (current == getExclusiveOwnerThread()) {
        // 自己已经持有锁 → 重入，state 累加（可重入的体现）
        int nextc = c + acquires;
        setState(nextc);
        return true;
    }
    return false; // 抢不到，准备入队阻塞
}
```

#### 释放锁流程

```
unlock() → tryRelease(1)：state 减 1
    │
    ├─ state 不为 0（还有重入）→ 继续持有，返回
    │
    └─ state 归 0 → 把独占线程置 null，唤醒 head 的下一个节点（unparkSuccessor）
                    → 被唤醒的线程从 park 处醒来，继续自旋抢锁
```

**小结**：AQS = 「一个 state + 一个 CLH 队列 + 模板方法」，独占锁用 `tryAcquire/tryRelease`，共享锁用 `tryAcquireShared/tryReleaseShared`。记住这个骨架，所有 JUC 锁都能秒懂。

::: tip 💡 面试题：AQS 的原理？
AQS 用一个 `volatile int state` 表示同步状态，用一个 CLH 双向队列管理等待线程，通过「CAS 改 state + park/unpark 阻塞唤醒」实现锁的获取与释放。结论：它是 `ReentrantLock`、`Semaphore` 等所有 JUC 同步器的公共底座。
:::

::: tip 💡 面试题：公平锁和非公平锁在 AQS 里的区别？
非公平锁在 `lock()` 时直接 CAS 抢一次 state，抢到就插队；公平锁会先判断队列里有没有线程在等，有就乖乖入队。结论：非公平锁吞吐高但可能饥饿，公平锁顺序严格但开销大。
:::

### 十五、synchronized 锁升级的底层：对象头 Mark Word

前面高级篇讲了锁升级的现象，这里下沉到字节级，看锁状态到底存在哪、怎么变的。

**背景**：锁信息不能凭空存在，JDK 把它压缩存储在「对象头」里，具体是一个叫 Mark Word 的机器字。

#### 对象内存布局

每个 Java 对象在堆内存里分三部分（详见 [JVM](/learn_backend/java/Java核心/JVM) 对象布局）：

```
对象内存布局：
┌──────────────────────────────────────────────┐
│  对象头(Object Header)                        │
│   ├── Mark Word（标记字）：存 hash、GC年龄、锁状态│
│   └── 类型指针(Klass Pointer)：指向类元数据      │
├──────────────────────────────────────────────┤
│  实例数据(Instance Data)：对象的字段            │
├──────────────────────────────────────────────┤
│  对齐填充(Padding)：补齐到 8 字节的倍数          │
└──────────────────────────────────────────────┘
```

#### Mark Word 在不同锁状态下的布局（64 位 JVM）

Mark Word 是「复用」的，同一个机器字在不同锁状态下存不同内容：

```
64 位 Mark Word（以 64 位虚拟机、无指针压缩为例，低 3 位是锁标志位）：

  无锁状态：
  [ hashcode(31) | unused(25) | 分代年龄(4) | biased_lock(1)=0 | 锁标志(2)=01 ]

  偏向锁：
  [ 线程ID(54) | epoch(2) | unused(1) | 分代年龄(4) | biased_lock(1)=1 | 锁标志(2)=01 ]

  轻量级锁：
  [ 指向栈中锁记录(Lock Record)的指针(62) | 锁标志(2)=00 ]

  重量级锁：
  [ 指向互斥量(monitor)的指针(62) | 锁标志(2)=10 ]

  GC 标记：
  [ 空(62) | 锁标志(2)=11 ]
```

锁标志位速记：**01 无锁/偏向锁、00 轻量级锁、10 重量级锁、11 GC 标记**。

#### 完整锁升级流程

```
线程 A 第一次进入 synchronized：
    无锁(01) ──► 偏向锁(01 + biased_lock=1)：Mark Word 写入线程 A 的 ID
      （A 反复重入，直接对比线程 ID，相等即放行，零 CAS 开销）

线程 B 也来竞争：
    B 发现偏向锁持有者是 A，尝试 CAS 修改偏向，失败
    ──► 偏向锁撤销：升级为轻量级锁(00)
      （JVM 会在安全点暂停 A，检查 A 是否还在临界区）

轻量级锁阶段（A、B 交替，无真正竞争）：
    每个线程在栈帧里建「锁记录(Lock Record)」，CAS 把 Mark Word 指向自己的锁记录
    抢不到的线程「自旋」重试（不挂起，因为预计很快释放）

自旋多次失败 / 竞争激烈：
    ──► 升级为重量级锁(10)：Mark Word 指向 ObjectMonitor
      （没抢到的线程被 park 挂起，交给操作系统调度，省 CPU 但切换开销大）
```

**小结**：锁升级的本质是「Mark Word 标志位变化 + 加锁策略变化」，从「记录线程 ID」到「CAS 自旋」再到「挂起线程」，代价逐步升高，是 JDK 对 `synchronized` 的性能优化。

::: tip 💡 面试题：偏向锁、轻量级锁、重量级锁的区别？
偏向锁在 Mark Word 记录线程 ID，单线程重入零开销；轻量级锁用 CAS 自旋，适合多线程交替无竞争；重量级锁用操作系统互斥量，挂起没抢到的线程，适合激烈竞争。结论：三者是「从乐观到悲观」的升级，竞争越激烈锁越重。
:::

### 十六、线程池的状态机与 execute 源码流程

线程池内部有 5 个状态，通过一个 `AtomicInteger`（高 3 位存状态、低 29 位存线程数）统一管理，是理解线程池「优雅关闭」的关键。

#### 线程池状态机

```
                        shutdown()
        RUNNING ──────────────────────────► SHUTDOWN
          │  (运行中，能接新任务)               (不再接新任务，处理队列剩余)
          │                                     │  队列空
          │ shutdownNow()                       ▼
          ├────────────────────────────► STOP   TIDYING ──► TERMINATED
          │  (立即停，中断所有线程，不处理队列)     (整理中)   (彻底终止)
          ▼
```

| 状态 | 说明 | 转换触发 |
| --- | --- | --- |
| RUNNING | 运行中，能接新任务、处理队列 | 初始状态 |
| SHUTDOWN | 不再接新任务，但处理队列剩余任务 | 调 `shutdown()` |
| STOP | 不接新任务、不处理队列、中断正在执行的任务 | 调 `shutdownNow()` |
| TIDYING | 所有任务终止，worker 数为 0，准备调 `terminated()` | 任务和线程都清空 |
| TERMINATED | `terminated()` 执行完毕 | TIDYING 之后 |

#### execute 方法完整源码流程

```java
// ThreadPoolExecutor.execute 核心逻辑（JDK 8 简化，加注释）
public void execute(Runnable command) {
    if (command == null) throw new NullPointerException();

    int c = ctl.get(); // ctl 是 AtomicInteger，高 3 位存状态、低 29 位存线程数
    // 1. 当前线程数 < corePoolSize
    if (workerCountOf(c) < corePoolSize) {
        // 直接新建核心线程执行（addWorker 会再校验一次状态）
        if (addWorker(command, true)) return;
        c = ctl.get();
    }
    // 2. 线程数 >= corePoolSize，尝试入队
    if (isRunning(c) && workQueue.offer(command)) {
        int recheck = ctl.get();
        // 入队成功后二次检查：万一此时线程池被 shutdown 了，要回滚
        if (!isRunning(recheck) && remove(command)) {
            reject(command); // 线程池已关闭，移除任务并拒绝
        } else if (workerCountOf(recheck) == 0) {
            addWorker(null, false); // 队列有任务但没线程（线程都超时销毁了），补一个非核心线程
        }
    }
    // 3. 队列满了，尝试新建非核心线程，失败则拒绝
    else if (!addWorker(command, false)) {
        reject(command); // 触发拒绝策略
    }
}
```

**小结**：状态机用 `ctl` 一个 int 同时表达「状态 + 数量」，execute 流程严格按「核心 → 队列 → 非核心 → 拒绝」四步走，双重检查保证与 shutdown 的竞态安全。

::: tip 💡 面试题：线程池的 shutdown() 和 shutdownNow() 的区别？
`shutdown()` 优雅关闭：不再接新任务，但等队列里的任务执行完；`shutdownNow()` 暴力关闭：立即停止、中断执行中的线程、返回未执行的任务列表。结论：需要平滑停止用 shutdown，紧急停止用 shutdownNow。
:::

### 十七、ThreadLocal 内存泄漏的底层机制

高级篇讲了「为什么要 remove」，这里下到 `ThreadLocalMap` 的内部结构，看清泄漏到底怎么发生。

#### 数据结构：Thread → ThreadLocalMap → Entry

```
Thread 对象
   │  threadLocals 字段（ThreadLocal.ThreadLocalMap）
   ▼
ThreadLocalMap（自定义的哈希表，不是 java.util.HashMap）
   │  内部数组 Entry[] table，下标用 ThreadLocal 的哈希值 & (len-1) 定位
   ▼
Entry（继承 WeakReference）
   ├── key：WeakReference 引用 ThreadLocal 对象（弱引用！）
   └── value：线程的变量副本（强引用）
```

#### 泄漏链条

```
1. ThreadLocal 对象被置 null（或局部变量离开作用域）
2. GC 时，Entry 的 key 因为是弱引用被回收 → key 变成 null
3. 但 value 是强引用，且被 Thread.threadLocals → Entry → value 链引用着
4. 线程池的线程长期存活（复用不销毁）→ 这条引用链一直存在 → value 永远回收不了
5. 结果：key 为 null 的「脏 Entry」越积越多 → 内存泄漏
```

```java
// 泄漏演示（配合线程池最典型）
public class ThreadLocalLeakDemo {
    public static void main(String[] args) {
        ThreadPoolExecutor pool = new ThreadPoolExecutor(
            5, 5, 60, TimeUnit.SECONDS, new ArrayBlockingQueue<>(10));

        for (int i = 0; i < 100; i++) {
            ThreadLocal<byte[]> local = new ThreadLocal<>();
            local.set(new byte[1024 * 1024]); // 每个线程存 1MB
            pool.execute(() -> {
                // 用 local.get() 干活
                local.remove(); // 为什么必须有？不 remove 的话，线程复用后 value 一直挂在 Thread 上，1MB 永远不释放
            });
        }
    }
}
```

#### 为什么 JDK 不直接「key 用强引用」解决？

key 用强引用的话，`ThreadLocal` 对象本身会一直被子线程强引用，连 `ThreadLocal` 都回收不了，泄漏更严重。JDK 用「弱引用 key + 惰性清理」：`get/set` 时会顺带清理一部分 `key == null` 的脏 Entry，但**不保证及时**，所以仍要求程序员手动 `remove()` 兜底。

**小结**：泄漏根源是「弱引用 key + 强引用 value + 线程长期存活」，根治办法是「用完 `remove()`」。

::: tip 💡 面试题：ThreadLocal 的 key 为什么用弱引用？
为了让 `ThreadLocal` 对象本身能被 GC 回收，避免 key 强引用导致 `ThreadLocal` 也无法回收。代价是 key 回收后 value 成无主引用，需要靠 `remove()` 或惰性清理兜底。结论：弱引用是「两害相权取其轻」，配合 remove 使用才安全。
:::

### 十八、ConcurrentHashMap 线程安全的底层实现

这是「并发 + 集合」的交叉考点，与 [Java集合](/learn_backend/java/Java核心/Java集合) 的 HashMap 强相关，重点理解 JDK 8 的「CAS + 锁单桶」设计。

#### JDK 7 vs JDK 8 设计对比

| 对比项 | JDK 1.7 | JDK 1.8 |
| --- | --- | --- |
| 数据结构 | Segment 数组 + HashEntry 链表 | Node 数组 + 链表 + 红黑树（同 HashMap） |
| 锁粒度 | 锁整个 Segment（分段锁，默认 16 段） | 只锁单个桶的头节点 |
| 并发度 | 固定 = Segment 数量 | 理论 = 桶数量，粒度更细 |
| 读操作 | 无锁（volatile） | 无锁（volatile） |

#### put 流程（CAS + synchronized 锁单桶）

```java
// JDK 8 ConcurrentHashMap.putVal 核心思路（简化）
final V putVal(K key, V value, boolean onlyIfAbsent) {
    // 1. 计算 hash：与 HashMap 一样，key 的 hashCode 高低 16 位异或，减少冲突
    int hash = spread(key.hashCode());
    // 2. for 死循环，CAS 失败就重试（无锁并发写入的关键）
    for (Node<K,V>[] tab = table;;) {
        if (tab == null || tab.length == 0) {
            tab = initTable(); // 3. 懒初始化数组（用 CAS 保证只有一个线程初始化）
        }
        Node<K,V> f = tabAt(tab, (tab.length - 1) & hash); // volatile 读桶头节点
        if (f == null) {
            // 4. 空桶：直接 CAS 放入，无需加锁（性能最高的路径）
            if (casTabAt(tab, (tab.length - 1) & hash, null,
                         new Node<>(hash, key, value))) {
                break;
            }
        } else if (f.hash == MOVED) {
            tab = helpTransfer(tab, f); // 5. 正在扩容，当前线程帮忙迁移（多线程协作扩容）
        } else {
            // 6. 非空桶：synchronized 锁住「桶的头节点」，只锁这一个桶
            synchronized (f) {
                // 在链表或红黑树上查找 key：存在则覆盖，不存在则尾插
            }
        }
    }
    addCount(1L, binCount); // 7. 计数（用 CounterCell 分散计数，避免 CAS 竞争）
    return null;
}
```

#### get 为什么不用加锁

```java
public V get(Object key) {
    Node<K,V>[] tab; Node<K,V> e;
    // tabAt 是 volatile 读，能保证读到最新的桶头节点
    // 节点里的 val 和 next 字段也都用 volatile 修饰，保证可见性
    if ((tab = table) != null && (e = tabAt(tab, (n - 1) & hash)) != null) {
        // 遍历链表或红黑树查找，全程无锁
    }
    return null;
}
```

`get` 无锁的前提：数组用 `volatile`（`Node[] table` 的每个桶通过 `Unsafe.getObjectVolatile` 读），节点的 `val`/`next` 都是 `volatile`，所以任何写操作完成后读线程都能看到最新值。

#### 计数：size() 的实现（LongAdder 思想）

`ConcurrentHashMap` 用 `baseCount + CounterCell[]` 分散计数：无竞争时 CAS 累加 `baseCount`，竞争激烈时各线程累加自己的 `CounterCell`，最后求和。这就是 `LongAdder` 的「分段累加」思想，避免高并发下单一 CAS 计数成为瓶颈。

**小结**：JDK 8 的 ConcurrentHashMap 核心是「**锁粒度最细化**」——读无锁、写 CAS 或锁单桶、计数分散、扩容协作，相比 Hashtable 的一把大锁，并发度有数量级提升。

::: tip 💡 面试题：ConcurrentHashMap 的 get 操作为什么不用加锁？
因为数组桶通过 `volatile` 读取、节点的 `value`/`next` 都是 `volatile` 修饰，保证任何线程写入后其他线程都能看到最新值。结论：JDK 8 读操作完全无锁，这是它比 Hashtable 快的关键。
:::

::: tip 💡 面试题：ConcurrentHashMap 和 Hashtable 的区别？
Hashtable 用一把 `synchronized` 大锁锁整个表，所有操作串行、性能差；ConcurrentHashMap 1.8 只锁单个桶、读无锁、计数分散。结论：并发场景一律用 ConcurrentHashMap，Hashtable 已过时。
:::

## 面试常问

1. **synchronized 和 volatile 的区别？** synchronized 保证原子性 + 可见性 + 有序性，会阻塞线程；volatile 只保证可见性 + 有序性，不保证原子性，不阻塞。原因是 synchronized 是锁机制，volatile 只是内存屏障。

2. **线程池的执行流程和 7 个核心参数？** 参数是核心线程数、最大线程数、存活时间、时间单位、队列、线程工厂、拒绝策略；执行流程是先核心线程、再队列、再扩容到最大、最后触发拒绝策略。原因是线程池要「复用线程 + 缓冲任务」，所以队列是关键缓冲。

3. **什么是 CAS？有什么问题？** CAS 是「比较并交换」，靠 CPU 原子指令实现无锁更新，是 `AtomicInteger` 的底层；问题有 ABA 问题和自旋开销大。原因是它只比较「值变没变」，感知不到值「变了又变回来」，且失败会一直空转重试。

4. **ThreadLocal 的原理和坑？** 每个线程内部一个 `ThreadLocalMap`，key 是弱引用的 `ThreadLocal`，value 是线程私有副本；坑是用完不 `remove()` 会内存泄漏。原因是 key 被 GC 后 value 成无主强引用，线程池线程长期存活导致 value 无法回收。

5. **volatile 能保证线程安全吗？** 不能保证复合操作的原子性。`i++` 这种「读-改-写」操作即使变量加 `volatile` 仍会丢更新，要改用 `AtomicInteger` 或加锁。原因是 volatile 只保证单次读写的可见性和有序性。

6. **sleep() 和 wait() 的区别？** sleep 是 `Thread` 静态方法、不释放锁、时间到自动醒；wait 是 `Object` 方法、释放锁、必须 `notify`/`notifyAll` 唤醒、须在 `synchronized` 内调用。原因是二者定位不同：sleep 是「定时休眠」，wait 是「协作等待」。

7. **ConcurrentHashMap 为什么线程安全？** JDK 8 用「CAS + synchronized 锁单个桶」实现写安全，读操作完全无锁（volatile 保证可见性）。原因是锁粒度从 Hashtable 的整表锁细化到单桶锁，并发度大幅提升。

8. **可重入锁是什么？为什么要可重入？** 一个线程持有锁后再次进入该锁保护的代码能直接通过，不会自己锁死自己。`synchronized` 和 `ReentrantLock` 都支持。原因是递归调用或嵌套方法时会重复获取同一把锁，不可重入会导致死锁。
