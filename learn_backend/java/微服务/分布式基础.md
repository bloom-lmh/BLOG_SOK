# 分布式基础

> 一句话定位：分布式基础是整个微服务/分布式体系的「理论地基」，它回答的是——把一个单体系统拆成多台机器、多个服务之后，**数据怎么保证一致（分布式事务）**、**主键怎么全局唯一（分布式 ID）**、**共享资源怎么加锁（分布式锁）**、**重复请求怎么不重复执行（幂等）**、**缓存扩容怎么少迁移（一致性哈希）**、**网络故障时一致性还是可用性（CAP/BASE）**这一系列通用问题的底层套路。

---

## 基础篇

### 1. 背景：为什么需要分布式

在讲任何分布式技术之前，先要搞清楚一个根本问题：**单体架构明明简单好用，为什么非要拆？**

#### 1.1 单体架构的困境

早期的互联网系统是「单体（Monolith）架构」：一个应用一个数据库，所有代码打成一个 War/Jar 包，部署到一台机器上。它开发快、部署简单、本地事务（数据库 `ACID`）天然保证数据一致。但随着用户量增长，单体架构会碰到四个天花板：

| 瓶颈 | 具体表现 | 单体的应对 | 局限 |
| --- | --- | --- | --- |
| 性能瓶颈 | 用户多、请求大，单机 CPU/内存打满 | 垂直扩展：换更好的机器 | 硬件有上限，成本指数增长 |
| 可用性瓶颈 | 一个模块 OOM，整个应用一起挂 | 多部署几台 + 负载均衡 | 代码还是一套，无法按模块隔离故障 |
| 扩展性瓶颈 | 只有订单模块忙，却要整个应用一起扩容 | 整体扩容 | 浪费资源，成本高 |
| 迭代瓶颈 | 团队大，多人改同一套代码，互相影响 | 规范、评审 | 治标不治本，部署冲突依旧 |

**结论**：单体架构的「单点」既是物理上的单机，也是逻辑上的单代码库。要突破，只能「拆」——这就是分布式。

#### 1.2 分布式的定义

> **分布式系统**：把一个大系统拆成多个子系统（服务/节点），部署在多台机器上，通过网络相互通信、协同完成同一套业务目标的系统。

拆的方式有两种典型路径：

```
单体架构 (Monolith)
   │  拆分
   ├── 垂直拆分（按业务模块）：用户服务 / 订单服务 / 商品服务 / 库存服务 ...
   └── 水平拆分（按数据/实例）：同一个服务部署多份，数据分片到多个库表
```

- **垂直拆分**：一个模块一个服务，模块间通过 RPC/HTTP 通信 → 演进出「微服务」。
- **水平拆分**：同一个服务/数据库复制多份，或数据按规则分片 → 演进出「集群、分库分表」。

绝大多数「微服务」架构是两者结合：先垂直拆成多个服务，再对热点服务水平扩容。

#### 1.3 分布式的收益与代价

| 维度 | 单体 | 分布式 | 说明 |
| --- | --- | --- | --- |
| 扩展性 | 加配置（垂直扩展） | 加机器（水平扩展） | 分布式可无限横向扩容 |
| 可用性 | 宕机即不可用 | 一台挂了其他顶上 | 冗余带来的高可用 |
| 一致性 | 本地事务天然一致 | 需要额外机制保证 | 这是分布式最大的痛点 |
| 性能 | 单机瓶颈 | 多机并行，吞吐更高 | 但引入网络延迟 |
| 复杂度 | 低 | 高（网络、一致性、分布式锁等） | 运维、调试、排查都更难 |
| 成本 | 机器少但贵 | 机器多但便宜 | 用普通服务器堆性能 |

**一句话总结**：分布式用「复杂度」换「可扩展性 + 可用性 + 性能」。它本身不解决业务问题，而是解决「业务大了单机扛不住」的问题，代价是引入了一堆新问题。

### 2. 分布式系统的三大经典问题

拆完之后，立即暴露出三个单体时代不存在的、绕不开的难题。理解这三大问题，是理解后面所有分布式技术（CAP、事务、锁、ID）的钥匙。

#### 2.1 问题一：网络不可靠

单体里函数调用是进程内调用，`null` 就是 `null`，返回值一定拿得到。分布式里服务间调用走网络，网络天然不可靠：

- **调用可能超时**：请求发出去了，但响应迟迟没回来——对方到底执行了没有？不知道。
- **调用可能失败**：连接被拒、断连、丢包。
- **调用结果可能乱序**：先发的请求后到。
- **无法区分「失败」还是「超时」**：这是最致命的。超时不代表没执行，可能对方已经成功，只是响应丢了。

```
调用方 ──请求──▶ 服务方
调用方 ◀──???──  服务方（到底执行成功了吗？）
   │
   └── 超时了：可能(1)没执行 (2)执行成功了但响应丢 (3)执行中还没完
```

**它催生的技术**：重试、幂等、超时控制、心跳检测、熔断降级（见 [Sentinel](/learn_backend/java/微服务/Sentinel)）。

#### 2.2 问题二：数据不一致

单体里一次转账就是一个本地事务，数据库用 `ACID` 保证要么都成、要么都败。分布式里「扣余额」在 A 服务、「加余额」在 B 服务，各自有各自的数据库，本地事务管不着跨库跨服务的操作：

```
单体：一个数据库事务包住所有操作
     BEGIN; 扣A; 加B; COMMIT;   ← 要么全成功要么全回滚

分布式：两个服务各自提交，中间没有统一协调
     A服务: 扣A成功并提交  ┐
     B服务: 加B失败        ┘ → A已扣、B没加，数据不一致了！
```

**它催生的技术**：分布式事务（2PC / TCC / 消息最终一致性）、一致性协议（Raft/Paxos）、CAP/BASE 理论。

#### 2.3 问题三：节点故障

单体里「挂了」是整体挂了，很好判断。分布式里是「部分失败（Partial Failure）」：某个节点、某条链路、某个进程挂了，但系统整体还在跑，故障的边界很难界定：

- 一个节点宕机，其他节点感知不到，继续把请求发给它 → 部分请求失败。
- 网络分区：一组节点和另一组节点之间网络断了，但各自内部都以为自己正常。
- 故障探测依赖心跳，而心跳又依赖网络，本身就不可靠。

**它催生的技术**：故障检测与自动摘除、选举（主从切换）、副本与数据冗余、健康检查。

> 小结：**网络不可靠、数据不一致、节点故障**这三大问题，构成了分布式系统设计的「原罪」。后面所有的理论（CAP/BASE）、组件（注册中心、配置中心、消息队列）、算法（一致性哈希、Raft）本质都是在跟这三大问题做斗争。

### 3. CAP 定理

CAP 是分布式领域最基础、最常被问、也最容易被误解的理论。它是分布式系统设计的「第一性原理」。

#### 3.1 定义与三个字母

CAP 定理由 Eric Brewer 在 2000 年提出，2002 年被证明。它描述的是一个分布式系统在**发生网络分区（Partition）**时，三个特性不可能同时满足：

| 字母 | 全称 | 中文 | 精确含义 |
| --- | --- | --- | --- |
| C | Consistency | 一致性 | 所有节点在同一时刻读到完全相同的数据（对任意客户端，任意时刻读到的都是最新写入的值） |
| A | Availability | 可用性 | 每个请求都能在合理时间内得到**非错误**的响应（不保证是最新数据） |
| P | Partition Tolerance | 分区容错性 | 网络分区（节点之间网络断开）发生时，系统仍能对外正常工作 |

**关键误区**：很多人把 CAP 理解成「三选二」，这是不准确的。正确理解是：

1. **P 是必须选的**：网络分区是分布式系统「客观存在」的故障，你没法保证网络永远不分区。既然分区一定会发生，系统就必须具备分区容错性（P），否则分区一来系统就废了。
2. **C 和 A 只能二选一**：分区发生的那一刻，你在 C 和 A 之间只能保一个。

所以 CAP 的准确说法是：**分布式系统在网络分区发生时，只能在 C（一致性）和 A（可用性）之间二选一，P 是必选项**。

#### 3.2 为什么 C 和 A 不能同时满足

用一个经典的「双机房」例子说明：

```
        ┌──────────────────────────────────────────────┐
        │             正常状态：C 和 A 都能满足            │
        │                                                │
        │   客户端 ──写 x=1──▶ [节点A]  ◀─同步─▶ [节点B]  │
        │                        │              │        │
        │                        └──────────────┘        │
        │                数据一致，读写都正常               │
        └──────────────────────────────────────────────┘

        ┌──────────────────────────────────────────────┐
        │           网络分区发生：A、B 之间网络断了          │
        │                                                │
        │   客户端 ──写 x=1──▶ [节点A]   ✗✗✗   [节点B]   │
        │   客户端 ─────────读 x───────▶ [节点B]          │
        │                                                │
        │   此时只能二选一：                               │
        │   选 C：节点B 拒绝读（不能返回旧值）→ 牺牲可用性    │
        │   选 A：节点B 返回旧值 x=0（可能不是最新）→ 牺牲一致│
        └──────────────────────────────────────────────┘
```

- 如果节点 B 为了「可用性」继续响应读请求，它只能返回**旧数据** `x=0`，因为它拿不到 A 上刚写的 `x=1` → **破坏了 C**。
- 如果节点 B 为了「一致性」拒绝返回旧数据，那它只能返回错误或阻塞等待 → **破坏了 A**。

两者不可兼得，根因就是「分区期间数据无法同步」。

::: tip 💡 面试题：CAP 为什么不能三者兼得？一句话结论是什么？
一句话结论：**CAP 不是「三选二」，而是「P 必选，C/A 二选一」**——网络分区发生时，节点间无法同步数据，要么拒绝响应保一致（CP），要么返回可能过期的数据保可用（AP），二者物理上互斥。
原因：分区意味着节点之间拿不到对方的最新写入，此时「返回最新数据」和「一定返回响应」不能同时成立。展开说：正常无分区时 C 和 A 都能满足；一旦分区，就必须在「宁可拒绝服务也不给错数据」和「宁可给旧数据也要保持响应」之间做选择，这就是 CP 和 AP 的由来。
:::

#### 3.3 常见系统的 CAP 取舍

工程上，不同组件根据自身定位，在 C 和 A 之间做了明确选择：

| 系统 | 取舍 | 定位 | 分区时的行为 |
| --- | --- | --- | --- |
| ZooKeeper | CP | 选主、配置、分布式协调 | 分区时，非多数派节点拒绝服务，保证一致 |
| Consul | CP | 注册中心/配置中心 | 类似 ZK，Raft 保证一致 |
| Eureka | AP | 注册中心（Spring Cloud 老牌） | 分区时继续提供服务，短暂不一致可接受，还有自我保护 |
| Nacos | AP / CP 可切换 | 注册中心 + 配置中心 | 临时实例走 AP（Distro），持久实例/配置走 CP（Raft） |
| Redis（主从/哨兵） | AP（默认） | 缓存 | 主从异步复制，可能读到旧值；用 `WAIT` 可偏向 CP |
| MySQL 主从 | 默认 AP | 数据库 | 异步复制，从库可能读到旧数据；半同步可偏向 CP |
| etcd | CP | 配置中心/K8s 底层 | Raft 保证强一致，分区时少数派不可用 |

**记忆口诀**：注册中心多 AP（要可用），配置中心/选主多 CP（要一致），缓存基本 AP（要性能）。

#### 3.4 实际怎么选

选择没有标准答案，取决于业务对「一致性」的容忍度：

1. **一致性要求高**（钱、账、权限）：选 CP。宁可短暂不可用，也不能出现「读到旧余额、重复扣款」。
2. **可用性要求高**（登录、浏览、社交）：选 AP。宁可短暂读到旧数据，也不能让用户打不开页面。
3. **绝大多数互联网业务**：选 AP + 最终一致（即 BASE），用「放弃强一致」换「高可用 + 高性能」。

### 4. BASE 理论

CAP 太绝对、太「理论」：现实业务往往不需要每时每刻都强一致，只要「最终能一致」就行。BASE 就是对 CAP 中「AP」这条路的工程化落地。

#### 4.1 定义与三要素

BASE 是三个英文词的首字母，**它是 AP 的延伸**，核心思想是「放弃强一致，换取可用性」：

| 字母 | 全称 | 中文 | 含义 |
| --- | --- | --- | --- |
| BA | Basically Available | 基本可用 | 允许系统在故障/高峰时损失部分可用性（如降级、限流、返回兜底页），但核心功能仍可用 |
| S | Soft State | 软状态 | 允许系统中存在「中间状态」，即不同节点的数据副本可以短暂不一致 |
| E | Eventually Consistent | 最终一致性 | 不要求实时一致，但保证「在没有新的更新的前提下」，系统最终会收敛到一致 |

#### 4.2 与 CAP、ACID 的关系

```
ACID（单机事务）：强一致、原子、隔离、持久      → 单体/单库世界
CAP（分布式理论）：分区时 C 与 A 不可兼得        → 理论天花板
BASE（工程实践）：放弃强一致，保证最终一致        → 互联网业务主流
```

- **ACID 是 BASE 的「严父」**：单机数据库事务提供强一致，是分布式里局部（单库）的一致保障。
- **BASE 是 CAP 的「现实妥协」**：既然 C 和 A 冲突，那就降低 C 的要求——不要求「立刻一致」，只要求「最终一致」。

#### 4.3 最终一致性的五种变体（面试加分项）

「最终一致」是个笼统说法，工程上根据「一致的方向」细分出五种：

| 变体 | 含义 | 典型场景 |
| --- | --- | --- |
| 因果一致性 | 有因果关系的操作，读到的顺序必须一致；无因果的可乱序 | 评论「回复」必须排在「原评论」之后 |
| 读己之写（Read Your Writes） | 用户总能读到「自己刚写入」的数据 | 发完微博立刻刷新能看到自己的微博 |
| 会话一致性 | 在一个会话/连接内保证读己之写 | 登录后同一个 session 内数据一致 |
| 单调读一致性 | 一旦读到新值，之后不会再读到更旧的值 | 避免「先看到评论数 10，刷新变成 5」 |
| 单调写一致性 | 同一个节点/进程的写操作按顺序被处理 | 保证自己的多次写不乱序 |

> 小结：BASE 不是「随便不一致」，而是把「一致」从「强一致」放宽成「可收敛的一致」，同时用工程手段（消息队列重试、定时补偿、对账）保证最终一定能一致。绝大多数互联网业务选它，因为它最贴合「高并发、高可用、容忍短暂不一致」的现实。

### 5. 一致性模型全景（补充）

前面反复提到「强一致」「弱一致」「最终一致」，这里给一个完整的分级框架，帮助建立体系（面试常被问到「强一致和最终一致的区别」）：

```
一致性强度从高到低：
线性一致性(强一致) > 顺序一致性 > 因果一致性 > 最终一致(弱一致)
     ↑                                    ↑
    CAP 里的 C                        BASE 里的 E
```

| 模型 | 定义 | 强度 | 典型实现 |
| --- | --- | --- | --- |
| 线性一致性（Linearizability） | 所有操作看起来像在「某个瞬间」原子完成，且顺序与真实时间一致；读一定读到最新写 | 最强 | etcd、ZooKeeper、Raft/Paxos |
| 顺序一致性 | 所有操作按某个全局顺序执行，每个进程看到顺序一致，但不要求与真实时间一致 | 强 | 较少单独使用 |
| 因果一致性 | 有因果的操作全局有序，无因果的可以不一致 | 中 | 消息队列、协作编辑 |
| 最终一致性 | 停止写入后，经过一段时间，所有副本最终收敛到同一值 | 弱 | DNS、Redis 主从、多数互联网业务 |

**一句话记忆**：CAP 的 C 指的是**线性一致性（强一致）**；BASE 的 E 指的是**最终一致性**。面试里说「我们选 AP」≈「我们放弃强一致，接受最终一致」。

## 高级篇

### 6. 分布式事务

分布式事务是整个分布式体系里「最重、最深、面试最密集」的一块，单独成节重点讲。

#### 6.1 背景：从 ACID 到分布式事务

单机事务靠数据库的 `ACID` 保证：

| 字母 | 含义 | 说明 |
| --- | --- | --- |
| A（Atomicity） | 原子性 | 要么全做，要么全不做 |
| C（Consistency） | 一致性 | 事务前后数据都满足约束 |
| I（Isolation） | 隔离性 | 并发事务互不干扰（见 [MySQL](/learn_database/MySQL) 的 MVCC） |
| D（Durability） | 持久性 | 提交后不丢 |

但微服务里「一次下单」可能横跨 4 个服务、4 个数据库：

```
下单流程（跨 4 个服务，4 个独立数据库）：
  订单服务(DB1)  → 创建订单
  库存服务(DB2)  → 扣减库存
  积分服务(DB3)  → 增加积分
  优惠券服务(DB4) → 核销优惠券
```

四个服务各自提交自己的事务，**中间任何一个失败，前面已经提交的服务无法回滚**——这就是分布式事务要解决的问题：**让跨多个服务/数据库的多个操作，要么全部成功、要么全部失败**。

#### 6.2 分布式事务的经典解决方案全景

先看全景，再逐个展开（2PC/TCC 的完整流程放到原理篇）：

| 方案 | 一致性 | 性能/阻塞 | 侵入性 | 典型实现 | 适用场景 |
| --- | --- | --- | --- | --- | --- |
| 2PC（两阶段提交） | 强一致 | 差（全程锁资源） | 低（框架层） | XA 事务、Seata AT（变体） | 对一致性要求极高、并发不高的内部系统 |
| TCC | 强一致（业务可控） | 中（不长时间锁 DB） | 高（业务要写三段） | Seata TCC、自研 | 资金、库存等需要业务补偿的场景 |
| 消息最终一致性 | 最终一致 | 好（异步解耦） | 中 | RocketMQ 事务消息 | 长流程、可异步的业务（下单后发积分） |
| 本地消息表 | 最终一致 | 好 | 中（要建表 + 补偿） | 自研 | 不依赖 MQ 或对 MQ 稳定性有顾虑 |
| 最大努力通知 | 最终一致（更弱） | 好 | 低 | 定时任务 + 重试 | 对结果要求不严格的通知类场景 |

**核心选型逻辑**：强一致选 2PC/TCC（代价是阻塞/侵入），性能优先选最终一致（消息/本地消息表）。互联网 90% 选**最终一致**。

#### 6.3 方案一：2PC（两阶段提交）

见 [原理篇 §11](#_11-2pc-两阶段提交的完整流程) 的完整流程。这里只讲「是什么 + 用在哪 + 为什么少用」：

- **是什么**：一个协调者（Coordinator）协调多个参与者（Participant），分「准备（Prepare）+ 提交（Commit/Rollback）」两个阶段完成全局事务。
- **用在哪**：数据库的 **XA 事务**（`BEGIN` 一个全局事务，多个 `XA` 数据源参与）。MySQL 支持 XA，但很少直接在生产用。
- **为什么少用**：同步阻塞（第二阶段前锁资源不释放）、单点故障（协调者挂了全卡住）、数据不一致风险（部分参与者提交成功、部分失败）。

#### 6.4 方案二：TCC（Try-Confirm-Cancel）

见 [原理篇 §12](#_12-tcc-的完整流程与三大异常) 的完整流程与异常处理。核心要点：

- **是什么**：把一次业务拆成 Try（预留资源）→ Confirm（确认提交）→ Cancel（取消回滚）三个阶段，**业务方自己实现**每个阶段的逻辑。
- **特点**：不长时间锁数据库资源，性能比 2PC 好；但**侵入业务**，每个业务都要写三段代码，且要处理幂等、空回滚、悬挂三大异常。
- **典型实现**：Seata 的 TCC 模式（见 [Seata](/learn_backend/java/微服务/Seata)），以及支付宝/银行内部的 TCC 框架。

#### 6.5 方案三：消息最终一致性（最常用）

这是互联网业务里**使用最广**的方案，用「本地事务 + 消息」解耦，靠 MQ 的重试保证最终一致：

```
                    业务方                           消息方
        ┌───────────────────────┐          ┌───────────────────────┐
        │ 1. 开启本地事务         │          │                       │
        │ 2. 执行业务（扣库存）    │          │                       │
        │ 3. 发送「半消息」到MQ    │──半消息──▶│  半消息暂存，不可消费    │
        │ 4. 提交本地事务         │          │                       │
        │    └─成功→ 通知MQ确认   │──确认──▶│  半消息变为可消费        │
        │    └─失败→ 通知MQ回滚   │──回滚──▶│  半消息删除             │
        └───────────────────────┘          └──────────┬────────────┘
                                                      │ 投递
                                              ┌───────▼───────┐
                                              │ 消费者消费消息   │
                                              │ 失败→ MQ 重试   │
                                              └───────────────┘
```

关键机制是 **RocketMQ 的事务消息**（见 [RocketMQ](/learn_backend/java/微服务/RocketMQ)）：
1. 生产者先发**半消息**（half message），此时消费者看不到。
2. 生产者执行本地事务。
3. 本地事务成功 → 提交半消息，消费者可消费；失败 → 回滚半消息，消费者永远看不到。
4. 若生产者本地事务后**迟迟不确认**，MQ 会定时**回查**（checkBack）生产者的本地事务状态，决定提交还是回滚。

```java
// 伪代码：RocketMQ 事务消息的完整可运行骨架（关键行加「为什么」注释）
public class OrderTransactionListener implements TransactionListener {

    // executeLocalTransaction：执行本地事务，返回「提交/回滚/未知」三种状态
    @Override
    public LocalTransactionState executeLocalTransaction(Message msg, Object arg) {
        try {
            // 为什么先扣库存再返回 COMMIT：本地事务成功才让消息可见，
            // 保证「消息可消费」一定发生在「本地事务成功」之后
            orderService.reduceStock();      // 本地事务：扣库存
            return LocalTransactionState.COMMIT_MESSAGE;   // 本地成功 → 消息提交
        } catch (Exception e) {
            return LocalTransactionState.ROLLBACK_MESSAGE; // 本地失败 → 消息回滚
        }
    }

    // checkLocalTransaction：MQ 回查，兜底「上面返回 UNKNOWN 或超时」的场景
    @Override
    public LocalTransactionState checkLocalTransaction(MessageExt msg) {
        // 为什么需要回查：可能 executeLocalTransaction 超时返回 UNKNOWN，
        // MQ 无法判断，主动来问「你那个本地事务到底成功没有」
        boolean committed = orderService.isStockReduced(msg.getTransactionId());
        return committed
                ? LocalTransactionState.COMMIT_MESSAGE
                : LocalTransactionState.ROLLBACK_MESSAGE;
    }
}
```

**优缺点**：
- 优点：异步解耦、不阻塞、吞吐高、最终一致；对业务侵入小（发消息即可）。
- 缺点：存在**短暂不一致窗口**（本地事务已提交、消费者还没消费完）；需要消费端做**幂等**（MQ 可能重复投递）。

#### 6.6 方案四：本地消息表

不依赖 MQ 的「自研版最终一致」，适合没有 MQ 或对 MQ 稳定性有顾虑的场景：

```
业务方事务内：
  1. 执行业务操作（扣库存）
  2. 在同一本地事务里，往「消息表」插一条待发送消息
  3. 提交事务（业务 + 消息表数据 一起提交，保证不丢）

后台定时任务：
  4. 扫描消息表，把「待发送」消息发给 MQ / 直接调用下游
  5. 发送成功 → 标记「已发送」；失败 → 下次重试
  6. 下游消费成功 → 标记「已完成」；失败 → 定时补偿重试
```

**核心思想**：把「发消息」这个动作**装进本地事务**，用消息表的落库来保证消息不丢；再用定时任务轮询 + 重试来保证最终送达。缺点是消息表会膨胀、需要额外的定时任务和清理逻辑。

#### 6.7 方案五：Seata 的 AT 模式（2PC 的工程化改良）

Seata 是阿里开源的分布式事务框架（见 [Seata](/learn_backend/java/微服务/Seata)），它的 AT 模式本质是**对 2PC 的改良**，解决了 2PC 全程锁资源的问题：

| 阶段 | 2PC（XA） | Seata AT |
| --- | --- | --- |
| 一阶段 | 执行业务 SQL，**不提交**，锁资源 | 执行业务 SQL，**直接提交**，同时记录 undo log |
| 二阶段 | 全局提交/回滚 | 成功则删 undo log；失败则用 undo log 反向补偿 |
| 锁策略 | 全程锁 DB 行 | 提交后释放 DB 锁，改用「全局锁」防脏读 |

- **AT 的核心**：一阶段提交时同时把「修改前的数据镜像」和「修改后的数据镜像」记录成 undo log；二阶段回滚时，用 undo log 生成反向 SQL 把数据改回去。
- **优点**：不长时间占用数据库连接和锁，性能远好于 XA。
- **缺点**：依赖 undo log、有「脏写」风险（需要用全局锁 + 版本号控制）。

#### 6.8 方案对比与选型总结

| 对比维度 | 2PC/XA | TCC | 消息最终一致 | 本地消息表 |
| --- | --- | --- | --- | --- |
| 一致性 | 强 | 强（业务可控） | 最终 | 最终 |
| 性能 | 差 | 中 | 好 | 好 |
| 是否阻塞 | 是（锁资源） | 否（短锁） | 否 | 否 |
| 业务侵入 | 低 | 高 | 中 | 中 |
| 实现复杂度 | 低 | 高 | 中 | 中 |
| 是否需要 MQ | 否 | 否 | 是 | 可选 |

**决策树**（背下来面试直接甩）：

```
要强一致吗？
 ├─ 要，且并发不高、能容忍锁 → 2PC/XA
 ├─ 要，且是资金/库存等需业务补偿 → TCC
 └─ 不要，只要最终一致
     ├─ 有可靠 MQ → 消息最终一致性（RocketMQ 事务消息）
     └─ 无 MQ / 想自研 → 本地消息表
```

### 7. 分布式 ID

多台机器各自生成主键，必须保证**全局唯一**。这是分布式体系里「最简单、最常用、也最容易出坑」的一个环节。

#### 7.1 背景：为什么不能继续用数据库自增

单机时代主键就是 MySQL 的 `AUTO_INCREMENT`，简单有序。拆库拆表后，问题来了：

1. **多库多表各自自增**，主键会冲突（库1 的 id=1 和库2 的 id=1 重复）。
2. **单表自增**有单点瓶颈：所有服务都靠一张表发号，这张表成了全系统的性能瓶颈和单点。
3. 即使能自增，**分布式环境也需要「趋势递增」**（见下），方便索引维护。

所以需要一种「不依赖单一数据库、全局唯一、最好还能趋势递增」的 ID 生成方案。

#### 7.2 各方案全景对比

| 方案 | 原理 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- | --- |
| UUID | 本地随机/算法生成 128 位 | 简单、无中心、无依赖 | 无序、字符串长、索引差（页分裂） | 无排序需求的分布式主键 |
| 数据库自增 | 单表 `AUTO_INCREMENT` | 简单、严格递增 | 单点、有性能瓶颈 | 小规模系统 |
| 数据库号段模式 | 一次从 DB 取一段 ID 放内存 | 减少 DB 访问、趋势递增 | 依赖 DB、号段用完要再取 | 中型系统（美团 Leaf 号段） |
| Redis 自增 | `INCR`/`INCRBY` | 快、严格递增 | 需持久化防丢、重启回退 | 对 ID 有递增要求的系统 |
| 雪花算法（Snowflake） | 时间戳 + 机器号 + 序列号 | 趋势递增、高性能、无中心 | 依赖时钟、时钟回拨会重复 | 绝大多数互联网系统（主流） |

#### 7.3 雪花算法（Snowflake）—— 面试重点

雪花算法是 Twitter 开源的高性能分布式 ID 方案，用一个 **64 位 long** 表示一个 ID，是目前**使用最广**的方案。它的字节级结构（见 [原理篇 §14](#_14-雪花算法的字节级内存布局)）如下：

```
  1bit        41bit             10bit          12bit
┌─────┬───────────────────┬──────────────┬─────────────┐
│ 符号 │      时间戳(毫秒)    │   机器号      │   序列号     │
│ 位   │    (可用 69 年)     │ (1024 台机器) │ (每毫秒 4096)│
└─────┴───────────────────┴──────────────┴─────────────┘
  0     时间戳自起始时间        数据中心5bit     同一毫秒内
        (默认从某固定时间开始)   + 机器5bit        自增，溢出等待
```

四段含义：

| 段 | 位数 | 作用 | 说明 |
| --- | --- | --- | --- |
| 符号位 | 1 bit | 恒为 0 | 保证 ID 是正数 |
| 时间戳 | 41 bit | 记录毫秒时间戳（相对自定义起始时间） | 41 位约可表示 69 年 |
| 机器号 | 10 bit | 区分机器（5bit 数据中心 + 5bit 机器） | 最多 1024 台机器 |
| 序列号 | 12 bit | 同一毫秒内的自增序列 | 每毫秒最多生成 4096 个 |

**为什么雪花 ID「趋势递增」对索引友好**：因为高位是时间戳，时间越晚 ID 越大，所以 ID 整体单调递增。MySQL 的 InnoDB 用**聚簇索引（B+ 树）**按主键排序存数据，递增主键插入时永远追加到末尾，不会触发 B+ 树的页分裂（详见 [MySQL](/learn_database/MySQL) 的 B+ 树）。而 UUID 是随机的，插入位置随机，频繁页分裂导致性能下降。

::: tip 💡 面试题：雪花算法最大的坑是什么？如何解决？
一句话结论：**时钟回拨（NTP 校时把机器时间往回拨）会导致生成重复 ID**，这是雪花算法最经典的坑。
原因：雪花 ID 唯一性依赖「时间戳 + 序列号」，如果机器时间被往回拨，之前已经用过的毫秒时间戳会再次出现，导致同一毫秒内序列号重复。解决三板斧：① 等待时钟追回（回拨时间短时，睡到时间追上再继续）；② 记录上次生成的时间戳，回拨时用备用机器号或拒绝发号；③ 引入第三方发号器（如美团 Leaf）做兜底。
:::

```java
// 雪花算法完整可运行实现（关键行加「为什么」注释）
public class SnowflakeIdWorker {

    // 起始时间戳：2020-01-01 00:00:00（为什么自定义起点而不是 1970：可省出更多时间位，延长可用年限）
    private final long startTime = 1577808000000L;

    private final long workerIdBits = 5L;     // 机器号占 5 位
    private final long datacenterIdBits = 5L; // 数据中心占 5 位（合计 10 位机器号）
    private final long sequenceBits = 12L;    // 序列号占 12 位

    private final long maxWorkerId = ~(-1L << workerIdBits);     // 31
    private final long maxDatacenterId = ~(-1L << datacenterIdBits); // 31
    private final long sequenceMask = ~(-1L << sequenceBits);    // 4095

    // 各段在 64 位中的左移位数（为什么这样移位：把各段拼到 long 的正确位置）
    private final long workerIdShift = sequenceBits;                       // 12
    private final long datacenterIdShift = sequenceBits + workerIdBits;    // 17
    private final long timestampLeftShift = sequenceBits + workerIdBits + datacenterIdBits; // 22

    private long workerId;
    private long datacenterId;
    private long sequence = 0L;
    private long lastTimestamp = -1L;

    public SnowflakeIdWorker(long workerId, long datacenterId) {
        if (workerId > maxWorkerId || workerId < 0) throw new IllegalArgumentException("workerId 越界");
        if (datacenterId > maxDatacenterId || datacenterId < 0) throw new IllegalArgumentException("datacenterId 越界");
        this.workerId = workerId;
        this.datacenterId = datacenterId;
    }

    public synchronized long nextId() {
        long timestamp = System.currentTimeMillis();

        // 为什么用 synchronized：保证同一毫秒内 sequence 自增不并发重复
        // 时钟回拨检测：当前时间小于上次时间，说明时钟被拨回去了
        if (timestamp < lastTimestamp) {
            throw new RuntimeException("时钟回拨，拒绝发号：" + (lastTimestamp - timestamp) + "ms");
        }

        if (timestamp == lastTimestamp) {
            // 同一毫秒内，序列号自增并取模（溢出则 sequence 归 0，等下一毫秒）
            sequence = (sequence + 1) & sequenceMask;
            if (sequence == 0) {
                // 这一毫秒 4096 个号用完了，忙等下一毫秒（为什么忙等：ID 必须严格递增）
                while (timestamp <= lastTimestamp) {
                    timestamp = System.currentTimeMillis();
                }
            }
        } else {
            sequence = 0L; // 新的一毫秒，序列号归零
        }

        lastTimestamp = timestamp;

        // 拼接：时间戳左移 22 位 | 数据中心左移 17 位 | 机器号左移 12 位 | 序列号
        return ((timestamp - startTime) << timestampLeftShift)
                | (datacenterId << datacenterIdShift)
                | (workerId << workerIdShift)
                | sequence;
    }
}
```

#### 7.4 数据库号段模式与美团 Leaf

号段模式是「数据库自增」的升级版，解决自增方案「每次都打 DB」的性能问题：

```
数据库表：号段表
  biz_tag | max_id | step
  订单    | 10000  | 1000

发号流程：
  1. 服务从 DB 取一段：UPDATE 号段表 SET max_id = max_id + step
     返回「旧 max_id + 1 ~ 新 max_id」这一段（如 10001 ~ 11000）
  2. 把这 1000 个号放内存，本地逐个发放，用完再取下一段
  3. 即使 DB 短暂不可用，内存里还有号，不影响发号
```

美团把「雪花算法」和「号段模式」都实现了，做成 **Leaf** 框架：`Leaf-snowflake`（雪花模式）和 `Leaf-segment`（号段模式）。它的雪花模式额外解决了**时钟回拨**问题（用 ZooKeeper 记录时间戳做兜底）。

#### 7.5 选型建议

| 场景 | 推荐方案 |
| --- | --- |
| 一般业务主键（订单、用户） | 雪花算法（趋势递增、高性能、无中心） |
| 要求严格递增（如订单号要连续） | Redis `INCR` 或号段模式 |
| 小规模、快速上线 | 数据库自增 + 多库分步长（库1 步长 2 从 1 开始，库2 步长 2 从 2 开始） |
| 无排序要求、纯唯一 | UUID |

### 8. 分布式锁

#### 8.1 背景：本地锁为什么失效

单体里多线程抢一个资源，用 JVM 的 `synchronized` / `ReentrantLock` 就够了（见 [并发编程](/learn_backend/java/Java核心/并发编程)）。但拆成多台机器后，每台机器有自己的 JVM，**本地锁只能锁住本机线程，锁不住别的机器**：

```
单体：1 台机器，JVM 锁能锁住所有线程
    ┌─────────┐
    │ JVM     │  synchronized / ReentrantLock  ✓ 有效
    │ 线程A/B │
    └─────────┘

分布式：3 台机器，本地锁各自为政，锁不住别人
    ┌─────────┐  ┌─────────┐  ┌─────────┐
    │ JVM1    │  │ JVM2    │  │ JVM3    │
    │ lock✓A  │  │ lock✓B  │  │ lock✓C  │  ← 各自锁各自，B/C 也能进来
    └────┬────┘  └────┬────┘  └────┬────┘
         └───────────┴──────┬─────┘
                            │ 都去扣同一个库存 → 超卖！
                 ┌──────────▼──────────┐
                 │   共享资源（DB 库存）  │
                 └─────────────────────┘
```

**分布式锁**就是「跨机器互斥」的锁：让多台机器上的进程，对某个共享资源**只有一个能拿到锁**，其他人必须等待或失败。

#### 8.2 分布式锁要满足的条件

一个合格的分布式锁必须满足这几点（背下来）：

1. **互斥性**：任何时刻只有一个客户端持有锁。
2. **不会死锁**：加锁后客户端宕机，锁要能自动释放（过期时间）。
3. **加锁解锁原子性**：加锁（`setnx` + 过期）和释放（判断 + 删除）都必须是原子操作。
4. **锁的归属正确**：只有加锁的人能解锁，不能误删别人的锁（value 校验 + Lua）。
5. **可重入**（可选）：同一个客户端可重复加锁（Redisson 支持）。
6. **容错**：锁服务（Redis/ZK）本身不能是单点。

#### 8.3 方案一：Redis 分布式锁（最常用）

**基础版（setnx + expire）**：

```java
// 错误示范：setnx 和 expire 分开，不是原子操作
Boolean ok = redisTemplate.opsForValue().setIfAbsent("lock:order:" + orderId, "1");
if (ok) {
    redisTemplate.expire("lock:order:" + orderId, 10, TimeUnit.SECONDS); // 这一步前宕机 → 锁永不过期
}
```

```java
// 正确做法：一条命令同时 setnx + 过期（为什么：保证原子性，避免加锁后宕机导致死锁）
Boolean ok = redisTemplate.opsForValue()
        .setIfAbsent("lock:order:" + orderId, "1", 10, TimeUnit.SECONDS); // SET key value NX EX 10
if (!Boolean.TRUE.equals(ok)) {
    throw new RuntimeException("获取锁失败"); // 别人正在处理，直接拒绝或重试
}
try {
    // 执行业务
} finally {
    // 用 Lua 脚本保证「判断 value 是自己 + 删除」的原子性，避免误删别人的锁
    redisTemplate.execute(lockScript, List.of("lock:order:" + orderId), "1");
}
```

```lua
-- 释放锁的 Lua 脚本（为什么用 Lua：Redis 单线程执行 Lua，
-- 「判断 + 删除」两条命令合并成原子操作，中间不会被插入别的命令）
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

**三大坑（面试高频）**：

| 坑 | 现象 | 解决 |
| --- | --- | --- |
| 加锁非原子 | `setnx` 后、`expire` 前宕机 → 锁永不过期，死锁 | `setnx` + 过期合并成一条命令（`SET NX EX`） |
| 误删别人的锁 | A 的业务超时，锁过期；B 拿到锁，A 又释放 → 把 B 的锁删了 | 释放前校验 value 是自己的，用 Lua 保证原子 |
| 锁过期早于业务 | 业务没跑完，锁过期了，别的线程进来 | 看门狗自动续期（Redisson `watchdog`） |

**生产级方案：Redisson**（推荐直接用，见 [原理篇 §15](#_15-redisson-看门狗与可重入锁原理) 的底层原理）：

```java
RLock lock = redissonClient.getLock("lock:order:" + orderId);
try {
    // 默认加锁时长为 30s，看门狗每 10s 自动续期（为什么：防止业务没跑完锁就过期）
    lock.lock();
    // 执行业务
} finally {
    lock.unlock();
}
```

#### 8.4 方案二：ZooKeeper 分布式锁

利用 ZooKeeper 的**临时顺序节点** + **watch 机制**实现：

```
加锁：
  1. 所有客户端在 /lock 下创建「临时顺序节点」，如 /lock/0001、/lock/0002...
  2. 谁创建的节点序号最小，谁拿到锁
  3. 没拿到锁的客户端，watch 比自己小一号的节点

释放：
  4. 拿锁的客户端业务完 / 宕机，临时节点自动删除（为什么用临时节点：客户端宕机后
     连接断开，ZK 自动删除其临时节点，锁自动释放，天然防死锁）
  5. watch 该节点的客户端收到通知，重新判断自己是不是最小
```

- **优点**：天然防死锁（临时节点）、公平（按序号排队）、无锁过期问题。
- **缺点**：性能远不如 Redis（ZK 是 CP，写要过半确认），维护复杂。

#### 8.5 方案三：数据库分布式锁

用数据库做锁，分两种：

| 方式 | 实现 | 优缺点 |
| --- | --- | --- |
| 唯一约束锁 | 往表里 `INSERT` 一条唯一记录，成功即获锁；释放时 `DELETE` | 简单，但依赖 DB、性能差、无过期（要额外清理） |
| 悲观锁 | `SELECT ... FOR UPDATE` 锁一行 | 简单，但锁粒度难控、依赖事务、连接占用 |

数据库锁基本只在小规模或没有 Redis/ZK 时用，性能是三者里最差的。

#### 8.6 三种方案对比

| 维度 | Redis | ZooKeeper | 数据库 |
| --- | --- | --- | --- |
| 性能 | 高 | 中 | 低 |
| 可靠性 | 中（依赖过期/续期） | 高（临时节点天然防死锁） | 中 |
| 复杂度 | 低（Redisson 开箱即用） | 中 | 低 |
| 公平性 | 一般（Redisson 支持公平锁） | 好（顺序节点天然公平） | 差 |
| 是否要额外组件 | 要 Redis | 要 ZK | 复用 DB |

**结论**：性能优先选 Redis（+Redisson），可靠性优先选 ZooKeeper，小系统/无中间件选数据库。

### 9. 幂等

#### 9.1 背景与定义

> **幂等（Idempotent）**：对同一个请求执行多次，产生的结果和执行一次完全相同。数学里 `f(f(x)) = f(x)`，工程里「重复提交、重复点击、重复消费」都不会产生副作用。

分布式环境天然会带来重复，源头有三：

| 重复来源 | 场景 |
| --- | --- |
| 网络重试 | 超时后客户端/框架自动重试，可能重复执行 |
| 重复点击 | 用户手抖连点两次「提交」，或前端没做防抖 |
| MQ 重复消费 | 消息队列「至少一次投递」语义，消费者可能重复收到同一条消息 |

#### 9.2 幂等 vs 防重（概念区分）

面试常问「幂等和防重是一回事吗」，答案是有区别：

| | 幂等 | 防重（防重复提交） |
| --- | --- | --- |
| 范围 | 任意多次调用结果一致 | 特指「同一用户在短时间内重复提交」 |
| 时效 | 长期有效 | 通常限「一次性/短窗口」 |
| 举例 | `set x=10` 执行 100 次还是 10 | 用 token 防同一表单连续提交两次 |

一句话：**幂等是防重的超集**，防重是幂等在「用户重复提交」场景的具体应用。

#### 9.3 实现手段（成体系）

| 方案 | 原理 | 适用场景 | 特点 |
| --- | --- | --- | --- |
| 唯一索引（数据库兜底） | 业务唯一键建唯一索引，重复插入报错 | 所有写库的兜底 | 最简单可靠，必须做 |
| 唯一 token | 提交前先取 token，提交时校验并删除 | 表单/下单防重复提交 | 需前端配合，token 一次性 |
| 状态机 | 状态只能按固定方向流转，非法转移拒绝 | 订单、审批流 | 从业务规则上天然幂等 |
| Redis `setnx` | 用 `setnx` 记录「已处理」标记 | MQ 消费去重、防重复提交 | 快，但要设过期时间 |
| 乐观锁（version） | `UPDATE ... SET version=version+1 WHERE version=?` | 并发更新同一条记录 | 影响行数为 0 说明已被改过 |

```java
// 唯一 token 方案的可运行示例
// 1. 进入页面时，后端生成 token 返回前端
String token = UUID.randomUUID().toString();
redisTemplate.opsForValue().set("idem:token:" + userId, token, 30, TimeUnit.MINUTES);

// 2. 前端提交时带上 token，后端校验并删除
public String submit(String token) {
    // 为什么用 setIfAbsent 的相反——这里用「删除」来判断：只有第一个请求能删成功
    Boolean deleted = redisTemplate.delete("idem:token:" + userId);
    if (!Boolean.TRUE.equals(deleted)) {
        throw new RuntimeException("重复提交"); // token 已被消费，说明是第二次提交
    }
    // 执行业务
    return "success";
}
```

```java
// 状态机 + 乐观锁 的幂等示例（订单状态）
// 为什么「状态判断」天然幂等：已支付订单不允许再变回未支付，
// 重复的「支付成功」请求会被状态机挡在门外
public void paySuccess(Long orderId) {
    // 乐观锁：只允许「待支付 → 已支付」，重复执行影响行数为 0
    int rows = orderMapper.updateStatus(orderId, "待支付", "已支付");
    if (rows == 0) {
        // 已经是「已支付」或不存在，说明是重复请求，直接忽略
        return;
    }
    // 只有第一次成功时才发积分、发消息
    pointService.addPoints(orderId);
}
```

### 10. 限流与降级（补充：分布式系统的自我保护）

限流降级虽不是「分布式基础」的核心考点，但它是分布式系统「高可用」的必备手段，这里简单成体系带过（详见 [Sentinel](/learn_backend/java/微服务/Sentinel)、[Gateway](/learn_backend/java/微服务/Gateway)）：

| 概念 | 目的 | 常见实现 |
| --- | --- | --- |
| 限流 | 保护系统不被流量打崩，超过阈值拒绝 | 计数器、滑动窗口、令牌桶、漏桶（Sentinel） |
| 降级 | 系统压力大时，关掉非核心功能保核心 | 熔断降级（Hystrix/Sentinel） |
| 熔断 | 依赖服务持续失败时，快速失败不再调用 | 熔断器（Closed/Open/HalfOpen 三态） |
| 隔离 | 把故障隔离在局部，不拖垮整体 | 线程池隔离、信号量隔离 |

它们与前面内容一脉相承：限流防「网络洪峰」、降级熔断防「节点故障扩散」、幂等防「重试副作用」，都是对「分布式三大问题」的工程回应。

## 原理篇

### 11. 2PC（两阶段提交）的完整流程

2PC（Two-Phase Commit）是最经典的强一致分布式事务协议，也是所有分布式事务思想的源头。虽然工程上很少直接用，但理解它才能理解 TCC、Seata AT 为什么那么设计。

#### 11.1 角色与流程

2PC 有两个角色：

| 角色 | 说明 |
| --- | --- |
| 协调者（Coordinator，TC） | 事务管理器，负责发起、决策、通知，通常是全局事务的入口 |
| 参与者（Participant，RM） | 资源管理器，实际执行事务的各个服务/数据库 |

完整流程分两阶段，第一阶段「投票」、第二阶段「执行」：

```
阶段一：准备阶段（Prepare / 投票）
┌──────────┐         prepare(提交请求)          ┌──────────┐
│ 协调者 TC │ ───────────────────────────────▶ │ 参与者 RM1 │
│          │ ◀─────────────────────────────── │           │
└──────────┘   yes/no（能否提交，锁住资源不提交） └──────────┘
    │  同样询问 RM2、RM3 ...
    │
    │  收集所有参与者的应答
    │
    ├─ 全部 yes ──────────────▶ 提交阶段：发 commit
    └─ 任一 no / 超时 ─────────▶ 回滚阶段：发 rollback

阶段二：提交/回滚阶段（Commit / Rollback）
    全部 yes：协调者发 commit  → 各参与者正式提交，释放资源
    任一 no： 协调者发 rollback → 各参与者回滚，释放资源
```

**关键点**：参与者在**准备阶段**执行事务但不提交，**锁住相关资源**，等待协调者的最终指令。这正是 2PC 阻塞、性能差的根源。

#### 11.2 三个致命问题

| 问题 | 说明 | 后果 |
| --- | --- | --- |
| 同步阻塞 | 准备阶段到提交阶段之间，所有参与者都锁着资源、等待协调者指令 | 并发能力差，长事务会锁死大量资源 |
| 单点故障 | 协调者是唯一决策者，一旦宕机，所有参与者卡在「待提交」状态 | 全局事务挂起，甚至系统不可用 |
| 数据不一致 | 第二阶段，协调者向部分参与者发了 commit 后宕机，剩下的没收到 | 部分提交、部分未提交 → 数据不一致 |

#### 11.3 XA 与 3PC

- **XA 规范**：2PC 在数据库层的落地标准，定义了「事务管理器」和「资源管理器」之间的接口（`xa_prepare`、`xa_commit`、`xa_rollback`）。MySQL、Oracle 都支持 XA。
- **3PC（三阶段提交）**：在 2PC 的「准备」和「提交」之间加了一个「预提交（PreCommit）」阶段，并引入**超时机制**（参与者等不到协调者指令会自动提交），缓解了 2PC 的单点阻塞问题，但复杂度更高、无法完全解决数据不一致，工程上很少用。

> 小结：2PC 的思想是「先问一遍能不能提交，再统一提交」，保证强一致，代价是阻塞和单点。Seata AT 把它改良成「一阶段就提交 + undo log 兜底」，TCC 把它改良成「业务自己拆三段 + 补偿」，都是为了绕开 2PC 的阻塞和锁资源问题。

### 12. TCC 的完整流程与三大异常

TCC（Try-Confirm-Cancel）是一种**业务层面的强一致**方案，核心是「把一次业务拆成三段，让业务方自己实现」。

#### 12.1 三段语义

| 阶段 | 职责 | 举例（扣库存 + 加积分） |
| --- | --- | --- |
| Try | 预留资源、检查能否执行 | 冻结库存（`冻结数+1`，`可用数-1`，不真正扣） |
| Confirm | 确认提交，真正执行业务 | 真正扣库存（`冻结数-1`），加积分 |
| Cancel | 取消回滚，释放预留资源 | 释放冻结（`冻结数-1`，`可用数+1`） |

```
正常流程：Try(预留) → Confirm(确认)
失败流程：Try(预留) → Cancel(回滚)
```

```java
// TCC 三段的可运行骨架（以「账户转账」为例，关键行加「为什么」注释）
public interface TransferService {
    // Try：预留资源（冻结金额），为什么要先冻结：真正的扣减放到 Confirm，
    // 这样 Cancel 时只需释放冻结，不需要反向转账，保证可回滚
    boolean tryTransfer(String from, String to, BigDecimal amount);

    // Confirm：确认提交（真正扣冻结金额、加余额）
    boolean confirmTransfer(String from, String to, BigDecimal amount);

    // Cancel：回滚（释放冻结金额）
    boolean cancelTransfer(String from, String to, BigDecimal amount);
}
```

#### 12.2 三大异常与处理（面试高频）

TCC 因为「业务自己分三段」，会出现 2PC 没有的三个坑，必须处理：

| 异常 | 现象 | 处理 |
| --- | --- | --- |
| 幂等 | 网络重试导致 Confirm/Cancel 被执行多次 | Confirm/Cancel 必须幂等（加状态判断/唯一键） |
| 空回滚 | 没调用 Try，却调用了 Cancel（Try 请求超时但实际没执行，协调者发 Cancel） | Cancel 要允许「没 Try 也能执行」——发现没有预留就直接返回 |
| 悬挂 | Cancel 先执行完了，Try 才姗姗来迟（Try 请求堵塞，Cancel 已回滚，Try 又执行了预留） | Try 执行前判断「是否已回滚」，已回滚则拒绝执行 Try |

这三个异常是 TCC 区别于 2PC 的核心难点，也是面试问「TCC 有哪些坑」的标准答案。

### 13. 一致性哈希

#### 13.1 背景：缓存扩容的迁移问题

分布式缓存（如 Redis 集群）要解决「key 该存到哪个节点」的问题。最简单的办法是**取模**：`hash(key) % N`，N 是节点数。但它有一个致命问题——**节点数变化时，几乎所有 key 都要迁移**：

```
传统取模 hash(key) % N：
  N=3 时：key=100 → 100%3=1 → 节点1
  N=4 时（加了一台）：key=100 → 100%4=0 → 节点0  ← 换地方了！

  节点数一变，绝大多数 key 的落点都变 → 缓存全部失效
  → 请求全打到数据库 → 缓存雪崩（见 面试常问）
```

**一致性哈希**就是为了解决「扩容/缩容时，尽量少迁移数据」这个问题。

#### 13.2 一致性哈希原理

核心思想：把**节点**和**key**都映射到同一个 **hash 环**（0 ~ 2^32-1）上，key 顺时针找到的第一个节点就是它的归属节点：

```
                    0
             ┌───────┐
            /         \
           │   节点A    │
           │    (hash)  │
          │             │
    key1 →│             │
          │     hash环   │
          │   (0~2^32)  │
           │             │
            \   节点B    /
             │         │
             └──┬──────┘
                │
              节点C

规则：key 顺时针找到的第一个节点，就是它要存的节点
```

- **加节点**：只有「新节点逆时针方向到上一个节点」之间的一小段 key 需要迁移，其他 key 不受影响。
- **删节点**：只有「被删节点负责的那一段 key」需要迁移到它的下一个节点。

```
加节点D前：key 归属 = 顺时针最近的节点
    A ---(这段归B)--- B ---(这段归C)--- C

加节点D（落在 B 和 C 之间）：
    A ---(归B)--- B ---(归D)--- D ---(归C)--- C
                        ↑
               只有原来归 C 的这段 key 迁移到 D，其余不动
```

#### 13.3 数据倾斜与虚拟节点

一致性哈希解决了「迁移量」问题，但带来新问题——**数据倾斜**：物理节点少时，hash 落点不均匀，可能某个节点负责环上一大段，负载不均衡。

**虚拟节点（Virtual Node）**就是解法：为每个物理节点创建多个虚拟节点，分散到环上：

```
物理节点A  →  虚拟节点 A#1、A#2、A#3 ...（每个有不同 hash，散落在环各处）
物理节点B  →  虚拟节点 B#1、B#2、B#3 ...

key 顺时针找到虚拟节点，再映射回它所属的物理节点
```

虚拟节点越多，分布越均匀，节点增减时迁移也更平滑。

```java
// 一致性哈希（带虚拟节点）的可运行骨架
public class ConsistentHash {
    // 为什么用 TreeMap：它的 key 天然有序，能快速找到「顺时针第一个 >= hash 的节点」
    private final TreeMap<Integer, String> ring = new TreeMap<>();
    private final int virtualNodeCount; // 每个物理节点的虚拟节点数

    public ConsistentHash(List<String> nodes, int virtualNodeCount) {
        this.virtualNodeCount = virtualNodeCount;
        for (String node : nodes) {
            addNode(node);
        }
    }

    public void addNode(String node) {
        // 为什么建虚拟节点：让一个物理节点在环上占多个位置，分布更均匀
        for (int i = 0; i < virtualNodeCount; i++) {
            int hash = hash(node + "#" + i);
            ring.put(hash, node);
        }
    }

    // 根据 key 找到归属节点
    public String getNode(String key) {
        int hash = hash(key);
        // 顺时针找第一个 >= hash 的节点；环是循环的，找不到就回到环首（tailMap 为空取 firstKey）
        Integer target = ring.ceilingKey(hash);
        if (target == null) {
            target = ring.firstKey(); // 越过 2^32-1 回到 0，取环上第一个节点
        }
        return ring.get(target);
    }

    private int hash(String key) {
        // 用稳定的 hash（如 MD5 取前 32 位），保证同一个 key 永远映射到同一个位置
        return Math.abs(key.hashCode());
    }
}
```

### 14. 雪花算法的字节级内存布局

把雪花算法拆到「bit」级别，看清它的内存结构，是面试的深度考点。

#### 14.1 64 位布局

一个雪花 ID 是一个 **Java long（64 位）**，从高位到低位（从左到右）分成四段：

```
bit 位置：   63   62            22   21          12   11             0
        ┌─────┬────────────────┬───────────────┬─────────────────┐
        │ 1bit │    41bit        │    10bit       │     12bit        │
        │ 符号 │  时间戳(毫秒)     │ 机器号(数据中心5+机器5) │ 序列号          │
        └─────┴────────────────┴───────────────┴─────────────────┘
          恒为0   相对于起始时间的毫秒      最多 1024 台机器       每毫秒 0~4095
```

| 段 | bit 数 | 取值范围 | 说明 |
| --- | --- | --- | --- |
| 符号位 | 1 | 0 | 恒 0，保证 ID 是正数 |
| 时间戳 | 41 | 0 ~ 2^41-1（约 2.2 万亿毫秒 ≈ 69 年） | 相对于「起始时间」的毫秒数，不是 1970 起算 |
| 机器号 | 10 | 0 ~ 1023 | 通常拆成 5bit 数据中心 + 5bit 机器号 |
| 序列号 | 12 | 0 ~ 4095 | 同一毫秒内自增，用满 4096 个等下一毫秒 |

#### 14.2 容量计算（面试会问「为什么是 69 年 / 4096 个」）

- **时间戳 41 位**：`2^41 = 2199023255552` 毫秒 ≈ 69.7 年。为什么不是 1970 起算？因为从「系统上线时间」起算，能把这 69 年都留给「未来」，而不是被 1970~上线 这 50 年白白吃掉。
- **机器号 10 位**：`2^10 = 1024` 台机器。
- **序列号 12 位**：`2^12 = 4096`，即每毫秒每台机器最多生成 4096 个 ID。所以单机理论 QPS ≈ `1000 * 4096 = 409.6 万/秒`。

#### 14.3 拼接的位运算

在 Java 里，把四段拼成一个 long 用的是**位移 + 或运算**（见 7.3 的实现）：

```java
return ((timestamp - startTime) << 22)      // 时间戳放高 41 位（左移 22 位给机器号+序列号让位）
        | (datacenterId << 17)              // 数据中心放第 17~21 位
        | (workerId << 12)                  // 机器号放第 12~16 位
        | sequence;                          // 序列号放低 12 位
```

> 小结：雪花算法的本质是**把唯一性分解到「时间 + 机器 + 序列」三个维度**——时间维度靠毫秒递增，机器维度靠 1024 台机器区分，序列维度靠每毫秒 4096 个自增兜底。三者组合保证了全局唯一，同时因为高位是时间戳而天然趋势递增。

### 15. Redisson 看门狗与可重入锁原理

Redis 分布式锁最经典的生产方案是 Redisson，它的两个核心机制——**看门狗自动续期**和**可重入**——值得下到源码结构层面理解。

#### 15.1 为什么需要看门狗

基础版 Redis 锁有一个「锁过期时间」的矛盾：设太短，业务没跑完锁就过期了（别的线程进来）；设太长，业务异常宕机后锁要很久才释放。**看门狗（watchdog）**就是解决这个矛盾的：

```
看门狗自动续期流程：
  1. 客户端 lock() 时不显式指定过期时间 → Redisson 默认给锁设 30s 过期
  2. 同时启动一个「看门狗定时任务」，每 10s（30s 的 1/3）检查一次
  3. 如果业务还在执行（锁还持有），就把过期时间续期回 30s
  4. 业务执行完 unlock()，看门狗任务取消，锁正常释放
  5. 如果客户端宕机，看门狗不再续期 → 30s 后锁自动过期释放
```

- **效果**：业务执行多久，锁就「智能地」续多久，不会提前过期；业务宕机了，锁最多 30s 就释放，不会死锁。

#### 15.2 可重入锁原理

Redisson 的可重入锁用 Redis 的 **Hash 结构 + Lua 脚本**实现：

```
锁的存储结构：Redis Hash
  key = 锁名（如 "lock:order:100"）
  field = 持有锁的线程标识（如 "thread-1"）
  value = 该线程的重入次数

加锁（Lua 脚本，原子）：
  if 锁不存在：
      hset key threadId 1; 设置过期时间; 返回加锁成功
  else if 锁的 field == 当前 threadId：   ← 自己已经持有，可重入
      hincrby key threadId 1; 返回加锁成功
  else：
      返回加锁失败（别人持有）

解锁（Lua 脚本，原子）：
  if 锁的 field != 当前 threadId：
      返回（不是自己的锁，不能解）
  else：
      value - 1
      if value == 0： 删除锁，取消看门狗   ← 重入次数归零才真正释放
      else： 返回（还有一层重入没退出）
```

```java
// Redisson 可重入锁使用示例
RLock lock = redissonClient.getLock("lock:order:" + orderId);
try {
    lock.lock();          // 第一次加锁，重入次数 = 1，启动看门狗
    doSomething();
    lock.lock();          // 同一线程再次加锁，重入次数 = 2（为什么能成功：可重入）
    try {
        doSomethingElse();
    } finally {
        lock.unlock();    // 释放一层，重入次数 = 1
    }
} finally {
    lock.unlock();        // 真正释放，重入次数 = 0，删除锁
}
```

> 小结：Redisson 用「Hash + Lua」实现可重入（field 存线程、value 存次数），用「后台定时续期」实现看门狗（业务未完锁不过期、宕机自动过期）。这两个机制是它比裸 `setnx` 强的地方。

### 16. 分布式一致性算法（Raft / Paxos）简述

前面反复出现「CP 用 Raft 保证一致」，这里把一致性算法给一个完整但不深入到论文级的框架（面试通常问到「Raft 和 Paxos 的区别、Raft 怎么选主」这个深度）：

#### 16.1 要解决的问题

分布式一致性问题本质是：**多个节点各有一份状态（数据），如何在「节点会宕机、网络会分区」的情况下，让所有节点对「当前状态」达成一致**。CAP 里选 C（一致性）的系统，底层都用它。

#### 16.2 Paxos：理论的鼻祖

Paxos 是最早的一致性算法（Lamport 提出），但论文难懂、实现复杂。它的核心是「两阶段投票」——提案者（Proposer）提议、接受者（Acceptor）投票、超过半数即通过。工程上直接用 Paxos 的系统很少。

#### 16.3 Raft：工程友好的主流

Raft 是「可理解」版的 Paxos，把一致性拆成三个独立子问题，是目前 CP 系统（etcd、TiKV、Consul、Nacos CP 模式）的**事实标准**：

| 子问题 | 说明 |
| --- | --- |
| 领导者选举（Leader Election） | 用「任期（term）+ 随机超时」选出唯一 Leader，Leader 负责处理所有写请求 |
| 日志复制（Log Replication） | Leader 把日志复制到 Follower，**过半确认即提交** |
| 安全性（Safety） | 保证已提交的日志不会再被覆盖（选举时选日志最新的节点当 Leader） |

```
Raft 角色状态机（三个角色，节点可在三者间切换）：

        ┌──────────┐   超时没有 Leader
        │ Follower │ ──────────────────▶ Candidate（候选人）
        └──────────┘                        │
              ▲                             │ 获得多数票
              │ 发现更高任期                 ▼
              │                       ┌──────────┐
              └───────────────────────│  Leader  │
                                      └──────────┘
                                           │ 发现更高任期
                                           ▼ 退回 Follower
```

- **选主核心**：每个 Follower 有一个随机超时时间，谁先超时谁先发起选举成为 Candidate，请求其他节点投票，**获得多数票（超过半数）即当选 Leader**。
- **为什么必须「过半」**：假设总共 N 个节点，两个 Leader 各自拿到 ≤ N/2 的票是可能同时出现的，但只要要求「过半」，就不可能同时有两个 Leader 都拿到多数票，从而保证**只有一个合法 Leader**。

#### 16.4 与 CAP/BASE 的关系

| 算法/理论 | 一致性强弱 | 典型组件 |
| --- | --- | --- |
| Raft/Paxos | 强一致（线性一致） | etcd、ZooKeeper、Consul、Nacos(CP) |
| 异步复制 | 最终一致 | Redis 主从、MySQL 主从 |
| 2PC | 强一致（但阻塞） | XA 事务 |

> 小结：CAP 告诉你「分区时 C 和 A 二选一」；选了 C 的系统，用 Raft/Paxos 来实现一致性；选了 A 的系统，用异步复制 + 最终一致（BASE）来实现。这就是整条分布式理论链路的闭环。

## 面试常问

### 1. CAP 是什么？实际怎么选？

**结论**：CAP 指一致性（C）、可用性（A）、分区容错性（P），分布式系统在网络分区时只能 C/A 二选一，P 必选。

**展开**：网络分区客观存在所以 P 必选；分区发生时节点间无法同步数据，要么拒绝响应保一致（CP），要么返回旧数据保可用（AP）。实际选型：一致性要求高选 CP（ZK、etcd），可用性优先选 AP（Eureka、Nacos 默认），绝大多数互联网业务选 AP + 最终一致（BASE）。

### 2. 分布式事务有哪些方案？分别怎么选？

**结论**：2PC（强一致但阻塞）、TCC（强一致但侵入业务）、消息最终一致性（最常用）、本地消息表（无 MQ 的自研版）。

**展开**：强一致且能容忍锁用 2PC/XA；资金库存等需业务补偿用 TCC；能异步、要性能用 RocketMQ 事务消息做最终一致；没有 MQ 或想自研就用本地消息表 + 定时补偿。互联网 90% 选最终一致。

### 3. 分布式 ID 怎么生成？雪花算法的坑是什么？

**结论**：主流用雪花算法（时间戳 + 机器号 + 序列号，趋势递增），注意时钟回拨。

**展开**：雪花 ID 是 64 位 long，高 41 位时间戳、10 位机器号、12 位序列号，天然趋势递增对 MySQL 聚簇索引友好。最大坑是时钟回拨导致 ID 重复，解决靠等待时钟追回、备用机器号、或美团 Leaf 兜底。

### 4. 分布式锁怎么实现？有哪些坑？

**结论**：Redis `setnx`（带过期）+ Lua 释放，生产用 Redisson；坑是加锁非原子、误删别人的锁、锁过期。

**展开**：加锁必须把 `setnx` 和过期合并成一条 `SET NX EX` 命令；释放前要校验 value 是不是自己，用 Lua 保证原子；业务没跑完锁就过期用看门狗自动续期。也可用 ZK 临时顺序节点实现（天然防死锁、公平），数据库锁性能最差。

### 5. 怎么保证幂等？

**结论**：唯一索引、唯一 token、状态机、Redis `setnx`、乐观锁五种手段按场景选用。

**展开**：数据库唯一索引做最终兜底；唯一 token 防表单重复提交；状态机从业务规则上天然幂等（订单状态不可逆）；Redis `setnx` 做消费去重；乐观锁（version）保证并发更新同一记录时只成功一次。

### 6. 为什么缓存集群加节点会导致缓存雪崩？一致性哈希怎么解决？

**结论**：传统取模 `hash(key) % N` 在 N 变化时几乎所有 key 落点都变，缓存全失效回源打崩 DB；一致性哈希用 hash 环让只有小部分 key 迁移。

**展开**：一致性哈希把节点和 key 都映射到 0~2^32 的环上，key 顺时针找最近节点，加/删节点只影响环上一小段。节点少时数据倾斜，用虚拟节点让分布更均匀。

### 7. 2PC 有什么问题？为什么 TCC / 最终一致更好？

**结论**：2PC 同步阻塞、单点故障、数据不一致风险；TCC 用业务补偿、最终一致用消息异步，性能和可用性更好。

**展开**：2PC 准备阶段锁资源直到第二阶段，阻塞并发；协调者挂了全局卡死；第二阶段部分提交成功会导致不一致。TCC 把事务拆成 Try/Confirm/Cancel 三段让业务自己实现，不长时间锁资源但侵入业务；消息最终一致用「本地事务 + 消息」解耦，靠 MQ 重试保证最终一致，是互联网主流。

### 8. Raft 为什么要求「过半」确认？怎么选主？

**结论**：过半确认保证任意时刻最多只有一个合法 Leader，避免脑裂；选主靠任期 + 随机超时，谁先超时谁发起选举，获多数票当选。

**展开**：如果不要求过半，两个分区各自选出 Leader 会脑裂导致数据不一致；过半投票保证两个 Leader 不可能同时存在。选主时 Follower 随机超时避免同时竞争，获得多数票的 Candidate 成为 Leader，之后 Leader 负责所有写请求并向 Follower 复制日志。
