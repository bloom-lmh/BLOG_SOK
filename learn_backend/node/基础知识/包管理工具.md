# 包管理工具

## 包管理相关知识

### 什么是包管理工具

我们在开发项目时会使用到项目内部模块也可能会使用一些外部模块，而这些外部模块就可以叫做为包。包英文单词是 `package` ，代表了一组特定功能的源码集合，包管理工具是管理包的应用软件，可以对包进行下载安装、更新、删除、上传等操作，借助包管理工具，可以

### 生产环境和开发环境

- 开发环境是程序员专门用来写代码的环境，一般是指程序员的电脑，开发环境的项目一般只能程序员自己访问
- 生产环境是项目代码正式运行的环境，一般是指正式的服务器电脑，生产环境的项目一般每个客户都可以访问

### 生产依赖与开发依赖

我们可以在安装时设置选项来区分依赖的类型，目前分为两类：

| 类型     | 命令            | 补充                                                                                      |
| -------- | --------------- | ----------------------------------------------------------------------------------------- |
| 生产依赖 | `npm i -S uniq` | `-S` 等效于 `--save，-S` 是默认选项<br>包信息保存在 `package.json` 中 `dependencies` 属性 |
| 开发依赖 | `npm i -D less` | `-D` 等效于 `--save-dev`<br>包信息保存在 `package.json` 中 `devDependencies` 属性         |

举个例子，比如说做蛋炒饭需要大米、油、葱、鸡蛋、锅、煤气、铲子等，其中锅、煤气、铲子属于开发依赖，只在制作阶段使用而大米、油、葱、鸡蛋属于生产依赖，在制作与最终食用都会用到所以开发依赖是只在开发阶段使用的依赖包，而生产依赖是开发阶段和最终上线运行阶段都用到的依赖包

### 全局安装和局部安装

对于外部模块的下载有**全局安装和局部安装**两种方式，所谓的全局下载就是模块下载后放入全局的`node_modules`文件中，此后任何文件任何地方都可以使用该模块，而局部安装会安装到本项目的`node_modules`文件下，对于该模块的使用仅限于本项目

我们可以执行安装选项 `-g` 进行全局安装，例如：`npm i -g nodemon`。全局安装完成之后就可以在命令行的任何位置运行 `nodemon` 命令。该命令的作用是 自动重启 `node` 应用程序

说明：

- 全局安装的命令不受工作目录位置影响
- 可以通过 `npm root -g `可以查看全局安装包的位置
- 不是所有的包都适合全局安装， 只有全局类的工具才适合，可以通过查看包的官方文档来确定安装方式，这里先不必太纠结

## npm 包管理工具

### 什么是 npm

`npm` 是 `Node.js` 包管理工具，使用它你可以安装、卸载、管理第三方包，它可以自动解决依赖关系，并管理各个包之间的依赖关系。

### npm 常用命令

1. 初始化项目：`npm init`，当使用`npm init` 时，会创建一个`package.json`的文件，这个文件记录着你的包相关信息以及依赖信息
2. 包的安装卸载与更新：`npm install 包名 [@version] [参数]  （uninstall,update）`
3. 查看包信息：`npm info 包名 [指定内容] `
4. 判断包是否过时：`npm outdated [包名]`
5. 包搜索：`npm s/search 关键字`

::: tip 依赖的占位符

- `"dependencies": {"md5": "^2.1.0"}`:`^`表示如果直接`npm install` 将会安装`md5` `2.*.*`最新版本
- `"dependencies": {"md5": "~2.1.0"}` `~`表示如果直接`npm install` 将会安装`md5` `2.1.*`最新版本
- `"dependencies": {"md5": "*"}` `*`表示直接`npm install` 将会安装`md5`最新版本

:::

### npm 仓库设置

由于 `npm` 的仓库是在国外，若使用国外仓库来下载对应的模块会受到网络限制，所以通常使用国内的镜像仓库。对 `npm` 仓库的设置通常有以下三种方式

1. 使用`nrm`工具来切换
2. 手动切换方式：`npm config set registry 镜像地址`
3. 下载`cnpm`：`npm install -g cnpm --registry=https://registry.npmmirror.com`

### npm 配置命令别名

在 `package.json` 中的 `scripts` 属性中可以配置命令别名，当使用别名时，`node` 会找寻 `package.json` 文件的 `scripts` 属性中是否有对应的别名。通过配置命令别名可以更简单的执行命令配置 `package.json` 中的 `scripts` 属性

```json
{
  //...
  "scripts": {
    "server": "node ./index.js",
    "start": "node ./index.js"
  }
  //...
}
```

配置完成之后，可以使用别名执行命令：

```bash
npm run server
npm run start
# 等价于
npm start
```

::: tip 关于`npm run`
`npm run` 本身可以执行可执行文件(`bin`所指向的`js`文件)，有自动向上级目录查找的特性，跟`require` 函数也一样；这样就保证一个项目依赖于一个`node_modules`中的依赖，而不用每个文件都创建一个`node_modules`
:::

### require 导入 npm 包基本流程

1. 在当前文件夹下的`node_modules` 中寻找同名的文件夹
2. 如果没有找到同名的文件夹，在上级目录中下的 `node_modules` 中寻找同名的文件夹，直至找到磁盘根目录

如果导入的路径是个文件夹，则会首先检测该文件夹下 `package.json` 文件中 `main` 属性对应的文件，如果存在则导入，反之如果文件不存在会报错。如果 `main` 属性不存在，或者 `package.json` 不存在，则会尝试导入文件夹下的 `index.js` 和 `index.json` ，如果还是没找到，就会报错

## cnpm 包管理工具

### cnpm 介绍

> 就是镜像工具

`cnpm` 是一个淘宝构建的 `npmjs.com` 的完整镜像，也称为『淘宝镜像』，网址https://npmmirror.com/。`cnpm` 服务部署在国内阿里云服务器上，可以提高包的下载速度。官方也提供了一个全局工具包 `cnpm` ，操作命令与 `npm` 大体相同。使用`npm install -g cnpm --registry=https://registry.npmmirror.com`下载即可

![cnpm 包管理工具](https://image-bucket-1307756649.cos.ap-chengdu.myqcloud.com/image/20251215215226517.png)

## yarn 包管理工具

### yarn 介绍

`yarn` 是由 `Facebook` 在 2016 年推出的新的 Javascript 包管理工具，官方网址： https://yarnpkg.com/。使用`npm install -g yarn`即可下载

### yarn 特点

- 速度超快：`yarn` 缓存了每个下载过的包，所以再次使用时无需重复下载。同时利用并行下载以最大化资源利用率，因此安装速度更快
- 超级安全：在执行代码之前，`yarn` 会通过算法校验每个安装包的完整性
- 超级可靠：使用详细、简洁的锁文件格式和明确的安装算法，`yarn` 能够保证在不同系统上无差异的工作

### yarn 的常用命令

| 命令                         | 功能                           |
| ---------------------------- | ------------------------------ |
| `yarn init` / `yarn init -y` | 初始化                         |
| `yarn add uniq`              | 安装包（生产依赖）             |
| `yarn add less --dev`        | 安装包（开发依赖）             |
| `yarn global add nodemon`    | 全局安装                       |
| `yarn remove uniq`           | 删除项目依赖包                 |
| `yarn global remove nodemon` | 全局删除包                     |
| `yarn`                       | 安装项目依赖                   |
| `yarn <别名>`                | 运行命令别名（不需要添加 run） |

### yarn 配置淘宝镜像

可以通过如下命令配置淘宝镜像：`yarn config set registry https://registry.npmmirror.com/`
可以通过 `yarn config list` 查看 `yarn` 的配置项

## pnpm

### pnpm 产生的背景

#### 1. 幽灵依赖

##### 什么是幽灵依赖

`pnpm` 出现主要目的就是为了解决幽灵依赖的问题。而所谓的幽灵依赖是指未在 `package` 中声明的依赖却下载了下来。比如我们创建一个全新的 vue3 项目。

![vue3 项目](https://image-bucket-1307756649.cos.ap-chengdu.myqcloud.com/image/20251215214443512.png)

然后我们正常地通过 `npm install` 来下载依赖。我们发现，`node_ modules` 文件夹下的很多依赖，我们在 `package.json` 中明明没去声明却都下载下来了

![幽灵依赖](https://image-bucket-1307756649.cos.ap-chengdu.myqcloud.com/image/20251215214518748.png)

那么这些没声明却下载的依赖就是`幽灵依赖（幻影依赖）`，这种现象出现的原因，就是是一个库依赖另一个库。我们能在项目中直接使用这些间接的幽灵依赖

##### 幽灵依赖存在的问题

因为存在幽灵依赖，所以我们可以在项目中去使用一个我们并没有声明的库，比如 `lodash`:

![幽灵依赖](https://image-bucket-1307756649.cos.ap-chengdu.myqcloud.com/image/20251215214711149.png)

但是这会导致许多的问题

1. 版本问题

![版本问题](https://image-bucket-1307756649.cos.ap-chengdu.myqcloud.com/image/20251215215524716.png)

比如一个项目用的`A`这个库，版本是`v1`,然后`A`这个库依赖`B`库，版本也是`v1`。`B`这个库就是我们没有声明的一个库，但是我们仍然在项目中去进行使用。但是如果有一天，我们对`A`这个库进行了升级，比如说升级到了`v2`的版本，然后它可能需要对应`B`库的`v2`版本，于是`B`库也跟着莫名其妙地进行升级了，而`B`库升级之后，它里面的`api`可能会发生变动，那么可能会导致我们之前的用`B`库的代码出现问题。这就是幽灵依赖的一种情况，当然，可能会有更复杂的情况，这个时候，我们可能不好排错和处理

2. 依赖丢失问题

还有一种依赖丢失的情况

![依赖丢失问题](https://image-bucket-1307756649.cos.ap-chengdu.myqcloud.com/image/20251215215648608.png)

现在`A`是一个开发时依赖，也就是到了生产环境里，是不会安装`A`这个依赖的，那么`B`也就不会安装，但是在开发的时候却使用了`B`，但是生成的时候`B`却没有了，所以这会发生依赖丢失的问题

#### 2. 其它包管理器的缺陷

##### npm 包管理器的缺陷

我们开发的时候会用到很多的包，包与包之间会形成一些依赖关系，比如`依赖树`，`依赖图`，但是`npm`这个包管理器，使用的是`文件结构`，而文件结构是一个`树结构`，这样的的话会导致重复的依赖下载下来，比如下面的`D`依赖：

![npm 包管理器的缺陷](https://image-bucket-1307756649.cos.ap-chengdu.myqcloud.com/image/20251215215950678.png)

##### yarn 包管理器的缺陷

后来出现了一个包管理工具`yarn`，它通过拍平的方式解决了`npm`依赖重复的问题

![yarn 包管理器的缺陷](https://image-bucket-1307756649.cos.ap-chengdu.myqcloud.com/image/20251215220027246.png)

那么这样怎么体现出包之间的依赖关系呢？`nodejs`有一个查询包的流程，就是在`import`或者`require`的时候，它找不到的话，会往上去找。`yarn`这样做的确解决了结构问题（现在新的`npm`也是`yarn`的处理方式），但是却依然没有解决幽灵依赖问题。

#### 3. pnpm 解决幽灵依赖和其包管理器的问题

`pnpm` 也是一个包管理工具，它解决了幽灵依赖的问题，它把所有的包存到一个仓库文件夹`.pnpm`里面，然后在 `node_modules` 里面用正常的树结构，来表达包依赖。这么做的好处就是不会有重复项，因为它使用的链接的方式来处理，也就是说他是 `npm` 和 `yarn` 方式的结合体，实际的包存放在仓库文件夹里面，而 `node_modules` 中只是以链接的形式来呈现依赖关系。这样即解决了 `npm` 重复依赖的问题，又解决了幽灵依赖

![pnpm 解决幽灵依赖和其包管理器的问题](https://image-bucket-1307756649.cos.ap-chengdu.myqcloud.com/image/20251215220239834.png)

### pnpm 的基本原理

#### pnpm 下的包结构

现在我们把之前的依赖删除，用 `pnpm` 来进行安装

![pnpm 下的包结构](https://image-bucket-1307756649.cos.ap-chengdu.myqcloud.com/image/20251215220310752.png)

这个`.pnpm`文件就是它的仓库，存放真实的依赖。`.pnpm`称为虚拟存储目录，以平铺的形式储存着所有的项目依赖包，每个依赖包都可以通过`.pnpm/@/node_modules/`路径找到实际位置。

![ pnpm 下的包结构](https://image-bucket-1307756649.cos.ap-chengdu.myqcloud.com/image/20251215220542668.png)

剩下的就是在`package.json`中声明的依赖，比如`vite、vue`采用的叫做符号链接（软链接）

#### pnpm 下的软链接和硬链接

- 硬链接：我们的文件数据，都是存在磁盘上的，我们创建一个文件，就给它分配一段磁盘空间，文件是一个指针，指针指向这个磁盘空间，可以通过文件`A`创建一个硬链接文件`B`，如果是通过硬链接来创建的话，那么`B`的指针和`A`是一样的，他也是同样指向这个磁盘空间，这样就是两个文件，共用一块磁盘空间，这样在硬链接的前提下，把文件`A`干掉了，不会影响文件`B`
- 软链接：软链接类似于快捷方式，它和硬链接的区别是，此处的文件`A`通过软链接创建文件`B`，文件`B`指向的是文件`A`，而不是磁盘空间，相当于`B`是`A`的一个快捷方式

![软链接和硬链接](https://image-bucket-1307756649.cos.ap-chengdu.myqcloud.com/image/20251215220830199.png)

`pnpm`中软链接和硬链接都用到了：`pnpm`使用符号链接`Symbolic link`（软链接）来创建依赖项的嵌套结构，将项目的直接依赖符号链接到`node_modules`的根目录，直接依赖的实际位置在`.pnpm/<name>@<version>/node_modules/<name>`，依赖包中的每个文件再硬链接（Hard link）到`.pnpm store`。

> 也就是说，依赖使用软连接形式，软链接的文件指向硬链接

```text
项目根目录
└── node_modules/
    └── lodash  →→→ (软链接) →→→ .pnpm/lodash@4.17.21/node_modules/lodash
                                      │
                                      └── (这个 lodash 目录里的每个文件)
                                            ↓
                                       (硬链接) ←→ 全局 store 中的真实文件
                                            (如 ~/.pnpm-store/.../lodash/4.17.21/index.js)
```

## 发布一个自己的包

### 创建与发布

我们可以将自己开发的工具包发布到 npm 服务上，方便自己和其他开发者使用，操作步骤如下：

1. 创建文件夹，并创建文件 `index.js`， 在文件中声明函数，使用 `module.exports` 暴露
2. `npm` 初始化工具包，`package.json` 填写包的信息 (包的名字是唯一的，不能使用中文、大写，默认值是文件夹的名称，所以文件夹名称也不能使用中文和大写)
3. 注册账号 [https://www.npmjs.com/signup](https://www.npmjs.com/signup)
4. 激活账号 （ 一定要激活账号）
5. 修改为官方的官方镜像 (命令行中运行 `nrm use npm` )
6. 命令行下 `npm login` 填写相关用户信息
7. 命令行下 `npm publish` 提交包 👌

### 更新包

后续可以对自己发布的包进行更新，操作步骤如下

1. 更新包中的代码
2. 测试代码是否可用
3. 修改 `package.json` 中的版本号
4. 发布更新`npm publish`

### 删除包

执行如下命令删除包

`npm unpublish --force`

删除包需要满足一定的条件， [https://docs.npmjs.com/policies/unpublish](https://docs.npmjs.com/policies/unpublish)

1. 你是包的作者
2. 发布小于 24 小时
3. 大于 24 小时后，没有其他包依赖，并且每周小于 300 下载量，并且只有一个维护者

## npx 和 npm run 命令

### npx 的工作原理

npx 是 Node Package Executor，它是从 npm 5.2.0 版本 ​ 开始与 npm 一起捆绑发布的命令行工具。它的主要作用是在不全局安装包的情况下，直接运行 npm 注册表中的包。它有几个好处：

- 避免全局安装，减少环境污染：当你运行 `npx <某个包>`时，`npx` 会首先检查这个包是否已经在你的本地项目依赖 (`node_modules`) 或全局安装中存在。如果没有找到，`npx` 会从 `npm` 仓库临时下载这个包的最新版本，在一个临时的目录中安装它，然后执行它。执行完成后，这个临时安装的包会被自动清理掉，不会留在你的系统中。这避免了全局安装大量只用一次的工具。
- 运行指定版本的包：你可以指定特定版本，例如：`npx create-react-app@5.0.0 my-app`。这比先全局安装/卸载某个版本要方便得多。

### npx 和 npm run 的区别

npx 和 npm run 都是 npm（Node.js 包管理器）提供的命令行工具，但它们的用途、工作方式和使用场景完全不同。下面用清晰的对比帮你彻底理解两者的区别：

| 特性               | `npm run`                                 | `npx`                                 |
| :----------------- | :---------------------------------------- | :------------------------------------ |
| **目的**           | 运行 `package.json` 中定义的脚本          | 临时运行某个 npm 包（无论是否已安装） |
| **依赖配置**       | 必须在 `package.json` 的 `scripts` 中定义 | 无需任何配置，直接指定包名            |
| **是否安装包**     | 不安装新包（只用已安装的依赖）            | 如果未安装，会临时下载                |
