# 分库分表

一句话定位：分库分表是把「单库单表」拆成「多库多表」来分摊数据量与读写压力，解决单表数据量过大导致查询变慢、单库连接数与磁盘 IO 打满的问题，是大型互联网系统应对海量数据的核心架构手段。

## 基础篇

### 为什么会有分库分表（背景与痛点）

先理解一个前提：再强的单机数据库也有物理天花板。一台 MySQL 的性能瓶颈通常来自四个方面：

| 瓶颈 | 表现 | 一句话解释 |
| --- | --- | --- |
| **单表数据量过大** | 几千万行后即使走索引也慢 | B+ 树层级变高，单次查询磁盘 IO 次数变多 |
| **单库连接数打满** | 报错 `Too many connections` | MySQL 默认 `max_connections` 有限，连接池耗尽 |
| **单库磁盘 IO 打满** | 慢查询变多、CPU 飙高 | 磁盘吞吐有上限，读写都挤在一台机器 |
| **单表 DDL 锁表** | 加字段、加索引卡几小时 | 大表 `ALTER TABLE` 要重建整表，锁表时间长 |

其中「单表数据量过大」是最典型的触发信号。为什么数据量大了会慢？本质还是索引结构的问题：

::: tip 💡 面试题：为什么单表数据量大了就会慢？
一句话结论：数据量越大，B+ 树层级越高，单次查询磁盘 IO 越多，性能指数级下降。原因：B+ 树每层是一次磁盘 IO，千万级数据可能从 3 层涨到 4 层甚至更高，每多一层就多一次随机 IO；同时 buffer pool 放不下全部索引页，命中率下降，大量读直接落盘。
:::

### 分库分表到底分什么（概念澄清）

很多同学搞混「分库」「分表」，先明确四个动作：

| 动作 | 拆的是什么 | 典型场景 |
| --- | --- | --- |
| **分表** | 同一张表的数据行，拆到同一个库的多张物理表 | 单表数据量太大，但单库还能扛 |
| **分库** | 整张表按规则拆到多个数据库实例 | 单库连接数、磁盘 IO 打满 |
| **分库分表** | 既分库又分表，数据散落在 `库 × 表` 的矩阵里 | 海量数据 + 高并发，最常见形态 |
| **垂直拆分** | 按业务/字段拆（拆列） | 表太宽、业务耦合 |

实际生产里说的「分库分表」默认指**水平拆分 + 分库分表**，即同一张表的数据按分片键散列到多个库的多张表上。下面先讲清「垂直」和「水平」这两个方向。

### 垂直拆分

垂直拆分是「按业务维度拆」，分两种粒度。

**垂直分表：把一张宽表按字段拆成多张窄表。**

比如用户表字段太多：`id、username、password、nickname、avatar、signature、last_login_time、create_time、...` 其中「登录相关字段」频繁读写，「个人资料字段」偶尔读。拆成两张：

```
user_base（热数据，频繁访问）          user_profile（冷数据，偶尔访问）
┌─────────────────────────┐        ┌─────────────────────────┐
│ id (主键)               │◄───────│ id (主键，与 base 一致) │
│ username                │        │ nickname                │
│ password                │        │ avatar                  │
│ last_login_time         │        │ signature               │
└─────────────────────────┘        └─────────────────────────┘
```

- **好处**：热点字段集中在一张小表，单页能放更多行，IO 更少；DDL 只影响一张小表。
- **代价**：查询要跨表时得 JOIN 或应用层组装。

**垂直分库：按业务把表拆到不同的库。**

微服务架构下最自然：用户服务一个库、订单服务一个库、商品服务一个库。

```
单体大库                             微服务分库
┌─────────────────┐                 ┌──────────┐  ┌──────────┐  ┌──────────┐
│ user 表          │                 │ user 库   │  │ order 库  │  │ goods 库  │
│ order 表         │    ──────►      │ (用户服务) │  │ (订单服务) │  │ (商品服务) │
│ goods 表         │                 └──────────┘  └──────────┘  └──────────┘
└─────────────────┘
```

- **好处**：业务解耦、各自独立扩容、故障隔离。
- **代价**：跨库无法直接 JOIN、无法用本地事务，分布式事务随之而来。

**垂直拆分的优缺点小结：**

| 优点 | 缺点 |
| --- | --- |
| 表更窄，单页行数更多，IO 更少 | 关联查询要跨表/跨库，不能直接 JOIN |
| 冷热数据分离，热点表更小 | 分布式事务复杂度上升 |
| 业务解耦，独立扩容、故障隔离 | 拆得太碎会过度设计 |

::: tip 💡 面试题：垂直拆分和水平拆分有什么区别？
一句话结论：垂直拆是「按字段/业务拆，拆列」，水平拆是「按数据行拆，拆行」。原因：垂直解决的是表太宽、业务耦合的问题，水平解决的是单表数据量太大导致的性能瓶颈；两者解决的问题不同，实际项目经常同时使用。
:::

### 水平拆分

水平拆分是「按数据行拆」，把同一张表的数据按某个字段（分片键）散列到多个库/表。这是「分库分表」的主角。

**水平分表：同一库内，一张表拆成多张物理表。**

订单表按 `user_id` 取模拆成 4 张：`order_0`、`order_1`、`order_2`、`order_3`，`user_id % 4` 决定落到哪张表。

```
                    ┌─────────────┐
  INSERT 订单        │  路由规则    │  user_id % 4
  user_id = 1003 ──► │ user_id % 4 │ ──────────────►  order_3
                    └─────────────┘
order 大表（假设）      order_0   order_1   order_2   order_3
┌───────────────┐    ┌───────┐ ┌───────┐ ┌───────┐ ┌───────┐
│ 1000 万行      │    │ 250万 │ │ 250万 │ │ 250万 │ │ 250万 │
└───────────────┘    └───────┘ └───────┘ └───────┘ └───────┘
```

**水平分库：数据按规则拆到多个数据库实例。**

数据量大了、单库扛不住连接和 IO 时，把 `order_0`、`order_1` 放 A 库，`order_2`、`order_3` 放 B 库。

```
                     ┌─────────────┐
  user_id % 4        │  路由规则    │
  ─────────────────► │ user_id % 4 │
                     └──────┬──────┘
             ┌──────────────┴──────────────┐
             ▼                             ▼
      A 库 (db_0)                    B 库 (db_1)
      ┌──────────┐                   ┌──────────┐
      │ order_0  │                   │ order_2  │
      │ order_1  │                   │ order_3  │
      └──────────┘                   └──────────┘
```

**水平拆分的优缺点：**

| 优点 | 缺点 |
| --- | --- |
| 数据量分摊，单表永远保持小表 | 跨库 JOIN、跨分片排序分页变难 |
| 读写压力分摊到多台机器，可水平扩展 | 分布式 ID、分布式事务成为必须 |
| 理论上可以无限扩容 | 扩容（加机器）要迁移数据 |

### 什么时候分、什么时候不分（决策顺序）

分库分表是「重型武器」，代价极大（改造量大、中间件依赖、运维复杂、数据迁移难）。所以铁律是：

> **能不分就不分，先榨干单机的所有优化空间。**

优化顺序（由轻到重）：

```
1. SQL 优化 + 索引优化        ← 先看慢查询日志，加索引、改写 SQL
        ↓ 解决不了
2. 缓存                      ← 读多写少，上 Redis 扛读
        ↓ 解决不了
3. 读写分离                  ← 一主多从，读走从库
        ↓ 解决不了
4. 数据归档/冷热分离          ← 历史数据定期搬到归档表
        ↓ 还是解决不了
5. 垂直拆分                  ← 表太宽先拆列
        ↓ 还是解决不了
6. 水平拆分（分库分表）        ← 最后手段
```

判断信号（满足其一就要考虑）：

| 信号 | 参考阈值（经验值，非绝对） |
| --- | --- |
| 单表数据量 | 超过 **1000 万行**，且索引优化后仍慢 |
| 单库数据量 | 超过 **2~5 GB**（数据 + 索引），buffer pool 装不下 |
| 单库连接数 | 频繁逼近 `max_connections` 上限 |
| 磁盘 IO / CPU | 单库 IO 打满，业务高峰 CPU 持续高位 |
| DDL 成本 | 加字段、加索引要锁表几小时，无法接受 |

::: tip 💡 面试题：什么时候该分库分表？
一句话结论：单表千万级、单库连接打满或 IO 打满，且索引优化、缓存、读写分离、归档都解决不了时才分。原因：分库分表引入跨库 JOIN、分布式事务、分布式 ID 等一堆新问题，代价极高，能用简单方案解决绝不上分库分表。
:::

## 高级篇

### 分片键怎么选（分库分表设计的核心）

分片键（sharding key）决定了每一行数据落到哪个库哪张表，是整套设计的灵魂。选错了后面全得推倒重来。

选分片键的三条铁律：

1. **查询绝大多数都带这个字段** —— 不带分片键的查询会退化成「全分片扫描」，性能灾难。
2. **分布均匀** —— 避免某个分片特别大（数据倾斜），造成热点。
3. **稳定性高** —— 选了就别轻易改，改分片键 = 全量数据迁移。

订单场景的经典对比：

| 分片键 | 优点 | 缺点 |
| --- | --- | --- |
| `user_id` | 「查我的订单」不用跨库 | 商家查「店铺订单」要全分片扫 |
| `order_id` | 单条订单定位快、分布最均匀 | 查用户全部订单要全分片扫 |
| `merchant_id` | 商家查店铺订单快 | 用户端查自己订单要全分片扫 |

实际项目常按**主导查询方**选：C 端（用户侧）主导就选 `user_id`，B 端（商家侧）主导就选 `merchant_id`。如果两头都要高性能，可以用**基因法**（见原理篇）让 `order_id` 携带 `user_id` 信息，兼顾两边。

### 分片算法详解

分片算法是把「分片键的值」映射到「具体库表位置」的规则。主流四种：

#### 1. 取模 / 哈希分片

最经典、最常用。对分片键做哈希或直接取模，映射到 N 个分片。

```
分片位置 = hash(user_id) % N        # N 是分片总数（库表数量）

示例：N = 4，user_id = 1001
      1001 % 4 = 1  →  落到 order_1
```

| 优点 | 缺点 |
| --- | --- |
| 实现简单、一行就能算 | **扩容灾难**：N 一变，几乎所有数据都要重新路由 |
| 分布均匀（散列效果好时） | 无法做范围查询（连续 id 被散到不同分片） |
| 分片键是字符串也能用（先 hash） | 数据迁移成本高 |

#### 2. 范围分片

按分片键的值区间划分，比如按 `order_id` 或时间分。

```
order_0 : id ∈ [0, 1000万)
order_1 : id ∈ [1000万, 2000万)
order_2 : id ∈ [2000万, 3000万)
...
```

| 优点 | 缺点 |
| --- | --- |
| 扩容方便，新分片接在末尾即可 | **热点**：新数据总落在最后一个分片 |
| 天然支持范围查询（`id BETWEEN`） | 分布不均，历史分片冷、最新分片热 |
| 迁移时可整段搬 | 需要预估区间大小，边界难定 |

#### 3. 一致性哈希

为解决「取模扩容难」而生的算法，用**哈希环 + 虚拟节点**把节点变化的影响降到最小（原理篇详解）。

| 优点 | 缺点 |
| --- | --- |
| 扩容只迁移相邻一小段数据，成本低 | 实现复杂 |
| 节点下线只影响相邻节点 | 不配虚拟节点时容易分布不均 |

#### 4. 复合分片 / 基因法

用「一个字段编码另一个字段」的方式，让一个 ID 同时满足两个维度的路由。详见原理篇的「基因法」。

分片算法选型速查：

| 场景 | 推荐算法 |
| --- | --- |
| 数据量可控、短期不扩容、主键是 id | 取模/哈希 |
| 数据天然有序、要做范围查询、能接受热点 | 范围分片 |
| 节点频繁增减、追求平滑扩容 | 一致性哈希 |
| 既要按用户查又要按订单查 | 基因法/复合分片 |

### 分布式 ID（分库分表的第一道坎）

分库分表后，原来单库的自增主键（`AUTO_INCREMENT`）失效了——每个库各自自增，ID 必然重复。必须引入**全局唯一 ID** 方案。

| 方案 | 原理 | 优点 | 缺点 |
| --- | --- | --- |
| **雪花算法 Snowflake** | 时间戳 + 机器号 + 序列号拼 64 位 | 高性能、趋势递增、本地生成 | 依赖时钟，回拨会重复 |
| **数据库号段** | 每台机器批量取一段 id 缓存本地 | 严格递增、实现简单 | 用完要回 DB 取，有 DB 依赖 |
| **Redis 自增** | `INCR` 原子自增 | 简单、快 | 依赖 Redis，持久化丢数据会重复 |
| **UUID** | 随机生成 128 位 | 完全无依赖 | 无序、字符串长，作主键会页分裂 |
| **美团 Leaf / 百度 UidGenerator** | 雪花/号段的工业级封装 | 生产可用、带监控 | 引入组件，有一定复杂度 |

雪花算法是最常考、最常用的，64 位结构见原理篇。号段方案的代表是美团 Leaf 的 segment 模式，核心思想是「一次取一批、本地慢慢发」：

```
DB 里维护一张号段表： biz_tag, max_id, step
业务启动时： UPDATE id_segment SET max_id = max_id + 1000 WHERE biz_tag='order'
            （原子地「抢」到 [max_id+1, max_id+1000] 这一段）
本地缓存这段 id，用完后再次去 DB 抢下一段
```

::: tip 💡 面试题：分库分表后自增主键怎么办？
一句话结论：自增主键会重复，改用雪花算法或数据库号段生成全局唯一 ID。原因：各库各自 `AUTO_INCREMENT` 会撞号；雪花算法本地生成、趋势递增、不依赖 DB，是最主流的方案，但要注意时钟回拨问题。
:::

### 跨库 JOIN 怎么办

数据散到不同库后，`JOIN` 直接失效（SQL 层面跨库 JOIN 成本极高且不可用）。四种替代方案：

| 方案 | 做法 | 适用场景 |
| --- | --- | --- |
| **应用层组装** | 分多次查，代码里拼结果 | 数据量不大、调用链路简单 |
| **字段冗余** | 把常用的关联字段冗余到目标表 | 读多写少、冗余字段很少变 |
| **全局表 / 广播表** | 每个库都放一份全量小表 | 字典表、配置表这类小表 |
| **ER 表绑定** | 关联紧密的表用同一分片键，路由到同一分片 | 订单 + 订单明细 |

其中「**ER 表绑定**」是分库分表设计里非常关键的一个思想：把关联紧密的两张表（如订单表和订单明细表）用**同一个分片键**（都按 `order_id` 分），这样同一订单的主表和明细表天然落在同一分片，直接 JOIN 就不跨库了。

```
订单表 order       按 order_id 分片
订单明细 order_item 按 order_id 分片   ← 同一个 order_id 落在同一个库，JOIN 不跨库
```

### 分布式事务怎么办

一次操作跨多个库，本地事务（`@Transactional` + 单库）失效，需要分布式事务方案。常见三种：

| 方案 | 原理 | 一致性 | 性能 | 代表 |
| --- | --- | --- | --- | --- |
| **2PC / XA** | 两阶段提交，先 prepare 再 commit | 强一致 | 低（锁资源久） | MySQL XA |
| **TCC** | Try-Confirm-Cancel 三段式补偿 | 最终一致（业务可控） | 中 | Seata TCC |
| **最终一致性（消息）** | 本地事务 + 事务消息，异步补偿 | 最终一致 | 高 | RocketMQ 事务消息 |
| **AT 模式** | 自动生成回滚日志（undo log），一阶段直接提交 + 全局锁 | 最终一致 | 高 | Seata AT |

分库分表场景下最常用的是 **Seata 的 AT 模式**（侵入小、性能尚可）或**消息最终一致性**（吞吐最高）。AT 模式的原理在原理篇展开。

::: tip 💡 面试题：跨库事务怎么处理？
一句话结论：本地事务失效，用 Seata 的 AT/TCC 模式或消息最终一致性解决。原因：一次操作跨多个库，无法用单库的 undo log 保证原子性；Seata AT 通过全局事务协调 + 自动回滚日志实现最终一致，侵入小，是分库分表下的主流选择。
:::

### 跨分片分页与排序

跨分片做全局 `ORDER BY ... LIMIT`，不能简单地把每个分片的前 N 条拼起来（那只是「每个分片内」的前 N，不是「全局」的前 N）。

正确做法：

```
全局取前 10 条（ORDER BY create_time DESC LIMIT 10）：
1. 每个分片都取前 10 条
2. 把 N 个分片的 N×10 条拉到内存合并
3. 全局排序后再取前 10 条
```

但分片越多，这个「N×pageSize」越大，内存和网络开销越高。分页越深越糟（`LIMIT 1000, 10` 要每个分片取 1010 条）。工业界的替代方案：

| 方案 | 做法 | 适用场景 |
| --- | --- | --- |
| **禁止深分页** | 只允许「上翻下翻」或限制最大页码 | 大多数业务够用 |
| **搜索引擎** | 数据同步到 ES，用 ES 做全局分页排序 | 需要复杂检索、全文搜索 |
| **宽表 / 预聚合** | 把需要全局排序的场景单独建一张宽表或聚合表 | 排序字段固定、写多读少 |
| **游标分页** | 用 `WHERE create_time < 上一条` 代替 `OFFSET` | 时间线类数据 |

::: tip 💡 面试题：跨分片分页排序怎么做？
一句话结论：每个分片取前 N 条，内存里合并排序取全局前 N 条，深分页用搜索引擎或宽表解决。原因：全局排序必须看到所有分片的数据，无法只靠单个分片得到全局正确结果；数据量大时把检索压力转移到 ES，而不是硬扛数据库。
:::

### 聚合统计怎么办

跨分片的 `COUNT`、`SUM`、`AVG`、`MAX/MIN` 同样要在每个分片算一遍，再在应用层合并：

- `COUNT` / `SUM`：各分片求和再相加。
- `AVG`：各分片求 `SUM` 和 `COUNT`，再 `SUM_total / COUNT_total`（不能直接对分片 AVG 求平均）。
- `MAX` / `MIN`：各分片取极值再取全局极值。

数据量大、要实时统计的场景，通常引入 **OLAP 体系**（把数据同步到 ClickHouse / Doris 之类做分析），不让分片库承担聚合压力。

### ShardingSphere 实战（完整可运行示例）

分库分表中间件里，国内最主流的是 **Apache ShardingSphere**，提供两种形态：

| 形态 | 说明 | 部署方式 |
| --- | --- | --- |
| **ShardingSphere-JDBC** | 以 jar 包方式嵌入应用，应用直连各分片库 | 轻量，无额外部署 |
| **ShardingSphere-Proxy** | 独立代理服务，应用连它就像连 MySQL | 独立进程，跨语言通用 |

下面以 **ShardingSphere-JDBC + Spring Boot** 演示「订单表按 user_id 分库分表」的完整配置。

**场景：** `order` 表按 `user_id` 取模，拆到 2 个库（`db_0`、`db_1`）各 2 张表（`order_0`、`order_1`）。

**步骤 1：引入依赖（pom.xml）**

```xml
<dependency>
    <groupId>org.apache.shardingsphere</groupId>
    <artifactId>shardingsphere-jdbc-core-spring-boot-starter</artifactId>
    <version>5.4.1</version>
</dependency>
```

**步骤 2：application.yml 配置分片规则**

```yaml
spring:
  shardingsphere:
    datasource:
      names: db0, db1   # 两个物理库
      db0:
        type: com.zaxxer.hikari.HikariDataSource
        driver-class-name: com.mysql.cj.jdbc.Driver
        jdbc-url: jdbc:mysql://localhost:3306/db_0?serverTimezone=Asia/Shanghai
        username: root
        password: root
      db1:
        type: com.zaxxer.hikari.HikariDataSource
        driver-class-name: com.mysql.cj.jdbc.Driver
        jdbc-url: jdbc:mysql://localhost:3306/db_1?serverTimezone=Asia/Shanghai
        username: root
        password: root
    rules:
      sharding:
        tables:
          order:                              # 逻辑表名
            actual-data-nodes: db$->{0..1}.order_$->{0..1}   # 实际 2 库 × 2 表 = 4 张
            database-strategy:                # 分库策略
              standard:
                sharding-column: user_id      # 分库分片键
                sharding-algorithm-name: db-inline
            table-strategy:                   # 分表策略
              standard:
                sharding-column: user_id      # 分表分片键（同一个字段）
                sharding-algorithm-name: table-inline
        sharding-algorithms:
          db-inline:                          # 库分片算法：user_id % 2
            type: INLINE
            props:
              algorithm-expression: db_$->{user_id % 2}
          table-inline:                       # 表分片算法：user_id % 2
            type: INLINE
            props:
              algorithm-expression: order_$->{user_id % 2}
    props:
      sql-show: true                          # 打印实际路由到的真实 SQL，便于调试
```

**步骤 3：业务代码照常写逻辑表名**

```java
@Service
public class OrderService {

    @Resource
    private JdbcTemplate jdbcTemplate;

    // 关键点：SQL 里写的是「逻辑表名 order」，不是 order_0/order_1
    // ShardingSphere 会在执行前拦截 SQL，按 user_id 自动改写为真实的库表
    public void insert(long userId, long orderId, BigDecimal amount) {
        String sql = "INSERT INTO `order` (order_id, user_id, amount) VALUES (?, ?, ?)";
        jdbcTemplate.update(sql, orderId, userId, amount);
    }

    public List<Map<String, Object>> listByUser(long userId) {
        // 查询带了分片键 user_id，ShardingSphere 能精确定位到唯一库表，不跨库
        String sql = "SELECT * FROM `order` WHERE user_id = ?";
        return jdbcTemplate.queryForList(sql, userId);
    }

    public long countAll() {
        // 不带分片键的聚合，会路由到全部 4 张表，再在内存合并
        String sql = "SELECT COUNT(*) FROM `order`";
        return jdbcTemplate.queryForObject(sql, Long.class);
    }
}
```

**为什么写逻辑表名就能路由？** ShardingSphere 在 JDBC 层做了 SQL 解析 → 路由改写 → 执行 → 结果归并的全流程，对应用完全透明（原理篇详述）。

**自定义分片算法（SPI）：** 内置的 `INLINE` 只够做取模。复杂规则可以自定义：

```java
// 实现 ShardingAlgorithm，返回真实分片名
public final class UserIdHashModAlgorithm implements StandardShardingAlgorithm<Long> {

    @Override
    public String doSharding(Collection<String> availableTargetNames,
                             PreciseShardingValue<Long> shardingValue) {
        long userId = shardingValue.getValue();      // 拿到分片键的值
        // 先用 hash 打散，再取模，避免连续 id 落到同一分片
        long idx = (userId ^ (userId >>> 16)) % availableTargetNames.size();
        for (String name : availableTargetNames) {
            if (name.endsWith("_" + idx)) {          // 匹配 order_0、order_1 ...
                return name;
            }
        }
        throw new UnsupportedOperationException("找不到分片");
    }

    @Override
    public Collection<String> doSharding(Collection<String> availableTargetNames,
                                         RangeShardingValue<Long> shardingValue) {
        // 范围查询（BETWEEN）时，无法精确定位，退回全分片
        return availableTargetNames;
    }

    @Override
    public String getType() {
        return "USER_ID_HASH_MOD";                    // SPI 注册名，yml 里引用
    }
}
```

## 原理篇

### 雪花算法：64 位 ID 的字节级内存布局

雪花算法（Snowflake）是分布式 ID 的标杆，核心是把一个 `long`（64 位）拆成四段，各段各司其职：

```
 1 bit        41 bit                  10 bit            12 bit
┌────┬────────────────────────────┬──────────────┬─────────────────┐
│符号│       毫秒时间戳            │   机器 ID     │     序列号       │
│ 0  │  (从起始时间到现在的毫秒)    │ (节点/进程)   │ (同毫秒内自增)    │
└────┴────────────────────────────┴──────────────┴─────────────────┘
 63   62                         22  21         12  11              0
```

各段含义：

| 段 | 位数 | 作用 | 说明 |
| --- | --- | --- | --- |
| 符号位 | 1 bit | 恒为 0 | 保证生成的 ID 是正数（`long` 首位为 1 是负数） |
| 时间戳 | 41 bit | 距起始时间的毫秒数 | 可用约 69 年（`2^41 ≈ 2.2 万亿` 毫秒） |
| 机器 ID | 10 bit | 区分节点 | 最多 1024 个节点（可拆成 5+5：机房 + 机器） |
| 序列号 | 12 bit | 同一毫秒内的自增序号 | 每毫秒最多 4096 个（`2^12`） |

**为什么它「趋势递增」？** 时间戳在高位、序列号在低位，同一毫秒内靠序列号递增，跨毫秒靠时间戳递增，所以整体 ID 是单调递增的（但严格说不是「全局严格递增」，因为不同机器时钟可能有偏差）。

**为什么性能高？** 整个 ID 在**本地内存**里用位运算拼出来，不依赖任何网络或数据库调用：

```java
public class Snowflake {
    // 各部分占的位数
    private final long workerIdBits = 5L;   // 机器 ID 用 5 位（示例）
    private final long sequenceBits = 12L;  // 序列号 12 位
    private final long maxWorkerId = ~(-1L << workerIdBits); // 31

    // 各部分左移的位数（关键：段与段之间用位移错开）
    private final long workerIdShift = sequenceBits;             // 12
    private final long timestampShift = sequenceBits + workerIdBits; // 17

    private final long epoch = 1700000000000L;   // 起始时间戳（自定义）
    private final long sequenceMask = ~(-1L << sequenceBits); // 4095

    private long workerId;
    private long sequence = 0L;
    private long lastTimestamp = -1L;

    public synchronized long nextId() {
        long timestamp = System.currentTimeMillis();

        // 1. 时钟回拨检测：时间比上次还小，说明系统时钟被拨回去了
        if (timestamp < lastTimestamp) {
            throw new RuntimeException("时钟回拨，拒绝生成 ID: "
                + (lastTimestamp - timestamp) + "ms");
        }

        if (timestamp == lastTimestamp) {
            // 2. 同一毫秒：序列号 +1，低位直接累加
            sequence = (sequence + 1) & sequenceMask;
            if (sequence == 0) {            // 序列号用满（4096 个），等下一毫秒
                timestamp = waitNextMillis(lastTimestamp);
            }
        } else {
            // 3. 新的毫秒：序列号归零
            sequence = 0L;
        }
        lastTimestamp = timestamp;

        // 4. 三段用「或运算」拼成一个 64 位 long（关键一步）
        //    (时间戳 << 17) 高位是时间 | (机器id << 12) 中间是机器 | 序列号 低位
        return ((timestamp - epoch) << timestampShift)
             | (workerId << workerIdShift)
             | sequence;
    }

    private long waitNextMillis(long last) {
        long t = System.currentTimeMillis();
        while (t <= last) {
            t = System.currentTimeMillis();   // 忙等，直到时钟追上来
        }
        return t;
    }
}
```

**时钟回拨是雪花算法的最大软肋**：如果机器时钟被 NTP 校准往回拨，时间戳变小，可能生成重复 ID。工业界的应对：

| 方案 | 思路 |
| --- | --- |
| 拒绝服务 | 回拨就抛异常（简单粗暴，可能影响可用性） |
| 等时钟追平 | 忙等直到时钟恢复到上次时间 |
| 用「回拨记录」容忍 | 百度 UidGenerator 记录回拨，借未来的序列号 |
| 改用号段/Leaf | 根本不用时钟，绕开问题 |

::: tip 💡 面试题：雪花算法为什么可能重复？怎么解决？
一句话结论：时钟回拨会导致时间戳变小，可能生成重复 ID。原因：雪花算法依赖「时间戳单调递增」的前提，一旦系统时钟被 NTP 往回拨，同一毫秒 + 同一序列号就会撞号；解决靠回拨检测（抛异常/忙等/借序列号），或干脆用不依赖时钟的号段方案。
:::

### 一致性哈希：扩容只迁移一小段的原理

取模分片（`hash(key) % N`）扩容难的根源是：N 变化后，**取模结果全部重算**，几乎所有数据都要搬家。一致性哈希用「哈希环」解决这个问题。

**哈希环结构：**

把哈希值的取值范围（如 `0 ~ 2^32 - 1`）首尾相接成一个环，节点和数据都哈希到环上的位置：

```
             哈希环 (0 ~ 2^32-1 首尾相连)
                    0
                   / \
                 /     \
        node A ●       ● node B
              /           \
             |             |
             |             |
        node C ●       ● node D
                   \     /
                    \   /
                  2^32-1

规则：数据 key 哈希到环上后，顺时针找第一个节点，就是它归属的节点
     key 落在 node A 和 node B 之间 → 归 node B 管
```

**扩容只影响相邻节点：** 新增节点 E 插到环上后，只有「E 到它逆时针上一个节点」之间这一小段数据需要从原节点迁移到 E，其余数据纹丝不动。

```
        扩容前                扩容后（新增 node E）
   node A ── node B        node A ── node E ── node B
   (A~B 之间数据归 B)       (A~E 之间数据归 E，E~B 之间仍归 B)
                            ← 只有 A~E 这一小段要迁移到 E
```

**虚拟节点解决分布不均：** 物理节点少时，哈希位置可能聚在一起，导致数据倾斜。给每个物理节点分配 N 个「虚拟节点」（`nodeA-1、nodeA-2、nodeA-3 ...`），把这些虚拟节点打散到环上，数据就均匀多了。

```
物理节点少、分布不均          加虚拟节点后打散
    A                          A-1        B-2
      \                        B-1   A-2     A-3
       \                       C-1   C-2  B-3  C-3
        B  C   ← 挤在一起       ← 均匀铺满整个环
```

::: tip 💡 面试题：为什么取模扩容难，一致性哈希扩容容易？
一句话结论：取模的分片位置依赖分片总数 N，N 一变几乎全部数据重新路由；一致性哈希的分片位置只依赖哈希环上的相邻节点，加节点只影响相邻一小段。原因：取模是「整体重排」，一致性哈希是「局部重排」，因此一致性哈希迁移成本低得多。
:::

### 基因法：一个 ID 同时满足两个分片维度

前面的矛盾是：订单按 `order_id` 分片，则「查我的订单」要全分片扫；按 `user_id` 分片，则「单点查订单」定位慢。基因法让 `order_id` 里**嵌入 user_id 的「基因」**，两头都能精确路由。

**核心思想：** 生成 `order_id` 时，把 `user_id % N` 的结果「注入」到 order_id 的二进制末位，这样 `order_id % N == user_id % N`，两者指向同一分片。

```
假设 N = 4（分 4 张表），user_id = 1003

步骤 1：取 user_id 的「基因」  = user_id % 4 = 1003 % 4 = 3（二进制 11）
步骤 2：生成 order_id 时，把末 2 位强制写成「11」：
        order_id = (snowflake 生成的 id 左移 2 位) | 3
步骤 3：于是 order_id % 4 恒等于 3 == user_id % 4

结果：
  按 user_id 路由 → user_id % 4 = 3 → order_3
  按 order_id 路由 → order_id % 4 = 3 → order_3
  两个维度都精确落到同一张表 ✓
```

```
order_id 二进制结构（末 2 位是 user_id 的基因）
┌───────────────────────────────┬────────┐
│  雪花算法生成的高位（时间+机器+序列） │ 基因(2bit)│
└───────────────────────────────┴────────┘
                                  ↑ 等于 user_id % 4
```

**代价：** 注入 N 位基因，等于把 id 的低 N 位「征用」了，牺牲了一点 ID 的连续性；且分片数 N 必须是 2 的幂（才能用位运算对齐）。

::: tip 💡 面试题：既想按用户查、又想按订单查，分片键怎么设计？
一句话结论：用基因法让 order_id 携带 user_id 的分片信息，两个字段都能精确路由到同一分片。原因：把 `user_id % N` 的结果写入 order_id 的低位，使两者取模结果一致，从而在不牺牲单点查询的前提下支持「查我的订单」。
:::

### ShardingSphere 路由执行原理

ShardingSphere-JDBC 能「透明分片」的关键，是它在 JDBC 层拦截并改写了 SQL。完整流程：

```
应用代码： jdbcTemplate.update("INSERT INTO order ...", ...)
                        │
                        ▼
┌─────────────────────────────────────────────────────────────┐
│ ShardingSphere-JDBC（以 jar 形式嵌入应用进程内）              │
│                                                             │
│  ① SQL 解析   ──► 词法/语法分析，得到逻辑表名、字段、条件      │
│         │                                                   │
│         ▼                                                   │
│  ② SQL 路由   ──► 根据分片键 + 分片算法，算出目标库表          │
│         │        （user_id=1003 → db_1.order_1）            │
│         ▼                                                   │
│  ③ SQL 改写   ──► 把逻辑表名替换成真实表名，补全列、分页改写    │
│         │        （order → order_1）                         │
│         ▼                                                   │
│  ④ SQL 执行   ──► 通过真实数据源把改写后的 SQL 发到各分片库      │
│         │                                                   │
│         ▼                                                   │
│  ⑤ 结果归并   ──► 把多分片结果合并、排序、聚合、分页后返回        │
└─────────────────────────────────────────────────────────────┘
                        │
                        ▼
                应用拿到最终结果（仿佛只有一张 order 表）
```

五个阶段的作用与关键点：

| 阶段 | 做什么 | 关键点 |
| --- | --- | --- |
| **SQL 解析** | 解析出逻辑表、分片键、查询条件 | 只解析支持分片的 SQL，复杂 SQL 可能不解析直接透传 |
| **SQL 路由** | 算出要访问哪些真实库表 | 带分片键=精确路由（1 张表）；不带=全路由（所有表） |
| **SQL 改写** | 逻辑表名 → 真实表名，修正分页/主键 | `ORDER BY ... LIMIT` 会被改写成各分片独立取再归并 |
| **SQL 执行** | 并行/串行执行真实 SQL | 走独立线程池，各分片并发查询 |
| **结果归并** | 合并排序、聚合、分页 | 内存归并是分片数多时的性能瓶颈 |

**为什么它「无侵入」？** 它实现的是 JDBC 标准接口（`DataSource`、`Connection`、`Statement`），应用以为自己在连一个普通 MySQL，实际上连接的是 ShardingSphere 的「逻辑数据源」，底层再分发给真实分片库。这和 MyBatis 拦截 SQL 是同一个思路——都在「应用和真实数据库之间」插入一层。

### 分布式事务 Seata AT 模式的原理

Seata AT 模式是分库分表场景下最常用的分布式事务方案，核心是「**全局事务协调 + 自动生成回滚日志**」。

**三个角色：**

```
         ┌────────────┐
         │    TC       │  Transaction Coordinator（事务协调者，Seata Server）
         │ 全局事务管理  │  负责维护全局事务状态、下发回滚指令
         └──────┬─────┘
                │
        ┌───────┴────────┐
        ▼                ▼
  ┌──────────┐      ┌──────────┐
  │    TM     │      │    RM     │
  │ 事务发起方 │      │ 资源管理器 │
  │ (业务入口) │      │ (各分片库) │
  └──────────┘      └──────────┘
```

**AT 模式执行流程：**

```
全局事务（下单 → 减库存，两个库）：

  ①  TM 向 TC 申请开启全局事务，拿到全局事务 ID（XID）
  ②  分支一：扣订单库（RM-1）执行本地 SQL
        └ 执行前 Seata 记录「前镜像」before image（改前的数据）
        └ 执行后记录「后镜像」after image（改后的数据）
        └ 把前后镜像 + SQL 存成 undo log（回滚日志），并注册分支到 TC
  ③  分支二：减库存库（RM-2）同样执行 + 记 undo log + 注册
  ④  两个分支都提交本地事务（注意：这里就提交了，不是两阶段锁着）
  ⑤  全部成功 → TM 通知 TC 全局提交 → 各 RM 异步删除 undo log
      任一失败 → TC 通知各 RM 全局回滚 → 用 undo log 做反向补偿
```

**关键点：**

- **一阶段直接提交本地事务**（不像 XA 两阶段锁着资源），所以性能比 XA 高。
- **回滚靠 undo log 反向补偿**：把 after image 还原成 before image，即「补偿」而非「物理回滚」。
- **代价**：undo log 会有写放大（每个事务多记一份前后镜像），且存在中间态（本地已提交但全局未提交），靠**全局锁**防止脏读。

### 全局唯一 ID 方案深度对比（选型落地）

把前面提到的方案放到一张「落地决策表」里：

| 维度 | 雪花算法 | 数据库号段 | Redis 自增 | UUID |
| --- | --- | --- | --- | --- |
| 性能 | 极高（本地生成） | 高（批量缓存） | 高 | 极高 |
| 趋势递增 | 是 | 严格递增 | 严格递增 | 否 |
| 依赖 | 无（本地时钟） | DB | Redis | 无 |
| 时钟回拨风险 | 有 | 无 | 无 | 无 |
| 单调/连续性 | 趋势递增、不连续 | 严格连续 | 严格连续 | 完全随机 |
| 作主键友好度 | 好（趋势递增利于索引） | 最好（严格递增） | 最好 | 差（随机导致页分裂） |
| 复杂度 | 中 | 低 | 低 | 极低 |

**选型建议：**

```
追求简单、严格递增、能接受 DB 依赖        → 数据库号段（Leaf segment）
追求高性能、无外部依赖、趋势递增即可        → 雪花算法（注意时钟回拨）
追求极致简单、对 ID 无序无所谓（非主键）    → UUID
雪花 + 号段都要、且要生产级监控/容灾         → 美团 Leaf 双模式
```

::: tip 💡 面试题：各种分布式 ID 方案怎么选？
一句话结论：默认雪花算法（高性能、趋势递增、无依赖），需要严格递增就用数据库号段，只做唯一标识不管有序就用 UUID。原因：雪花算法本地生成无 IO 开销，号段保证严格递增最适合做主键，UUID 无序会导致 B+ 树页分裂、插入性能差。
:::

## 面试常问

1. **什么时候该分库分表？**
   结论：单表千万级、单库连接打满或 IO 打满，且索引、缓存、读写分离、归档都解决不了时才分。
   展开：分库分表代价极高，会引入跨库 JOIN、分布式事务、分布式 ID 等新问题；能不分就不分，先榨干单机优化空间，实在不行再上水平拆分。

2. **垂直拆分和水平拆分有什么区别？**
   结论：垂直拆「列」（按字段/业务），水平拆「行」（按数据散列）。
   展开：垂直解决表太宽和业务耦合，水平解决单表数据量太大；两者解决不同问题，大项目常同时用（先垂直再水平）。

3. **分片键怎么选？**
   结论：选高频查询字段、分布均匀、稳定不常变，如订单场景的 `user_id`。
   展开：不带分片键的查询会退化成全分片扫描，分片键分布不均会产生热点，改分片键等于全量迁移；订单场景常用 `user_id` 或基因法设计的 `order_id`。

4. **取模分片和一致性哈希有什么区别？为什么取模扩容难？**
   结论：取模结果依赖分片总数 N，N 一变几乎全部数据重路由；一致性哈希用哈希环，加节点只影响相邻一小段。
   展开：取模是「整体重排」，一致性哈希是「局部重排」；一致性哈希再配合虚拟节点解决分布不均，是频繁扩缩容场景的首选。

5. **分库分表后自增主键怎么办？**
   结论：自增主键会重复，改用雪花算法或数据库号段生成全局唯一 ID。
   展开：雪花算法本地生成、趋势递增、无 DB 依赖，是主流，但要注意时钟回拨；号段方案严格递增，最适合做主键，代表是美团 Leaf。

6. **跨库 JOIN 怎么办？**
   结论：用应用层组装、字段冗余、全局表、或 ER 表绑定四种方式替代。
   展开：ER 表绑定让关联紧密的表用同一分片键路由到同一分片，直接 JOIN 不跨库，是最优雅的做法；跨分片强制 JOIN 会全分片扫，代价不可接受。

7. **跨库事务怎么处理？**
   结论：用 Seata 的 AT/TCC 模式或消息最终一致性。
   展开：本地事务跨库失效；Seata AT 一阶段直接提交、靠 undo log 反向补偿，侵入小、性能尚可，是分库分表下的主流；追求最高吞吐可选 RocketMQ 事务消息做最终一致。

8. **跨分片分页和聚合怎么做？**
   结论：每个分片取前 N 条，内存合并排序取全局前 N；聚合则各分片算完再合并。
   展开：深分页和实时统计开销巨大，数据量大时把检索和分析下放到 ES / ClickHouse，不让分片库扛。
