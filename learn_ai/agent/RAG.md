# RAG

一句话定位：RAG（Retrieval-Augmented Generation，检索增强生成）是在大模型生成答案之前，先从外部知识库检索出与问题相关的文档片段，再把这些片段拼进提示词一起喂给模型，让模型「照着资料回答」，解决「模型不知道私有数据、知识过期、一本正经胡说八道（幻觉）」三大问题。

---

## 基础篇

### 为什么需要 RAG

大模型（LLM）有三大天然缺陷，RAG 就是冲着它们来的。先看这三条缺陷各自「卡」在哪，再理解 RAG 为什么是最经济的解法。

| 缺陷 | 具体表现 | 举例 | RAG 怎么解决 |
| --- | --- | --- | --- |
| 知识截止 | 模型只学训练截止日之前的数据，之后发生的事一律不知道 | 问「2025 年最新发布的手机型号」答不上 | 外部知识库可实时更新，检索最新文档 |
| 私有数据 | 模型没见过公司内部文档、业务数据、个人资料 | 问「我们公司的报销制度是什么」答不上 | 把私有文档切分入库，按需检索喂给模型 |
| 幻觉 | 不知道也编得一本正经，还无法溯源 | 编一个不存在的 API、虚构的论文 | 答案有检索到的原文做依据，可给出出处 |

这三条缺陷的**共同根源**是：模型的知识是「训练时固化进权重」的，一旦训练完就「冻结」了。想让它掌握新知识，只有三条路，对比一下成本和灵活性：

| 方案 | 做法 | 成本 | 灵活性 | 更新方式 | 适用场景 |
| --- | --- | --- | --- | --- | --- |
| 提示词工程（Prompt） | 直接把资料塞进 prompt | 最低 | 受上下文长度限制 | 每次提问手动粘贴 | 少量、一次性资料 |
| RAG | 检索相关资料后拼 prompt | 低 | 知识库可随时增删改 | 改库即可，无需重训 | 私有知识问答、企业文档 |
| 微调（Fine-tuning） | 用新数据继续训练模型权重 | 高 | 改知识需重新训练 | 重新训练模型 | 改变模型风格/格式/领域能力 |

**一句话总结选择策略**：想让模型「知道新事实」用 RAG；想让模型「改变说话方式、输出格式、领域风格」用微调；资料很少且只用一次，直接塞 prompt。

::: tip 💡 面试题：RAG 和微调的区别？
RAG 是「外挂知识、不改模型」，微调是「改模型权重、内化知识」。RAG 更新快、成本低、可溯源、知识库可插拔，但每次推理多一步检索，且吃上下文窗口；微调不占上下文、推理快、能改风格，但成本高、更新难、容易灾难性遗忘。实际工程里两者常配合使用：微调定「格式和语气」，RAG 供「实时事实」。
:::

### 什么是 RAG

RAG 的核心思想可以用一句话概括：**把模型从「闭卷考试」变成「开卷考试」**。

- 普通 LLM 回答 = 闭卷：只凭脑子里（权重里）记得的东西答，忘了/没学过就瞎编。
- RAG 回答 = 开卷：先到资料库里翻出相关章节，摆在面前照着答，还能标出「答案出自第几页」。

形式化定义：给定问题 `q`，RAG 先通过检索器 `Retriever` 从外部语料库 `D` 中召回 top-k 个相关片段 `{d1, d2, ..., dk}`，再把这些片段作为上下文和问题一起交给生成模型 `Generator`，得到答案 `a`：

```
a = LLM( prompt(q, {d1, d2, ..., dk}) )
```

其中 `prompt` 负责把「问题 + 检索到的资料 + 指令约束」拼装成一个完整的提示词。检索器是 RAG 的灵魂，它决定了「模型能看到哪些资料」，检索错了，后面生成得再漂亮也是错的。

### RAG 整体架构

一条完整的 RAG 系统，从「原始文档」到「最终答案」，可以分成**离线索引**和**在线检索生成**两个阶段。用一张 ASCII 图把全链路画出来：

```
┌─────────────────────────────── 离线索引（准备阶段，只做一次） ───────────────────────────────┐
│                                                                                              │
│   原始文档           切分                 向量化               写入                           │
│  (PDF/网页/DB) ──►  Chunking ──►  Embedding ──►  向量数据库                                    │
│   "员工手册.pdf"     切成 N 段      每段→向量      [vec, text, metadata]                       │
│                                                                                              │
└──────────────────────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────── 在线检索生成（每次提问都走一遍） ───────────────────────────────┐
│                                                                                              │
│   用户问题           向量化               检索                 拼装 Prompt          生成      │
│  "报销流程?" ──►  Embedding ──►  向量库 top-k ──►   [问题+资料+指令] ──►  LLM ──►  答案       │
│                  (同一模型)      找最相似 k 段        "根据以下资料回答..."                       │
│                                                                                              │
└──────────────────────────────────────────────────────────────────────────────────────────────┘
```

两个阶段是**解耦**的：离线阶段建好的索引可以被无数次在线查询复用，这是 RAG 成本低的关键——索引只建一次，之后每次提问只是「查一下 + 生成一下」，不用重复切分和向量化。

### RAG 的两阶段流程详解

**阶段一：离线索引（写库）**

这是「准备食材」的过程，核心目标是：把五花八门的原始文档，变成「向量库能检索、模型能读」的标准片段。完整流程：

```
1. 加载（Load）     从 PDF/网页/数据库/API 读入原始文本，并抽取出结构（标题、段落、表格）
2. 清洗（Clean）    去噪：去掉页眉页脚、乱码、无意义字符，统一格式
3. 切分（Chunk）    把长文档切成固定/语义的小块，块与块之间可选重叠
4. 向量化（Embed）  每个 chunk 用 Embedding 模型转成一个高维向量
5. 入库（Store）    把 [向量, 原文, 元数据(来源/标题/时间)] 一起写进向量数据库，并建立索引
```

**阶段二：在线检索生成（读库 + 生成）**

这是「现炒现吃」的过程，用户每次提问都实时走一遍：

```
1. 向量化（Embed）  把用户问题用「同一个 Embedding 模型」转成查询向量
2. 检索（Search）   在向量库中做相似度检索，取出 top-k 个最相关的 chunk
3. 重排（可选）     用更强的 Rerank 模型对 top-k 再排序，挑最相关的几条
4. 拼装（Prompt）   把「系统指令 + 检索到的原文 + 用户问题」拼成完整 prompt
5. 生成（Generate） LLM 基于上下文生成答案，通常还会要求模型标注出处
```

用一段可运行的伪代码把整个流程串起来：

```python
# 为什么分两步写：离线是"准备食材"，在线是"现炒现吃"。
# 索引只建一次，之后每次提问都复用，避免重复切分和向量化。

# ---------- 离线：建索引 ----------
def build_index(docs):
    chunks = split(docs, chunk_size=500, overlap=50)   # 切分，overlap 保留边界上下文
    vectors = [embed(c) for c in chunks]                # 每段转成向量
    vector_db.insert(chunks, vectors)                   # 文本+向量+元数据一起入库

# ---------- 在线：检索 + 生成 ----------
def ask(question):
    q_vec = embed(question)                             # 问题也要转成同一空间的向量
    hits = vector_db.search(q_vec, top_k=5)             # 找最相似的 5 段
    context = "\n".join([h.text for h in hits])         # 拼成上下文
    prompt = f"""请严格根据以下资料回答，资料没有答案就说不知道：

资料：
{context}

问题：{question}"""
    return llm(prompt)                                  # 带上下文生成
```

注意 `embed` 在离线阶段和在线阶段用的是**同一个模型**——这一点极其重要，原因会在[原理篇](#为什么向量相似能代表语义相近)展开：只有把 query 和文档放进同一个向量空间，算出来的距离才有意义。

### 核心组件体系

RAG 是一条「流水线」，每个环节是一个可替换的组件。理解每个组件的职责和主流选型，是搭好 RAG 的前提：

| 组件 | 职责 | 常见选型 | 选型要点 |
| --- | --- | --- | --- |
| 文档加载器（Loader） | 读取 PDF/网页/数据库等原始数据 | LangChain Loaders、LlamaIndex Readers | 能否正确解析表格、代码块、扫描件 |
| 文本切分器（Splitter） | 把长文档切成小块 chunk | 按字数 / 按语义 / 按结构切分 | 平衡语义完整与检索精准 |
| Embedding 模型 | 把文本映射成向量 | OpenAI text-embedding-3、BGE、M3E、bge-m3 | 维度、多语言能力、上下文长度 |
| 向量数据库 | 存向量 + 高效相似度检索 | Milvus、Chroma、pgvector、FAISS | 见[向量数据库](/learn_ai/agent/向量数据库) |
| 重排序模型（Rerank） | 对召回结果精排 | bge-reranker、Cohere Rerank | 精度 vs 延迟的权衡 |
| 生成模型（LLM） | 拿到上下文后生成答案 | GPT、DeepSeek、Qwen、GLM | 长上下文、指令遵循能力 |

这六个组件里，**Embedding 模型决定了检索质量的上限**，向量数据库只是「快速找到近邻」的容器；而**切分器是效果的第一道关口**，切不好后面全白搭。下面逐个展开最关键的几个。

### 文档加载（Loader）

文档加载器解决「原始数据从哪来、怎么变成干净文本」。真实世界的知识库来源五花八门：

| 数据源 | 加载器示例 | 注意事项 |
| --- | --- | --- |
| PDF | PyPDFLoader、PDFPlumber | 扫描版 PDF 是图片，需先 OCR |
| 网页 | WebBaseLoader、Playwright | 会混入导航栏、广告等噪声 |
| Word/PPT | Unstructured、python-docx | 表格、图片可能解析不完整 |
| Markdown/代码 | TextLoader | 保留代码块结构，别切成碎块 |
| 数据库 | 自定义 Loader | 直接 SQL 导出，结构最规整 |
| API/知识库 | 自研连接器 | 处理好分页和鉴权 |

加载阶段的核心任务是**保结构、去噪声**：标题层级、段落边界这些结构信息对后续切分极其重要，而页眉页脚、水印、导航栏这些噪声会污染向量，必须尽量剥离。一个通用建议是：**优先保留 Markdown 结构**（标题、列表、代码块），很多切分策略都依赖这些结构标记。

### 文档切分（Chunking）

切分是 RAG 效果的第一道关口，核心矛盾是**在「上下文完整」和「检索精准」之间找平衡**。

- **chunk 太大**：一段里信息多，但粒度粗，检索命中的片段可能含大量无关内容，还白白浪费宝贵的上下文窗口。
- **chunk 太小**：检索精准，但可能把一句话切两半，语义不完整，模型看不懂。

这个「平衡」可以用一张图直观理解：

```
文档原文：  「RAG 由检索和生成两部分组成。检索负责从知识库召回相关内容。
            生成负责基于召回内容给出答案。两者缺一不可。」

切分方式A（chunk 太小，语义被切断）：
  chunk1: 「RAG 由检索和生成两部分组成。检索负责从」  ← 话没说完
  chunk2: 「知识库召回相关内容。生成负责基于召回内容」  ← 上下文缺失
  chunk3: 「给出答案。两者缺一不可。」

切分方式B（chunk 合适，重叠保留边界）：
  chunk1: 「RAG 由检索和生成两部分组成。检索负责从知识库召回相关内容。」
  chunk2: 「检索负责从知识库召回相关内容。生成负责基于召回内容给出答案。两者缺一不可。」
            └──────── overlap 重叠区 ────────┘
```

常用的切分策略：

| 切分策略 | 做法 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- | --- |
| 固定长度 | 按 N 个字符/token 硬切 | 简单、快、可控 | 语义被切断 | 初步原型、结构简单的文本 |
| 重叠切分 | 相邻 chunk 重叠一部分（overlap） | 保留边界上下文 | 有冗余、存储增加 | 通用场景（几乎必配） |
| 按结构 | 按标题/段落/章节/代码块切 | 语义完整、易定位 | 依赖文档结构规范 | Markdown、结构化文档 |
| 语义切分 | 用模型判断断句位置 | 效果最好 | 慢、贵 | 高质量知识库 |
| 递归切分 | 先按大分隔符（段落），再按小分隔符（句）递归下探 | 尽量贴语义又保证长度 | 实现稍复杂 | 通用场景（主流默认） |

**实践中的经验值**：

- `chunk_size` 常用 **256~1024 token**（中文约 300~800 字），具体取决于文档类型和模型上下文长度。
- `overlap` 取 chunk_size 的 **10%~20%**，用于缓解边界切断问题。
- 切分后往往还要给每个 chunk 加上「父级标题/章节」作为元数据，检索命中时一起返回，帮模型定位（这就是「父子文档检索」的基础，见[高级篇](#父子文档检索)）。

::: tip 💡 面试题：chunk 大小怎么定？
chunk 不是越大越好也不是越小越好：大了检索钝、浪费上下文；小了语义碎、答不全。常见做法是小 chunk 检索保证精准 + 命中后回溯父级大 chunk 补全上下文，兼顾精度和完整性。经验值 256~1024 token、overlap 10%~20%。
:::

### Embedding 与相似度

Embedding（嵌入）是整个 RAG 检索的地基：它把「文本」映射成「高维向量」，让语义相近的文本在向量空间里也挨得近。

```
文本 "今天天气不错"  --Embedding-->  [0.12, -0.34, 0.98, ..., 0.41]   (1536 维)
文本 "今天是个好天"  --Embedding-->  [0.11, -0.31, 0.95, ..., 0.39]   ← 向量很接近

文本 "红烧肉怎么做"  --Embedding-->  [-0.78, 0.52, -0.11, ..., -0.62] ← 向量差很远
```

向量之间「像不像」用相似度度量来衡量，最常见的三种：

| 度量 | 公式 | 取值范围 | 特点 | 适用场景 |
| --- | --- | --- | --- | --- |
| 余弦相似度 | `cos = (A·B) / (|A|·|B|)` | [-1, 1] | 只看方向、忽略长度 | 文本语义（最常用） |
| 内积（点积） | `A·B = Σ a_i·b_i` | (-∞, +∞) | 受方向和模长双重影响 | 向量已归一化时（等价余弦） |
| 欧氏距离 | `sqrt(Σ (a_i-b_i)²)` | [0, +∞) | 越小越相似，对长度敏感 | 图像等对绝对距离敏感的场景 |

为什么文本语义默认用余弦相似度？因为「一句话说得长还是短」不该影响它的语义——「天气不错」和「天气不错啊天气不错啊天气不错」意思一样，但向量模长不同。余弦只看方向（夹角），正好屏蔽掉长度的影响。

::: tip 💡 面试题：为什么向量检索能「理解语义」，关键词检索不能？
向量检索靠 Embedding 把「语义相近」映射成「向量相近」，所以「怎么退钱」能召回「退款流程」；关键词检索只做字面匹配，同义词、改写、口语就匹配不上。但向量检索对精确词（型号、编号）反而容易漏，所以实际工程常用「向量 + 关键词」混合检索。
:::

### 关键词检索 vs 向量检索

这两路检索各有盲区，理解它们的互补关系是「混合检索」的前提：

| 维度 | 关键词检索（BM25） | 向量检索（Embedding） |
| --- | --- | --- |
| 匹配依据 | 词项字面匹配 | 语义相似度 |
| 精确词（编号、型号、专有名词） | 强，能精确命中 | 可能漏（低频词向量训练不充分） |
| 同义词/改写/口语 | 弱，匹配不上 | 强 |
| 多语言 | 弱（需分词+词典） | 强（同一向量空间） |
| 冷启动 | 无需训练，上来就能用 | 需先做 Embedding |
| 可解释性 | 强（能说清命中哪个词） | 弱（向量不可解释） |
| 典型实现 | Elasticsearch、Lucene | 向量数据库 + Embedding 模型 |

结论：**两者是互补而非替代**。精确匹配交给关键词检索，模糊语义交给向量检索，最后把两路结果融合——这就是下一节要讲的混合检索。

### 最简完整示例：手写一条 RAG 链路

不依赖任何框架，用最少的代码跑通「建库 → 检索 → 生成」全流程，帮助理解 RAG 的本质：

```python
# 最简 RAG：不依赖 LangChain，纯手写，跑通全链路
# 依赖：pip install numpy openai  （openai 仅作示例，可换成任意 embedding/llm 接口）

import numpy as np

# 1. 知识库（现实中来自 PDF/网页，这里用 4 段文本代替）
documents = [
    "公司报销流程：员工填写报销单，提交直属领导审批，通过后财务打款。",
    "年假制度：工作满一年享受 5 天带薪年假，随工龄递增。",
    "加班调休：周末加班可申请调休，需提前一天在系统提交申请。",
    "招聘流程：简历筛选通过后安排两轮面试，最后由 HR 谈薪发 offer。",
]

# 2. 切分：这里每段较短，直接把一段当做一个 chunk
#    真实场景要按 chunk_size/overlap 切，见「文档切分」一节
chunks = documents

# 3. 向量化：这里用一个「玩具 Embedding」模拟——按词是否出现编码
#    为什么这样做：真实 Embedding 是训练好的模型，这里用词袋向量只是让例子能跑通，
#    本质上它演示的流程和真 RAG 完全一样：文本 -> 向量 -> 相似度检索
def simple_embed(text: str) -> np.ndarray:
    vocab = set("".join(chunks) + text)              # 简陋的词表
    return np.array([1.0 if ch in text else 0.0 for ch in vocab])

# 建立索引：把所有 chunk 转成向量存起来
chunk_vectors = [simple_embed(c) for c in chunks]

# 4. 检索：余弦相似度找最相关的 top-k
def cosine(a, b):
    return float(np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b) + 1e-8))

def retrieve(question, top_k=2):
    q_vec = simple_embed(question)                   # query 用同一个 embed 函数
    scores = [cosine(q_vec, cv) for cv in chunk_vectors]
    top_idx = np.argsort(scores)[::-1][:top_k]       # 按分数降序取前 k
    return [chunks[i] for i in top_idx]

# 5. 拼装 prompt + 生成（真实场景这里调用 LLM，这里直接打印上下文示意）
def ask(question):
    context = retrieve(question)
    prompt = (
        "请严格根据以下资料回答，资料没有答案就回答'不知道'：\n\n"
        + "\n".join(f"- {c}" for c in context)
        + f"\n\n问题：{question}"
    )
    return prompt   # 真实场景：llm(prompt) 得到答案

print(ask("怎么申请调休？"))
```

运行结果（示意）：检索器会优先命中「加班调休」那一段，把它作为上下文拼进 prompt。这就是 RAG 的全部骨架——**切分、向量化、相似度检索、拼 prompt、生成**，五步一个不落。真实系统只是把每一步换成生产级组件（真实 Embedding 模型、真正的向量库、带 Rerank 的检索），流程完全一致。

## 高级篇

基础篇搭起的是「能跑」的 RAG，高级篇解决的是「能用、好用」。真实生产里，光靠向量检索 + 拼 prompt 远不够，这一篇逐个展开工程化的关键升级。

### 混合检索 + 融合排序

工程上很少只用一种检索，因为向量检索漏精确词、关键词检索不懂语义。**混合检索（Hybrid Search）= 向量检索 + 关键词检索**，两路各自召回，再通过融合算法合并成一路结果。流程如下：

```
                    用户问题
                       │
          ┌────────────┴────────────┐
          ▼                         ▼
   向量检索（Embedding）      关键词检索（BM25）
   语义相似，召回 top 100     字面匹配，召回 top 100
          │                         │
          └────────────┬────────────┘
                       ▼
                融合排序（RRF）
              两路结果合并成一个排名
                       ▼
               取前 N 个进 prompt
```

为什么不能简单把两路分数相加？因为**两路分数的尺度完全不同**：BM25 分数无上限、可以几十上百；余弦相似度在 [-1, 1] 之间。尺度不一致，直接加权就会「谁分大谁说了算」。解决思路是**不看分数看排名**，排名在任何检索系统里都是可比较的。

最常用的融合算法是 **RRF（Reciprocal Rank Fusion，倒数排名融合）**：

```
RRF_score(d) = Σ  1 / (k + rank_i(d))
               i∈各路检索

其中：
  rank_i(d) = 文档 d 在第 i 路检索结果中的排名（从 1 开始）
  k         = 平滑常数，通常取 60
```

RRF 的直觉：**一个文档只要在某一两路检索里排得靠前，就能拿到较高分**；排名靠后的文档贡献的分数会迅速衰减（因为是倒数）。k=60 的作用是防止「排名第一（1/1=1）」的文档分数过高、把其他文档全淹没。

用代码实现 RRF 融合：

```python
# RRF 融合：输入多路检索的文档排名列表，输出融合后的统一排名
# 为什么用排名而不是分数：BM25 和余弦相似度的分数量纲不同，无法直接相加

def rrf(results_by_retriever, k=60):
    # results_by_retriever: 每路检索返回的 doc_id 有序列表，排前面的名次小
    scores = {}
    for doc_ids in results_by_retriever:
        for rank, doc_id in enumerate(doc_ids, start=1):   # 排名从 1 开始
            scores[doc_id] = scores.get(doc_id, 0) + 1.0 / (k + rank)
    # 按融合分数降序返回
    return sorted(scores.items(), key=lambda x: -x[1])

# 示例：向量检索和 BM25 各召回前几名
vector_hits = ["docA", "docB", "docC"]      # 向量检索排名：A 第1、B 第2、C 第3
bm25_hits   = ["docB", "docD", "docA"]      # BM25 排名：B 第1、D 第2、A 第3

print(rrf([vector_hits, bm25_hits]))
# docA: 1/61 + 1/63 ≈ 0.0323
# docB: 1/62 + 1/61 ≈ 0.0325   ← B 在两路都靠前，综合排名最高
```

融合后的结果：docB 因为在两路都排得靠前，最终排第一。这就是混合检索「取长补短」的效果——既抓住了语义相似（向量路），又抓住了精确匹配（关键词路）。

::: tip 💡 面试题：RRF 为什么用排名而不是分数？
因为不同检索器（BM25、向量、甚至 BM25 变体）的分数分布差异巨大，无法直接比较和相加；而排名是无量纲的、天然可比较。RRF 用 `1/(k+rank)` 对排名取倒数再求和，简单、无需调参、鲁棒，是工业界融合的默认选择。
:::

### 重排序（Rerank）

混合检索解决了「召回更全」，但召回阶段追求的是「快 + 全」，会拉回来几十上百个候选，其中很多是「沾点边但不精确」的。**重排序（Rerank）**用更强的模型对这几十个候选重新打分，把最相关的几条挑进 prompt。

两阶段检索的经典分工：

| 阶段 | 目标 | 模型 | 数量 | 延迟 |
| --- | --- | --- | --- | --- |
| 召回（Retrieve） | 快、尽量全 | 向量/关键词检索（双塔） | top 50~100 | 毫秒级 |
| 重排（Rerank） | 准、排对顺序 | Cross-Encoder（交叉编码） | top 3~5 | 几十毫秒 |

**为什么需要 Rerank？** 关键在于两种模型的架构差异：

```
双塔模型（Bi-Encoder，用于召回）：
  query ──► [query 编码器] ──► 向量 q
  doc   ──► [doc 编码器]   ──► 向量 d    ──► 相似度 cos(q, d)
                    ↑
      q 和 d 独立编码，编码时互不见面，
      只能靠"向量空间里离得近"间接判断相关，精度有限但快（可预计算 doc 向量）

交叉编码（Cross-Encoder，用于重排）：
  [query + doc 拼接] ──► 编码器 ──► 相关性分数
                    ↑
      query 和 doc 拼成一段一起过模型，两者充分交互，
      能捕捉细粒度的语义匹配，精度高但慢（必须每次现算，无法预计算）
```

所以两者的配合是：**双塔负责在百万级文档里快速缩小范围，交叉编码负责在小范围里精挑细选**。Rerank 慢，但只用在最后一步（几十个候选），成本可控。

Rerank 的使用示例：

```python
# 为什么需要 Rerank：召回阶段用双塔粗筛，只保证"相关"，不保证"最相关"
# Rerank 用交叉编码精排，把最贴题的几条顶到最前面

def retrieve(question):          # 召回：双塔向量检索，快而全
    return vector_db.search(embed(question), top_k=50)

def rerank(question, candidates): # 重排：交叉编码精排，准而慢
    return reranker.score(question, candidates, top_k=5)

hits = rerank(question, retrieve(question))  # 先召回 50，再精排取 5
context = "\n".join(h.text for h in hits)    # 只有最相关的 5 条进 prompt
```

::: tip 💡 面试题：为什么 Rerank 能显著提升效果？
召回用双塔模型，query 和 doc 独立编码、互不交互，只能靠向量距离间接判断；Rerank 用交叉编码，把 query 和 doc 拼一起过模型做细粒度交互，精度远高于双塔。代价是慢（无法预计算），所以只对 top-k 候选精排。常用模型如 bge-reranker、Cohere Rerank。
:::

### 查询改写（Query Rewriting）

用户的问题往往很口语、信息不全，直接拿去检索效果差。**查询改写**是在检索前先对 query 做加工，让它更容易命中正确的文档。这是「检索质量」这一维度的关键提升手段。

| 改写方法 | 做法 | 解决的问题 | 典型场景 |
| --- | --- | --- | --- |
| 多查询（Multi-Query） | 用 LLM 把一个问题扩写成多个不同表述，分别检索后合并 | 单一表述召回率低 | 同义词、不同问法 |
| HyDE | 先让 LLM 根据问题生成一个「假设答案」，拿假设答案去检索 | query 和文档表述差异大 | 口语问题 vs 规范文档 |
| 子问题拆分 | 把复杂问题拆成多个子问题分别检索再汇总 | 多跳/复合问题 | 「A 和 B 的对比」 |
| Step-back | 先抽象成更上位的通用问题去检索 | 问题太具体、太窄 | 具体细节问不到时 |

**HyDE（Hypothetical Document Embeddings）**特别值得展开，它反直觉却有效：

```
普通检索：  query("怎么退钱")  --向量化-->  [口语向量的位置]  --检索--> 可能召回不准
                                           （"退钱"口语，文档里写的是"退款流程"）

HyDE 检索： query("怎么退钱")
              │
              ▼ 先让 LLM 生成假设答案
            "用户可在订单页点击申请退款，填写退款原因，审核通过后原路退回"
              │
              ▼ 用这个"答案"去检索
            召回 "退款流程" 相关文档  ← 命中率高，因为答案和文档的用词风格更接近
```

HyDE 的原理：query 往往短而口语，文档往往长而规范，两者的向量距离天然远；而「假设答案」是 LLM 按文档风格生成的，用词和文档更接近，用它当检索向量反而更容易命中。代价是多一次 LLM 调用。

### 上下文工程与 Prompt 模板

检索到的片段怎么「喂」给模型，直接决定生成质量。一个合格的 RAG prompt 至少要包含三要素：**角色指令、检索上下文、用户问题**，最好再加「出处标注」和「拒答兜底」：

```python
# RAG Prompt 模板：为什么这么设计——每个字段都有明确作用
RAG_PROMPT = """你是公司的智能助手，请严格根据下面提供的资料回答问题。

【回答要求】
1. 只使用资料中的信息，资料没有答案就明确说"资料中未找到相关信息"。
2. 回答要给出依据，标注引用的资料编号。
3. 不要编造资料中没有的内容。

【资料】
{context}

【问题】
{question}

【回答】"""

def build_prompt(hits, question):
    # 把检索到的片段编号，方便模型标注出处
    context = "\n".join(f"[{i}] {h.text}" for i, h in enumerate(hits, start=1))
    return RAG_PROMPT.format(context=context, question=question)
```

几个工程经验：

- **加「拒答兜底」**：明确告诉模型「没有就直说」，能显著降低幻觉。
- **标注资料编号**：让模型引用 `[1]`、`[2]`，实现答案可溯源。
- **控制 context 长度**：片段不是越多越好，多了模型容易「迷失」在噪声里，也浪费 token。
- **片段排序**：把最相关的片段放最前或最后（首尾效应），模型更容易注意到。

### 父子文档检索（Parent Document Retriever）

这是解决「小 chunk 精准但信息不足，大 chunk 完整但检索钝」的经典方案，核心思想是**「检索用小块，喂给模型用大块」**：

```
离线建库时，同时维护两层：
  ┌─────────────────────────────────────────────┐
  │  父文档（大块，如整章/整节，含完整上下文）       │
  │    ┌─────────────┬─────────────┬─────────────┐
  │    │ 子块1（小）  │ 子块2（小）  │ 子块3（小）  │  ← 用来做向量检索，精准
  │    └─────────────┴─────────────┴─────────────┘
  │    每个子块记录自己归属的父文档 id              │
  └─────────────────────────────────────────────┘

在线检索时：
  问题 → 检索命中「子块2」（精准）→ 根据映射关系回溯「父文档」（完整）
       → 把整段父文档喂给模型，而不是只喂子块2那一小段
```

好处：检索用小块，向量更「纯」、定位更准；生成用大块，上下文更完整、模型能答全。缺点是父文档较大时，可能又引入无关内容，需要权衡父文档的粒度。

### 多路召回与元数据过滤

除了「向量 + 关键词」混合，生产级 RAG 还常叠加**元数据过滤**，实现「在满足条件的文档里找相似」：

| 过滤维度 | 示例 | 实现 |
| --- | --- | --- |
| 时间 | 只查最近一年的文档 | 向量库标量过滤 |
| 来源 | 只查技术文档、不查聊天记录 | 元数据 `source` 字段 |
| 权限 | 只查当前用户有权看的资料 | 元数据 `acl` 字段 |
| 分类 | 只查「产品文档」分类 | 元数据 `category` 字段 |

向量库会在向量索引之外维护标量字段的过滤索引，检索时**先过滤圈定候选集，再在候选集内做向量近邻搜索**，两者结合（详见[向量数据库](/learn_ai/agent/向量数据库)的「过滤实现」一节）。

### 进阶 RAG 技术概览

基础 RAG（检索一次 → 生成一次）在实际复杂场景下会暴露不足，学术界和工业界衍生出一系列进阶方案：

| 方案 | 核心思想 | 解决的痛点 |
| --- | --- | --- |
| Self-RAG | 模型自我反思：决定要不要检索、检索结果好不好 | 盲目检索、检索质量不可控 |
| CRAG（Corrective RAG） | 先评估检索质量，差了就纠正（重写 query / 换检索器） | 检索结果差时硬着头皮生成 |
| GraphRAG | 先建知识图谱，用图结构检索实体关系 | 多跳推理、全局性问答 |
| Agentic RAG | 让 Agent 自主规划：查哪、查几次、怎么验证 | 复杂多步问答 |
| 多模态 RAG | 检索图片/表格/音视频等多模态片段 | 纯文本 RAG 覆盖不了多模态 |

这些进阶方案都建立在一个共识上：**单一的一次性检索难以应对复杂问题，需要在检索和生成之间加入「评估、纠正、多轮」的闭环**。它们与[Agent 编排](/learn_ai/agent/Agent编排)的思路深度耦合。

### RAG 评估

RAG 效果要从两个维度分别评：**检索质量**（找没找到对的东西）和**生成质量**（答没答对、有没有胡编）。

| 维度 | 指标 | 衡量 | 一句话解释 |
| --- | --- | --- | --- |
| 检索 | Recall（召回率） | 相关文档被找到的比例 | 该找的都找到了吗 |
| 检索 | Precision（精确率） | 找到的文档里真正相关的比例 | 找回来的都是对的吗 |
| 检索 | MRR | 第一个相关文档的排名倒数的均值 | 对的文档排得靠前吗 |
| 生成 | Faithfulness（忠实度） | 答案是否忠于检索到的原文 | 有没有脱离原文胡编 |
| 生成 | Answer Relevance | 答案是否真的回答了问题 | 有没有答非所问 |
| 生成 | Context Relevance | 检索上下文是否与问题相关 | 喂进去的资料贴题吗 |

评估可以「自动 + 人工」结合：自动评估常用 **RAGAS** 框架（用 LLM 打分忠实度、相关性），人工评估针对关键 case 逐一核对。工程上建议**先搭好评估集再调参**，否则调 chunk_size、改 prompt 都是在「盲调」。

### 常见问题与对策总表

| 问题 | 原因 | 对策 |
| --- | --- | --- |
| 召回不全 | 切分太碎 / 向量语义匹配不足 / 问题太口语 | 混合检索、查询改写（HyDE/多查询）、调大 top_k |
| 召回不准 | 召回的片段无关 / 排名靠前的不是最相关 | Rerank、提高 chunk 质量、元数据过滤 |
| 答案胡编 | 上下文不够 / 模型本身幻觉 / 无拒答约束 | 增加 chunk 上下文、加忠实度约束、明确「不知道就说」 |
| 上下文超限 | 拼了太多片段 | 控制 top_k、Rerank 后只取前几名、压缩片段 |
| 精确词漏检 | 向量对低频词/编号不敏感 | 混合检索，关键词一路兜底 |
| 回答不完整 | 小 chunk 信息碎片化 | 父子文档检索，命中后回溯大块 |

## 原理篇

基础篇讲「是什么、怎么用」，原理篇讲「为什么这么设计、底层发生了什么」。这一篇下到机制层面，把 RAG 的几个核心原理彻底讲透。

### 为什么 LLM 会幻觉

要理解 RAG 为什么能治幻觉，先要理解幻觉的根源。LLM 的本质是**一个巨大的「下一个 token 预测器」**：它学到的不是「事实数据库」，而是「在给定前文的情况下，下一个词最可能是什么」的统计规律。

```
输入前文：  "中国的首都是"
              │
              ▼ 模型在词汇表上算出一个概率分布
        P("北京") = 0.95
        P("上海") = 0.02
        P("广州") = 0.01
        ...（所有词都有概率）
              │
              ▼ 采样生成下一个词
            "北京"
```

关键点在于：**模型对任何问题都能给出一个「看起来通顺」的回答**，因为它只是在做「语言接龙」，而不是在「查事实」。当被问到自己没掌握的内容时，它不会说「我不知道」（除非训练时专门强化了这一点），而是继续按语言模型「编」一个最通顺的答案——这就是幻觉。

RAG 的思路**不是消除模型的这个特性**（那等于换模型），而是**把真实资料塞进上下文，让模型照着资料复述**：

```
无 RAG（自由发挥）：  模型 ──"编一个通顺答案"──► 可能胡编

有 RAG（有依据复述）： 模型 + 检索到的原文 ──"照着资料组织语言"──► 有依据、可溯源
```

本质上，RAG 把模型的生成任务从「开放生成」变成了「约束生成」——上下文里摆着标准答案，模型只需要「转述 + 组织语言」，大大压缩了「自由发挥」的空间。这是它能治幻觉的根本原因：**不是让模型更诚实，而是让它没机会瞎编**。

### 为什么向量相似能代表语义相近

向量数据库本身不懂语义，它只是个「存向量 + 找近邻」的容器。**「向量距离近 = 语义相近」这个性质，是 Embedding 模型训练出来的**，不是向量库赋予的。

Embedding 模型的训练目标，可以简单理解为「**让语义相近的文本，向量距离更近；语义无关的文本，向量距离更远**」。经典思路有两种：

```
思路一：词共现（如 Word2Vec）
  "猫" 和 "狗" 经常出现在相似的上下文里（都能"养"、都会"叫"）
  → 训练时让它们的向量互相靠近
  → 结果："猫" 的向量和 "狗" 的向量距离近

思路二：对比学习（现代 Embedding 主流）
  正样本对（语义相近的句对）→ 拉近它们的向量
  负样本对（语义无关的句对）→ 推远它们的向量
  训练目标：让正样本对的相似度 > 负样本对的相似度
```

训练完成后，向量空间就形成了一个「语义地图」：意思接近的文本天然聚成一团，意思不同的散在各处。于是检索时「找向量最近的邻居」，自然等价于「找语义最相近的文本」。

**这引出一个极其重要的工程铁律**：同一个 Embedding 模型必须同时用于「索引阶段（文档）」和「查询阶段（问题）」。因为每个模型学到的「语义地图」不一样，query 和 doc 必须放进**同一个向量空间**，距离才有意义。如果你建库时用模型 A 编码，查询时用模型 B 编码，两个空间对不上，检索结果会完全乱套。

::: tip 💡 面试题：为什么 Embedding 模型不能混用？
Embedding 模型训练时各自学出不同的向量空间，query 和 doc 必须用同一个模型编码、放进同一个空间，算出来的距离才代表「语义相似」。混用两个模型等于在两个坐标系里比较距离，毫无意义。所以 RAG 系统里 query 和 doc 的 Embedding 必须严格一致。
:::

### 向量检索的索引原理：为什么能这么快

暴力扫描（Flat）要把 query 向量和库里**每一个**向量都算一遍相似度，复杂度 O(N)。百万、亿级数据下太慢，所以用**近似最近邻（ANN）索引**，用一点点精度损失换数量级的速度提升。核心原理分两类（详见[向量数据库](/learn_ai/agent/向量数据库)）：

```
IVF（倒排索引，先聚类再搜）：
  建库时把所有向量聚成 N 个桶（质心）
  检索时只搜离 query 最近的几个桶，跳过绝大多数数据
  复杂度从 O(N) 降到 O(N/桶数 × 搜几个桶)

HNSW（分层可导航小世界图）：
  把向量建成多层图：上层稀疏、下层密集
  检索时从上层某点出发，贪心地往"离目标更近"的邻居跳
  上层大步跨越快速定位区域，逐层下降，底层精细搜索
  复杂度接近 O(log N)
```

这里的核心洞察是：**RAG 的检索是「近似」检索，允许牺牲一点精度换速度**——因为反正后面还有 LLM 兜底，召回差一点，生成阶段可能还能补。这个「允许近似」的前提，是向量检索能工程化落地的关键。

### 余弦相似度、内积、欧氏距离的数学细节

三种度量在数学上是什么关系，为什么工程上各有取舍：

```
余弦相似度：cos(A, B) = (A·B) / (|A|·|B|)
  = 向量夹角的余弦值
  = 先各自归一化，再做点积
  范围 [-1, 1]，只和"方向"有关，和"长度"无关

内积（点积）：A·B = Σ a_i·b_i = |A|·|B|·cos(θ)
  = 余弦 × 两个模长
  同时受方向和长度影响

欧氏距离：d(A, B) = sqrt(Σ (a_i - b_i)²)
  = 两点之间的直线距离
  越小越相似

三者的关系（关键）：
  若 A、B 都做了 L2 归一化（模长 = 1），则：
    内积(A, B) = cos(A, B)               ← 内积等价于余弦
    d(A, B)² = 2 - 2·cos(A, B)           ← 欧氏距离和余弦单调相关，等价
```

所以结论是：**三者本质上是同一件事的不同表述**。工程上默认用余弦（或归一化后的内积）是因为文本语义只关心方向，不关心长度。向量库在建库时选定一种度量，检索时必须用同一种，不能中途换。

### RRF 融合的机制流程

RRF 为什么鲁棒、为什么是「排名」而不是「分数」，完整机制如下：

```
输入：K 路检索结果，每路是一份按相关性排序的文档列表

第 1 步：对每一路，给每个文档标上它的排名 rank（1 为最相关）
        向量路：  docA(1) > docB(2) > docC(3) > ...
        BM25 路： docB(1) > docD(2) > docA(3) > ...

第 2 步：对每个文档，累加它在各路中的"排名贡献"：
        RRF(doc) = Σ 1 / (k + rank_i(doc))    k=60

        docA = 1/(60+1) + 1/(60+3) ≈ 0.0323
        docB = 1/(60+2) + 1/(60+1) ≈ 0.0325
        docC = 1/(60+3) + 0        ≈ 0.0159
        docD = 0        + 1/(60+2) ≈ 0.0161

第 3 步：按 RRF 分数降序，输出最终排名：
        docB > docA > docD > docC
```

为什么用倒数 `1/(k+rank)` 而不是直接用 `1/rank`？加常数 k 是为了**平滑**：`1/1 = 1` 比 `1/2 = 0.5` 高出一倍，第一名太强势，会把其他文档的贡献淹没；`1/61 ≈ 0.0164` 和 `1/62 ≈ 0.0161` 差异很小，各路、各名次之间的权重更均衡。这是 RRF 论文里验证过的经验值。

### 双塔 vs 交叉编码：检索与重排的分工原理

RAG 里「召回用双塔、重排用交叉编码」的分工，根源于两种架构的**计算特性差异**：

| 特性 | 双塔（Bi-Encoder） | 交叉编码（Cross-Encoder） |
| --- | --- | --- |
| 编码方式 | query、doc 独立编码成向量 | query、doc 拼接后一起编码 |
| 交互程度 | 无交互（只在向量空间比距离） | 充分交互（逐 token 注意力） |
| 精度 | 较低 | 高 |
| 速度 | 快（doc 向量可离线预计算） | 慢（每次都要现算） |
| 是否可预计算 | 是（海量 doc 向量提前算好存库） | 否 |
| 用途 | 召回（面对百万级全集） | 重排（面对 top 几十候选） |

分工的本质是**「计算预算的分配」**：双塔可以把海量文档向量离线预计算好，检索时只需算一个 query 向量，所以能扛住百万级全集；交叉编码精度高但每个 query-doc 对都要现算，只能用在已经被双塔缩小到几十个的候选上。两者组合，用可接受的总延迟换来了显著的效果提升。

### chunk 大小影响效果的原理

chunk 大小为什么是「万恶之源」级的调参难题，原理在**向量语义的纯度**和**上下文完整性**之间的此消彼长：

```
chunk 小（如 100 token）：
  向量语义"纯"——一段就一个主题，向量指向明确
  检索精准——容易精准命中
  但信息碎片化——单段答不全，需要看多段，且容易切断语义
  ↓ 模型拿到的是"碎片"，需要自己拼图，容易拼错

chunk 大（如 2000 token）：
  单段信息完整——一个主题的前因后果都在一段里
  但向量被"稀释"——多主题混在一个向量里，每个主题的语义都被平均掉
  检索变钝——问 A 主题，可能因为段里混了 B 主题而排不到前面
  ↓ 模型拿到的是"大杂烩"，无关内容也一起塞进来，浪费上下文
```

这解释了为什么「父子文档检索」（小 chunk 检索 + 大 chunk 生成）是主流方案：它把「检索」和「生成」两个阶段对 chunk 的**相反需求**解耦了——检索要小块（纯）、生成要大块（全），分别用不同粒度满足。切分没有唯一正确答案，取决于文档类型和下游任务。

### RAG 完整信息流机制（一张图贯穿）

把前面所有原理串起来，看一条 query 从进来到答案出去的完整数据流：

```
用户问题 q
   │
   ▼
[1] 查询改写（可选）            q → LLM → {q1, q2, ...} / 假设答案 / 子问题
   │
   ▼
[2] 多路召回
   ├── 向量检索：embed(q) → ANN 索引 → top 100（语义相似）
   └── 关键词检索：BM25(q) → 倒排索引 → top 100（字面匹配）
   │
   ▼
[3] 融合排序                    RRF 合并两路 → 统一排名 top 50
   │
   ▼
[4] 元数据过滤（可前置）        在候选集内再按时间/权限/分类过滤
   │
   ▼
[5] 重排序 Rerank               Cross-Encoder 精排 top 50 → top 5
   │
   ▼
[6] 上下文拼装                  [5] 中最相关片段 + 编号 + 原文，拼成 context
   │
   ▼
[7] Prompt 生成                 system 指令 + context + question + 拒答约束
   │
   ▼
[8] LLM 生成                    LLM 照着 context 生成答案 + 标注出处
   │
   ▼
最终答案（可溯源）
```

这 8 步里，[1][2][3][4][5] 都在「检索质量」上做功，[6][7][8] 在「生成质量」上做功。工程优化就是在这 8 个环节里做权衡：哪些环节值得加（成本 vs 效果）、每个环节的参数怎么调。理解了这条数据流，就理解了整个 RAG 的优化空间。

### RAG 的成本与性能分析

RAG 不是「免费」的，它把一部分成本从「训练」转移到了「推理」。理解成本结构，才能做合理的架构决策：

| 成本项 | 一次性还是持续 | 说明 |
| --- | --- | --- |
| Embedding 建库 | 一次性（新增文档时增量） | 每段文本过一遍 Embedding 模型，量大时成本可观 |
| 向量存储 | 持续 | 向量维度 × 文档量，高维向量存储不小 |
| 检索延迟 | 每次查询 | ANN 索引下毫秒级，通常可忽略 |
| Rerank 延迟 | 每次查询 | 交叉编码较慢，是延迟的主要增量 |
| LLM 生成 | 每次查询 | 上下文变长，token 消耗增加 |

核心权衡：**上下文长度 vs 检索质量**。塞更多片段 → 检索更全但 token 更贵、模型更容易被噪声干扰。工程上常用「Rerank 后只取前 3~5 条」来在效果和成本间取平衡。相比微调的一次性高成本，RAG 的持续成本更低、更可预测，这是它被广泛采用的经济性原因。
