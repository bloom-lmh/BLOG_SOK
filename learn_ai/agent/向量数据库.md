# 向量数据库

一句话定位：向量数据库是专门存储「向量（高维浮点数组）」并支持高效「相似度检索」的数据库，它把文本、图片、音频经 Embedding 模型转成高维向量，再通过 ANN（近似最近邻）索引在海量向量里毫秒级找出最相近的 top-k 个，是大模型 RAG、推荐、以图搜图、去重等场景的底层存储与检索引擎。

## 基础篇

### 为什么需要向量数据库

传统数据库（MySQL、Redis、Elasticsearch 等）从诞生起擅长的是「**精确匹配**」：`WHERE id = 123`、`WHERE name LIKE '%张三%'`、甚至倒排索引的 `term` 匹配。它们的核心假设是「**两个东西相同，就是一模一样**」。

但大模型时代的需求变了，核心变成了「**语义相似度检索**」——「找出和这句话意思最接近的 5 条」。这类查询有三个传统数据库搞不定的特征：

1. **不是等值匹配**：「今天天气不错」和「外面现在下雨吗」字面完全不同，但语义相关，传统 `LIKE` 或全文索引都匹配不上。
2. **高维浮点数据**：一条文本被 Embedding 成几百上千维的 `float` 数组，传统 B+ 树、倒排索引对这种高维连续数据的「近邻」查询无能为力（维度灾难）。
3. **海量规模**：RAG 知识库动辄百万、千万、亿级文档，必须毫秒级返回，暴力扫描 O(N) 不可行。

向量数据库解决三个问题：

1. **存储**：把高维向量（几百上千维）存下来，附带原始文本（payload）和元数据（metadata）。
2. **检索**：给定一个查询向量，快速返回最相似的 top-k 个向量及其原始内容。
3. **规模**：在百万、亿级向量上仍能毫秒级响应，靠的是 ANN 索引算法而非暴力扫描。

::: tip 💡 面试题：一句话说清向量数据库是干嘛的？
向量数据库 = 「把语义变成向量存起来」+「用近似最近邻索引快速找相似」的存储引擎。它本身不产生语义，语义是 Embedding 模型赋予的；它只负责「存得快、找得准、扛得住量」。
:::

### 向量与 Embedding 到底是什么

这是理解向量数据库的第一块地基。先看「背景 → 定义 → 特性 → 示例 → 小结」完整链条。

**背景**：计算机只能算数字，无法直接「理解」文字、图片、音频的语义。要让机器比较「两句话意思近不近」，必须先把这些非结构化数据变成数字。

**定义**：

- **向量（Vector）**：一串有序的浮点数，如 `[0.12, -0.34, 0.98, ..., 0.55]`，可以看作高维空间里的一个「点」或「从原点出发的箭头」。
- **Embedding（嵌入/向量化）**：把一个非结构化对象（文本、图片、音频、代码）映射成向量的过程，以及这个映射出的向量本身。这个映射通常由神经网络模型完成，叫 **Embedding 模型**。

**特性（关键规则）**：

1. **语义相近 → 向量相近**：Embedding 模型训练的目标就是让语义相近的对象在向量空间里距离更近。这是向量检索成立的根基。
2. **维度由模型决定**：不同的 Embedding 模型输出的维度固定，如 OpenAI `text-embedding-3-small` 是 1536 维，`text-embedding-3-large` 是 3072 维，本地 `bge-m3` 是 1024 维。
3. **同一个库必须用同一个模型**：建库时的向量和检索时的查询向量必须来自**同一个 Embedding 模型**，否则它们不在同一个向量空间，比较距离毫无意义。
4. **向量本身不可读**：`[0.12, -0.34, ...]` 人类看不懂，所以必须把原始文本一起存下来，检索命中后再把原文取出来给人看。

**示例**：

```python
# 为什么用伪代码：不同的 Embedding SDK 接口不同，这里展示通用逻辑
# 同一个模型把「语义相近」的两句话映到相近的位置
a = embed("今天天气真不错")   # [0.12, -0.34, 0.98, ...] 1536 维
b = embed("外面现在下雨吗")   # [0.15, -0.31, 0.92, ...] 和 a 比较近
c = embed("红烧肉怎么做")     # [0.88, 0.02, -0.41, ...] 和 a 距离远

# 为什么 c 会离得远：模型在训练时见过大量语料，
# 学会了「天气类」和「菜谱类」在语义空间里属于不同区域
```

**小结**：向量数据库自己不会产生语义，它只是「存储 + 检索」向量。向量的质量上限由 Embedding 模型决定——**模型好，向量库找出来的近邻才是真近邻；模型差，向量库再快也是精确地找出错误答案**。

### 核心概念逐个展开

下面把向量数据库里最常出现的几个概念逐个讲透，这是后续读代码、看文档、做选型的基础。

#### 1. 集合（Collection）

- **背景**：类比关系型数据库的「表（Table）」，是向量数据库里组织和隔离数据的一级单位。
- **定义**：一个 Collection 是一组「向量 + 元数据」的集合，建库时必须声明**维度（dimension）**和**距离度量（metric）**。
- **特性/规则**：同一个 Collection 内所有向量维度必须一致；Collection 建好后 metric 一般不能中途改（改了索引和检索结果会全乱）。
- **示例**：`create_collection("docs", dimension=1536, metric="COSINE")`。
- **小结**：Collection 是「先定规矩、再存数据」的容器，维度与度量是它的两个不可变契约。

#### 2. 维度（Dimension）

- **定义**：向量的长度，等于向量数组里浮点数的个数。
- **特性**：由 Embedding 模型决定；建库时必须声明，写入向量长度必须严格匹配。
- **为什么重要**：维度越高，语义表达力越强，但计算量、存储、索引内存也越大（维度灾难的根源）。

#### 3. 距离度量（Metric）

- **定义**：衡量两个向量「有多像」的数学函数。
- **特性**：建库时固定，检索时用同一种。度量选择错误会直接导致检索结果语义错乱。
- **展开**：三种主流度量见下一节。

#### 4. 索引（Index）

- **背景**：海量向量若逐条和查询向量算距离（暴力扫描）是 O(N)，数据大了就不可接受。
- **定义**：为「快速找近邻」预先构建的加速结构，常见有 IVF、HNSW、PQ 等。
- **特性**：**近似**（ANN）索引用一点精度换数量级的速度；不同索引在速度、精度、内存之间取舍不同。
- **小结**：索引是向量数据库的性能核心，选型本质是「速度 vs 精度 vs 内存」的三角权衡。

#### 5. top-k

- **定义**：检索时返回「最相似的前 k 个结果」。
- **特性**：k 不是越大越好——k 越大，召回越全但噪声越多、上下文越杂、token 消耗越大；RAG 里常见取 3~8。

### 三种相似度度量（公式 + 计算示例）

这是面试必考，必须能徒手说清公式和差异。先给总览，再逐个展开。

| 度量 | 公式 | 直觉含义 | 特点 | 适用 |
| --- | --- | --- | --- | --- |
| 余弦相似度 | `cos(A,B) = (A·B) / (‖A‖·‖B‖)` | 夹角余弦 | 只看方向，忽略长度 | 文本语义（最常用） |
| 内积 / 点积 | `A·B = Σ aᵢbᵢ` | 投影长度 | 方向越一致、模越大分越高 | 向量已归一化时等价余弦 |
| 欧氏距离 | `d = √Σ(aᵢ-bᵢ)²` | 两点直线距离 | 值越小越相似 | 图像等对绝对距离敏感场景 |

#### 余弦相似度（Cosine Similarity）

- **背景**：文本语义更多由「方向」而非「长度」决定。两句话哪怕一个词多、一个词少，只要语义方向一致就应算相近。
- **定义**：两个向量夹角的余弦值，范围 `[-1, 1]`，越接近 1 越相似。
- **特性**：**对向量长度（模长）不敏感**——你把某条向量整体放大 10 倍，夹角不变，余弦不变。
- **示例**：`A=[1,0]`、`B=[1,1]`，夹角 45°，余弦 ≈ 0.707；`A=[1,0]`、`C=[0,1]`，夹角 90°，余弦 = 0。

```python
# 为什么手写公式：面试和底层优化时要知道它在算什么
import numpy as np

def cosine(a, b):
    # 分子是点积，分母是两个模长之积，本质是「单位向量上的点积」
    return np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b))

print(cosine(np.array([1, 0]), np.array([1, 1])))  # 0.7071
print(cosine(np.array([1, 0]), np.array([0, 1])))  # 0.0
```

#### 内积 / 点积（Inner Product / Dot Product）

- **定义**：对应元素相乘再求和，`A·B = Σ aᵢbᵢ`，值域 `(-∞, +∞)`。
- **特性**：同时受「方向」和「模长」影响——方向越一致、模越大，分数越高。
- **与余弦的关系**：当所有向量都做了 **L2 归一化**（模长为 1）后，`‖A‖=‖B‖=1`，此时 `A·B = cos(A,B)`，内积等价于余弦。
- **为什么工程上常用内积**：归一化后内积和余弦等价，但内积只算一次点积、省了两次开方，计算更便宜，所以很多库（如 Milvus）默认用 `IP` 并要求向量预先归一化。

#### 欧氏距离（Euclidean / L2 距离）

- **定义**：两点在多维空间里的直线距离，值越小越相似。
- **特性**：**对长度敏感**——绝对坐标差异大，距离就大。
- **适用**：图像特征、位置坐标等「绝对差异有物理意义」的场景。
- **与余弦的对照**：余弦看「角度」，欧氏看「距离」。

::: tip 💡 面试题：余弦相似度和欧氏距离的区别？
余弦看「方向」、对向量长度不敏感；欧氏看「绝对距离」、对长度敏感。文本语义通常只关心方向，所以默认用余弦（或归一化后的内积）；图像等需要绝对差异的场景才用欧氏。若用内积而不归一化，长文本/长向量会天然得分更高，导致「越长越像」的偏差。
:::

#### L2 归一化（Normalization）为什么这么关键

- **定义**：把向量除以自己的模长，使模长变为 1，方向不变。
- **为什么重要**：归一化后余弦与内积等价，且消除「长度偏差」——否则一段很长的文本 Embedding 后模长大，内积/欧氏里天然占便宜。
- **示例**：

```python
# 为什么归一化：让内积退化成余弦，消除模长对分数的影响
v = np.array([3, 4])
v_norm = v / np.linalg.norm(v)   # [0.6, 0.8]，模长变成 1
print(np.linalg.norm(v_norm))    # 1.0
```

#### 其他度量（了解即可）

| 度量 | 含义 | 适用 |
| --- | --- | --- |
| 曼哈顿距离（L1） | 各维绝对差之和 | 稀疏向量、格子路径 |
| 汉明距离 | 二进制位不同个数 | 二值哈希、指纹去重 |
| 杰卡德相似度 | 集合交集比并集 | 离散集合相似 |

### 和传统数据库对比

| 维度 | 传统数据库（MySQL/Redis/ES） | 向量数据库 |
| --- | --- | --- |
| 数据形式 | 结构化行、字符串、数值 | 高维浮点向量 + 元数据 |
| 查询方式 | 精确匹配、范围、模糊、关键词 | 相似度（top-k 最近邻） |
| 索引结构 | B+ 树、Hash、倒排索引 | ANN 索引（HNSW/IVF/PQ） |
| 结果 | 精确命中 | 近似结果（允许牺牲精度换速度） |
| 一致性 | 强事务（ACID） | 多为最终一致，弱事务 |
| 典型场景 | 业务增删改查 | 语义检索、推荐、去重、RAG |

关键结论：**两者不是替代关系，是分工关系**。向量数据库通常存「向量 + 少量标量元数据」，真正的业务主数据仍在 MySQL，向量库只负责「语义召回」，命中后再拿 id 回 MySQL 查详情。

### 最简使用流程（完整可运行示例）

下面用一个「假想的统一 SDK」把「建库 → 写 → 查 → 拿结果」串起来，关键行都有「为什么」注释。真实产品的 API 略有差异，但四步逻辑完全一致。

```python
# 为什么分四步：向量库只认向量、不认文本，
# 所以文本必须先 Embedding 成向量，检索出向量后再拿回原始文本。

from vector_db_client import VectorDBClient   # 为什么用伪 SDK：各产品 API 不同，逻辑一致

client = VectorDBClient("milvus://localhost:19530")

# 第 1 步：建集合 —— 固定维度和距离度量，这是后续写入的契约
collection = client.create_collection(
    name="docs",
    dimension=1536,          # 为什么：必须和 Embedding 模型输出维度完全一致，否则写入报错
    metric="COSINE",         # 为什么：度量方式影响索引构建和检索结果，建库后不能中途改
)

# 第 2 步：写入 —— 向量 + 原始文本 + 元数据一起存
# 为什么必须存原文：向量 [0.12,-0.34,...] 人看不懂，检索命中后要把原文取回展示
docs = [
    "今天天气真不错，适合出去散步。",
    "红烧肉的做法是先把五花肉焯水。",
    "今年新能源汽车销量增长很快。",
]
collection.insert([
    {
        "id": i,                                # 为什么要有业务 id：方便回 MySQL 关联详情、去重、更新
        "vector": embed(doc),                   # embed() 是同一个 Embedding 模型的封装
        "text": doc,                            # 原始文本（payload）
        "source": "knowledge_base",             # 元数据，用于过滤
        "year": 2024,
    }
    for i, doc in enumerate(docs)
])

# 第 3 步：检索 —— 查询也要用同一个 Embedding 模型转成向量
hits = collection.search(
    vector=embed("外面现在下雨吗"),             # 为什么：查询必须和写入用同一个模型，否则不在同一向量空间
    top_k=2,                                   # 为什么 top_k 不是越大越好：越大召回越全但噪声越多、token 越费
    filter="year >= 2024",                     # 为什么有 filter：先圈定业务范围再做语义搜索
    output_fields=["text", "source"],          # 为什么只取需要的字段：减少网络和解析开销
)

# 第 4 步：拿回原始文本（向量本身没法给人看）
for h in hits:
    print(h.score, h.text)   # score 是相似度分数，text 是原始文本
```

**小结**：向量数据库的使用永远绕不开这四步——**建库定契约 → 写入带原文 → 同模型查询 → 取回原文**。其中「同一个 Embedding 模型」是最容易踩坑的点。

### 基础篇小结

- 向量数据库是「存向量 + 快速找相似」的引擎，语义由 Embedding 模型赋予，它只负责「存得快、找得准、扛得住量」。
- 三大核心契约：**维度**（由模型定）、**度量**（余弦/内积/欧氏）、**同一个 Embedding 模型**。
- 使用永远是四步：**建库定契约 → 写入带原文 → 同模型查询 → 取回原文**。
- 向量数据库与传统数据库是**分工关系**：向量库做语义召回，业务主数据仍在 MySQL。

## 高级篇

### 1. 一条向量从写入到命中的完整生命周期

基础篇讲了四步使用流程，但那是「用户视角」。工程视角下，一条向量从 `insert` 到被检索命中，背后要经过「写入链路」和「查询链路」两条路径：

```
【写入链路（离线，可以批量、异步）】
原始文档 ──► 切分(Chunk) ──► Embedding 模型 ──► 向量 [0.12,...]
                                                  │
                                                  ▼
                              ┌────────────────────────────────┐
                              │  向量数据库                    │
                              │  ① 写入 WAL/日志（先落盘）      │
                              │  ② 写入内存段/缓存（可即时查）   │
                              │  ③ 后台合并(Merge) 刷成不可变段 │
                              │  ④ 为段构建 ANN 索引           │
                              └────────────────────────────────┘

【查询链路（在线，必须毫秒级）】
查询文本 ──► 同一个 Embedding 模型 ──► 查询向量 q
                                          │
                                          ▼
              ┌─────────────────────────────────────────┐
              │ ① 可选：标量过滤（filter）先圈定范围       │
              │ ② 走 ANN 索引找候选集（如 HNSW 图游走）    │
              │ ③ 对候选集精算距离（可选：ReRank 精排）    │
              │ ④ 按分数排序取 top-k，回取原文/元数据       │
              └─────────────────────────────────────────┘
```

**为什么要区分「写入」和「查询」两条链路**：

- 写入允许**异步、批量、延迟可见**，重点是吞吐和压缩（PQ 量化、段合并、索引重建）。
- 查询要求**低延迟、实时**，重点是索引加速和裁剪（ANN 索引、提前过滤、top-k 裁剪）。

两条链路的指标完全不同：写入看「每秒能吞多少条」，查询看「单次毫秒级 + 召回率」。

::: tip 💡 面试题：向量数据库的写入为什么可以是最终一致？
一句话结论：写入链路追求吞吐和压缩，索引构建（如 IVF 训练、HNSW 建图）天然是批量离线任务，允许延迟可见。原因：向量检索本质是「近似召回」，少量延迟对结果影响可忽略，换来的是更高的写入吞吐和更省的存储。展开：所以绝大多数向量库采用「WAL 日志 + 内存段 + 后台合并刷盘」的 LSM 式架构，读路径优先读已落盘的不可变段，新写入的数据在段刷盘前可能查不到。
:::

### 2. Embedding 的工程实践

向量数据库只是容器，**Embedding 模型决定检索质量上限**。工程上围绕 Embedding 有三个高频问题。

#### 2.1 模型选型

| 模型 | 维度 | 特点 | 适用 |
| --- | --- | --- | --- |
| OpenAI `text-embedding-3-small` | 1536 | 效果好、API 收费、云端 | 快速接入、数据不出域要求低 |
| OpenAI `text-embedding-3-large` | 3072 | 效果更强、更贵 | 对召回要求高 |
| BGE（BAAI）`bge-m3` | 1024 | 开源、多语言、支持稠密+稀疏 | 中文场景、私有化部署 |
| M3E | 768 | 中文优化、轻量 | 中文、低资源本地 |
| Jina Embeddings v2 | 8192 | 超长上下文 | 长文档 |

**选型要点**：① 是否支持目标语言；② 维度（影响存储和计算）；③ 私有化 vs API（数据合规）；④ 上下文长度上限（chunk 不能超过模型窗口）。

#### 2.2 批处理（Batch）

```python
# 为什么批量 Embedding：模型推理有固定开销，一次喂一批比逐条喂快一个数量级
# 单条调用：每条都要一次网络往返 + 一次推理框架开销
# 批量调用：一次网络往返 + GPU 并行推理，摊薄了固定开销

texts = [doc["text"] for doc in docs]            # 取出所有待向量化的文本
vectors = embedding_model.encode(texts, batch_size=256)  # 一次 256 条，GPU 并行

# 为什么 batch_size 不是越大越好：太大内存峰值高、可能 OOM，太小则摊薄不了开销
# 经验值 128~512，视 GPU 显存和文本长度调整
```

#### 2.3 增量更新（Upsert by id）

```python
# 为什么用 upsert 而不是 insert：文档更新时，同一个业务 id 应该覆盖旧向量，
# 否则库里会出现「同一文档的新旧两个版本」，检索结果重复且可能召回过期内容

collection.upsert([            # upsert：存在则覆盖，不存在则插入
    {
        "id": 1001,             # 业务 id 唯一标识一条文档
        "vector": embed("更新后的文本"),   # 用同一个模型重新向量化
        "text": "更新后的文本",
    }
])

# 为什么删除也要按 id：向量库没有「改文本」的概念，只有「按 id 删旧、写新」
collection.delete(ids=[1001])
```

::: tip 💡 面试题：向量库更新文档为什么是「删了重写」而不是原地改？
一句话结论：向量是 Embedding 模型的输出，文本改了向量必然全变，且 ANN 索引（尤其 HNSW 图）不支持原地改节点。原因：语义变化导致向量在高维空间的位置移动，索引结构里的连接关系要重建，代价等同于删旧建新。展开：所以增量更新统一用「按业务 id upsert」，底层是「标删除 + 写新向量」，真正物理删除发生在段合并时。
:::

### 3. 标量过滤与混合检索

#### 3.1 向量检索 + 标量过滤（filter）

真实业务几乎不会「全库裸搜」，而是「在满足条件的文档里找语义相似的」，比如「只搜 2024 年的文档」「只搜某个知识库」。这就引出过滤的两种时机：

| 方式 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **Pre-filter（前置过滤）** | 先用标量条件过滤出子集，再在子集里做向量检索 | 召回不会漏（只要过滤准确） | 过滤条件太宽时子集仍很大，退化成全量；太窄时又可能过滤掉本应召回的结果 |
| **Post-filter（后置过滤）** | 先向量检索出候选，再对结果做标量过滤 | 向量索引始终高效 | 若过滤条件苛刻，top-k 可能被过滤后凑不满 k 条，召回不足 |

**为什么这是个两难**：Pre-filter 的过滤条件要是和「语义」强相关（比如「只搜医学类」），很可能把语义上最像但类别标签写错的结果漏掉；Post-filter 则可能在「top-100 里有 95 条都不满足 filter」时，实际只返回 5 条甚至 0 条。

**工程上的折中**：现代向量库（Milvus、Qdrant）内部做了「过滤 + 向量联合剪枝」——在 ANN 图游走时**边游走边判断节点是否满足 filter**，跳过不满足的节点继续找下一个，兼顾效率和召回。使用时一个通用经验是：**过滤条件选择性低（命中一大半）时用 Pre-filter，选择性高（命中极少数）时加大 top_k + Post-filter**。

#### 3.2 混合检索（Hybrid Search）：稠密向量 + 稀疏检索

纯向量检索有个盲区：**对「精确关键词」「专有名词」「编号」不敏感**。比如用户搜「AK-47 的拆解」，向量检索可能召回一堆「枪械」相关内容但漏掉精确含「AK-47」的文档；反过来，纯关键词检索（BM25/倒排）对「近义词、同义改写」又无能为力。

所以生产级 RAG 普遍用**混合检索**：

```
查询 "AK-47 的拆解步骤"
        │
        ├──► 稠密检索（向量库）：语义召回 top-k1（抓「拆解、枪械」语义）
        │
        ├──► 稀疏检索（BM25/倒排）：关键词召回 top-k2（精确命中 "AK-47"）
        │
        └──► 融合(RRF) ──► 去重合并 ──► 精排(ReRank) ──► 最终 top-k
```

**RRF（Reciprocal Rank Fusion，倒数排名融合）** 是最常用的融合算法，不关心各路的原始分数（向量相似度和 BM25 分数量纲不同，直接相加无意义），只看「排名」：

```
RRF_score(d) = Σ_r  1 / (k + rank_r(d))
其中 r 遍历所有检索通路（稠密、稀疏），rank_r(d) 是文档 d 在该通路里的排名，k 是平滑常数（常取 60）
```

```python
# 为什么用 RRF 而不是直接加分数：向量相似度(0~1) 和 BM25 分数(无上界) 量纲不同，
# 直接相加会被大分数的通路主导；RRF 只看排名，天然无量纲、可融合任意多路
def rrf(rerank_lists, k=60):
    scores = {}
    for docs in rerank_lists:
        for rank, doc_id in enumerate(docs):
            # 排名越靠前（rank 越小），1/(k+rank) 越大，贡献越高
            scores[doc_id] = scores.get(doc_id, 0) + 1.0 / (k + rank + 1)
    return sorted(scores.items(), key=lambda x: -x[1])   # 按融合分降序
```

::: tip 💡 面试题：为什么 RAG 要做「混合检索」而不是纯向量检索？
一句话结论：向量检索抓语义、抓不到精确关键词，BM25 抓关键词、抓不到语义改写，两者互补。原因：向量对「AK-47」这种罕见专有名词的精确匹配能力弱，关键词检索对「近义词/同义改写」无能为力。展开：用 RRF 按排名融合两路结果（向量分数和 BM25 分数量纲不同，不能直接相加），再叠加 ReRank 精排，是生产 RAG 检索质量的标配。
:::

### 4. 召回评估指标

向量检索是「近似」检索，**测召回质量**是上线前的必修课。几个核心指标：

| 指标 | 公式 / 含义 | 说明 |
| --- | --- | --- |
| **Recall@k** | 检索出的 top-k 里，命中的真实相关文档数 / 全部真实相关文档数 | 最常用，「找没找全」 |
| **Precision@k** | top-k 里真实相关的比例 | 「找得准不准」 |
| **MRR** | 第一个相关文档出现位置的倒数均值 | 看重「第一个就命中」 |
| **nDCG** | 考虑相关性和排名的加权打分 | 看重「排序是否合理」 |

```python
# 为什么写这段：面试常问「怎么评估向量检索效果」，手写 Recall@k 最直观
def recall_at_k(predicted_ids, relevant_ids, k):
    # predicted_ids: 检索返回的前 k 个 id；relevant_ids: 人工标注的真实相关 id 集合
    top_k = predicted_ids[:k]                 # 只看前 k 个
    hits = len(set(top_k) & set(relevant_ids))   # 命中了几个真实相关
    return hits / len(relevant_ids)           # 命中数 / 真实相关总数

# 例：真实相关有 3 条，检索 top-10 只命中了 2 条 → Recall@10 = 2/3 ≈ 0.67
```

**评估要点的工程姿势**：

- **标注集**：从真实查询日志采样，人工标注「相关/不相关」，作为 ground truth。
- **指标和参数一起看**：`nprobe`/`efSearch` 越大召回越高但越慢，要画出「召回率-延迟」曲线选工作点。
- **RAG 端到端**：最终看的其实是「答案是否正确」，Recall@k 只是检索环节的代理指标，别忘了 ReRank 和生成环节。

### 5. 常见坑（生产踩坑合集）

| 坑 | 现象 | 根因 | 解法 |
| --- | --- | --- | --- |
| 维度不匹配 | `insert` 报维度错误 | 建库声明的 dimension 和模型输出不一致 | 用 `model.get_sentence_embedding_dimension()` 动态取维度，或写死并加断言 |
| 模型不一致 | 检索结果牛头不对马嘴 | 写入和查询用了不同的 Embedding 模型 | 全链路统一一个模型，模型版本变更要全量重建 |
| 没归一化用内积 | 长文本得分虚高 | 内积受模长影响，长文本模长大 | 统一 L2 归一化，或用余弦度量 |
| metric 选错 | 结果排序诡异 | 建库和查询度量不一致 / 度量与数据不匹配 | 建库时就固定，文本用 COSINE/IP，图像用 L2 |
| top_k 过大 | 上下文噪声多、token 爆 | k 越大召回越全但噪声越多 | RAG 取 3~8，配合 ReRank 精排后再截断 |
| 只用 filter 不用向量 | 漏召回 | Post-filter 把 top-k 过滤后凑不满 | 加大 top_k，或让库做「过滤+向量联合剪枝」 |
| 没做召回评估 | 上线后效果差 | 凭感觉调参 | 建标注集，跑 Recall@k，画召回-延迟曲线 |
| 空库冷启动 | 查询返回空 | 库里还没数据 / 数据没刷盘 | 写后强制 flush，或提示「知识库为空」 |
| 忽略增量更新 | 改了文档查到的还是旧内容 | 只 insert 不 upsert/delete | 按业务 id upsert，删除用软删+段合并物理删 |

::: tip 💡 面试题：向量检索最常见的三个坑是什么？
一句话结论：模型不一致、维度不匹配、度量选错。原因：三者都会导致「同一个库」里的向量和查询向量根本不在同一个可比空间里。展开：模型不一致 → 语义空间错位；维度不匹配 → 直接写不进去；度量选错 → 距离算出来没意义。这三个坑的共同点是「建库契约」没守住。
:::

### 6. 方案选型对比（Milvus / Chroma / pgvector / FAISS / Qdrant / Weaviate / Pinecone）

选型先看四个问题：**数据规模多大？要分布式吗？要不要事务/关联？预算多少？** 下面按「形态」分组对比。

| 方案 | 形态 | 定位 | 规模 | 索引 | 一致性/事务 | 部署成本 | 适用场景 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **Milvus** | 分布式服务 | 云原生、大规模生产 | 亿级 | HNSW/IVF/PQ/DiskANN/GPU | 最终一致，弱事务 | 中（Docker/K8s） | 大规模 RAG、推荐、以图搜图 |
| **Qdrant** | 单机/分布式 | Rust 高性能，过滤强 | 千万~亿级 | HNSW + 强 payload 过滤 | 最终一致 | 低（单二进制） | 需要强标量过滤的中大规模 |
| **Weaviate** | 分布式服务 | 模块化、混合检索内置 | 千万级 | HNSW/倒排 | 最终一致 | 中 | 需要开箱即用混合检索 |
| **pgvector** | PG 扩展 | SQL、强一致 | 百万级 | IVFFlat/HNSW | **ACID 强一致** | 极低（复用 PG） | 已有 PG、要 join/事务、中小规模 |
| **Chroma** | 嵌入式 | Python 原生、demo 神器 | 十万~百万级 | HNSW | 单机 | 极低（pip） | 原型、本地 RAG、学习 |
| **FAISS** | 库（非数据库） | 极致性能索引库 | 亿级 | IVF/HNSW/PQ/LSH 全家桶 | 无持久化/无服务 | 低（内嵌） | 需要极致性能、自建存储 |
| **Pinecone** | SaaS | 托管、零运维 | 亿级 | 托管 | 最终一致 | 付费 | 不想运维、要快速上线 |

**关键区分点**：

- **FAISS 不是「数据库」**：它是 Facebook 出的**索引库**，只有「建索引 + 搜索」，没有持久化、增删改、网络服务、元数据管理。你用 FAISS 得自己搭存储和 CRUD 层，所以它常被 Milvus 等当成底层索引引擎之一。
- **pgvector 是「最小成本」**：如果你已经有 PostgreSQL，装个扩展就能用 SQL 做向量检索，还能和业务表 `JOIN`、享受 ACID 事务。代价是规模天花板（百万级）和并发能力不如专用向量库。
- **Chroma 是「最快上手」**：`pip install chromadb` 就能跑，进程内、API 极简，是原型验证和教程的标准选择，但别指望它扛亿级生产流量。
- **Milvus 是「生产主力」**：真正的分布式架构（计算/存储/索引分离），支持流批一体、段级管理、多种索引，是大规模 RAG 的首选。

**选型决策树（文字版）**：

```
数据量 < 10 万，只想快速 demo？
  ├─ 是 → Chroma（pip 即用）
  └─ 否 → 已有 PostgreSQL 且 < 几百万、要 join/事务？
            ├─ 是 → pgvector
            └─ 否 → 要生产级、亿级、分布式？
                       ├─ 是 → Milvus（或托管 Pinecone）
                       └─ 否 → 单机、强过滤 → Qdrant；要开箱即用混合检索 → Weaviate
```

::: tip 💡 面试题：FAISS 和向量数据库（Milvus/Chroma）的区别？
一句话结论：FAISS 是「索引库」，只做向量索引和搜索；向量数据库是「数据库」，额外有持久化、CRUD、元数据、网络服务和分布式能力。原因：FAISS 关注极致检索性能，把存储和增删改留给你自己。展开：Milvus 底层就用了 FAISS/HNSW 等索引，但封装了完整的数据管理；选 FAISS 意味着你要自己搭存储层，选向量数据库则开箱即用。
:::

### 7. RAG 中的向量数据库

向量数据库在 RAG 里扮演「检索层」的角色。完整链路（详细见 [RAG](/learn_ai/agent/RAG)）：

```
离线索引阶段：文档 → Chunking → Embedding → 向量数据库（建 ANN 索引）
在线检索阶段：问题 → Embedding → 向量数据库召回 top-k → ReRank 精排 → 拼 prompt → LLM 生成
```

向量数据库在 RAG 里要关注的几个工程点：

1. **Chunking 质量决定检索上限**：chunk 太大语义被稀释、太小上下文断裂，向量库只是忠实地检索「被切出来的片段」。
2. **元数据过滤**：给 chunk 存「来源文档、章节、时间、类别」，检索时先过滤再搜，大幅降低噪声。
3. **混合检索 + ReRank**：纯向量召回常搭配 BM25 稀疏召回，再用 Cross-Encoder ReRank 精排，是提升 RAG 检索质量的三件套。
4. **召回数量与上下文预算**：向量库返回的 top-k 要能被 prompt 上下文装下，k 通常 3~8，精排后再截断到最终 3~5 条。

### 高级篇小结

- 写入和查询是两条链路：写入追求吞吐（批量、最终一致、段合并），查询追求低延迟（ANN 索引、过滤剪枝）。
- Embedding 三件事：选模型、批处理、按业务 id upsert 做增量更新。
- 过滤有 Pre/Post 两难，现代库做「过滤+向量联合剪枝」；生产标配「稠密+稀疏混合检索 + RRF 融合 + ReRank 精排」。
- 召回质量用 Recall@k / MRR / nDCG 评估，配合召回-延迟曲线调参。
- 选型看规模与形态：demo 用 Chroma，已有 PG 用 pgvector，生产亿级用 Milvus，极致性能自建用 FAISS。

## 原理篇

### 1. 为什么需要 ANN：暴力扫描与维度灾难

#### 1.1 暴力扫描（Brute Force）的代价

最朴素的「精确最近邻」就是暴力扫描：拿查询向量和库里**每一条**向量算一次距离，排序取 top-k。

```
暴力扫描：
for 库里的每一条向量 x_i (共 N 条):
    score_i = distance(q, x_i)      # 每条 O(D) 次浮点运算
排序所有 score，取最小的 k 个

总代价：O(N · D)
```

**算一笔账**：100 万条 1024 维向量，一次查询要做 `10^6 × 1024 ≈ 10^9` 次浮点运算，还要读 `10^6 × 1024 × 4 字节 ≈ 4GB` 内存。单次查询秒级到几十秒，**完全不可用**。而 RAG 要求毫秒级响应。

#### 1.2 维度灾难（Curse of Dimensionality）

更根本的问题在于：**在高维空间里，「最近邻」这个概念本身在退化**。

- 低维空间（如 2D、3D）：点的分布有明确的「远近」，最近邻和「随机点」距离差异很大，区分度好。
- 高维空间（几百上千维）：随着维度 D 增大，任意两点的距离会「向均值集中」——**所有点彼此的距离都差不多**（这是「测度集中」现象，concentration of measure）。

**直觉解释**：一个 1000 维的单位立方体里，两个随机点在各维上都有差异，欧氏距离 `√Σ(aᵢ-bᵢ)²` 累加了 1000 项，随机波动被「平均」掉了，导致任何两点距离都趋向同一个常数。结果是「最近邻」和「最远点」的距离几乎一样，暴力扫描算出来也分不出谁更近。

**结论**：既然「精确最近邻」在高维下既算不动、又没意义，业界就用**近似最近邻（ANN）**——**牺牲一点点精度（允许偶尔漏掉真正的最近邻），换数量级的速度**。这正是向量数据库所有索引算法的出发点。

::: tip 💡 面试题：为什么向量检索要用近似（ANN）而不是精确（暴力）？
一句话结论：暴力扫描 O(N·D) 在大规模高维数据上算不动，而且高维下「精确最近邻」本身因维度灾难而失去意义。原因：100 万 × 1024 维一次查询就是 10^9 次运算 + 4GB 读；高维下所有点距离趋同，精确和近似结果几乎一样。展开：ANN 用「索引裁剪 + 量化压缩」把计算量降到 O(log N) 或 O(nprobe 子集)，用 95% 的召回换千倍速度。
:::

### 2. 索引总览：速度 vs 精度 vs 内存的三角权衡

所有 ANN 索引都在下面三个维度里做取舍，**没有免费的午餐**：

```
            精度（召回率 Recall）
               ▲
               │
              ╱ ╲
             ╱   ╲
            ╱  ▲  ╲
           ╱ ╱   ╲ ╲
          ╱ ╱     ╲ ╲
         ╱╱        ╲╲
        ╱─────────────╲
   速度（QPS/延迟）   内存/存储（占用）
```

| 索引 | 召回 | 速度 | 内存/存储 | 特点 |
| --- | --- | --- | --- | --- |
| **Flat（暴力）** | 100%（精确） | 慢 O(N) | 全量向量 | 无索引、小数据量 |
| **IVF** | 中（nprobe 可调） | 快 | 存全量向量 | 先聚类再只搜部分簇，可配 PQ 压缩 |
| **HNSW** | 高（90%+） | 快 O(log N) | **大**（存图结构，约为向量的数倍） | 内存图，召回最高但吃内存 |
| **IVF+PQ** | 中（量化损失） | 快 | **极小**（压缩几十倍） | 亿级压缩存储的主力 |

选型口诀：**内存够、要召回高 → HNSW；数据亿级、内存不够 → IVF+PQ；小数据要精确 → Flat**。

### 3. 暴力搜索（Flat / Brute Force）

Flat 本质就是不建索引，查询时全量扫描。它是所有 ANN 算法的「基准线」（召回 100%）和「兜底」。

```python
# 为什么还要讲 Flat：它是召回上界，也是 IVF/HNSW 内部候选集精算时用的同款暴力
import numpy as np

def flat_search(query, vectors, top_k=5):
    # 向量库就是 N×D 的矩阵，query 是 D 维向量
    # 一次性算 query 到所有向量的距离（矩阵运算，比循环快）
    dists = np.linalg.norm(vectors - query, axis=1)   # N 个欧氏距离
    top_idx = np.argsort(dists)[:top_k]               # 距离升序取前 k
    return top_idx, dists[top_idx]
```

**Flat 的适用场景**：数据量小（< 几万）且要求 100% 精确，比如小规模检索、或者作为「ANN 索引 + Flat 精排」组合里的精排环节。

### 4. IVF：倒排索引（Inverted File Index）

#### 4.1 核心思想

暴力扫描的浪费在于「每条都比」。IVF 的思路是**先聚类、再只搜附近的簇**：把全库向量用 k-means 聚成 `nlist` 个簇，每个簇有一个中心点（centroid）。查询时先算查询向量到 `nlist` 个中心的距离，只进最接近的 `nprobe` 个簇里做暴力扫描。

#### 4.2 三步流程

**① 训练（Train）**：在抽样向量上跑 k-means，得到 `nlist` 个聚类中心。这一步是离线的一次性计算。

```
k-means（nlist=4 示意）：
  1. 随机选 4 个点作为初始中心
  2. 把每个向量分给最近的中心，形成 4 个簇
  3. 每个簇取均值更新中心
  4. 重复 2~3 直到收敛 → 得到 4 个稳定中心 c1~c4
```

**② 建索引（Build）**：把每条向量分给最近的中心，存进对应的「倒排列表（posting list）」：

```
倒排列表（inverted lists）：
  c1 → [x1, x5, x9, ...]     # 离 c1 最近的向量都挂在 c1 下
  c2 → [x2, x6, ...]
  c3 → [x3, x7, ...]
  c4 → [x4, x8, ...]
```

**③ 查询（Search）**：算 query 到所有中心的距离，取最近的 `nprobe` 个簇，只在这几个簇里暴力扫描。

```
查询 q：
  1. 算 q 到 c1~c4 的距离 → 排序
  2. 取最近的 nprobe=2 个簇（假设是 c1、c3）
  3. 只在 c1、c3 的倒排列表里暴力扫描
  4. 返回 top-k

  代价从 O(N) 降到 O(nlist) + O((nprobe/nlist) · N)
```

#### 4.3 两个关键参数

| 参数 | 含义 | 调大 | 调小 |
| --- | --- | --- | --- |
| `nlist` | 簇的数量 | 每个簇更小、扫描更细，但查中心更慢 | 簇更少，但簇内更大、扫描变多 |
| `nprobe` | 查询时探测的簇数 | 召回↑、速度↓ | 召回↓、速度↑ |

**经验值**：`nlist ≈ 4 × √N`（N 为向量数），`nprobe` 取 `nlist` 的 1%~10%，按召回目标调。

#### 4.4 伪代码

```python
# IVF 查询伪代码：为什么先算中心距离——用 nlist 次距离计算，裁剪掉 (1 - nprobe/nlist) 的扫描量
def ivf_search(q, centroids, inverted_lists, nprobe, top_k):
    # 1. 算 q 到所有中心的距离
    dist_to_centroids = [dist(q, c) for c in centroids]      # O(nlist · D)
    # 2. 挑最近的 nprobe 个簇
    probe_ids = argsort(dist_to_centroids)[:nprobe]
    # 3. 只在被探测的簇里暴力扫描
    candidates = []
    for pid in probe_ids:
        for x in inverted_lists[pid]:                        # 只扫 nprobe/nlist 比例的数据
            candidates.append((dist(q, x), x))
    # 4. 排序取 top-k
    candidates.sort()
    return candidates[:top_k]
```

::: tip 💡 面试题：IVF 里 nprobe 调大调小有什么影响？
一句话结论：nprobe 越大召回越高但越慢，nprobe 越小越快但越容易漏。原因：nprobe 决定「查多少个簇」，越大扫描的数据比例越高，越接近暴力扫描。展开：nprobe=1 只搜最近一个簇，速度快但 query 落在簇边缘时容易漏掉邻近簇里的真实近邻；nprobe=nlist 退化成全量暴力。工程上按召回目标在「召回-延迟」曲线上选工作点。
:::

### 5. HNSW：分层可导航小世界图

HNSW（Hierarchical Navigable Small World）是当前**召回率最高、最常用**的 ANN 索引，本质是「跳表 + 图」的结合。

#### 5.1 从跳表到可导航小世界

回忆跳表（Redis ZSet 底层也用它，见 [Redis](/learn_database/Redis)）：多层链表，底层是完整有序链表，上层是稀疏索引，查询从最高层往下跳，O(log N)。

HNSW 把跳表的一维思想搬到高维图里：

- 底层（Layer 0）是一个「小世界图」：所有点都在，每个点连到它的若干近邻。
- 上层是稀疏的「高速路」：点数指数递减，用于快速跳过大部分空间。

**小世界图（NSW）为什么能 O(log N) 查找**：小世界网络有「六度分隔」特性——任意两点的图距离（跳数）很短，而且「贪心游走」（每步往离目标更近的邻居走）在这种图上天然高效。HNSW 用多层放大这个优势。

#### 5.2 结构（分层图）

```
Layer 2:  [少量点，稀疏，高速路]      ── 概率 1/M 选出
Layer 1:  [中等数量点]                ── 概率 1/M 选出
Layer 0:  [全部点，密集小世界图]        ── 所有点
```

- 每个节点以指数衰减的概率决定自己的**最高层**（类似跳表的随机层高）。
- 每个节点在它所在的每一层，连到 `M` 个最近邻（`M` 是每层最大连接数）。
- 层越高点越少，跳得越远；层 0 最密，负责最终精确命中。

#### 5.3 插入（构建图）

```
插入新点 p：
  1. 随机决定 p 的最高层 L（概率随层高指数递减）
  2. 从最顶层开始，贪心搜索到「离 p 最近的点」，作为入口，逐层下降
  3. 在每一层 l ≤ L：
     a. 在该层找 p 的 efConstruction 个最近邻候选
     b. 从候选中挑 M 个连边（p ↔ 邻居）
     c. 对每个邻居做「剪边」：若邻居的边数超过 M_max，删掉最远的边
```

- 关键参数 `efConstruction`：插入时搜索的候选队列大小，越大图质量越高（连边越准），但建图越慢。
- 为什么叫「可导航」：图建好后，任意两点都能通过「往更近的邻居走」到达，无需全局坐标。

#### 5.4 搜索

```
搜索 q：
  1. 从最顶层的入口点开始
  2. 贪心下降：每层找离 q 最近的点作为下一层入口，直到 Layer 0
  3. 在 Layer 0 做「贪心 + 扩大的候选集」搜索：
     - 维护一个大小为 efSearch 的候选堆
     - 每次从堆里取离 q 最近、且还没扩展过的点，把它的邻居加进堆
     - 直到候选堆里最远的点都比「待扩展点」更近，或达到扩展上限
  4. 返回堆里最近的 top-k
```

- 关键参数 `efSearch`：查询时的候选堆大小，**越大召回越高、越慢**。要求 `efSearch ≥ top_k`。

#### 5.5 三个参数总结

| 参数 | 作用 | 调大 | 调小 |
| --- | --- | --- | --- |
| `M` | 每层最大连接数 | 图更密、召回高，但内存大 | 省内存，召回降 |
| `efConstruction` | 建图时候选队列 | 图质量高，建图慢 | 建图快，质量降 |
| `efSearch` | 查询时候选队列 | 召回高、慢 | 快、召回降 |

**典型值**：`M=16`，`efConstruction=200`，`efSearch=100`（再按召回目标调）。

#### 5.6 复杂度与内存

- **查询复杂度**：约 O(log N)（多层跳跃 + 小世界图）。
- **内存**：每个节点要存 `M` 条边 + 向量本身，**内存约为原始向量的数倍**，是 HNSW 的主要代价。
- **代价**：HNSW 是「内存换召回」的代表——召回最高，但吃内存，亿级数据可能放不进内存，这时要用 IVF+PQ 或磁盘索引（DiskANN）。

::: tip 💡 面试题：HNSW 为什么快、代价是什么？
一句话结论：HNSW 是多层小世界图，利用「六度分隔」让贪心游走 O(log N) 到达近邻，代价是内存大。原因：上层稀疏层做高速跳转，底层密集图做精确命中，查询时贪心下降；每个节点要存 M 条边，内存数倍于原始向量。展开：M、efConstruction、efSearch 三个参数在「召回/速度/内存」间权衡，efSearch 是查询时调召回的主要旋钮。
:::

### 6. PQ：乘积量化（Product Quantization）

#### 6.1 背景：内存装不下亿级向量

HNSW 召回高但内存大，亿级向量（比如 1 亿 × 1024 维 × 4 字节 ≈ 400GB）根本放不进内存。PQ 的目标是**把向量压缩几十倍**，让亿级数据塞进内存（或少量 SSD）。

#### 6.2 核心思想：分块量化

PQ 把「对整个向量做聚类」改成「对向量分段、每段分别聚类」。核心洞察：**高维向量可以拆成多个低维子向量，每个子向量在自己的子空间里聚类，用码本索引来近似表示**。

```
把 D 维向量切成 m 段，每段 D/m 维：
  [x1..x16][x17..x32][...][x1009..x1024]   (假设 D=1024, m=64, 每段 16 维)

对每一段 j（共 m 段）：
  1. 在该子空间跑 k-means，聚成 256 个中心 → 得到码本 codebook_j
  2. 每个子向量用「离它最近的中心编号」(0~255，8 bit) 表示
```

#### 6.3 编码（压缩存储）

一个 D 维 `float32` 向量原来占 `D × 4` 字节，PQ 压缩后只存 `m` 个字节（每段一个 0~255 的编号）：

```
1024 维 float32：1024 × 4 = 4096 字节
PQ (m=64, 每段 8bit)：64 字节   → 压缩 64 倍！

1 亿 × 1024 维：400GB → 6.25GB（能装进内存了）
```

**压缩率公式**：`原始 D×4 字节 → m 字节`，压缩 `4D/m` 倍。m 越大（段越多）压缩越狠，但每段维度越低、量化损失越大。

#### 6.4 距离计算：ADC（非对称距离计算）

量化后的向量只有「码本编号」，怎么算和查询向量的距离？PQ 用 **ADC（Asymmetric Distance Computation，非对称距离）**：

- **非对称**：查询向量 q **保持全精度**（不量化，避免查询侧损失），库向量用码本近似。
- 先预计算 q 的每一段到该段码本里 256 个中心的距离，存成「距离查找表」，之后算任意库向量到 q 的距离就是**查表相加**：

```
1. 对每段 j，预计算 q_j 到 codebook_j 的 256 个中心的距离
   → 得到 m 张「距离表」，每张 256 个值
2. 库向量 x 被编码成 m 个编号 (c1, c2, ..., cm)
3. dist(q, x) ≈ Σ_j 距离表_j[c_j]     # 每段查一次表，共 m 次加法
```

```python
# PQ 距离计算（ADC）伪代码：为什么预计算距离表——
# 把「高维点积/距离」变成「查表 + m 次加法」，比暴力算 D 维距离快几十倍
def pq_distance(q, code, distance_tables):
    # code: 库向量的 m 个码本编号；distance_tables[j][c]: q 第 j 段到码本 c 的距离
    total = 0
    for j, c in enumerate(code):          # 遍历 m 段
        total += distance_tables[j][c]    # 每段查一次预计算表
    return total
```

#### 6.5 IVF + PQ：亿级压缩检索的标准组合

PQ 只解决「内存压缩」，不解决「搜索范围」。两者结合成 **IVF+PQ**：

```
IVF 负责「裁剪」：先算 query 到 nlist 个中心的距离，只进 nprobe 个簇
PQ  负责「压缩」：簇里的向量用 PQ 编码，距离用 ADC 查表
```

这样既把搜索范围缩小到 `nprobe/nlist`，又把内存压到几十倍，是 **FAISS 里 `IndexIVFPQ`、Milvus 里 `IVF_PQ` 的底层**，支撑亿级甚至十亿级向量。

::: tip 💡 面试题：PQ 乘积量化是怎么压缩向量的？有什么代价？
一句话结论：PQ 把高维向量切成 m 段，每段各自聚类、用码本编号（8bit）近似存储，压缩 4D/m 倍；代价是量化误差导致召回下降。原因：每段只保留「最近的中心」而非精确值，信息有损。展开：距离用 ADC 非对称计算——查询向量保持全精度，预计算距离表后查表相加，既省内存又控制精度损失；通常和 IVF 组合成 IVF+PQ 支撑亿级规模。
:::

### 8. 一次查询的完整执行流程（把原理串起来）

把前面所有原理串起来，一条查询在向量库里大致是这样跑的：

```
查询文本
  │ ① Embedding（同一个模型）
  ▼
查询向量 q
  │
  ▼
② 标量过滤（可选）──► 确定候选的段/分区（如「只看 2024 年」）
  │
  ▼
③ ANN 粗召回
   ├─ HNSW：从顶层贪心下降，Layer0 用 efSearch 候选堆扩展 → 得到候选集
   └─ IVF+PQ：算 q 到 nlist 中心距离 → 进 nprobe 个簇 → ADC 查表算距离 → 候选集
  │
  ▼
④ 精算 + 排序（可选）
   - 对候选集用「全精度向量」重算精确距离（因为 PQ 量化过的距离有误差）
   - 这一步叫「ReRank / 精排」，通常取粗召回的 top-N（如 100）重算
  │
  ▼
⑤ 截断 top-k，回取原文/元数据 → 返回结果
```

**为什么要有「粗召回 + 精排」两段**：粗召回用近似索引（甚至量化向量）快速缩小到候选集，精排用精确向量在候选集上重算，兼顾「快」和「准」。这也是向量库内部默认会做的事。

### 9. 存储与一致性原理

#### 9.1 LSM 式架构（以 Milvus 为代表）

大规模向量库（Milvus 等）借鉴了 LSM 树的思路，把数据组织成「流 + 段」：

```
写入：数据先进 WAL（预写日志，落盘保不丢）
      → 同时进「内存段」（growing segment，可立即被检索）
      → 内存段写满后 flush 成「不可变段」（sealed segment）

不可变段：落盘（对象存储/S3），后台为它批量构建 ANN 索引
         → 多个小段后台合并（merge/compaction）成更大的段，减少段数量
```

- **为什么先写 WAL**：内存段在宕机时会丢，WAL 落盘保证可恢复（类似 Redis AOF、MySQL redo log 的思路）。
- **为什么不可变段 + 后台建索引**：ANN 索引（尤其 HNSW）建图代价高，只读的不可变段可以离线批量构建，不用随写随改。
- **为什么合并**：段太多会导致查询要扫的段多，合并减少段数、同时真正物理删除被标删的向量。

#### 9.2 为什么是最终一致

- 新写入的数据在「内存段」里，**flush 成不可变段 + 建好索引之前**，可能查不到（或只被部分索引覆盖）。
- 删除/更新是「软删除」：先打删除标记，物理删除要等段合并。
- 所以向量库普遍是**最终一致**，读到的可能不是最新写入，这是它和 MySQL 强事务的根本区别，也是「向量库只做召回、业务主数据在 MySQL」的原因之一。

### 原理篇小结

- ANN 的必要性：暴力扫描 O(N·D) 算不动，且高维下「精确近邻」因维度灾难失去意义。
- 索引三角权衡：Flat 精确但慢；IVF 先聚类再只搜部分簇；HNSW 多层小世界图召回最高但吃内存；PQ 分块量化压缩几十倍，配 IVF 支撑亿级。
- HNSW 三参数 M / efConstruction / efSearch；IVF 两参数 nlist / nprobe。
- 查询执行 = Embedding → 过滤 → ANN 粗召回 → 精算重排 → 截断 top-k。
- 存储用「WAL + 内存段 + 不可变段 + 后台合并」的 LSM 式架构，天然最终一致。

## 面试常问

### 概念类

**Q1：向量数据库是干嘛的？**
存向量 + 用 ANN 索引快速找相似 top-k 的存储引擎；语义由 Embedding 模型赋予，它只负责「存得快、找得准、扛得住量」。

**Q2：Embedding 是什么？为什么同一个库必须用同一个模型？**
Embedding 是把文本/图片映射成高维向量的过程；不同模型的向量空间不同，混用会导致距离比较毫无意义，所以建库和查询必须同模型。

**Q3：向量数据库和传统数据库（MySQL/Redis/ES）的区别？**
传统库做精确匹配（等值/范围/关键词），向量库做相似度检索（top-k 近邻）；索引一个是 B+ 树/倒排，一个是 ANN（HNSW/IVF/PQ）；向量库多为最终一致。

**Q4：向量数据库和 FAISS 的区别？**
FAISS 是「索引库」，只做索引和搜索；向量数据库额外有持久化、CRUD、元数据、网络服务和分布式。Milvus 底层就用了 FAISS 等索引。

### 度量类

**Q5：余弦相似度和欧氏距离的区别？**
余弦看方向、对长度不敏感，欧氏看绝对距离、对长度敏感；文本语义默认用余弦（或归一化后内积），图像用欧氏。

**Q6：为什么工程上常用内积（IP）而不是余弦？**
归一化后内积与余弦等价，但内积只算一次点积、省了两次开方，更便宜；所以很多库默认 IP 并要求向量预先 L2 归一化。

**Q7：不归一化直接用内积会有什么问题？**
长文本/长向量模长大，内积天然得分高，导致「越长越像」的偏差；归一化消除模长影响。

### 索引类

**Q8：为什么要 ANN 而不是精确检索？**
暴力扫描 O(N·D) 在大规模高维下算不动（100 万×1024 维一次查询约 10^9 次运算 + 4GB 读），且高维下精确近邻因维度灾难失去意义，用 95% 召回换千倍速度。

**Q9：IVF 的原理？**
先用 k-means 聚成 nlist 个簇，查询时算 query 到中心距离，只进最近 nprobe 个簇暴力扫描；nprobe 越大召回越高越慢。

**Q10：IVF 里 nlist 和 nprobe 怎么定？**
nlist 经验值 4√N，nprobe 取 nlist 的 1%~10%，按召回目标在「召回-延迟」曲线上调。

**Q11：HNSW 的原理和代价？**
多层小世界图，上层稀疏做高速跳转、底层密集做精确命中，贪心游走 O(log N)；代价是内存大（每点存 M 条边，数倍于向量）。

**Q12：HNSW 的三个参数 M / efConstruction / efSearch？**
M 是每层最大连接数（内存/召回）；efConstruction 是建图候选队列（图质量）；efSearch 是查询候选队列（召回旋钮，≥top_k）。

**Q13：PQ 乘积量化怎么压缩？代价？**
把向量切 m 段、每段各自 k-means 聚 256 中心、用 8bit 码本编号近似，压缩 4D/m 倍；代价是量化误差导致召回下降。

**Q14：PQ 的距离怎么算？**
ADC 非对称距离：查询向量保持全精度，预计算每段到码本的距离表，算任意库向量就是查表相加。

**Q15：IVF+PQ 为什么是亿级标配？**
IVF 裁剪搜索范围（nprobe 个簇），PQ 压缩内存（几十倍），两者组合让亿级向量能进内存且毫秒检索。

### 工程类

**Q16：向量库更新文档为什么是「删了重写」？**
文本变了向量全变，且 ANN 图不支持原地改节点；统一按业务 id upsert，底层是标删 + 写新向量。

**Q17：过滤的 Pre-filter 和 Post-filter 有什么区别？**
Pre-filter 先过滤再检索（召回稳但宽条件退化成全量），Post-filter 先检索再过滤（索引高效但苛刻条件可能凑不满 k）；现代库做「过滤+向量联合剪枝」折中。

**Q18：为什么要混合检索？RRF 是什么？**
向量抓语义、抓不到精确关键词，BM25 抓关键词、抓不到语义改写，两者互补；RRF 是倒数排名融合，只看排名把多路结果融合，解决分数量纲不同问题。

**Q19：怎么评估向量检索的召回质量？**
建标注集（ground truth），算 Recall@k（找没找全）、MRR（第一个命中）、nDCG（排序质量），配合召回-延迟曲线调参。

**Q20：Milvus / Chroma / pgvector 怎么选？**
demo 用 Chroma（pip 即用）；已有 PG 且中小规模要 join/事务用 pgvector；生产亿级分布式用 Milvus；极致性能自建用 FAISS。

**Q21：向量数据库为什么是最终一致？**
写入先进 WAL + 内存段，flush 成不可变段并后台建索引后才可检索，删除是软删等段合并，所以读可能不是最新数据。

### RAG 类

**Q22：向量数据库在 RAG 里负责什么？**
离线存 chunk 的向量并建 ANN 索引，在线把查询向量召回 top-k 相关片段供 LLM 生成；质量上限由 chunking 和 Embedding 决定，向量库只负责检索。

**Q23：top_k 怎么选？**
RAG 取 3~8，再配合 ReRank 精排截断到最终 3~5；太大噪声多、token 费，太小召回不全。
