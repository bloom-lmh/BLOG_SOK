# Agent 编排

一句话定位：Agent 编排是把一个或多个 AI Agent（大模型 + 工具 + 记忆）组织起来、按一定结构协作完成任务的流程设计与框架，解决「单个 Agent 能力有限、复杂任务需要分工协作、中间过程需要管理和传递」这三个问题——说白了就是回答三件事：**谁来干、按什么顺序干、信息怎么传**。

---

## 基础篇

### 什么是 Agent

先厘清「Agent」和「编排」是两个层次的东西。Agent 编排的前提是先有一个「Agent」，Agent 这个词在 AI 圈已经被用滥了，面试时先给一个精确的定义：

```
一个 Agent = 大模型（大脑） + 工具（手脚） + 记忆（记性）
```

- **大脑（LLM）**：负责理解目标、做决策、规划下一步；
- **手脚（Tools）**：搜索引擎、数据库、代码执行器、API……让模型能「动手」而不只是「动嘴」；
- **记性（Memory）**：短期记忆（当前对话上下文）+ 长期记忆（外部存储的持久化信息），让 Agent 不「失忆」。

**判断一个东西是不是 Agent 的关键**：看它能不能**自主决策「下一步做什么」**。一个固定流程的 RAG（检索 → 生成）不是 Agent，因为它每一步都是写死的；只有当模型能「自己决定要不要调工具、调哪个工具、调几次、什么时候停」，才叫 Agent。

### 什么是 Agent 编排

一个 Agent = 大模型 + 工具 + 记忆，能自主决策调工具完成目标。但单个 Agent 有天花板：

- 一次要处理的东西太多，上下文塞不下；
- 不同子任务需要不同的角色和专长（写代码的、查资料的、审稿的）；
- 一个 Agent 既当「指挥官」又当「执行者」容易乱。

编排就是把这些 Agent 当「可调度的零件」，设计它们**怎么分工、按什么顺序跑、信息怎么传递**。

一句话理解两者的关系：**Agent 是「单个智能体」，编排是「让多个智能体（或一个智能体的多个步骤）协作的规则」**。编排的对象可以是多个 Agent，也可以是单个 Agent 的复杂循环控制。

### 单个 Agent 的核心循环：ReAct

不管多复杂的编排，最底层都是同一个循环——**ReAct**（Reasoning + Acting，思考与行动交替）：

```
Thought（想） → Action（调工具） → Observation（看结果） → Thought（再想）...
直到能 Answer（回答）
```

ReAct 是 2022 年论文提出的范式，核心洞察是：**让模型把「推理」和「行动」交织在一起**，而不是先想好所有步骤再一次性执行。推理（Thought）让模型明确下一步该做什么、为什么这么做，行动（Action）调用工具获取外部信息，观察（Observation）把工具返回结果喂回模型，形成闭环。

```python
# 为什么是循环而不是直线：Agent 无法预知要调几次工具，
# 必须"试一次、看结果、再决定下一步"，所以核心结构是 while 循环。
while not done:
    thought = model.reason(state)          # 思考：要不要调工具
    if thought.needs_tool:
        result = call_tool(thought.tool)   # 行动：调工具
        state.append(result)               # 观察：把结果塞回上下文
    else:
        return thought.answer              # 结束
```

这一循环在 [LangGraph](/learn_ai/agent/LangGraph) 里就是「agent 节点 + 工具节点 + 条件边」的闭环图。

::: tip 💡 面试题：什么是 ReAct？它的核心是什么？
ReAct = Reasoning（推理）+ Acting（行动），让模型在「思考下一步」和「调用工具」之间循环，直到能给出最终答案。核心是把推理过程显式化，并且让推理结果直接驱动工具调用，解决「纯推理模型没有外部信息、纯行动模型没有规划」的问题。
:::

### ReAct 与 Function Calling 的关系

面试高频追问：ReAct 和 Function Calling（工具调用）是一回事吗？

**不是一回事，但 ReAct 依赖 Function Calling 落地**：

| 概念 | 层次 | 作用 |
| --- | --- | --- |
| Function Calling | 能力层（模型接口） | 模型能输出「要调用哪个函数 + 参数」的结构化 JSON |
| ReAct | 范式层（编排逻辑） | 用「思考→行动→观察」的循环把多次工具调用串起来 |

通俗讲：**Function Calling 是「模型会点菜」，ReAct 是「整个点菜、上菜、吃、再点」的流程**。没有 Function Calling，ReAct 的「Action」就没有落地接口；没有 ReAct 的循环，Function Calling 就只是单次工具调用，无法完成多步任务。详见 [Function Calling](/learn_ai/agent/Function Calling)。

### 最简可运行示例：手写一个 ReAct Agent

不依赖任何框架，用最少的代码跑通「思考 → 调工具 → 观察 → 再思考」的完整循环，理解 Agent 的本质：

```python
# 最简 ReAct Agent：不依赖 LangChain/LangGraph，纯手写，跑通核心循环
# 为什么这么设计：Agent 的本质就是"模型反复决策 + 工具反复执行"，
# 骨架只有三样：工具定义、循环控制、把结果喂回模型。

# 1. 工具：每个工具就是一个函数，带名字和描述（描述很重要，模型靠它决定调谁）
TOOLS = {
    "search":  {"desc": "搜索网页信息，入参 query", "fn": lambda q: f"搜索结果：关于'{q}'的摘要..."},
    "calc":    {"desc": "计算数学表达式，入参 expr", "fn": lambda e: str(eval(e))},
}

# 2. 模拟模型：真实场景这里调用 LLM，让 LLM 输出"思考 + 下一步动作"
#    为什么返回值是结构化 dict：要让循环能判断"继续调工具"还是"结束回答"
def llm_reason(messages):
    # 这里简化为：根据最后一条消息决定动作，真实场景由 LLM 生成 {thought, action}
    last = messages[-1]["content"]
    if "计算" in last or "+" in last:
        return {"action": "calc", "args": "1+2"}
    return {"action": "answer", "args": "已经完成任务"}

# 3. ReAct 循环
def run_agent(question, max_steps=5):
    messages = [{"role": "user", "content": question}]
    for step in range(max_steps):
        decision = llm_reason(messages)                 # 思考：下一步做什么
        if decision["action"] == "answer":              # 能回答了就结束
            return decision["args"]
        tool = TOOLS[decision["action"]]                # 行动：找到工具
        result = tool["fn"](decision["args"])           # 执行工具
        # 观察：把工具结果作为新消息喂回模型，形成闭环——这是 ReAct 的关键
        messages.append({"role": "tool", "content": result})
    return "超过最大步数"                                 # 兜底：防止死循环

print(run_agent("帮我计算 1+2"))
```

运行结果（示意）：模型先决策「调 calc」，拿到结果 `3` 后，下一轮再决策「回答」。这段代码虽然简陋，但它演示的循环结构和真实 Agent 完全一致——**决策 → 执行 → 反馈 → 再决策**，四步一个不落。真实系统只是把 `llm_reason` 换成真正的 LLM 调用、把工具换成生产级工具，循环逻辑不变。

### Plan-and-Execute：先规划再执行

ReAct 是「走一步看一步」，Plan-and-Execute 是「先列计划再逐步执行」：

| 模式 | 思路 | 优点 | 缺点 |
| --- | --- | --- | --- |
| ReAct | 边想边做 | 灵活、能应对变化 | 步骤多时容易跑偏 |
| Plan-and-Execute | 先出完整计划再执行 | 目标感强、步骤清晰 | 计划出错要重来 |

简单任务用 ReAct，**复杂多步任务**（如「调研竞品并写报告」）用 Plan-and-Execute 更稳。

```python
# Plan-and-Execute 与 ReAct 的区别：ReAct 是"每步都重新想"，
# Plan-and-Execute 是"先想好一份完整计划，再逐条执行"。
# 为什么大任务要先规划：步骤一多，边走边想容易在中间迷失方向，
# 先有一份明确计划当"导航"，执行阶段就不容易跑偏。

def plan(goal):
    # 让 LLM 输出一个步骤列表，而不是单个动作
    return ["查资料A", "查资料B", "对比总结", "写报告"]

def execute(steps):
    results = []
    for s in steps:
        results.append(do(s))      # 逐条执行
    return synthesize(results)     # 汇总成最终结果

# 关键点：plan 和 execute 是解耦的两个阶段，
# 计划可以"人审"（Human-in-the-loop）——这在高风险任务里很重要。
```

### 三种「自主程度」的对比

面试常让区分「工作流 vs Agent」的边界。按「模型自主决策的程度」从低到高排列：

| 类型 | 决策者 | 例子 | 特点 |
| --- | --- | --- | --- |
| 固定工作流（Workflow） | 代码写死 | RAG、传统流水线 | 可控、可预测、成本低，但死板 |
| Agent | 模型自主决策 | 单 Agent 循环 | 灵活、能应对未预见的路径，但不可控 |
| 多 Agent 编排 | 模型 + 编排规则 | 主管/交接式多 Agent | 分工协作，处理复杂异构任务 |

核心结论：**自主性越高，能力越强，但可控性和可预测性越差**。工程上不是「越 Agent 越好」，而是「在可控的前提下，把该交给模型的决策交给模型」。这正是编排框架存在的意义——用「图/规则」给模型的自主决策加一个可控的骨架。

## 高级篇

基础篇搭起的是「单个 Agent 能跑」的骨架，高级篇解决的是「多个 Agent 能协作、能上生产」。这一篇覆盖多 Agent 结构、状态管理、通信模式、工程化升级。

### 多 Agent 的四种经典结构

多个 Agent 协作，常见四种「队形」：

| 结构 | 组织方式 | 特点 | 适用 |
| --- | --- | --- | --- |
| Sequential（顺序） | A 干完 → B 干 → C | 简单，单向流水线 | 固定工序，如「写稿→审稿→润色」 |
| Supervisor（主管） | 一个主管 Agent 统一派活、收结果 | 集中调度、可控 | 任务种类多、需要统一兜底 |
| Hierarchical（层级） | 主管下面还有小主管 | 规模大、分工细 | 大型复杂系统 |
| Swarm/Handoff（交接） | 无中心，Agent 之间直接「转交」对话 | 去中心、灵活 | 客服转接、多角色对话 |

::: tip 💡 面试题：多 Agent 编排有哪些常见结构？
Sequential（顺序流水线）、Supervisor（主管集中调度）、Hierarchical（层级）、Swarm/Handoff（去中心交接）。核心区别在于是「谁来分配任务」：顺序模式没有调度者，主管/层级模式有集中调度者，Swarm 模式靠 Agent 自主转交。
:::

四种结构用图直观对比：

```
Sequential（无调度者，单向流水线）：
  [Agent A] ──► [Agent B] ──► [Agent C] ──► 结果

Supervisor（集中调度，星形）：
                      ┌─► [Agent A]
  [Supervisor 主管] ──┼─► [Agent B] ──► 结果收回主管统一汇总
                      └─► [Agent C]

Hierarchical（分层调度，树形）：
                [总主管]
               /        \
        [小组长1]      [小组长2]
         /    \          /    \
      [A]    [B]      [C]    [D]

Swarm/Handoff（去中心，直接转交）：
  [Agent A] ◄──转交──► [Agent B] ◄──转交──► [Agent C]
      ▲                                              │
      └──────────────── 消息流 ───────────────────────┘
```

### 两种通信范式：共享状态 vs 消息传递

多 Agent 之间怎么交换信息，是编排设计的第一性问题。两大范式：

| 维度 | 共享状态（Shared State） | 消息传递（Message Passing） |
| --- | --- | --- |
| 机制 | 所有 Agent 读写同一个全局 State | Agent 之间直接发送消息 |
| 代表框架 | LangGraph（State 图） | AutoGen、Swarm（对话交接） |
| 优点 | 状态集中、易追溯、易做断点恢复 | 解耦彻底、天然适合对话式转交 |
| 缺点 | 状态易膨胀、并发写需要控制 | 消息流难追踪、易丢上下文 |
| 适用 | 流程型、需要强管控的任务 | 对话型、角色切换频繁的任务 |

**LangGraph 是共享状态的典型**：所有节点读写同一个 `State` 对象，节点之间不直接通信，而是「改 State → 图根据 State 决定下一步」。**AutoGen 是消息传递的典型**：Agent 之间像聊天一样互相发消息，谁收到消息谁干活。

::: tip 💡 面试题：多 Agent 通信有哪两种范式？各有什么取舍？
共享状态（如 LangGraph）：所有 Agent 读写同一份 State，状态集中、易追踪、易恢复，但状态会膨胀、并发写要控制。消息传递（如 AutoGen）：Agent 直接互发消息，解耦彻底、适合对话转交，但消息流难追踪、上下文容易丢。选型看任务性质：流程型用共享状态，对话型用消息传递。
:::

### 什么时候需要多 Agent

不是越复杂越好，多数场景单 Agent 就够了。判断标准：

- **单 Agent 够**：任务单一、工具不多、上下文放得下；
- **上多 Agent**：子任务明显异构（需要不同专长）、上下文会超、要并行加速、不同角色要隔离不同的提示词和工具。

多 Agent 的代价是**更慢、更贵、更难调试**，所以原则是「能用单 Agent 就不用多」。

补充一个工程判断信号：**当你的单 Agent 提示词里塞满了「如果是 A 场景就……如果是 B 场景就……」的分支时**，说明该拆多 Agent 了——因为一个模型既要当多个角色，提示词之间会互相干扰。拆开后每个 Agent 只背一个角色的指令，提示词更干净、更可控。

### 主流编排框架对比

| 框架 | 定位 | 特点 |
| --- | --- | --- |
| [LangChain](/learn_ai/agent/LangChain) | 组件化链式编排 | 快速搭线性流程、RAG |
| [LangGraph](/learn_ai/agent/LangGraph) | 有状态图编排 | 循环/分支/多 Agent/断点恢复，生产级 |
| AutoGen | 多 Agent 对话框架 | 微软出品，强调 Agent 间自动对话协作 |
| CrewAI | 角色化团队编排 | 每个 Agent 有角色、目标、背景故事，上手快 |
| OpenAI Swarm | 轻量交接式编排 | 主打「交接 + 无状态」，极简 |
| Semantic Kernel | 企业级编排 SDK | 微软出品，与企业服务深度集成 |
| Dify / Coze / n8n | 低代码编排平台 | 拖拽式搭建，可视化，非程序员友好 |

选型一句话：**要控制力、要上生产选 LangGraph；要快速体验多 Agent 对话选 CrewAI/AutoGen；简单线性流程用 LangChain 就够了。**

补充选型的三个判断维度：

```
1. 控制粒度：你需要"图/状态机"级别的精确控制，还是"对话"级别的松散协作？
   → 精确控制 → LangGraph；松散协作 → AutoGen/CrewAI
2. 有状态需求：是否需要断点恢复、人工审批、长期运行？
   → 需要 → LangGraph（Checkpoint 持久化）；不需要 → Swarm（无状态）
3. 团队背景：工程师团队 → 代码框架；产品/运营 → 低代码平台（Dify/Coze）
```

### 编排要解决的三个工程问题

1. **状态与上下文传递**：哪个 Agent 能看到哪些信息、对话历史怎么流转（LangGraph 用 State 解决）；
2. **调度与循环控制**：谁先跑、什么时候停、失败要不要重试（图的条件边/循环解决）；
3. **可观测性**：多 Agent 跑起来后，要能追踪每个 Agent 的输入输出、工具调用、token 消耗，否则出问题没法查。

这三点对应三个具体工程问题，展开讲透：

### 状态管理：编排的「记忆中枢」

多 Agent 系统里，状态管理解决「谁记得什么、谁忘了什么」。设计状态时最核心的问题是**「这个字段谁写、谁读」**：

| 状态设计问题 | 说明 | 反面案例 |
| --- | --- | --- |
| 全局 vs 局部 | 哪些信息全局共享，哪些只属于某个 Agent | 把临时中间变量塞进全局状态，导致状态爆炸 |
| 谁写谁读 | 每个字段的「生产者」和「消费者」要明确 | 两个 Agent 同时改一个字段，结果不确定 |
| 持久化 | 状态要不要落库（断点恢复） | 长任务中途崩溃，全部重来 |

LangGraph 的 State 通过 **Reducer（归约器）**解决并发写问题——当多个节点都要往同一个字段（如消息列表）写东西时，Reducer 定义了「怎么合并」（比如 append 拼接），避免了覆盖丢失。

### 上下文管理：编排的核心难题

多 Agent 最难的工程问题是**上下文爆炸**：N 个 Agent 的中间过程都塞进上下文，很快超限。常见解法：

| 解法 | 做法 |
| --- | --- |
| 隔离 | 每个 Agent 只看自己相关的上下文，不共享全部 |
| 压缩 | 用模型把上游结果压缩成摘要再传给下游 |
| 结构化传递 | Agent 之间只传结构化结果（JSON），不传原始对话 |

面试常问一句：**多 Agent 系统里上下文不是越多越好，要按「最小必要信息」原则传递**。

再补一个关键点：**「最小必要信息」不是「最少信息」**。传递的信息要足以让下游 Agent 独立完成任务，少了会导致下游「猜」，多了会引入噪声。经验法则是：**传「结论 + 关键依据」，不传「完整推导过程」**。

### 反思与自我修正（Reflection）

Agent 会犯错，高级 Agent 的关键能力是**能发现自己的错误并改正**。反思（Reflection）的典型实现是「生成 → 自我批评 → 重生成」：

```
生成 Agent 产出结果
      │
      ▼
反思 Agent 用"挑刺"的提示词审查结果（找错误、找漏洞）
      │
      ▼
有问题？──是──► 把批评意见反馈给生成 Agent，重新生成
      │
      否
      ▼
    输出结果
```

反思能显著提升复杂任务（代码、写作、推理）的质量，代价是**多一轮 LLM 调用**。工程上通常给反思设一个上限（比如最多重试 2~3 次），防止无限循环。

::: tip 💡 面试题：Agent 的反思（Reflection）机制是什么？为什么有效？
反思是「生成 → 自我批评 → 重生成」的循环：一个 Agent（或同一 Agent 换个提示词）专门挑错，把批评意见反馈给生成者改进。有效的原因是：模型在「挑别人的错」时往往比「自己做」更客观，且多一次生成 = 多一次采样改进的机会。代价是多一次调用，需设重试上限防死循环。
:::

### 工具选择与错误处理

Agent 调工具是「最不可控」的环节，工程上要处理三类问题：

| 问题 | 表现 | 对策 |
| --- | --- | --- |
| 工具选错 | 模型调了不相关的工具 | 工具描述写清楚「何时用、何时不用」，提供分类提示 |
| 参数填错 | 参数格式不对、缺字段 | 用 Function Calling 的 schema 强约束 + 参数校验兜底 |
| 工具调用失败 | 超时、网络错误、工具返回异常 | 重试（带退避）、降级（换备选工具）、失败后反馈给模型 |

一个常见的工程模式是「**错误回灌**」：工具调用失败时，不是直接抛异常，而是把错误信息作为 Observation 喂回模型，让模型自己决定「换个参数重试」还是「换个工具」还是「告诉用户失败」。这比写死重试逻辑更灵活。

### Human-in-the-Loop（人工介入）

生产级 Agent 不会全自动，关键节点要「人审」。人工介入的典型位置：

| 介入点 | 场景 | 实现 |
| --- | --- | --- |
| 计划审批 | 执行高风险计划前让人确认 | Plan-and-Execute 里 plan 阶段挂起等人确认 |
| 关键动作前 | 发邮件、付款、删除数据等不可逆操作 | 工具层加「需人工批准」标记 |
| 结果兜底 | 模型不确定、置信度低时转人工 | 条件边判断置信度，低了走人工节点 |

LangGraph 通过 **Checkpoint + interrupt** 实现人工介入：图执行到某节点挂起（中断），把状态持久化，等人批准后从断点继续。这是「有状态编排」的核心优势——无状态编排很难实现这种「暂停-恢复」。

### Agent 评估

Agent 比单个模型难评估，因为要评的不是「一句话答得对不对」，而是「一整段多步行为好不好」。常用评估维度：

| 维度 | 衡量 | 指标示例 |
| --- | --- | --- |
| 任务成功率 | 最终有没有完成任务 | 成功率（完成数 / 总任务数） |
| 轨迹质量 | 过程合不合理（有没有绕弯路、乱调工具） | 平均步数、工具调用次数 |
| 成本效率 | 花了多少 token/钱 | 平均 token 消耗、平均成本 |
| 鲁棒性 | 面对干扰/失败能不能恢复 | 注入错误后的成功率 |

Agent 评估常用「**模拟环境跑 benchmark**」：把 Agent 放进一个有标准答案的环境（如代码任务、网页操作任务），跑一批任务统计指标。也可以让「评估 Agent」给「被测 Agent」的轨迹打分（LLM-as-Judge），但要注意评判本身的偏差。

### 常见坑与对策总表

| 坑 | 表现 | 原因 | 对策 |
| --- | --- | --- | --- |
| 无限循环 | Agent 反复调同一个工具不停 | 没有终止条件 / 模型卡住 | 设 max_steps、连续相同动作检测 |
| 上下文爆炸 | 多轮后 token 超限 | 中间过程全堆进上下文 | 压缩/摘要/只传结构化结果 |
| 工具幻觉 | 模型调了不存在的工具、编造参数 | 工具描述不清 / 模型幻觉 | 严格 schema + 校验 + 错误回灌 |
| 职责混乱 | 多 Agent 互相推诿或重复干活 | 角色边界不清 | 明确每个 Agent 的职责和触发条件 |
| 状态丢失 | 长任务中途崩溃无法恢复 | 状态没持久化 | Checkpoint 持久化 + 断点恢复 |
| 成本失控 | 多 Agent 反复重试导致 token 暴涨 | 反思/重试无上限 | 设重试上限、缓存中间结果 |

## 原理篇

基础篇讲「是什么、怎么用」，原理篇讲「为什么这么设计、底层发生了什么」。这一篇下到机制层面，把编排的几个核心原理彻底讲透。

### 为什么编排的本质是「状态机」

把任意 Agent 流程抽象后，本质都是一张**有向图（状态机）**：

- **状态** = 当前上下文（对话历史 + 中间结果 + 已完成步骤）；
- **转移** = 每个 Agent/工具执行后，状态如何变化、下一步去哪。

所以无论 LangGraph 的图、还是 AutoGen 的对话，底层都在做同一件事：**定义状态、定义状态如何流转**。理解了「状态 + 转移」，就理解了所有编排框架。

形式化定义：一个 Agent 编排可以表示为一个状态机 `M = (S, s0, Σ, δ, F)`：

```
S   = 状态集合（对话历史 + 中间结果 + 已用工具）
s0  = 初始状态（用户问题）
Σ   = 动作集合（调工具、回答、转交另一个 Agent）
δ   = 转移函数 δ(s, a) → s'（执行动作后状态如何变）
F   = 终止状态（给出最终答案）

一次 Agent 运行 = 从 s0 出发，反复选择动作 a，沿 δ 转移，
直到进入终止状态 F。选择"下一个动作 a"的策略，就是 Agent 的"大脑"（LLM）。
```

这个抽象解释了为什么编排框架都用「图」：**因为状态机天然用图表达**——节点是状态（或处理步骤），边是转移（含条件判断）。LangGraph 的「节点 + 边 + 条件边」就是这个数学模型的工程实现。

### 为什么「图」比「链」更强大

LangChain 早期是「链（Chain）」，LangGraph 升级成「图（Graph）」。这一字之差背后是**计算能力的本质区别**：

| 能力 | 链（Chain，线性） | 图（Graph，有向图） |
| --- | --- | --- |
| 循环 | ❌ 不支持 | ✅ 支持（边可以指回已访问节点） |
| 分支 | 有限 | ✅ 条件边，任意分支 |
| 状态 | 隐式、难控制 | ✅ 显式 State |
| 并行 | 难 | ✅ 多路 fan-out |
| 断点恢复 | 难 | ✅ Checkpoint |

关键点：**ReAct 循环需要「循环」，链表达不了循环**。所以一旦要构建真正的 Agent（而不是固定流水线），就必须用图。这解释了为什么 LangChain 官方自己推出了 LangGraph——链式抽象的天花板就是「不能回头」。

### 状态机 vs 决策树：Agent 为何不是「if-else」

有人会问：既然本质是状态机，那 Agent 是不是就是一堆 if-else？不是，本质区别在于**「转移函数 δ 由谁来算」**：

```
传统工作流（if-else）：
  δ 由程序员写死——遇到 A 情况走分支1，B 情况走分支2
  缺点：情况无穷多，写不完；边界情况一漏就崩

Agent 编排：
  δ 由 LLM 动态计算——模型根据当前状态，判断"下一步最合理做什么"
  缺点：不可预测、可能出错；但能处理写死覆盖不了的开放情况
```

所以 Agent 编排的核心创新是：**把「转移决策」从代码交给了模型**，图的骨架仍然由人（框架）控制，保证有边界，但每条边的「什么时候走」由模型判断，保证灵活。**图是笼子，模型是笼子里的决策者**——这是对「可控 + 灵活」这一矛盾的最优解。

### ReAct 的底层：一个「工具增强」的马尔可夫决策过程

ReAct 循环在数学上可以看成一个 **MDP（马尔可夫决策过程）** 的特例：

```
MDP = (状态, 动作, 转移, 奖励)

ReAct 里的对应：
  状态   = 当前对话上下文（含所有历史）
  动作   = 调工具 / 回答
  转移   = 动作执行后，新信息加入上下文 → 新状态
  奖励   = 隐式的（最终答案的质量），没有显式奖励信号

Agent 的"策略" π(s) → a，就是 LLM 在给定上下文下"生成下一个动作"。
```

为什么这个对应关系重要？因为它揭示了两个深层问题：

1. **没有显式奖励**：Agent 每一步「调哪个工具」没有即时打分，只能靠「最终答没答对」来事后评价。所以 Agent 的训练/优化比普通监督学习难得多（这是 RLHF/强化学习用在 Agent 上的动机）。
2. **状态包含全部历史**：MDP 的「马尔可夫性」（下一状态只依赖当前状态）要求当前状态「包含做决策所需的全部信息」——这就是为什么上下文管理是 Agent 的核心难题，一旦上下文被压缩/截断，就破坏了「状态完整性」，模型会做出错误决策。

### 上下文窗口的数学：为什么 N 个 Agent 会「爆炸」

多 Agent 上下文爆炸是有数学规律的。假设每个 Agent 的中间过程（思考 + 工具调用 + 结果）平均占用 `k` 个 token，一个任务串行经过 `N` 个 Agent：

```
总 token 消耗（最坏情况，全量传递）：
  T = Σ_{i=1..N} k_i ≈ N · k̄

如果加上"反思重试"，每个 Agent 平均重试 r 次：
  T ≈ N · k̄ · (1 + r)

如果多轮对话（用户追问 m 轮），每轮都重新跑一遍：
  T ≈ m · N · k̄ · (1 + r)
```

结论：**token 消耗随「Agent 数 × 重试次数 × 对话轮数」线性甚至超线性增长**。而上下文窗口是硬上限（如 128K），一旦超出就要截断或压缩，进而引发「遗忘中间信息 → 决策变差」的恶性循环。这就是为什么「隔离、压缩、结构化传递」不是锦上添花，而是多 Agent 系统的**生存必需**。

### 工具调用的协议级细节：模型如何「动手」

Agent 调工具在底层是怎么实现的？以 OpenAI 的 Function Calling 为例，协议分三步：

```
第 1 步：请求时声明工具
  POST /chat/completions
  {
    "messages": [...],
    "tools": [
      {
        "type": "function",
        "function": {
          "name": "get_weather",                      // 工具名
          "description": "查询指定城市天气",           // 描述（模型靠它判断调谁）
          "parameters": {                             // 参数 schema（JSON Schema 约束）
            "type": "object",
            "properties": {"city": {"type": "string"}},
            "required": ["city"]
          }
        }
      }
    ]
  }

第 2 步：模型返回 tool_call（不直接给最终答案）
  {
    "choices": [{
      "message": {
        "role": "assistant",
        "tool_calls": [{                              // 模型"请求"调工具
          "id": "call_abc123",
          "function": {"name": "get_weather", "arguments": "{\"city\":\"北京\"}"}
        }]
      },
      "finish_reason": "tool_calls"                   // 关键：结束原因 = 要调工具
    }]

第 3 步：客户端执行工具，把结果作为 tool 消息回传
  {
    "messages": [
      ...,
      {"role": "assistant", "tool_calls": [...]},
      {"role": "tool", "tool_call_id": "call_abc123", "content": "北京晴，25度"}  // 结果回传
    ]
  }
  → 模型再基于这个结果决定：继续调工具 or 给最终答案
```

理解这个协议的三个关键点：

1. **`finish_reason` 是循环的控制信号**：`tool_calls` 表示「还没完，要继续」，`stop` 表示「给最终答案了」。ReAct 循环的「done 判断」就靠这个字段。
2. **参数用 JSON Schema 约束**：这不是给模型看的「提示」，而是**硬约束**，模型会尽量生成符合 schema 的参数。这是「参数填错」问题的第一道防线。
3. **`tool_call_id` 是关联纽带**：一次请求可能有多个 tool_call，回传结果时必须带上对应的 id，模型才能对上号。

### 为什么模型会「调错工具」：从概率角度理解

模型调工具不是「查表」，而是「生成」。它本质是在生成一个「最可能的工具调用」，所以会犯错：

```
模型面对 "帮我查一下明天北京天气" 时，实际上是在算：
  P(下一个 token = "get_weather" | 上文) = 高
  P(下一个 token = "search"     | 上文) = 中
  P(下一个 token = "calc"       | 上文) = 低
  ...
然后采样（或贪心）选一个。采样意味着"有小概率选错"。

工具描述的作用 = 改变这个概率分布：
  description 写清楚 "查天气用 get_weather，别用 search"
  → P(get_weather) 升高，P(search) 降低
```

所以「工具描述写得好不好」直接决定「工具选得对不对」，这不是玄学，是有概率原理支撑的。同理，「错误回灌」（把失败信息喂回模型）能纠错的原理是：失败信息进入上下文后，改变了模型下一次决策的概率分布，让它倾向换个选择。

### 有状态编排的 Checkpoint 机制

LangGraph 的「断点恢复」是生产级 Agent 的刚需，底层原理是 **Checkpoint（检查点）**：

```
每次节点执行后，把 State 完整序列化保存（落库/内存）

执行流程：
  [节点A] ──checkpoint──► [节点B] ──checkpoint──► [节点C]
      │                      │                      │
      ▼                      ▼                      ▼
  保存 State₁            保存 State₂            保存 State₃

崩溃恢复：
  系统崩溃在节点C → 从最近的 checkpoint（State₂）恢复 → 从节点C重跑

人工介入：
  节点B 设置 interrupt → 执行到节点B 挂起 → 人等操作 → 从 State₂ 继续
```

Checkpoint 的两个作用：**故障恢复**（crash 后不用从头来）和**人工介入**（挂起等待时状态不丢）。它要求 State 是**可序列化**的——这也是为什么 LangGraph 强调「State 里别放不可序列化的对象」。

## 面试常问

- **Q：什么是 Agent？** 大模型 + 工具 + 记忆的自主决策体，核心是能自己决定「下一步做什么」，区别于写死流程的工作流。

- **Q：什么是 Agent 编排？** 把单个或多个 Agent 组织起来、按结构协作完成任务的流程设计与框架，回答「谁来干、按什么顺序、信息怎么传」。

- **Q：ReAct 是什么？** 思考与行动交替的循环：模型不断「思考→调工具→观察结果」直到能给出答案，是几乎所有 Agent 的底层范式。

- **Q：ReAct 和 Plan-and-Execute 的区别？** ReAct 走一步看一步（灵活但易跑偏），Plan-and-Execute 先列完整计划再逐步执行（目标感强但计划错要重来）。

- **Q：ReAct 和 Function Calling 的关系？** Function Calling 是模型「输出工具调用」的接口能力，ReAct 是用循环把多次工具调用串起来的编排范式；ReAct 依赖 Function Calling 落地。

- **Q：多 Agent 常见结构？** Sequential（顺序）、Supervisor（主管）、Hierarchical（层级）、Swarm/Handoff（交接），区别在「谁来调度」。

- **Q：多 Agent 通信有哪两种范式？** 共享状态（LangGraph，集中 State）和消息传递（AutoGen，Agent 互发消息）；流程型用前者，对话型用后者。

- **Q：什么时候需要多 Agent？** 子任务异构、上下文会超、要并行或隔离角色时；否则单 Agent 更简单更省。

- **Q：编排的本质是什么？** 一张有向图（状态机）：状态 = 上下文，转移 = 执行动作后的流转；所有框架底层都在做「定义状态 + 定义流转」。

- **Q：为什么图（Graph）比链（Chain）更强？** 图支持循环、分支、显式状态、并行、断点恢复；ReAct 的循环用链表达不了，所以真正 Agent 必须用图。

- **Q：多 Agent 的上下文怎么管？** 按「最小必要信息」原则：隔离（各看各的）、压缩（摘要传递）、结构化传递（只传 JSON 结论），避免 N 个 Agent 中间过程堆爆上下文。

- **Q：反思（Reflection）是什么？** 「生成 → 自我批评 → 重生成」的循环，靠挑错反馈改进结果，代价是多一次调用，需设重试上限。

- **Q：Agent 怎么避免无限循环？** 设 max_steps 上限、检测连续相同动作、明确终止条件（finish_reason = stop）。

- **Q：Agent 为什么难评估？** 要评的不是一句话而是多步轨迹，维度包括任务成功率、轨迹质量、成本、鲁棒性，常用模拟环境跑 benchmark。
