# 提交规范 Conventional Commits

## 什么是 Conventional Commits

就是一种提交规范，用这种规范来进行提交，可以让你的提交历史更加清晰，更容易被其他人理解。格式如下：

```Text
<type>[optional scope]: <description>

[optional body]

[optional footer(s)]
```

> 官网：https://www.conventionalcommits.org/

## 为什么使用 Conventional Commits？

| 好处                     | 说明                                                              |
| ------------------------ | ----------------------------------------------------------------- |
| 自动生成 CHANGELOG       | 工具（如 `conventional-changelog`）可解析 commit 生成发布日志     |
| 自动语义化版本（SemVer） | 工具（如 `standard-version`, `semantic-release`）自动 bump 版本号 |
| 提高团队协作效率         | 提交信息标准化，新人也能快速理解历史变更                          |
| 支持自动化发布流程       | CI/CD 可根据 commit 类型决定是否发版、发什么版本                  |
| 更好地集成 Git 工具      | 如 `git log --oneline` 输出更清晰                                 |

## 格式说明

### Type（类型）

表示本次提交的**意图**，常用类型包括：

| 类型       | 说明                                              |
| ---------- | ------------------------------------------------- |
| `feat`     | 新增功能（`feature`）                             |
| `fix`      | 修复 `bug`                                        |
| `docs`     | 文档更新（如 `README`、注释）                     |
| `style`    | 代码格式调整（不影响逻辑，如空格、分号）          |
| `refactor` | 重构（既不是新增功能，也不是修复 `bug`）          |
| `perf`     | 性能优化                                          |
| `test`     | 添加或修改测试                                    |
| `build`    | 构建系统或外部依赖变更（如 `webpack、npm``）      |
| `ci`       | CI 配置文件和脚本（如 `GitHub Actions, Jenkins`） |
| `chore`    | 杂项（如更新 `.gitignore`、脚本工具）             |
| `revert`   | 回滚之前的提交                                    |

::: tip 💡 提示
这些类型通常与 **语义化版本（SemVer）** 对应：

- `feat` → **MINOR** 版本（v1.**2**.0）
- `fix` / `perf` → **PATCH** 版本（v1.1.**1**）
- 含 `BREAKING CHANGE` → **MAJOR** 版本（v**2**.0.0）

:::

### Scope（作用域）

用括号括起来，表示本次变更影响的模块或组件：

```text
feat(user): add profile picture upload
fix(api): handle null response in /orders
```

### Description（描述）

- 简洁说明**做了什么**
- 使用**祈使句**（imperative mood），如 “add”, “fix”, “update”（不要用 “added”, “fixed”）
- 首字母小写，结尾不加句号
  - 正确：`feat: add dark mode toggle`
  - 错误：`feat: Added dark mode toggle.`

### Body（正文）

- 详细解释**为什么改**、**如何改**
- 可包含背景、设计决策、对比方案等
- 每行建议 ≤72 字符（便于终端查看）

### Footer（页脚）

常用于：

1. **关联 Issue**：

```text
Closes #123
Fixes #456
```

2. **重大变更（Breaking Change）**：

```text
BREAKING CHANGE: The `userId` parameter is now required.
```

> ⚠️ 只要包含 `BREAKING CHANGE:`（大小写不敏感），就视为**破坏性变更**，会触发主版本号升级。

## 相关工具

| 工具                                                                             | 作用                                        |
| -------------------------------------------------------------------------------- | ------------------------------------------- |
| [`commitizen`](https://commitizen.github.io/cz-cli/)                             | 交互式生成符合规范的 `commit`               |
| [`husky` + `commitlint`](https://commitlint.js.org/)                             | 在 `commit` 时校验格式                      |
| [`standard-version`](https://github.com/conventional-changelog/standard-version) | 自动生成 `CHANGELOG + bump` 版本 + 打 `tag` |
| [`semantic-release`](https://semantic-release.gitbook.io/)                       | 全自动发布（`CI` 中运行）                   |

## 示例

```text
feat: allow provided config object to extend other configs

The new `extends` property in config allows users to inherit from base configs.
This reduces duplication in large projects.

Closes #87

---
fix(ui): correct button padding in mobile view

Padding was too large on iOS Safari.

---
docs: update contribution guide

---
BREAKING CHANGE: remove support for Node 12

Node.js 12 has reached end-of-life. Minimum supported version is now Node 14.
```
