## 节省磁盘空间

![节省磁盘空间](https://image-bucket-1307756649.cos.ap-chengdu.myqcloud.com/image/20251019102535606.png)

使用 `npm` 时，如果你有 100 个项目(100 个`node_modules`)，这 100 个项目都依赖于相同的依赖，则这个依赖会复制 100 份到这些项目中，即磁盘上将保存该依赖的 100 个副本。使用 `pnpm`，依赖将存储在内容可寻址存储中，因此：

1. 增量更新：如果你依赖于不同版本的依赖，则仅将不同的文件添加到存储中。

> 例如，如果它有 100 个文件，并且新版本仅对其中一个文件进行了更改，则 `pnpm update` 将仅向存储添加 1 个新文件，而不是仅针对单个更改克隆整个依赖。

2. 硬链接技术：所有文件都保存在磁盘上的一个位置。安装软件包后，它们的文件从该位置进行硬链接，不消耗额外的磁盘空间。这允许你跨项目共享相同版本的依赖。

因此，你可以节省大量磁盘空间，与项目和依赖的数量成正比，并且安装速度更快！

## 提高安装速度

pnpm 分三个阶段执行安装：

1. 依赖解析：pnpm 解析 `package.json` 文件，并计算出需要安装和更新的依赖，然后安装它们。

> 大白话 ​：pnpm 先看你项目的 package.json（就像你的购书清单），然后去“中央仓库”（npm 官网）查一下，要买《lodash》这本书，需不需要同时买《书签》、《练习册》这些附属品（也就是依赖的依赖）。查清楚后，它会把所有需要的书都登记下来，并确保这些书在它自己的“中央仓库”（也就是本地的一个存储中心）里都有存货。

2. 目录结构计算：`node_modules` 目录结构是根据依赖计算出来的

> 大白话 ​：书都齐了，现在要规划一下怎么放进你的“书架”（也就是 node_modules 文件夹）。pnpm 会设计一个非常巧妙和节省空间的“摆放方案”，确保每本书都放在最合理的位置，不会重复摆放，并且你（你的项目）能很容易地找到它们。

3. 链接依赖：所有剩余的依赖都会从存储中获取并硬链接到 `node_modules`。

> 大白话 ​：这是 pnpm 最牛的地方！它不会真的把书从“中央仓库”里再复印一本新的放到你的书架上。而是创建一种“快捷方式”​​（硬链接）。
> npm/yarn 的做法 ​：是直接复印一本新书给你，你有 100 个项目，就有 100 本一模一样的书，非常占地方。
> ​pnpm 的做法 ​：它只是在你的书架上放一个“牌子”（硬链接），这个牌子直接指向“中央仓库”里的那唯一的一本实体书。当你（你的项目）要看书时，通过这个牌子就能直接读到中央仓库里的那本书。

![pnpm解析](https://image-bucket-1307756649.cos.ap-chengdu.myqcloud.com/image/20251019104315449.png)
这种方法比解析、获取所有依赖并将所有依赖写入 node_modules 的传统三阶段安装过程要快得多。

![传统解析方式](https://image-bucket-1307756649.cos.ap-chengdu.myqcloud.com/image/20251019104339632.png)

::: tip 总结
pnpm 带来了以下优势：

1. 并行下载
2. 依赖硬链接代替复制
3. 增量更新

## 幽灵依赖

使用 `npm` 或 `Yarn Classic` 安装依赖时，所有包都会提升到模块目录的根目录。因此，源代码可以访问未作为依赖添加到项目中的依赖(这会导致幽灵依赖)。

### 什么是幽灵依赖(扁平的 node_modules)

幽灵依赖 ​：你的项目代码中，引用了某个没有在 `package.json` 的 `dependencies` 或 `devDependencies` 中声明的包。
产生原因（`npm/yarn` 的扁平化结构）​​：

1. `npm` 或 `Yarn Classic` 会把所有依赖（包括依赖的依赖）​ 提升到 `node_modules`根目录。
2. 你的代码可以直接 `require('axios')`，即使你的 `package.json`里根本没写 `axios`，它可能是某个直接依赖（比如 vue）自己带来的依赖。
3. 这就像你的项目里“幽灵”般地出现了一个包，你可以直接用，但它并不是你明确声明的。

### 产生幽灵依赖的本质原因

`node`的包查找机制就是从根目录开始，一层一层的查找`node_modules`文件夹，直到找到依赖的模块。

### pnpm 如何解决幽灵依赖？(非扁平的 node_modules)

`pnpm` 默认使用符号链接，只把你项目在 `package.json`里直接声明的依赖，链接到 `node_modules`的根目录。

默认情况下，`pnpm` 使用符号链接仅将项目的直接依赖添加到模块目录的根目录中，如下所示：
![创建非扁平 node_modules 目录](https://image-bucket-1307756649.cos.ap-chengdu.myqcloud.com/image/20251019105256654.png)

对比`npm`和`yarn`
::: code-group

```bash [​npm/yarn（扁平化）​​]
node_modules/
├── axios/          <-- 依赖的依赖，被提升到根目录
├── react/          <-- 直接依赖
└── lodash/         <-- 直接依赖
```

```bash [pnpm（非扁平化）​​]
node_modules/
├── .pnpm/          <-- 所有依赖的实际存储位置（嵌套结构）
├── react/ -> .pnpm/.../react/   <-- 符号链接：只有直接依赖在根目录
└── lodash/ -> .pnpm/.../lodash/
```

:::

### 依赖提升

有些时候你需要使用一些非直接依赖，你仍然可以使用 `pnpm` 并将 `nodeLinker` 设置设置为 `hoisted`。这将指示 `pnpm` 创建一个与 `npm` 和 `Yarn Classic` 创建的目录类似的 `node_modules` 目录。

> 大白话：pnpm 中如果想要使用一些非直接依赖时，可以将其提升到根目录，这样项目就可以直接使用了
