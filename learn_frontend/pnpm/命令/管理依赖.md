## `pnpm add <pkg>`

### 基本介绍

作用：安装软件包及其依赖的任何软件包。默认情况下，任何新包都会作为生产依赖安装。
| 命令 | 意义 |
|---------------------|-------------------------------|
| `pnpm add sax` | 保存到 `dependencies` |
| `pnpm add -D sax` | 保存到 `devDependencies` |
| `pnpm add -O sax` | 保存到 `optionalDependencies` |
| `pnpm add -g sax` | 全局安装包 |
| `pnpm add sax@next` | 从 `next` 标签安装 |
| `pnpm add sax@3.0.0`| 指定版本 `3.0.0` |

### 支持的包位置

#### 从 npm 注册表安装

默认情况下，`pnpm add package-name` 会从 `npm` 注册表 安装最新版本的 `package-name`。
版本兼容：如果在工作区中执行，该命令将首先尝试检查工作区中的其他项目是否使用指定的包。如果是这样，将安装已使用的版本范围。

假设你的 `monorepo` 结构如下：

```bash
my-monorepo/
├── packages/
│   ├── project-a/
│   │   └── package.json  # 已声明 "lodash": "^4.17.21"
│   └── project-b/
│       └── package.json  # 未声明 lodash
├── pnpm-workspace.yaml
```

在 `project-b` 目录下执行 `pnpm add lodash`，`pnpm` 会检测到 `project-a`已经用了 `lodash@^4.17.21`，因此会优先安装 `^4.17.21`范围内的最新版本 ​（如 `4.17.21`），而不是直接装最新的 `lodash@5.x`。这样做有两个好处：

1. 避免版本冲突 ​：确保工作区内所有项目使用相同的主要版本 ​（比如都兼容 `lodash@4.x`），防止因版本不一致导致的运行时错误。
2. 减少重复安装 ​：如果工作区已有该包，直接复用，节省磁盘空间和安装时间。

#### 从工作区安装

当你在 `pnpm` 的 `workspace`（`monorepo` 多包项目）里安装依赖时，具体从哪里安装（是本地链接还是远程 `npm` 仓库），取决于两个关键配置：​

##### link-workspace-packages

`link-workspace-packages`：控制是否优先直接链接工作区内的包，而不是从远程 `npm` 安装(如果有则从全局`store`进行硬链接)。

1.  `true`（默认）：优先使用工作区内的包 ​（如果存在）。

```bash
monorepo/
├── packages/
│   ├── utils/     # 本地包 `@my/utils`
│   └── app/       # 需要安装 `@my/utils`
```

`app`的 `node_modules/@my/utils`​ 直接指向 `../utils`​（文件系统链接）

2.  `false`：​ 总是从 npm 或其他注册表安装，即使工作区里有同名包。比如：

```bash
cd packages/app
pnpm add @my/utils
```

`pnpm` 会检查全局 `store` 是否有 `@my/utils`：

- 如果有 → 从 `store` ​ 硬链接到 `app/node_modules`（不重复下载）。
- 如果没有 → 从 `npm` 下载到 `store`，再硬链接。

##### workspace-protocol

在 `package.json`中强制指定某个依赖必须来自工作区，格式为 `"workspace:*"`或 `"workspace:版本"`。

```json
{
  "dependencies": {
    "@my/utils": "workspace:*" // 始终使用工作区内的最新代码
  }
}
```

`workspace:*`：总是链接工作区内的最新版本（类似 yarn workspace:）。
`workspace:1.0.0`：必须匹配工作区内的 `1.0.0` 版本（否则报错）。

#### 从本地文件系统安装

从本地文件系统安装有两种方法：

1. 来自 `tarball` 文件（`.tar`、`.tar.gz` 或 `.tgz`）
2. 从目录

```bash
pnpm add ./package.tar.gz
pnpm add ./some-directory
```

当你从目录安装时，将在当前项目的 `node_modules` 中创建符号链接，因此与运行 `pnpm link` 相同。

#### 其它安装方式

因为其它方式不常用，所以请参见：[官网文档](https://pnpm.nodejs.cn/cli/add#install-from-npm-registry)

### 选项

好的！根据图片中的命令行选项，我为你整理成分类表格，包含解释和使用示例。

#### 依赖类型选项

| 选项          | 全称                               | 解释                               | 使用示例                   |
| ------------- | ---------------------------------- | ---------------------------------- | -------------------------- |
| `-P`          | `--save-prod`                      | 保存为**生产依赖**（项目运行必需） | `pnpm add -P lodash`       |
| `-D`          | `--save-dev`                       | 保存为**开发依赖**（仅开发时需要） | `pnpm add -D typescript`   |
| `-O`          | `--save-optional`                  | 保存为**可选依赖**（非必需依赖）   | `pnpm add -O fsevents`     |
| `-E`          | `--save-exact`                     | **精确版本**（避免自动升级）       | `pnpm add -E react@18.2.0` |
| `--save-peer` | 保存为**对等依赖**（宿主环境提供） | `pnpm add --save-peer react`       |

比如`monorepo`开发场景:

```bash
# 给特定包安装生产依赖
pnpm --filter=web-app add -P axios

# 给所有包安装相同的开发工具
pnpm --filter="*" add -D prettier

# 精确版本的工作区依赖
pnpm add --workspace -E typescript
```

#### 工作区相关选项

| 选项                  | 解释                         | 使用示例                         |
| --------------------- | ---------------------------- | -------------------------------- |
| `--workspace`         | 只在**工作区根目录**安装依赖 | `pnpm add --workspace eslint`    |
| `--filter <selector>` | **过滤特定包**进行操作       | `pnpm --filter=my-app add axios` |

#### 全局安装选项

| 选项            | 解释                         | 使用示例               |
| --------------- | ---------------------------- | ---------------------- |
| `-g` `--global` | **全局安装**（所有项目可用） | `pnpm add -g @vue/cli` |

## pnpm install

### 基本介绍

作用：`pnpm install` 用于安装项目的所有依赖。

::: warning 注意

- 在 `CI` 环境中，如果存在锁定文件但需要更新，则安装会失败。
- 在 `workspace` 内，`pnpm install` 安装所有项目中的所有依赖。如果要禁用此行为，请将 `recursive-install` 设置设置为 false。

:::

### 版本锁

版本锁就是精确记录依赖包的版本号的文件，作用是锁住版本，避免升级导致的 Bug
比如：`package.json`中的版本范围（如 `^1.2.0`）,如果没有版本锁，那么每次运行 `pnpm install` 时都会自动升级依赖包到最新版本，这会导致项目运行时出现问题。
有了版本锁，就可以保证每次运行 `pnpm install` 时，依赖包的版本都是固定的，不会自动升级。

### `CI/CD` 环境

所谓的 `CI` (Continuous Integration)环境就是开发人员频繁（每天多次）将代码变更合并到主分支时，​ 自动触发构建和测试的环境。
所谓的`CD`(Continuous Delivery/Deployment)环境是在 `CI` 通过后，​ 自动将代码发布到测试或生产环境的流程。

> `vercel`其实就是`CI`和`CD`环境的实现

在`CI`环境下，我们需要使用`--frozen-lockfile`选项，确保每次运行 `pnpm install` 时，即使 `package.json`变了，​ 也会报错而非自动更新。

### 选项

以下列出了常用选项：
| 选项名称 | 默认值 | 类型 | 说明 |
| -------------------- | ---------------------------------------------------------- | ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `--prod`, `-P` | `false` | 布尔值 | 如果为 `true`，pnpm 不会安装 `devDependencies` 中的包，并删除已安装的 `devDependencies`；如果为 `false`，则安装 `dependencies` 和 `devDependencies` 中的所有包。 |
| `--dev`, `-D` | 无默认值（行为开关） | 布尔值（行为开关） | 仅安装 `devDependencies`，并删除已安装的 `dependencies`。 |
| `--no-optional` | 无默认值（行为开关） | 布尔值（行为开关） | 不安装 `optionalDependencies`。 |
| `--shamefully-hoist` | `false` | 布尔值 | 创建扁平的 `node_modules` 目录结构，类似于 npm 或 yarn。<br>**警告：** 非常不推荐使用。 |
| `--force` | 无默认值（行为开关） | 布尔值（行为开关） | 强制重新安装依赖：重新获取存储中已修改的包，重新构建由不兼容版本的 pnpm 创建的锁定文件或模块目录；同时安装所有可选依赖，即使它们不满足当前环境（CPU、操作系统、架构）。 |
| `--offline` | `false` | 布尔值 | 如果为 `true`，pnpm 仅使用本地存储中已有的包。如果本地找不到包，安装将失败。 |
| `--prefer-offline` | `false` | 布尔值 | 如果为 `true`，会跳过缓存数据的过期检查，但仍会从服务器请求缺失的数据。如需完全离线模式，请使用 `--offline`。 |
| `--frozen-lockfile` | 非 CI 环境：`false`<br>CI 环境：`true`（如果存在锁定文件） | 布尔值 | 如果为 `true`，pnpm 不会生成锁定文件，且如果锁定文件与清单（package.json）不同步、需要更新或不存在，安装将失败。<br>在持续集成（CI）环境中默认开启（有检测 CI 的代码）。 |

## pnpm update

### 基本介绍

`pnpm update` 根据指定范围将软件包更新到最新版本。当不带参数使用时，更新所有依赖，常用命令即选项如下：
| 命令 | 意义 |
|---------------------|---------------------------------------|
| `pnpm up` | 更新所有依赖，遵守 `package.json` 中指定的范围 |
| `pnpm up --latest` | 将所有依赖更新到最新版本 |
| `pnpm up foo@2` | 将 `foo` 更新到 v2 的最新版本 |
| `pnpm up "@babel/*"`| 更新 `@babel` 范围下的所有依赖 |

### 选择具有模式的依赖

你可以使用模式来更新特定的依赖。比如更新所有 `babel` 软件包：

```bash
pnpm update "@babel/*"
```

更新除 `webpack` 之外的所有依赖：

```bash
pnpm update "\!webpack"
```

模式也可以组合，因此下一个命令将更新除 `core` 之外的所有 `babel` 包：

```bash
pnpm update "@babel/*" "\!@babel/core"
```

### 选项

| 选项名称        | 简写 | 说明                                                       |
| --------------- | ---- | ---------------------------------------------------------- |
| `--latest`      | `-L` | 忽略 `package.json` 中的版本范围，将所有依赖升级到最新版本 |
| `--recursive`   | `-r` | 递归更新所有子项目（适用于 `monorepo`）                    |
| `--global`      | `-g` | 更新全局安装的包                                           |
| `--dev`         | `-D` | 仅更新 `devDependencies`                                   |
| `--prod`        | `-P` | 仅更新 `dependencies`（不更新 `devDependencies`）          |
| `--interactive` | `-i` | 交互式选择要更新的依赖(显示过时的依赖并选择要更新的依赖)   |
| `--workspace`   | 无   | 仅更新工作空间内的包                                       |
| `--filter`      | 无   | 仅更新匹配指定选择器的包                                   |

## pnpm remove

别名：`rm`、`uninstall`、`un`
从 `node_modules` 和项目的 `package.json` 中删除包。

| 选项名称          | 简写 | 说明                                                                                               |
| :---------------- | :--- | :------------------------------------------------------------------------------------------------- |
| `--recursive`     | `-r` | 在工作区内使用时，从每个工作区包中删除依赖；不在工作区内使用时，从子目录中找到的每个包中删除依赖。 |
| `--global`        | `-g` | 删除全局安装的包。                                                                                 |
| `--save-dev`      | `-D` | 仅从 `devDependencies` 中删除依赖。                                                                |
| `--save-optional` | `-O` | 仅从 `optionalDependencies` 中删除依赖。                                                           |
| `--save-prod`     | `-P` | 仅从 `dependencies` 中删除依赖。                                                                   |
| `--filter`        | 无   | 仅对与给定选择器匹配的包执行删除操作。                                                             |

## :star: pnpm link

### 基本介绍

别名：`ln`
使当前本地包可在系统范围内或在其他位置访问。

```bash
pnpm link <dir|pkg name>
pnpm link
```

### 选项

#### pnpm link <目录>

将 `<dir>` 目录中的包链接到你执行此命令的包的 `node_modules`。

> 假设你有两个项目文件夹（比如 项目 A 和 项目 B）都在你电脑上。你正在 项目 B 里开发一个工具包，然后想在 项目 A 里测试这个工具包好不好用。

1.  进入 项目 A 的文件夹，然后执行命令 `pnpm link ../项目B`
2.  这会在 项目 A 的 `node_modules` 文件夹里创建一个“快捷方式”，直接指向你本地的 项目 B。这样，项目 A 就能直接使用 项目 B 的最新代码了，你不用再把 项目 B 发布到网上。

#### pnpm link

将执行此命令的位置的包链接到全局 `node_modules`，因此可以从另一个带有 `pnpm link <pkg>` 的包中引用它。此外，如果包具有 `bin` 字段，则包的二进制文件在系统范围内可用。

> 你开发好了一个工具包（比如在 项目 B 里），希望它不仅能给 项目 A 用，还能给你电脑上任何其他项目使用。

1. 进入你这个工具包的文件夹（项目 B），然后执行命令 `pnpm link`
2. 这个命令会把项目 B 注册到你电脑的一个全局位置（相当于一个“公共工具墙”）。之后，在任何其他项目里，你都可以通过它的名字来找到并链接它了。如果这个包有可执行命令，那么这些命令也会在全局生效

::: tip bin 文件
当输入全局指令时会去对应相同报名的`bin`字段指定的路径下寻找可执行文件。这在使用命令行工具的时候十分有用
:::

#### pnpm link <包名>

将指定的包 (`<pkg>`) 从全局 node_modules 链接到执行此命令的包的 node_modules。其实就是将全局包软链接到本地，可以配合`pnpm link`使用。

> 你已经用上面的 pnpm link 命令把某个包（比如叫 my-tool）挂到了“公共工具墙”上。现在你想在另一个新项目（比如 项目 C）里使用它。

1. 进入项目 C 的文件夹，然后执行命令 `pnpm link my-tool`
2. 这个命令会去“公共工具墙”上找到名为 `my-tool`的包，然后在项目 C 里创建一个指向它的“快捷方式”。这样，项目 C 就能直接用上你本地开发的 `my-tool`了

### 最佳实践

#### 测试包

假设你有一个使用 `foo` 包的项目。你想要对 `foo` 进行更改并在你的项目中测试它们。在这种情况下，你可以使用 `pnpm link` 将本地版本的 `foo` 链接到你的项目。

```bash
cd ~/projects/foo
pnpm install # install dependencies of foo
pnpm link # link foo globally
cd ~/projects/my-project
pnpm link foo # link foo to my-project
```

你还可以将包从一个目录链接到另一个目录，而无需使用全局 `node_modules` 目录：

```bash
cd ~/projects/foo
pnpm install # install dependencies of foo
cd ~/projects/my-project
pnpm link ~/projects/foo # link foo to my-project
```

#### 全局添加二进制文件

如果你正在开发包含二进制文件的软件包（例如 `CLI` 工具），则可以使用 `pnpm link` 使二进制文件在系统范围内可用。这与使用 `pnpm install -g foo` 相同，但它将使用本地版本的 `foo`，而不是从注册表下载。
请记住，仅当包的 `package.json` 中有 `bin` 字段时，二进制文件才可用。

```bash
cd ~/projects/foo
pnpm install # install dependencies of foo
pnpm link # link foo globally
```

### pnpm link 和使用 file: 协议有什么区别

#### 软链接 -pnpm link

当你使用 `pnpm link` 时，链接的包是从源代码符号链接的。你可以修改链接包的源代码，**所做的更改将反映在你的项目中**。使用此方法 `pnpm` 将不会安装链接包的依赖，你必须在源代码中手动安装它们。当你必须对链接包使用特定的包管理器时，这可能会很有用，例如，如果你想对链接包使用 `npm`，但对项目使用 `pnpm`。

::: tip 总结
链接的包做出的更改将会反应到项目，同样，也意味着`pnpm`不会自动帮你安装被链接包自己的依赖,你需要手动安装链接包的依赖。
:::

#### 硬链接 -file: 协议

当你在 `dependencies` 中使用 `file:` 协议时，链接包硬链接到你的项目 `node_modules`，你可以修改链接包的源代码，所做的更改将反映在你的项目中。通过这种方法，`pnpm` 还将安装链接包的依赖，覆盖链接包的 `node_modules`。

::: tip 总结
`pnpm` 会自动帮你管理被链接包的依赖，或者说它会帮你安装链接包的依赖，覆盖链接包的 `node_modules`。
注意：是你项目中的下载的这个依赖包的`node_modules`被覆盖，而不是链接包的`node_modules`被覆盖
:::

### 关于对等依赖

比如一个 `React` 组件库（比如一个按钮组件）

1. 它的 `​peerDependencies`​ （对等依赖）里会声明需要 `react`和 `react-dom`
2. 这个组件库自己不打包 ​ `React`
3. 它期望使用它的主项目 ​（比如你开发的网站）已经安装了 `React`。它直接“对接”使用主项目里的那个 `React`

于是这个组件库的对等依赖就是 `react` 和 `react-dom`

::: tip 这有什么意义呢？
当你“链接的包”本身需要有这种“对等依赖”时（比如它指定需要某个版本的 `React`），​ 更推荐使用 `file:`协议。因为 `pnpm`能更好地处理这种情况，确保链接包使用的是你主项目里的 `React`版本，这样行为更一致，不容易出错。
:::

## pnpm unlink

### 基本介绍

取消链接系统范围的包（与 `pnpm link` 相反）。如果不带参数调用，则当前项目内的所有链接依赖都将取消链接。
这与 `yarn unlink` 类似，只不过 `pnpm` 在删除外部链接后重新安装依赖。
::: tip 删除全局软链接
如果你想删除使用 `pnpm link --global <package>` 建立的链接，你应该使用 `pnpm uninstall --global <package>`。`pnpm unlink` 仅删除当前目录中的链接。
:::

### 选项

- `--recursive, -r`：在 workspace 中执行时，取消子目录或每个工作区包中找到的每个包的链接
- `--filter <package_selector>`

## pnpm import

`pnpm import` 从另一个包管理器的锁定文件生成 `pnpm-lock.yaml`。支持的源文件：

- `package-lock.json`
- `npm-shrinkwrap.json`
- `yarn.lock`

> 比如：你接手了一个老项目，这个项目之前一直用 npm 或者 yarn 来管理依赖（所以它的根目录下有 package-lock.json 或 yarn.lock 文件）。现在你想用更快的 pnpm 来管理这个项目的依赖
> 直接删除原来的 `node_modules` 和锁定文件，然后用 `pnpm install` 安装，虽然可以，但无法保证安装的依赖版本和原来一模一样，可能会有微小的版本差异，导致项目运行不稳定

`pnpm import` 的作用就是来解决这个问题的！它能：

1. 自动读取项目中已经存在的、由其他包管理器生成的锁定文件（比如 `npm` 的 `package-lock.json` 或 `yarn` 的 `yarn.lock`）。
2. 精准转换将这个文件里的依赖树信息，原汁原味地转换生成一个 `pnpm` 自家的锁定文件 `pnpm-lock.yaml`。

::: warning 注意
如果你希望导入依赖的工作区，则需要事先在 `pnpm-workspace.yaml` 文件中声明它们。
:::
这句话是针对一种叫 `​Monorepo`（多包仓库）​​ 的复杂项目结构的。

1. 工作区指的是一个仓库里包含多个独立的子项目。
2. 像 `npm` 或 `yarn` 也有自己的工作区定义。
3. 这条提示的意思是：如果你的原项目是这种多包项目，光用 `pnpm import` 命令还不够。你需要先手动创建一个 `pnpm-workspace.yaml`文件，在里面告诉 `pnpm` 哪些文件夹是子工作区。然后 `pnpm import`命令才能正确地把所有子项目的依赖关系都导入进来。

## pnpm prune

### 基本介绍

这个命令就像给你的项目文件夹做一次“大扫除”或“瘦身”。它会扫描 `node_modules`文件夹，​ 删除那些在你的 `package.json`中没有被声明为必要依赖的包。

> 比如你安装了一个包 A，它自己带了依赖包 B 和 C。后来你删除了包 A，但包 B 和 C 可能还残留在 node_modules 里。prune 命令就是用来清理这些“孤儿”包的。

### 选项

- `--prod, -P`：除了删除没有在 `package.json` 中声明的依赖，还会额外删除所有开发依赖 ​（`devDependencies`）,比如项目要部署到生产服务器了，服务器上不需要测试工具、代码打包器等开发环境用的包
- `--no-optional`：删除所有可选依赖 ​（`optionalDependencies`）, 确保环境纯净，或解决某些因可选依赖引起的问题。

::: warning 注意
如果你的项目是包含多个子包的 `​Monorepo，pnpm prune` 命令不能递归地在每个子包中执行。
:::
