# 1 Maven

## 1.1 常用配置

> GAV 坐标定位依赖，`dependencyManagement` 声明版本号，`dependencies` 才真正引入。

1. GAV 三要素：`groupId + artifactId + version` 唯一定位一个依赖
2. `dependencyManagement`：父工程声明有哪些依赖及版本，子模块无需再写 version
3. `dependencies`：子模块真正引入；不写 version 就用父工程锁定的
4. Spring Boot 做法：继承 `spring-boot-starter-parent`，内部 BOM 锁定所有常用依赖版本

## 1.2 生命周期

- 三套生命周期：**clean**（清理 target）、**default**（编译打包主线）、**site**（站点文档）
- default 常用阶段：`compile → test → package → install → deploy`，执行某阶段会自动先执行它前面的所有阶段
- package 打出本模块 jar；install 装进本地仓库供其他模块依赖；deploy 发到远程仓库
- 常用命令：`mvn clean package`（先清理再打包）

# 2 Java

## 2.1 注解

注解就是给类/方法/字段打标签，让编译期或运行期产生副作用，框架声明式驱动的基石。

**自定义注解**：接口前加 `@`，成员是抽象方法（`String value()`）；只有 `value` 时可省略名字（`@RequireLogin("xxx")`）；`default` 给默认值；成员类型限基本类型/String/Class/枚举/注解/数组。

**元注解（标注注解的注解）**：

| 元注解        | 作用                      |
| ------------- | ------------------------- |
| `@Target`     | 能贴到哪（类/方法/字段…） |
| `@Retention`  | 保留到什么时候            |
| `@Repeatable` | 同一位置可否重复标注多次  |

**@Retention 三种策略**：

| 策略      | 保留阶段                   | 典型用途                            |
| --------- | -------------------------- | ----------------------------------- |
| `SOURCE`  | 编译时丢弃，字节码里没有   | `@Override`，只给编译器做语法检查   |
| `CLASS`   | 保留到字节码，运行期不可见 | Lombok `@Getter`，编译期处理器用    |
| `RUNTIME` | 一路保留到 JVM，反射可读   | Spring `@Autowired`，运行时反射读取 |

两种使用方式：**编译时处理**（Processor 处理 AST 注入代码，如 Lombok）/ **运行时处理**（反射读取，如 Spring 依赖注入）。

Spring 组合注解：外层注解通过元注解复用功能，`@AliasFor` 覆盖元注解的属性。

`@RestController` = `@Controller` + `@ResponseBody`；注解本身只是标记，Spring 扫描到后完成 **Bean 注册 + 依赖注入 + 路由映射**。

## 2.2 异常

> 自定义异常携带业务错误码 + 全局处理器统一拦截，Controller 不用写 try-catch。

- `BizException extends RuntimeException`：携带 `code`（错误码）+ `message`
- `@RestControllerAdvice` 统一拦截所有 Controller 抛出的异常，本质是 AOP 切面
- 核心价值：**异常处理与业务逻辑解耦**，前端拿到统一 JSON 结构

# 3 Spring Boot

## 3.1 本质

简化依赖、配置、部署四件事：

- **依赖聚合**：starter 一个依赖引入一组功能的所有 jar
- **版本仲裁**：BOM 统一管版本号，子模块不用写
- **配置简化**：YAML 替代 XML，外部化配置
- **部署简化**：内嵌 Tomcat，`java -jar` 直接跑

## 3.2 起步依赖 Starter

本质是 `dependencyManagement` 做版本仲裁：`spring-boot-starter-parent` → `spring-boot-dependencies`（BOM）声明所有依赖版本 → 子模块引入不写 version。

## 3.3 配置文件

`.properties` 优先级高于 `.yml`（properties 后加载，覆盖 yml）。

## 3.4 配置注入

| 方式                                    | 适用场景         | 特点                             |
| --------------------------------------- | ---------------- | -------------------------------- |
| `@Value("${xxx}")`                      | 单一零散属性     | 简单直接，不支持复杂结构         |
| `@ConfigurationProperties(prefix="xx")` | 批量注入一类属性 | 成组绑定，支持嵌套/List/Map/校验 |

## 3.5 多环境配置 Profile

- 文件：`application-{profile}.yml`（如 `application-dev.yml`）
- 激活：`spring.profiles.active=dev`（配置文件/命令行/环境变量）
- 覆盖规则：**命令行 > 环境变量 > 文件**

## 3.6 日志记录

> SLF4J 是门面接口，背后是 Logback（默认）、Log4j2 等实现。

- **门面模式**：业务代码只依赖 SLF4J 接口，换实现不改代码
- **级别**（低→高）：`TRACE < DEBUG < INFO < WARN < ERROR`，设 WARN 则只出 WARN/ERROR；配合 Profile：开发 DEBUG、生产 WARN
- **执行链**：`log.info()` 产生 LoggingEvent → 发给所有 Appender（观察者模式）→ 每个 Appender 内 Filter 链过滤 → Encoder 格式化
- **logback-spring.xml**：yml 不够用时（错误日志分文件、彩色输出）做高级控制；必须叫这个名才能用 `<springProfile>` 分环境

## 3.7 配置文件加载顺序

命令行 > 环境变量 > jar 外 `{profile}.yml` > jar 外 `application.yml` > jar 内 `{profile}.yml` > jar 内 `application.yml` > 默认。

核心：**jar 外部 > jar 内部**，不重新打包就能改线上配置。

## 3.8 条件注解

> 配置按条件生效，是自动配置的基石。

`@ConditionalOnMissingBean`：容器里没有才配（你没配我才配默认的，你配了就不覆盖）。常用：

| 注解                           | 生效条件               |
| ------------------------------ | ---------------------- |
| `@ConditionalOnClass`          | classpath 存在指定类   |
| `@ConditionalOnMissingBean`    | 容器中不存在指定 Bean  |
| `@ConditionalOnProperty`       | 配置项存在且匹配指定值 |
| `@ConditionalOnWebApplication` | 是 Web 应用            |

## 3.9 参数校验

| 对比     | @Valid（JSR-303 标准）    | @Validated（Spring 的） |
| -------- | ------------------------- | ----------------------- |
| 分组校验 | ❌ 不支持                 | ✅ 支持（指定 groups）  |

## 3.10 拦截器与过滤器

| 维度                | 过滤器 Filter              | 拦截器 Interceptor       |
| ------------------- | -------------------------- | ------------------------ |
| 归属                | Servlet 规范               | Spring MVC               |
| 作用范围            | 所有请求（含静态资源）     | 进入 Controller 的请求   |
| 能否拿 Spring Bean  | 不能直接拿（手动从容器取） | 能（本身是 Spring Bean） |
| 能否拿 Handler 方法 | 不能                       | 能（`HandlerMethod`）    |
| 典型场景            | 编码、CORS、日志           | 登录鉴权、权限、性能统计 |

配置：实现 `WebMvcConfigurer#addInterceptors`，`addPathPatterns("/**")` 拦截 + `excludePathPatterns("/login")` 放行，SpringMVC 启动时加载。

**跨域 CORS**：浏览器发现跨域 → 非简单请求先发 OPTIONS 预检 → 后端返回 `Access-Control-Allow-Origin` 响应头 → 浏览器对比当前来源，匹配才放行让 JS 拿到数据。配置用 `WebMvcConfigurer#addCorsMappings`（`allowedOriginPatterns` / `allowedMethods` / `allowCredentials` / `maxAge`）；`maxAge` 缓存预检结果，期间不再重复发 OPTIONS。

## 3.12 事务

一系列 SQL 操作同时成功或同时失败。

**传播行为**：B 调 A，两个都有事务，什么关系？

- `REQUIRED`（默认）：加入当前事务，任何一方异常整体回滚
- `REQUIRES_NEW`：挂起当前事务开新事务，各自独立回滚（订单成功、日志失败互不影响）

**隔离级别三个问题**：

| 问题       | 原因                  | 后果                       |
| ---------- | --------------------- | -------------------------- |
| 脏读       | 读了别人没提交的数据  | 数据是假的，别人回滚你就错 |
| 不可重复读 | 两次读之间被人改了    | 同一条数据两次读不一样     |
| 幻读       | 两次读之间被插了/删了 | 同一范围两次查行数不一样   |

记忆：脏读是数据假的，不可重复读是值变了，幻读是行数变了。

**声明式 vs 编程式**：编程式（`TransactionTemplate.execute()`）粒度细，可部分成功（每个订单独立事务，失败标记 `setRollbackOnly` 不影响其他）。

**只读事务**：`@Transactional(readOnly = true)` 告诉数据库查询不用加锁，可做优化。

**@Transactional 失效七种场景**：

1. this 调用内部方法（代理失效）→ 注入自身引用解决
2. 非 public 方法（只对 public 生效）→ 改成 public
3. 异常被 try-catch 吞掉 → 不吞，或手动 `TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()`
4. 受检异常默认不回滚 → 加 `rollbackFor = Exception.class`
5. 存储引擎不支持事务（如 MyISAM）
6. 方法被 final 修饰 → 动态代理无法重写
7. 事务内开新线程异步 → 用 `@TransactionalEventListener` 事务提交后再异步

## 3.15 发布事件

发布订阅模式的运用：创建事件对象 → `ApplicationEventPublisher.publishEvent()` 发布 → 订阅者回调。

四种方式：`@EventListener`（推荐最简单）/ 实现 `ApplicationListener` 接口 / 异步监听 / 条件监听。

**事务监听器** `@TransactionalEventListener`：监听事务不同阶段（AFTER_COMMIT 最常用 / AFTER_ROLLBACK / AFTER_COMPLETION / BEFORE_COMMIT）。

- AFTER_COMMIT：事务提交后才执行，数据已落库；监听器抛异常**不会**导致业务回滚；适合发 MQ、发邮件

# 4 Spring Security

> 前后端分离 JSON 登录，无状态 JWT 方案。

## 4.1 过滤器链

```
Servlet FilterChain
→ DelegatingFilterProxy
→ FilterChainProxy
→ 匹配当前请求的 SecurityFilterChain
→ Spring Security 内部过滤器
→ DispatcherServlet
```

- `FilterChainProxy` 选择第一个匹配的 `SecurityFilterChain`，并负责请求结束后安全上下文清理
- `addFilterBefore(jwtAuthFilter, UsernamePasswordAuthenticationFilter.class)` 里该类只是**排序参照**；前后端分离关闭 formLogin 后默认登录过滤器根本不在链中

## 4.2 核心四件套

1. **UserDetailsService**：自己实现，决定如何加载 UserDetails（用户信息 + 权限）
2. **Authentication**：认证对象，`UsernamePasswordAuthenticationToken` 是其实现。三个属性：`principal`（是谁，=userDetails）、`credentials`（凭证，JWT 已验证所以 null）、`authorities`（权限）
3. **AuthenticationManager**：`authenticate()` 内部调 UserDetailsService 查询，与密码比对，产出**已认证**的 Authentication
4. **SecurityContextHolder**：保存当前请求的认证上下文，后续授权基于它

## 4.3 常用配置

Security 6 用 Lambda 式 `SecurityFilterChain` Bean 配置（旧的 `WebSecurityConfigurerAdapter` 已移除）。前后端分离无状态版：

```java
@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .csrf(AbstractHttpConfigurer::disable)                 // Token 认证不靠 Cookie，无需 CSRF
            .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))  // 无状态，不建 Session
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/user/login", "/api/user/register").permitAll()  // 白名单
                .anyRequest().authenticated())                     // 其余都要登录
            .addFilterBefore(jwtAuthFilter, UsernamePasswordAuthenticationFilter.class);
        return http.build();
    }
}
```

- 授权规则**从上往下匹配，命中即止**，白名单必须写在 `anyRequest()` 之前
- 不声明这个 Bean 时 Boot 才提供默认链（全接口要登录 + 打印随机密码）——「你没配我才配」，和条件注解同一套路；自己一声明，默认规则全部失效
- 旧 API 对照：`antMatchers` → `requestMatchers`，`@EnableGlobalMethodSecurity` → `@EnableMethodSecurity`

## 4.4 认证流程

### 4.4.1 首次登录

不走默认登录过滤器，由 Controller 主动调 AuthenticationManager：

1. `JwtAuthFilter` 没发现 Bearer Token 放行；`AuthorizationFilter` 见 `/api/user/login` 是 `permitAll()` 放行进 Controller
2. Controller 构造未认证对象：`UsernamePasswordAuthenticationToken.unauthenticated(username, password)`
3. 调 `authenticationManager.authenticate(token)`，内部链路：

```
AuthenticationManager
→ ProviderManager
→ DaoAuthenticationProvider（用户名密码认证就是它，不存在 UsernamePasswordAuthenticationProvider）
→ UserDetailsService 查询用户
→ PasswordEncoder 校验密码
→ 检查账号启用/锁定/过期
```

4. 验证成功返回已认证 `Authentication` → 取出 LoginUser → 生成 JWT 返回前端
5. 无状态模式不需要把登录结果长期存进 `SecurityContextHolder`

### 4.4.2 登录后请求

每次请求带 `Authorization: Bearer <token>`：

1. `JwtAuthFilter` 提取 Token，校验：签名、过期时间、token 类型 = access
2. 读出 username/userId → 查 UserDetails（检查是否禁用/锁定、拿最新权限）
3. 构造已认证对象并放入上下文：

```java
UsernamePasswordAuthenticationToken.authenticated(userDetails, null, userDetails.getAuthorities());
SecurityContextHolder.getContext().setAuthentication(auth);
```

4. 请求结束清理 `SecurityContextHolder`，下次请求按 JWT 重建

## 4.5 鉴权流程

1. **Filter 层 · URL 鉴权**：`AuthorizationFilter` 按 `authorizeHttpRequests` 规则从上往下匹配，命中即止——未登录访问受保护接口 → 401；已登录权限不足 → 403；通过才进 Controller
2. **方法层 · 注解鉴权**：`@EnableMethodSecurity` + `@PreAuthorize("hasAuthority('course:delete')")`，由 `AuthorizationManagerBeforeMethodInterceptor` 在方法执行前校验

易错：Security 6 的 URL 鉴权是 `AuthorizationFilter`，不是旧资料的 `FilterSecurityInterceptor`。

## 4.6 经典场景

### 4.6.1 双Token

背景：在实际的场景中AccessToken是无状态的，签出去就收不回，没法吊销。所以如果被盗，就没办法止损，因此AccessToken需要设计的时间很短比如15分钟。但这产生了一个问题用户 15 分钟就得重新输一次密码，体验不好。所以要解决这个问题就得采用双Token。

| Token        | 有效期     | 用途           |
| ------------ | ---------- | -------------- |
| AccessToken  | 10~30 分钟 | 只访问业务接口 |
| RefreshToken | 数天到数周 | 只访问刷新接口 |

具体来说，用户将RefreshToken存在LocalStorage，保存一定的天数，每15分钟通过RefreshToken去换一个最新的AccessToken，这样既保证了不断有AccessToken用，又保证了每次AccessToken都是最新的。这样即保证了用户体验，也用AccessToken的低频率保证了安全。具体操作如下

1. 用户登录：后端生成AccessToken和RefreshToken，并将RefreshToken和用户ID存入Redis。前端拿到AccessToken和RefreshToken后通常将AccessToken放到SessionStorage，RefreshToken放到LocalStorage。
2. AccessToken失效：后端返回401，前端拿RefreshToken去换最新的AccessToken，然后存入再请求。同时Redis也会删除原来旧的旧的RefreshToken，生成新的RefreshToken，同时用剩余过期作为TTL（非滑动续期）

有了双token其实可以实现很多场景

1. 记住我：无非就是把RefreshToken设置的时间多一点或者设置为滑动续期
2. 退出登录：前端移除RefreshToken和AccessToken，后端Redis移除RefreshToken
3. 踢下线：就是一个用户ID对应多个IP，把某个用户的IP对应的

### 4.6.4 短信验证码设计

图片验证码是第一道屏障防止轰炸短信

1. 用户输入手机号，点击获取短信，后端生成图片验证码及其uuid存入Redis，前端展示图片验证码
2. 用户输入图片验证码，传入后端进行比对（Lua脚本，Redis中进行比对）
   - 若没有图片验证码直接失败，返回-1
   - 有验证码，比对成功则清除图片验证码及其图片验证码计数器
   - 有验证码，比对失败
     - 如果是用户第一次尝试，则初始化图片验证计数器，图片验证计数器和图片验证码的TTL时间一致
     - 如果不是第一次尝试（有图片验证计数器），则判断是否超过了最大尝试次数，如果超过则直接删除图片验证码和图片计数器Key
3. 当用户图片验证码比对成功，然后发送手机验证码
   - 首先判断是否有冷却Key如果有则提示频繁
   - 如果没有冷却Key，则会先生成冷却key（防止在冷却时间多次频繁发送）、手机验证码（实际运营商发送），返回给用户
   - 然后用户如果尝试失败了，那么和1、2步骤一致

# 5 MapStruct

## 5.1 PO\VO\DTO

1. PO是数据库模型与JAVA实体直接1：1映射
2. DTO是前端传给后端的PO切面
3. VO是返回给前端的PO切面（字段子集）

| 对象    | 全称                 | 在哪层用                    | 职责                                       |
| :------ | :------------------- | :-------------------------- | :----------------------------------------- |
| **PO**  | Persistent Object    | DAO / Mapper 层             | 与数据库表**一一对应**，一个字段对应表一列 |
| **DTO** | Data Transfer Object | Service / Controller 层     | 承载**接口的入参和出参**，不暴露数据库结构 |
| **VO**  | View Object          | Controller 层（返回给前端） | 专门给前端展示用的，可能组合多个 PO 的数据 |

这样的好处在于即便数据库模型发生了变化，只需要变更POJO，而VO和DTO可以不用变化，这样就实现了前端与数据库之间的解耦。

> 而MapStruct是DTO/VO/PO 转换工具：**编译期**生成转换器实现，零反射，和手写 setter 一样快（转换依赖 Lombok 生成的 getter/setter）。

## 5.2 基本使用

### 基础映射

1. 定义转换器：`@Mapper(componentModel = "spring")` 标注接口，编译期生成 `xxxConverterImpl`（自动标 `@Component`），直接 `@Autowired` 注入
2. 字段映射：
   - 同名同类型字段**自动映射**，一行配置都不用写
   - 字段名不同用 `@Mapping(source = "createTime", target = "createdAt")`；
   - 不想映射，保留空值用 `ignore = true`
3. 格式转换：对于时间等类型可以指定转换格式如`dateFormat = "yyyy-MM-dd HH:mm:ss"`、`numberFormat`；基本类型不匹配会自动转（如 String ↔ Integer）

```java
// 定义一个转换器接口：MapStruct 编译期自动生成实现类，并且自动生成为 Spring Bean，可 @Autowired 注入
@Mapper(componentModel = "spring")
public interface UserConverter {

    // 字段名相同时，自动映射（无需额外配置）
    UserVO toVO(UserPO po);

    // 字段名不同时，用 @Mapping 指定
    @Mapping(source = "password", target = "password", ignore = true)  // 忽略密码
    @Mapping(source = "createTime", target = "createdAt", dateFormat = "yyyy-MM-dd HH:mm:ss")
    UserVO toVOWithMapping(UserPO po);
}
```

编译后自动生成的代码（可以反编译看到）：

```java
// MapStruct 在编译期生成了这个实现类
@Component
public class UserConverterImpl implements UserConverter {

    @Override
    public UserVO toVO(UserPO po) {
        if (po == null) return null;
        UserVO vo = new UserVO();
        vo.setId(po.getId());
        vo.setUsername(po.getUsername());
        // ... 全部字段自动赋值
        return vo;
    }
}
```

### 多个对象合并

方法可以接受多个参数： `toVO(OrderPO order, UserPO user)`，表示这两个对象的属性要合并为一个对象。`@Mapping(source = "order.id", target = "orderId")`

```java
// 把多个 PO 合并成一个 VO
@Mapper(componentModel = "spring")
public interface OrderConverter {

    @Mapping(source = "order.id", target = "orderId")
    @Mapping(source = "user.username", target = "userName")
    @Mapping(source = "product.title", target = "productName")
    OrderVO toVO(OrderPO order, UserPO user, ProductPO product);
}
```

### 集合转换

声明 `List<UserVO> toVOList(List<UserPO> list)`，自动复用单个对象的映射方法，完成集合转换

```java
@Mapper(componentModel = "spring")
public interface UserConverter {
    // 单个对象
    UserVO toVO(UserPO po);

    // 集合：List<UserPO> → List<UserVO>，调用toVO方法
    List<UserVO> toVOList(List<UserPO> poList);
}
```

## 5.3 三种填值方式

1. `ignore`：转换时忽略该字段，新对象中保持 Java 默认值，如引用类型为 `null`
2. `defaultValue`：源字段为 `null` 时，使用指定的固定默认值。
3. `expression`：使用 Java 表达式计算并设置目标字段的值。

```java
@Mapper(componentModel = "spring")
public interface UserConverter {

    @Mapping(
            target = "fullName",
            expression = "java(buildFullName(userPO))")
    UserVO toVO(UserPO userPO);

    default String buildFullName(UserPO userPO) {
        return userPO.getFirstName() + userPO.getLastName();
    }
}
```

> `ignore = true` 的字段不再参与映射，`default` 方法也不会被调用

## 5.4 和Lombok 配合

Lombok 先生对象 `getter/setter`，MapStruct 才能用它们生成转换代码；两个注解处理器都要配好，否则找不到 Impl 报错，也就是我们需要配置编译顺序。需要在`spring-boot-maven-plugin`的`plugins`中配置


## 5.5 未映射字段处理

`unmappedTargetPolicy`：配置目标类里有、但源里找不到对应字段的属性时的行为方式。比如 `UserPO` 有 `password`、`createTime`，而 `UserDTO` 没有

| 值               | 效果                             | 场景                 |
| :--------------- | :------------------------------- | :------------------- |
| `IGNORE`（默认） | 静默跳过，不报错不警告           | 宽松，但漏字段看不出 |
| `WARN`           | 打印警告，不中断编译             | 提醒但不阻塞         |
| **`ERROR`**      | **编译直接失败**，强制你显式处理 | 最严格，安全敏感场景 |

```java
// 项目里推荐 ERROR：目标字段漏处理 → 编译失败，而不是悄悄留 null
@Mapper(componentModel = "spring", unmappedTargetPolicy = ReportingPolicy.ERROR)
public interface UserConverter {
    // 因 ERROR，凡是下面没显式 ignore、DTO 里也没有的字段，编译必失败
    @Mapping(target = "id", ignore = true)
    @Mapping(target = "password", ignore = true)
    UserPO toPO(UserDTO dto);
}
```

> `unmappedTargetPolicy` 只管**目标类有**的字段；VO 里根本没有 password 就不算 unmapped，不报错

## 5.6 使用已有对象

参数添加 `@MappingTarget` 后，MapStruct 不再创建新对象，而是把来源对象的数据写入调用方传入的已有对象：

```java
@Mapper(componentModel = "spring", unmappedTargetPolicy = ReportingPolicy.ERROR)
public interface CourseConverter {

    @BeanMapping(nullValuePropertyMappingStrategy = NullValuePropertyMappingStrategy.IGNORE)
    @Mapping(target = "id", ignore = true)
    @Mapping(target = "viewCount", ignore = true)
    @Mapping(target = "buyCount", ignore = true)
    void updateEntity(CourseSaveDTO source, @MappingTarget Course target);
}
```

两个参数的职责：

- `CourseSaveDTO source`：数据来源，MapStruct 从中读取字段。
- `@MappingTarget Course target`：修改目标，MapStruct 直接调用它的 setter。

```java
Course course = courseMapper.selectById(id);
courseConverter.updateEntity(dto, course);
courseMapper.updateById(course);
```

MapStruct 生成的实现大致如下：

```java
@Override
public void updateEntity(CourseSaveDTO source, Course target) {
    if (source == null) {
        return;
    }
    if (source.getTitle() != null) {
        target.setTitle(source.getTitle());
    }
    if (source.getPrice() != null) {
        target.setPrice(source.getPrice());
    }
}
```

`NullValuePropertyMappingStrategy.IGNORE` 表示来源字段为 `null` 时保留目标对象原值，因此常用于部分更新。

## 6.1 OpenApi

```java
@RestController

            @Parameter(description = "用户 ID", example = "1")    // 参数说明
            @PathVariable Long id) { ... }
}

@Schema(description = "用户注册请求")                             // DTO 及字段说明
public class UserRegisterDTO {
    @Schema(description = "登录名", example = "zhangsan")

}
```

# 7 Redis

## 7.1 五大数据结构

| 类型   | 底层编码                                          | 要点与场景                                                       |
| ------ | ------------------------------------------------- | ---------------------------------------------------------------- |
| String | int（数字）/ embstr / raw（SDS）                  | 最大 512MB；缓存 JSON、计数器 INCR（原子）、分布式锁 NX+EX、位图 |
| Hash   | listpack（少）→ hashtable 拉链（多）              | 字段级更新不用重写整对象；购物车、对象缓存                       |
| List   | quicklist：双向链表，每个节点是顺序 listpack      | LPUSH+LTRIM 最新 N 条、BRPOP 阻塞消息队列                        |
| Set    | intset（全整数且少，排序数组二分查找）→ hashtable | 无序去重；SINTER 共同好友、SRANDMEMBER 抽奖、IP 去重             |
| ZSet   | listpack（少）→ 跳表 + 哈希                       | 有序去重；排行榜、延迟队列（score 存执行时间戳）                 |

注意：**listpack 只属于 Hash 和 ZSet**，Set 小数据用的是 intset，混入非整数或超量才升级 hashtable。

## 7.2 其它数据类型

1. **Bitmap**：一个 bit 表示一个状态，签到、活跃统计（SETBIT / BITCOUNT）
2. **HyperLogLog**：基数统计（UV 去重计数），固定约 12KB，误差 0.81%，PFMERGE 合并
3. **Geo**：存经纬度，查附近的人

## 7.3 事务

Redis 保证单命令不被中断（单命令原子）；事务针对**多命令**打包顺序执行，但不保证原子：

1. 入队阶段语法错误 → 整个事务一个都不执行
2. 执行中某条出错 → 跳过它，其余继续执行
3. WATCH 乐观锁：监视的 key 在 WATCH 之后、EXEC 之前被**任何客户端**改过（含本客户端事务外的修改）→ EXEC 返回 nil 失败；仅对下一次 EXEC 生效

## 7.4 发布订阅

SUBSCRIBE 订阅 channel，PUBLISH 向 channel 发布。消息不持久化，离线收不到（轻量通知用；可靠队列用 List 或 MQ）。

## 7.5 缓存三大问题

> 本质都是"打数据库"，解决方案就是如何不打数据库，让缓存成为数据库的屏障。

1. **穿透**：查不存在的 key，缓存永不命中直打 DB
   - 空值缓存：DB 查不到也写个空值 + 短过期，相同请求直接命中空值
   - 布隆过滤器：缓存和 DB 之前加一层，key 不存在直接拦截
2. **击穿**：一个热点 key 过期瞬间，并发全部涌入 DB
   - 互斥锁重建：只放一个请求查 DB 重建缓存，其余等待或返回旧值
   - 逻辑过期：不设物理 TTL，值里内嵌过期字段；读到过期先返回旧值，后台异步重建
3. **雪崩**：大批 key 同时失效或 Redis 宕机
   - 过期时间加随机值 `EX + random`，错开过期点
   - 高可用（主从/哨兵/集群）+ 接口限流熔断降级

## 7.6 数据一致性

> 缓存数据和数据库数据不一致的问题。

**旁路缓存（Cache Aside）**：

- 读：命中走缓存；未命中查 DB 回填缓存
- 写：**先更新数据库，再删除缓存**（不是更新缓存，避免无效计算和并发覆盖）

**延迟双删**：先删缓存 → 更新 DB → 隔一小段时间再删一次，清掉间隙里产生的脏缓存。

本质只能做到**最终一致**（删除总有间隙）；强一致要锁/串行化，不值得。

## 7.7 持久化

| 方案 | 机制                                                  | 特点                                   |
| ---- | ----------------------------------------------------- | -------------------------------------- |
| RDB  | 定期 fork **子进程**生成内存快照（二进制文件）        | 恢复快；快照间隔内的数据丢             |
| AOF  | 每条写命令执行后追加到 Append Only File，重启重放命令 | 丢数据少（everysec ≤1s）；文件大恢复慢 |
| 混合 | 4.0+：重写时 RDB 全量打底 + 增量 AOF 追加             | 兼顾恢复速度和丢失量                   |

## 7.8 主从复制

主写从读、读写分离，从节点是全量副本；主挂了从顶上，是哨兵和集群高可用的基础。

1. 主节点 master：负责写
2. 从节点 slave：负责读

从节点复制有延迟，存在读到旧数据的窗口（最终一致）。

## 7.9 哨兵

监控主从、自动故障转移：主挂了选一个从升主。

1. 监控：定期 PING 主从节点判断存活
2. 通知：故障通知管理人员

**主观/客观下线**：

- 主观下线（sdown）：单个哨兵 PING 超时
- 客观下线（odown）：多数哨兵（quorum）都认为主不可达，才触发故障转移

**故障转移流程**：

```
1. 多个哨兵判定主客观下线（odown）
2. 哨兵间投票选出领头哨兵（Raft 选举）
3. 领头哨兵从健康从节点选新主（优先级高的 > 复制偏移量大的 > runid 小的）
4. 通知其他从节点复制新主
5. 原主恢复后降级为从
```

## 7.10 集群

每个 key 用 `CRC16(key) % 16384` 计算槽位，数据按槽分片到多主，突破单机容量：

1. master1（槽 0~5460）+ slave1
2. master2（槽 5461~10922）+ slave2
3. master3（槽 10923~16383）+ slave3

每个主配从节点保高可用；**分片管容量，复制管高可用**。

客户端请求到不负责该槽的节点 → 返回 `MOVED` 重定向到正确节点；多 key 操作需同槽，用 `{}` hash tag。

架构演进线：

```
单机：简单，容量/写压力到顶就完
→ 主从：加从库分摊读，但容量没变（都是全量副本）
→ 哨兵：自动故障转移，容量还是没变
→ 集群：分片，容量 = 机器数之和，这才动了「容量」本身
```

## 7.11 分布式锁

**背景**：并发下的超卖——卖了 2 台，库存只少 1；`synchronized` 只锁 JVM 内，分布式多实例锁不住。

```
时间   请求A                请求B                 库存实际值
t1    读到 100                                   100
t2                         读到 100               100      ← B 读早了！
t3    算出 99                                     100
t4                         算出 99               100
t5    写入 99                                     99
t6                         写入 99               99       ← 卖了 2 台，只减了 1
```

初版 `SETNX lock 1` 加锁、业务完 `DEL lock` 释放，互斥成立但有四个层层递进的缺陷：

| #   | 缺陷             | 根因                                                                   | 对策                                           |
| --- | ---------------- | ---------------------------------------------------------------------- | ---------------------------------------------- |
| 1   | 死锁：锁永不释放 | 持锁进程宕机，`DEL` 未执行，key 无过期时间永久滞留                     | 加过期时间兜底：`EXPIRE lock 30`               |
| 2   | 死锁仍可能发生   | `SETNX` 与 `EXPIRE` 是两条命令，可能死在两条之间（锁已挂、定时器未设） | 合并为单命令原子：`SET lock {uuid} NX EX 30`   |
| 3   | 误删他人锁       | 业务超时 → 锁提前过期被 B 拿到 → A 执行完直接 `DEL`，释放了 B 的锁     | value 写持锁人唯一标识（UUID），释放前校验归属 |
| 4   | 误删仍可能发生   | 「GET 校验 + DEL 删除」两步间有竞态窗口（校验通过后锁恰好易主）        | Lua 脚本把「校验 + 删除」合并为原子操作        |

**手写版最终形态**：

```bash
# 加锁：互斥（NX）+ 防死锁（EX），单命令保证原子
SET lock:order:1001 {uuid} NX EX 30

# 释放：校验归属 + 删除，Lua 保证原子
EVAL "if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) else return 0 end" 1 lock:order:1001 {uuid}
```

**核心三板斧**：原子加锁（`SET NX EX`）+ 唯一标识（UUID）+ Lua 原子释放。

**遗留问题（生产用 Redisson）**：

1. 业务耗时超过 TTL → 锁提前过期互斥失效 → **看门狗**：默认 30s，后台每 10s 检查未完成自动续期；进程宕机停止续期，锁到点自动释放
2. 主从切换丢锁（加锁未同步、主宕机、从升主）→ 理论方案 **RedLock**（多独立节点过半加锁），但有争议（时钟跳变/GC 停顿）；绝大多数场景「单节点 + 看门狗」足够

## 7.12 布隆过滤器

原理：Bitmap + k 个哈希函数，利用哈希能把字符串映射为位图下标的特性。

```
添加 "redis"：hash1→位3, hash2→位7, hash3→位11，把 3/7/11 置 1
判断 "redis"：看位 3/7/11 是否都为 1 → 是，可能存在
判断 "mysql"：看对应位置 → 有一个为 0 → 一定不存在
```

- **判不存在绝对可靠**（插入过的元素 k 位必全为 1）；**判存在只是可能**（位共享，可能是其他元素哈希置的 1）
- 本质：牺牲少量误判率换空间；误判代价可接受——被误判的请求只是多走一次 MySQL
- 空间越大 / k 越合理，误判率越低（1 亿数据约 100MB @ 3%）
- **不能删除元素**：位共享，删 A 的位会误杀 B；要删除用计数型布隆过滤器

## 7.13 Lua 脚本和 Pipeline

Lua 脚本：Redis是单线程执行命令的，每个命令具有原子性。一个命令在执行过程中对其它命令具有排他性，而Lua脚本被Redis视为一个命令。脚本中途报错，前面已执行的命令保持生效，只有后面的不执行。所以 Lua 的原子性说的是调度上不可分割，不是出错全回退。

下面介绍Redis中常用Lua语法

```lua
-- 1. 变量：一律加 local（不加会变成全局变量）
local stock = 10
local name = 'redis'            -- 字符串单双引号都行

-- 2. 条件：if ... then ... end（没有大括号，靠 then/end 收尾）
if stock > 0 then
    stock = stock - 1
elseif stock == 0 then
    return 0
end

-- 3. 循环：while / for（for 含两端）
while stock > 0 do
    stock = stock - 1
end

-- 4. 函数
function add(a, b)
    return a + b
end
```

Pipeline：把多条命令打包一次发送，减少网络往返（RTT），但不保证原子性（命令是依次执行，中间可能插入其他客户端命令）

## 7.15 场景实战

### 课程详情缓存整体逻辑

**背景**：课程详情读多写少，适合使用 Cache Aside（旁路缓存）。读取时优先访问 Redis，修改课程时更新 MySQL 并删除缓存。

1. 设计 Redis Key

```java
private static final String CACHE_PREFIX = "course:detail:v1:";
private static final String LOCK_PREFIX = "course:detail:lock:";

String cacheKey = CACHE_PREFIX + courseId; // course:detail:v1:1
String lockKey = LOCK_PREFIX + courseId;   // course:detail:lock:1
String lockToken = UUID.randomUUID().toString(); // UUID 是锁的 value
```

缓存 key 拼接的是课程 ID，不是 UUID；UUID 用于标识锁属于哪个线程。

2. 处理缓存穿透和缓存击穿
   - 查询 Redis，命中课程详情就直接返回。

   - 数据库不存在该课程时，向 Redis 写入短期 `NULL`，防止同一个无效 ID 反复穿透到 MySQL。

   - 热门课程缓存失效时，多个线程通过 `setIfAbsent` 竞争 `course:detail:lock:{courseId}`，防止缓存击穿。

   - 没抢到锁的线程等待 50ms 后有限重试；抢到锁的线程允许查询 MySQL 并重建缓存。

   - 抢到锁后再次查询 Redis。等待锁期间其他线程可能已经完成重建，这次检查可避免重复查询和重复写缓存。

   - 使用“UUID token + Lua”释放锁，避免误删其他线程后来获得的锁。

```java
String json = redisTemplate.opsForValue().get(cacheKey);
if (json != null) return readJson(json);

String lockToken = tryLock(lockKey);
if (lockToken == null) return retry(courseId);

try {
    json = redisTemplate.opsForValue().get(cacheKey); // double-check
    if (json != null) return readJson(json);

    CourseDetailVO course = courseMapper.selectCourseWithTeacher(courseId);
    if (course == null) {
        redisTemplate.opsForValue().set(cacheKey, "NULL", Duration.ofSeconds(60));
        return null;
    }
    redisTemplate.opsForValue().set(cacheKey, writeJson(course), randomTtl());
    return course;
} finally {
    releaseLockWithLua(lockKey, lockToken);
}
```

3. 处理缓存雪崩

给基础 TTL 增加随机值，使课程缓存分散过期：

```java
long ttlMinutes = 30 + ThreadLocalRandom.current().nextInt(10);
// 最终过期时间为 30～39 分钟
```

4. Cache Aside（旁路缓存）

读取：先查 Redis，未命中再查 MySQL 并重建缓存。

写入：先修改 MySQL；事务提交成功后，通过事件监听器删除 Redis 缓存。下一次查询再从数据库读取新数据并重建缓存。

```java
// 新增、修改或删除课程后发布事件
eventPublisher.publishEvent(new CourseChangedEvent(courseId));

@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void evictAfterCommit(CourseChangedEvent event) {
    redisTemplate.delete(CACHE_PREFIX + event.courseId());
}
```

# 9. mybatis

## 背景

在没有Mybatis时传统JDBC操作数据库需要经历下面四步：

1. 获取连接器
2. 预编译SQL
3. 执行SQL
4. 获取结果集

ResultSet是一个通过游标遍历的结果集

```tex
ResultSet
┌────┬──────────┬─────┐
│ id │ username │ sex │
├────┼──────────┼─────┤
│ 1  │ zhangsan │  1  │ ← 游标当前指向这一行
└────┴──────────┴─────┘
```

```java
ResultSet rs = statement.executeQuery();

while (rs.next()) {
    Long id = rs.getLong("id");
    String username = rs.getString("username");
    Integer sex = rs.getObject("sex", Integer.class);

    System.out.println(id);
    System.out.println(username);
    System.out.println(sex);
}
```

MyBatis 就是为了解决以上问题的

> 也就是说Mybatis是一个 **半自动 ORM 持久层框架**，把 SQL 与 Java 方法绑定起来，解决原生 JDBC 里手写连接、拼接参数、预编译执行SQL、遍历结果集繁琐的问题，让你把精力专注在 SQL 本身。

## 动态SQL

`<if>` + `<where>`：可选条件

```xml
<select id="listByCondition" resultType="User">
    SELECT * FROM user
    <!-- 为什么用 <where>：它会智能地去掉开头多余的 AND/OR，
         且当所有条件都不满足时，连 WHERE 关键字本身都不输出（避免 SELECT * FROM user WHERE 空） -->
    <where>
        <!-- test 里是 OGNL 表达式：判断 name 既不为 null 也不为空字符串 -->
        <if test="name != null and name != ''">
            AND user_name LIKE CONCAT('%', #{name}, '%')
        </if>
        <if test="age != null">
            AND age = #{age}
        </if>
    </where>
</select>
```

`<choose>` / `<when>` / `<otherwise>`：多选一

```xml
<select id="listByPriority" resultType="User">
    SELECT * FROM user
    <where>
        <!-- 为什么用 choose：相当于 Java 的 if/else if/else，多个条件只命中第一个成立的 -->
        <choose>
            <when test="name != null and name != ''">
                AND user_name = #{name}
            </when>
            <when test="age != null">
                AND age = #{age}
            </when>
            <otherwise>
                AND status = 1
            </otherwise>
        </choose>
    </where>
</select>
```

`<trim>`：自定义修剪（where / set 的底层实现）

```xml
<!-- <trim> 是 <where> 和 <set> 的通用底层，用 prefix/suffix/prefixOverrides/suffixOverrides 控制拼接 -->
<select id="listByTrim" resultType="User">
    SELECT * FROM user
    <!-- prefix="WHERE"：前缀补 WHERE；prefixOverrides="AND |OR "：去掉开头多余的 AND/OR -->
    <trim prefix="WHERE" prefixOverrides="AND |OR ">
        <if test="name != null">AND user_name = #{name}</if>
        <if test="age != null">AND age = #{age}</if>
    </trim>
</select>
```

`<set>`：动态更新，避免多余的逗号

```xml
<update id="updateSelective">
    UPDATE user
    <!-- 为什么用 <set>：动态更新时只更新非空字段，
         <set> 会自动去掉末尾多余的逗号，避免 UPDATE user SET user_name=?, 这种语法错误 -->
    <set>
        <if test="userName != null">user_name = #{userName},</if>
        <if test="age != null">age = #{age},</if>
        <if test="email != null">email = #{email},</if>
    </set>
    WHERE id = #{id}
</update>
```

`<foreach>`：集合遍历（批量查询 / 批量插入）

```xml
<!-- 批量查询：foreach 把集合拼成 (?, ?, ?)，open/separator/close 分别控制括号、分隔符、结尾 -->
<select id="listByIds" resultType="User">
    SELECT * FROM user WHERE id IN
    <foreach collection="ids" item="id" open="(" separator="," close=")">
        #{id} <!-- 每个元素都走 #{} 预编译，既安全又高效 -->
    </foreach>
</select>
```

`<sql>` + `<include>`：SQL 片段复用

```xml
<!-- 为什么抽 SQL 片段：多个查询共用同一批列，改一处就能全局生效，避免漏改 -->

    id, user_name, age, email
</sql>

    SELECT <include refid="Base_Column_List"/> FROM user WHERE id = #{id}
</select>

<select id="list" resultType="User">

```

## 结果集映射

当列名和属性名对不上或需要关联查询或需要构造器注入时，`resultType` 的自动映射就力不从心了，这时就要上 `resultMap`。它就像一张列属性的对照表。

```xml
<!-- resultMap 的「为什么」：连表/别名查询后列名和属性名对不上，
     靠它显式指定每一列怎么映射到哪个属性 -->
<resultMap id="UserMap" type="User">
    <!-- 主键用 <id> 标签：为什么单独区分主键——MyBatis 用主键做缓存的 key，
         标识主键有助于缓存命中与比较性能 -->
    <id property="id" column="id"/>
    <!-- 普通列用 <result>：property 是 Java 属性，column 是数据库列 -->
    <result property="userName" column="user_name"/>
    <result property="age" column="age"/>
</resultMap>

<select id="getById" resultMap="UserMap">
    SELECT id, user_name, age FROM user WHERE id = #{id}
</select>
```

`resultMap` 的子元素全览：

| 子元素            | 作用                            |
| :---------------- | :------------------------------ |
| `<id>`            | 标识主键映射，利于缓存与比较    |
| `<result>`        | 普通列 → 属性映射               |
| `<constructor>`   | 用构造器注入（指定 `arg` 顺序） |
| `<association>`   | 一对一关联（单个对象）          |
| `<collection>`    | 一对多关联（集合）              |
| `<discriminator>` | 鉴别器，根据某列值动态选择映射  |

### 一对多嵌套查询

关联查询时引用别的SQL语句，并传入参数，但是会有N+1问题

```xml

<resultMap id="UserWithOrders2" type="User">

    <collection property="orders" ofType="Order"
                select="com.example.mapper.OrderMapper.listByUserId"
                column="id"/>
</resultMap>

<select id="getUserWithOrders2" resultMap="UserWithOrders2">
    SELECT id, user_name FROM user WHERE id = #{id}
</select>
```

> N+1问题及其解决：N+1 的根源是嵌套查询把一次查询拆成了 1 次主查询 和N 次子查询，用嵌套结果代替嵌套查询

```te
N+1 问题示意图（查询 N 个用户及其订单）：

  主查询：SELECT * FROM user            → 得到 N 行（1 次查询）
  子查询：每个用户再查一次订单
         SELECT * FROM orders WHERE user_id = 1   → 1 次
         SELECT * FROM orders WHERE user_id = 2   → 1 次
         ... 共 N 次

  总查询次数 = 1 + N，数据量一大就慢得离谱
```

MyBatis 本身不提供物理分页，只提供逻辑分页，所以可以使用pageHelper，它会拦截 Executor 的查询方法，从 ThreadLocal 取出分页参数，改写即将执行的 SQL 追加 LIMIT

## 批处理方式

批量插入/更新有几种做法，性能差异巨大：

| 方案                      | 机制                      | 性能                    | 适用     |
| :------------------------ | :------------------------ | :---------------------- | :------- |
| 循环单条 `insert`         | 每条独立往返              | 慢                      | 数据极少 |
| `<foreach>` 拼多条 VALUES | 一条 SQL 多组值           | 快，但有 SQL 长度上限   | 几千条内 |
| `ExecutorType.BATCH`      | JDBC 批处理，攒够批量提交 | 最快，不受 SQL 长度限制 | 海量数据 |

```java
// ExecutorType.BATCH：为什么最快——复用同一个 PreparedStatement 攒批，
// 由 JDBC 的 addBatch/executeBatch 一次性提交，减少往返和解析
try (SqlSession session = factory.openSession(ExecutorType.BATCH)) {
    UserMapper mapper = session.getMapper(UserMapper.class);
    for (int i = 0; i < 10000; i++) {
        mapper.insert(new User("user" + i, 18));
        if (i % 500 == 0) {
            session.flushStatements(); // 每 500 条刷一次，控制内存
        }
    }
    session.commit();
}
```

## 类型处理器

默认的 TypeHandler 只能处理基本类型与 String/Date 的映射。当实体里有枚举、JSON 字符串、自定义类型时，需要自定义 TypeHandler。

比如下面Java实体类型是枚举，而数据库里面是数字

```java
// 场景：数据库存的是数字状态码，Java 里想用枚举表达
public enum Sex { MALE(1), FEMALE(2), UNKNOWN(3); }
```

这时候如果要将数字字段（JDBC类型）转换为Java实体枚举类型，就需要自己定义类型处理器来完成转换了，如下：

```java
// 标注Java类型
@MappedTypes(Sex.class)
// 标注数据库类型
@MappedJdbcTypes(JdbcType.INTEGER)
// 自定义 TypeHandler：实现 Java 的 Sex 枚举和数据库的整数之间自动转换
public class SexTypeHandler extends BaseTypeHandler<Sex> {
 /**
     * 将非空的 Sex 枚举转换成整数并写入 SQL 参数。
     *
     * <p>当参数为 null 时，BaseTypeHandler 会统一处理，
     * 因此该方法只负责非空参数。
     *
     * @param ps        JDBC 预编译 SQL 对象，用于设置 SQL 中的参数
     * @param i         当前参数在 SQL 中的位置，从 1 开始
     * @param parameter 需要写入数据库的 Sex 枚举值，保证非空
     * @param jdbcType  当前参数对应的 JDBC 类型，例如 INTEGER
     * @throws SQLException 设置 JDBC 参数失败时抛出
     */
    @Override
    public void setNonNullParameter(
            PreparedStatement ps,
            int i,
            Sex parameter,
            JdbcType jdbcType) throws SQLException {

        // 使用稳定的业务 code 存库，不使用 ordinal()。
        // 枚举顺序改变时 ordinal 会变化，而自定义 code 可以保持不变。
        ps.setInt(i, parameter.getCode());
    }

    /**
     * 根据数据库列名读取整数，并转换为 Sex 枚举。
     *
     * @param rs         JDBC 查询结果集
     * @param columnName 要读取的数据库列名，例如 sex
     * @return 对应的 Sex 枚举；数据库字段为 null 时返回 null
     * @throws SQLException 读取查询结果失败时抛出
     */
    @Override
    public Sex getNullableResult(
            ResultSet rs,
            String columnName) throws SQLException {

        // getObject 可以区分数据库 NULL 和数字 0。
        Integer code = rs.getObject(columnName, Integer.class);
        return code == null ? null : Sex.of(code);
    }

    /**
     * 根据结果集中的列下标读取整数，并转换为 Sex 枚举。
     *
     * @param rs          JDBC 查询结果集
     * @param columnIndex 要读取的列位置，从 1 开始
     * @return 对应的 Sex 枚举；数据库字段为 null 时返回 null
     * @throws SQLException 读取查询结果失败时抛出
     */
    @Override
    public Sex getNullableResult(
            ResultSet rs,
            int columnIndex) throws SQLException {

        Integer code = rs.getObject(columnIndex, Integer.class);
        return code == null ? null : Sex.of(code);
    }

    /**
     * 从存储过程的输出参数中读取整数，并转换为 Sex 枚举。
     *
     * <p>CallableStatement 主要用于调用数据库存储过程。
     *
     * @param cs          JDBC 存储过程调用对象
     * @param columnIndex 输出参数的位置，从 1 开始
     * @return 对应的 Sex 枚举；输出参数为 null 时返回 null
     * @throws SQLException 读取存储过程结果失败时抛出
     */
    @Override
    public Sex getNullableResult(
            CallableStatement cs,
            int columnIndex) throws SQLException {

        Integer code = cs.getObject(columnIndex, Integer.class);
        return code == null ? null : Sex.of(code);
    }
}
```

# MybatisPlus

## 基本介绍

MybatisPlus主要封装了Mybatis的常用的场景，对Mybtis只做增强不做修改

1. 封装基础CRUD，`BaseMapper` 把 90% 的单表 CRUD 覆盖掉了。
2. 分页、逻辑删除、乐观锁、自动填充、多租户全部做成插件

> 判断一个操作能不能用 BaseMapper 搞定，就看它是不是单表、按主键或简单条件；一旦涉及多表 join、子查询、聚合统计，就回到 Mapper 里自定义方法写原生 SQL

## 条件构造器

Wapper的本质是条件建造者，用 Java 链式调用的方式，帮你拼出 `WHERE` 后面的 SQL 片段，避免手写一堆 `<if>` 判断

| 类型                     | 字段写法                 | 是否可写 set（更新） | 使用场景                   |
| :----------------------- | :----------------------- | :------------------- | :------------------------- |
| `QueryWrapper<T>`        | 字符串列名 `"name"`      | 否                   | 纯查询，图省事             |
| `LambdaQueryWrapper<T>`  | 方法引用 `User::getName` | 否                   | **推荐**，编译期校验字段名 |
| `UpdateWrapper<T>`       | 字符串列名               | 是                   | 更新时带 set               |
| `LambdaUpdateWrapper<T>` | 方法引用                 | 是                   | **推荐**，更新时带 set     |

> 优先使用Lambda版本，因为`User::getAge` 是方法引用，字段名由编译器从实体上解析，一旦数据库字段或实体字段改名，编译直接报错；而字符串 `"age"` 写错了是运行时才暴露的静默 bug

### 基本示例

```java
LambdaQueryWrapper<User> wrapper = new LambdaQueryWrapper<>();
wrapper.eq(User::getName, "张三")                 // where name = '张三'
       .gt(User::getAge, 18)                     //   and age > 18
       .like(User::getEmail, "gmail")            //   and email like '%gmail%'
       .orderByDesc(User::getCreateTime);        //   order by create_time desc

List<User> list = userMapper.selectList(wrapper);
```

### 动态条件

实际项目里，查询条件是有才拼、没有就不拼的。所有条件方法第一个参数都能传一个 `boolean condition`：

```java
// 前端传了 name 才拼 name 条件，传了 age 区间才拼 age 条件
LambdaQueryWrapper<User> wrapper = new LambdaQueryWrapper<>();
wrapper.eq(StringUtils.hasText(name), User::getName, name)
       .between(ageStart != null && ageEnd != null, User::getAge, ageStart, ageEnd)
       .orderByDesc(User::getCreateTime);
// 为什么第一个参数是 boolean：为 false 时这段条件直接跳过，避免 null 条件污染 SQL
```

### 复杂嵌套条件

需求：查询（姓张 且 年龄 > 18）或（邮箱不为空 且 年龄 < 60）的用户。

```java
LambdaQueryWrapper<User> wrapper = new LambdaQueryWrapper<>();
wrapper.and(w -> w.like(User::getName, "张").gt(User::getAge, 18))
       .or(w -> w.isNotNull(User::getEmail).lt(User::getAge, 60));
```

生成的 SQL：

```java
WHERE ( name LIKE '张%' AND age > 18 )
   OR ( email IS NOT NULL AND age < 60 )
```

### UpdateWarpper

更新场景下，用 `UpdateWrapper` 可以直接拼 `set` 片段，不需要先查实体：

```java
// 需求：把年龄大于 30 的用户邮箱清空（直接按条件更新，不用先 select）
LambdaUpdateWrapper<User> uw = new LambdaUpdateWrapper<>();
uw.set(User::getEmail, null)          // set email = null
  .gt(User::getAge, 30);              // where age > 30
userMapper.update(null, uw);
```

### 灵活扩展

| 方法                                  | 说明                                                                           |
| :------------------------------------ | :----------------------------------------------------------------------------- |
| `apply(String sql, Object... params)` | 直接拼一段 SQL 片段，如 `apply("date_format(create_time,'%Y') = {0}", "2026")` |
| `last(String lastSql)`                | 在最后追加，如 `last("limit 1")`（**有 SQL 注入风险**）                        |
| `select(String... columns)`           | 指定查询列（QueryWrapper 专用）                                                |
| `func(Consumer<Children>)`            | 条件分支的语法糖，见 3.5                                                       |

> 总结

1. 查询用 `LambdaQueryWrapper`，更新用 `LambdaUpdateWrapper`，字段一律用方法引用。
2. 所有条件方法都支持 `condition` 参数实现「动态拼接」。
3. 复杂逻辑用 `and / or / nested` 组合出带括号的嵌套条件。
4. `apply / last` 是最后的逃生门，能不用就不用，避免 SQL 注入。

## 分页插件

分页是列表页最高频的操作。MP 的分页不是内置默认开启的，**必须手动注册 `PaginationInnerInterceptor` 插件**。

### 注册分页插件

```java
@Configuration
public class MybatisPlusConfig {

    @Bean
    // 为什么必须手动注册分页插件：MyBatis-Plus 3.x 后分页是独立插件，
    // 不注册的话 Page 参数会被当成普通参数忽略，不会真的分页（查回全表）
    public MybatisPlusInterceptor mybatisPlusInterceptor() {
        MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();
        PaginationInnerInterceptor pagination = new PaginationInnerInterceptor(DbType.MYSQL);
        // 单页最大 500 条，防止恶意传超大 pageSize 拖垮数据库
        pagination.setMaxLimit(500L);
         // 超过最大页时是否回到首页（false 表示不处理）
        pagination.setOverflow(false);
        interceptor.addInnerInterceptor(pagination);
        return interceptor;
    }
}
```

### 使用

```java
// 分页查询：第 1 页，每页 10 条，按年龄降序
Page<User> page = new Page<>(1, 10);
Page<User> result = userMapper.selectPage(page,
        new LambdaQueryWrapper<User>().orderByDesc(User::getAge));

result.getRecords();   // 当前页数据 List<User>
result.getTotal();     // 总条数
result.getPages();     // 总页数
result.getCurrent();   // 当前页码
result.getSize();      // 每页大小
```

### 多表分页

分页也能和自定义 SQL 结合：只要 Mapper 方法第一个参数是 `Page`，返回值是 `IPage`，MP 就会自动帮你做 count + limit 改写：

```java
public interface UserMapper extends BaseMapper<User> {
    // 自定义多表分页查询，第一个参数是 Page，返回 IPage，MP 自动分页
    IPage<UserVO> selectUserPage(Page<UserVO> page, @Param("deptId") Long deptId);
}
```

```xml
<!-- UserMapper.xml -->
<select id="selectUserPage" resultType="com.example.vo.UserVO">
    SELECT u.*, d.name AS deptName
    FROM user u LEFT JOIN dept d ON u.dept_id = d.id
    WHERE u.dept_id = #{deptId}
</select>
```

> 注意：自定义分页 SQL 里**不要再自己写 `limit`**，MP 的分页插件会统一在最后追加 `LIMIT ?,?`

## 主键策略

主键生成是数据表设计的第一道坎。MP 通过 `@TableId(type = ...)` 提供多种策略。

| IdType        | 说明                          | 适用场景                   |
| :------------ | :---------------------------- | :------------------------- |
| `ASSIGN_ID`   | **默认**，雪花算法生成 Long   | 分布式系统、分库分表       |
| `ASSIGN_UUID` | 生成 32 位 UUID（去掉中划线） | 需要字符串主键的场景       |
| `AUTO`        | 数据库自增                    | 单库、主键从 1 递增        |
| `INPUT`       | 手动输入                      | 由业务生成主键（如订单号） |
| `NONE`        | 无主键策略                    | 交给全局配置决定           |

雪花算法（Snowflake）是 Twitter 开源的分布式 ID 生成算法，MP 默认用它。它生成一个 64 位的`Long`：

```tex
┌─┬───────────────────────┬──────────────────────┬────────────┐
│1│        41 bit         │      10 bit          │   12 bit   │
│符│      时间戳(毫秒)      │  机器标识(5+5)        │  序列号     │
│号│  (可用约 69 年)        │ datacenter+worker    │ 同毫秒内    │
│位│                       │  可部署 1024 台机器    │ 最多 4096  │
└─┴───────────────────────┴──────────────────────┴────────────┘
  1(符号位，恒为0) + 41 + 10 + 12 = 64 bit
```

特点：

- **趋势递增**：按时间戳排序，整体是递增的，利于索引。
- **全局唯一**：不同机器 + 序列号保证同一毫秒内也不冲突。
- **不依赖数据库**：纯内存生成，性能极高。

> 雪花算法生成的是**分布式环境全局唯一、趋势递增**的 Long 型 ID，不需要数据库自增、不依赖单库，天然适配分库分表；而数据库自增 ID 在多库多表下会冲突，UUID 虽唯一但无序、不利于索引。雪花算法用「时间戳 + 机器标识 + 序列号」三段位组合，在单机内存里就能生成，性能与唯一性兼顾。

| 查询 | `SELECT ... WHERE id=?`       | `SELECT ... WHERE id=? AND deleted=0`                |

## 乐观锁

场景：两个人同时打开同一个订单页面，A 改了金额保存，B 改了备注保存。B 保存时会把 A 的金额改动覆盖掉（因为 B 手里是旧数据）。解决并发更新的两种思路：

- **悲观锁**：读取时就 `SELECT ... FOR UPDATE` 加锁，别人改不了（性能差，锁冲突）。
- **乐观锁**：加一个 `version` 版本号字段，更新时校验版本号，版本号变了说明别人改过，本次更新失败（无锁，性能好）。

MP 提供的是乐观锁方案，通过 `@Version` + 插件实现。

```java
@Configuration
public class MybatisPlusConfig {
    @Bean
    public MybatisPlusInterceptor mybatisPlusInterceptor() {
        MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();
        // 乐观锁插件
        interceptor.addInnerInterceptor(new OptimisticLockerInnerInterceptor());
        // 分页插件（可共存）
        interceptor.addInnerInterceptor(new PaginationInnerInterceptor(DbType.MYSQL));
        return interceptor;
    }
}
```

```java
// 实体字段
@Version
private Integer version;    // 数据库默认 0，每次更新自动 +1
```

> 乐观锁的底层原理：MP 的乐观锁依赖 `OptimisticLockerInnerInterceptor`：在 `update` 语句执行前，拦截器读取实体里的 `@Version` 字段旧值，把它拼进 `WHERE` 子句，同时在 `SET` 子句里让 `version = version + 1`。这样只有版本号未变的那次更新能成功，其余更新影响 0 行，由业务层判断失败重试。核心就是用版本号 CAS的乐观并发控制替代数据库行锁。

## 自动填充

`create_time`、`update_time`、`create_by` 这类审计字段几乎是每张表的标配。如果每个接口都手动 `setCreateTime(now())`，既啰嗦又容易漏。自动填充就是：**在 insert/update 时，由 MP 统一帮你填上这些字段**。

```java
@Component
public class MyMetaObjectHandler implements MetaObjectHandler {

    // 插入时触发
    // metadata是mybatis正在操作的对象
    @Override
    public void insertFill(MetaObject metaObject) {
        // strictInsertFill：字段没有值时才填充（有值不覆盖）
        this.strictInsertFill(metaObject, "createTime", LocalDateTime.class, LocalDateTime.now());
        this.strictInsertFill(metaObject, "updateTime", LocalDateTime.class, LocalDateTime.now());
        // 也可填当前登录用户
        this.strictInsertFill(metaObject, "createBy", String.class, getCurrentUser());
    }

    // 更新时触发
    @Override
    public void updateFill(MetaObject metaObject) {
        this.strictUpdateFill(metaObject, "updateTime", LocalDateTime.class, LocalDateTime.now());
    }
}
```

填充时机

| 枚举值          | 填充时机     |
| :-------------- | :----------- |
| `DEFAULT`       | 不填充       |
| `INSERT`        | 插入时       |
| `UPDATE`        | 更新时       |
| `INSERT_UPDATE` | 插入和更新时 |

```java
@TableField(fill = FieldFill.INSERT)           // 仅在 insert 时填充
private LocalDateTime createTime;

@TableField(fill = FieldFill.INSERT_UPDATE)    // insert 和 update 都填充
private LocalDateTime updateTime;
```

strictFill 的几种变体

| 方法                                                 | 说明                       |
| :--------------------------------------------------- | :------------------------- |
| `strictInsertFill(metaObject, fieldName, type, val)` | 严格填充：目标字段为空才填 |
| `strictUpdateFill(metaObject, fieldName, type, val)` | 严格填充：目标字段为空才填 |
| `fillStrategy(metaObject, fieldName, val)`           | 直接填充，无论字段是否为空 |
| `setFieldValByName(fieldName, val, metaObject)`      | 无条件设置                 |

## 代码生成器

## 多租户

所谓的多租户就是一套系统服务多个企业或组织，通常共用数据库表，通过 `tenant_id` 区分并隔离各租户的数据。比如

```
租户1：培训机构A
租户2：培训机构B
```

它们使用同一套后端程序，但机构A不能查看机构B的用户、课程和订单。最常见的实现是在业务表中加入 `tenant_id`这叫行级多租户：

```sql
CREATE TABLE course (
    id        BIGINT PRIMARY KEY,
    tenant_id BIGINT NOT NULL,
    title     VARCHAR(100)
);
```

MP 用 `TenantLineInnerInterceptor` 实现行级租户隔离，即**在所有 SQL 上自动追加 `tenant_id = ?` 条件**

```java
@Bean
public MybatisPlusInterceptor mybatisPlusInterceptor() {
    MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();

    // 多租户插件
    interceptor.addInnerInterceptor(new TenantLineInnerInterceptor(new TenantLineHandler() {
        // 获取当前租户 ID（通常从登录上下文/ThreadLocal 取）
        @Override
        public Expression getTenantId() {
            return new LongValue(LoginUserHolder.getTenantId());
        }
        // 哪些表需要租户隔离（返回 true 则追加 tenant_id 条件）
        @Override
        public boolean ignoreTable(String tableName) {
            return "sys_config".equals(tableName);  // 公共配置表不隔离
        }
    }));
    return interceptor;
}
```

效果：查询 `SELECT * FROM order WHERE ...` 会被自动改写为 `SELECT * FROM order WHERE ... AND tenant_id = 1001`，业务代码无需关心租户过滤

## 批量操作与性能优化

### 分批插入

```java
// ✅ 正确：saveBatch 内部用一条 SQL 批量提交（JDBC batch）
userService.saveBatch(list);   // 内部自动分批，每 1000 条 flush 一次
```

`saveBatch` 原理：底层用 JDBC 的 `PreparedStatement.addBatch()` + `executeBatch()`，一次性把多条 SQL 打包发给数据库，避免反复网络往返。

### 常用性能优化项

| 优化项            | 做法                                                | 收益                       |
| :---------------- | :-------------------------------------------------- | :------------------------- |
| 批量操作          | 用 `saveBatch / updateBatchById / removeBatchByIds` | 减少数据库往返             |
| 只查需要的列      | `wrapper.select("id","name")`                       | 减少数据传输               |
| 分页 count 优化   | `optimizeCountSql = true`（默认）                   | count 时去掉 order by 提速 |
| 避免全表更新/删除 | 加 `BlockAttackInnerInterceptor` 防呆               | 防止误操作全表             |
| 关闭 SQL 日志     | 生产环境去掉 `StdOutImpl`                           | 减少 IO 开销               |

### 防全表更新/删除插件

```java
// 防止 update/delete 忘记带 where 条件导致全表更新/删除的「防呆」插件
interceptor.addInnerInterceptor(new BlockAttackInnerInterceptor());
```

加上后，`UPDATE user SET age=20`（无 where）这种 SQL 会直接抛异常，保护生产数据。

# SpringMVC

Spring MVC 是 Spring 生态的 Web MVC 框架，核心通过`DispatcherServlet`前端控制器统一接收 HTTP 请求，根据 URL 分发至 Controller，实现请求路由、业务处理与响应返回，提供可扩展的 Web 请求处理能力。

## 过滤器和Servlet

早期是通过过滤器链来进行的请求处理的，一个servlet里面要进行手动解析参数、拼 SQL、拼 HTML。这违背了单一职责。

```java
// 反例：所有逻辑堆在一个 Servlet 里，页面越多越失控
@WebServlet("/user")
public class UserServlet extends HttpServlet {
    protected void doGet(HttpServletRequest req, HttpServletResponse resp) {
        String action = req.getParameter("action");       // 靠一个 action 参数区分业务
        if ("add".equals(action)) {
            String name = req.getParameter("name");
            // 1. 解析参数（还要手动处理乱码、类型转换）
            // 2. 查数据库（业务逻辑写死在 Servlet 里）
            // 3. 拼 HTML 返回（视图也写死在 Servlet 里）
            resp.getWriter().write("<html><body>..." + name + "...</body></html>");
        } else if ("list".equals(action)) {
            // ... 又是一大段
        }
    }
}
```

拦截器在Spring容器实例化之前就初始化完成了

## MVC架构

MVC 把一次 Web 交互拆成三个职责单一的组件

- model：处理业务
- view：处理视图
- controller：控制器

> 前后端分离后 Spring MVC 的 View 基本名存实亡，因为Controller返回json

## 参数绑定

### 查询参数映射`@RequestParam`

作用：将查询字符串的属性映射到方法参数上

案例：`?name=zhangsan&page=1&pageSize=10`

```java
@GetMapping("/list")
public List<User> list(@RequestParam("name") String name,
                       @RequestParam(value = "page", defaultValue = "1") int page,
                       @RequestParam(value = "pageSize", required = false) Integer pageSize) {
    return userService.list(name, page, pageSize);
}
```

参数属性：

- `defaultValue`：前端没有传值时注入默认值
- `required`: 是否允许空值，`@RequestParam` 默认 `required = true`，参数缺失直接抛 `MissingServletRequestParameterException`（返回 400）。

### 路径参数映射`@PathVariable`

作用：将RESTful 风格的路径参数进行映射

案例：`/user/1001`

```java
// 多级路径：/user/1001/orders/2002
@GetMapping("/{userId}/orders/{orderId}")
public Order getOrder(@PathVariable Long userId, @PathVariable Long orderId) { ... }
```

注意：占位符 `{id}`与方法参数名一致时，`@PathVariable` 的 `value` 可省略

## 静态资源拦截

背景：`DispatcherServlet` 是 Spring MVC 的前端控制器，如果你配置它的拦截路径为 `/`，那么所有请求，都会被`DispatcherServlet`接管。包括接口 `/user/list`、还有静态资源 `/css/style.css`、`/js/main.js`、`/img/a.png`。对于静态资源，`DispatcherServlet` 只会去找`Controller`接口；静态 `css/js` 图片没有对应的 `Controller` 方法，找不到处理器就返回 404。所以要做静态资源处理。

处理方式：

1. springboot默认静态资源映射：Spring Boot 默认已有静态资源映射 `/static`、`/public`、`/resources`、`/META-INF/resources`
2. 如果想要自定义静态资源处理，可以如下进行：

```java
// 如果需要自定义，用 WebMvcConfigurer：
@Configuration
public class WebConfig implements WebMvcConfigurer {
    @Override
    public void addResourceHandlers(ResourceHandlerRegistry registry) {
        // 把 /files/** 的请求映射到磁盘目录 E:/upload
        registry.addResourceHandler("/files/**")
                .addResourceLocations("file:E:/upload/");
    }
}
```

## 拦截器

拦截器本质上是职责链模式来设计的。

### 配置

```java
@Component
public class LoginInterceptor implements HandlerInterceptor {

    // preHandle：方法执行前。返回 false 直接拦截，不再往下走
    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
        // 为什么在 preHandle 校验 token：登录态必须在业务方法执行前判断，
        // 否则未登录用户也能进入核心业务逻辑，校验就失去意义
        String token = request.getHeader("Authorization");
        if (token == null || !tokenService.isValid(token)) {
            throw new UnauthorizedException("未登录"); // 抛异常交给全局异常处理器统一返回
        }
        return true; // 放行
    }

    // postHandle：方法执行后、视图渲染前（此时已拿到 ModelAndView）
    @Override
    public void postHandle(HttpServletRequest request, HttpServletResponse response, Object handler,
                           ModelAndView modelAndView) {
        // 可以对返回的数据做统一加工
    }

    // afterCompletion：整个请求完成后执行（资源清理、日志记录）
    @Override
    public void afterCompletion(HttpServletRequest request, HttpServletResponse response, Object handler, Exception ex) {
        // 为什么放清理逻辑在这：无论前面是否抛异常，afterCompletion 都会执行
    }
}
```

注册拦截器（务必注册，否则拦截器不生效）：

```java
@Configuration
public class WebConfig implements WebMvcConfigurer {
    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(new LoginInterceptor())
                .addPathPatterns("/**")            // 拦截所有
                .excludePathPatterns("/login", "/register", "/static/**"); // 放行登录注册和静态资源
    }
}
```

### 拦截器和过滤器

| 对比项               | 过滤器 Filter               | 拦截器 Interceptor                        | Spring AOP                          |
| :------------------- | :-------------------------- | :---------------------------------------- | :---------------------------------- |
| 归属                 | Servlet 规范（Java EE）     | Spring MVC 框架                           | Spring 框架                         |
| 能否拿到 Spring Bean | 不能直接注入（在容器外）    | 可以（本身是 Spring 组件）                | 可以                                |
| 拦截范围             | 所有请求（含静态资源）      | 只拦 Spring MVC 处理的请求                | 拦截 Bean 方法（不限于 Controller） |
| 执行时机             | 在 `DispatcherServlet` 之前 | `DispatcherServlet` 之后、Controller 之前 | 方法调用前后（动态代理）            |
| 粒度                 | 粗（按 URL）                | 中（按 URL + 方法）                       | 细（按方法 + 注解 + 表达式）        |
| 典型场景             | 编码、跨域、日志、XSS 过滤  | 登录校验、权限、性能统计                  | 事务、缓存、日志切面                |

### 模拟拦截器

```java
import java.util.ArrayList;
import java.util.List;
class Req {
    String token;
    Req(String token) {
        this.token = token;
    }
}
class Res {
    int status = 200;
    String body;
}
interface Interceptor {
    void doGet(Req req, Res res, InterceptorChain chain);
}
class InterceptorChain {
    private int index = 0;
    private final List<Interceptor> interceptors =
        new ArrayList<>();
    public void addInterceptor(Interceptor interceptor) {
        interceptors.add(interceptor);
    }
    public void doGet(Req req, Res res) {
        // 所有拦截器执行完成，进入 Controller
        if (index >= interceptors.size()) {
            System.out.println("执行 Controller");
            res.body = "请求成功";
            return;
        }
        // 先让索引指向下一个，再执行当前拦截器
        Interceptor interceptor = interceptors.get(index++);
        interceptor.doGet(req, res, this);
    }
}

class LogInterceptor implements Interceptor {
    @Override
    public void doGet(
        Req req,
        Res res,
        InterceptorChain chain
    ) {
        System.out.println("日志拦截器：请求前");

        chain.doGet(req, res);

        System.out.println("日志拦截器：请求后");
    }
}

class AuthInterceptor implements Interceptor {
    @Override
    public void doGet(
        Req req,
        Res res,
        InterceptorChain chain
    ) {
        if (req.token == null) {
            res.status = 401;
            res.body = "未登录";

            // 不调用 chain.doGet()，责任链到此结束
            return;
        }

        System.out.println("认证通过");
        chain.doGet(req, res);
    }
}
public class Main {

    public static void main(String[] args) {
        Req req = new Req("token");
        Res res = new Res();

        InterceptorChain chain = new InterceptorChain();
        chain.addInterceptor(new LogInterceptor());
        chain.addInterceptor(new AuthInterceptor());

        chain.doGet(req, res);

        System.out.println(res.status);
        System.out.println(res.body);
    }
}
```

## 全局异常处理

全局拦截所有 Controller 抛出的异常，并把返回值序列化成 JSON

1. `@ExceptionHandler` 的匹配规则是找最精确的异常类型，所以 `BusinessException` 和 `Exception` 可以共存，前者优先。
2. 可以设置order执行顺序

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    // 业务异常：返回业务状态码 + 提示
    @ExceptionHandler(BusinessException.class)
    public Result<Void> handleBusiness(BusinessException e) {
        // 统一返回 Result 包装：前端拿到固定结构 {code,msg,data}，解析逻辑只需写一次
        return Result.error(e.getCode(), e.getMessage());
    }

    // 参数校验异常：把校验失败信息友好地返回
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public Result<Void> handleValid(MethodArgumentNotValidException e) {
        String msg = e.getBindingResult().getFieldError().getDefaultMessage();
        return Result.error(400, msg);
    }

    // 兜底异常：任何没被上面的 handler 接住的异常都走这里
    @ExceptionHandler(Exception.class)
    public Result<Void> handleOther(Exception e) {
        log.error("未捕获异常", e); // 为什么这里要打日志：兜底异常往往意味着 bug，需要留痕排查
        return Result.error(500, "服务器开小差了");
    }
}
```

## 响应结果执行流程

```java
Controller
    ↓ 返回 Result / 抛出异常
@RestControllerAdvice
    ↓ 将异常转换为 Result
HandlerMethodReturnValueHandler
    ↓ 选择返回值处理方式
ResponseBodyAdvice
    ↓ 国际化、统一加工响应体
HttpMessageConverter
    ↓ 将 Java 对象转换为 JSON
HttpServletResponse
    ↓ 写入 HTTP 响应
Servlet Filter
    ↓ 处理响应头、日志等
客户端
```

### ResponseBodyAdvice

这个方法是在Java对象序列化(也就是HttpMessageConverter方法执行)之前执行。可以最后一步处理返回数据，比如做i18h国际化

```java
@RestControllerAdvice
public class GlobalResponseAdvice implements ResponseBodyAdvice<Object> {
    // 为什么需要 supports 判断：避免把已经是 Result 的返回值二次包装成 Result<Result>
    @Override
    public boolean supports(MethodParameter returnType, Class converterType) {
        return !returnType.getParameterType().equals(Result.class);
    }
    @Override
    public Object beforeBodyWrite(Object body, MethodParameter returnType, MediaType type,Class converterType, ServerHttpRequest request, ServerHttpResponse response) {
        // 在 HttpMessageConverter 写响应体之前，把原始返回对象包进 Result
        return Result.ok(body);
    }
}
```

### HttpMessageConverter

`@ResponseBody` / `@RequestBody` 真正干活的是 `HttpMessageConverter` 这一策略接口，实际上会根据MIME类型来调用不同的Converter来进行处理。

#### 接口定义

```java
public interface HttpMessageConverter<T> {
    boolean canRead(Class<?> clazz, MediaType mediaType);   // 能否把请求体读成 clazz
    boolean canWrite(Class<?> clazz, MediaType mediaType);  // 能否把 clazz 写成响应体
    List<MediaType> getSupportedMediaTypes();               // 支持的媒体类型
    T read(Class<? extends T> clazz, HttpInputMessage inputMessage) throws IOException;
    void write(T t, MediaType contentType, HttpOutputMessage outputMessage) throws IOException;
}
```

#### 常见实现

| 实现类                                | 支持的媒体类型                      | 作用                                  |
| :------------------------------------ | :---------------------------------- | :------------------------------------ |
| `StringHttpMessageConverter`          | `text/plain`                        | 字符串读写                            |
| `MappingJackson2HttpMessageConverter` | `application/json`                  | Jackson 处理 JSON（Spring Boot 默认） |
| `GsonHttpMessageConverter`            | `application/json`                  | Gson 处理 JSON                        |
| `ByteArrayHttpMessageConverter`       | 全类型                              | 字节流（文件下载）                    |
| `FormHttpMessageConverter`            | `application/x-www-form-urlencoded` | 表单                                  |
| `ResourceHttpMessageConverter`        | 全类型                              | 资源下载                              |

#### 序列化流程

```java
Controller 返回 User 对象（带 @ResponseBody）
    │
    ▼
RequestMappingHandlerAdapter 遍历所有 HttpMessageConverter
    │
    ▼
找到 canWrite(User.class, application/json) 为 true 的转换器
    │
    ▼
MappingJackson2HttpMessageConverter.write()
    │ 内部调用 Jackson 的 ObjectMapper.writeValue()
    ▼
把 User 序列化成 JSON 字符串写进 HttpServletResponse 的输出流
```

> 💡 面试题：接口返回日期为什么会变成一串数字或时区错乱？因为 Jackson 默认把 `Date` 序列化成时间戳（毫秒数），且默认用 UTC 时区，导致展示成 8 小时偏差。解决：在字段上标注 `@JsonFormat(pattern = "yyyy-MM-dd HH:mm:ss", timezone = "GMT+8")` 显式指定格式和时区，或全局配置 Jackson 的日期格式。

#### 自定义消息转换器

```java
@Configuration
public class WebConfig implements WebMvcConfigurer {
    @Override
    public void extendMessageConverters(List<HttpMessageConverter<?>> converters) {
        // 自定义 Jackson 转换器：全局统一日期格式，比在每个字段加 @JsonFormat 省事
        MappingJackson2HttpMessageConverter converter = new MappingJackson2HttpMessageConverter();
        ObjectMapper om = new ObjectMapper();
        om.setDateFormat(new SimpleDateFormat("yyyy-MM-dd HH:mm:ss"));
        om.setTimeZone(TimeZone.getTimeZone("GMT+8"));
        converter.setObjectMapper(om);
        converters.add(0, converter); // 加到最前面，优先级最高
    }
}
```

## 参数校验

### 常用的校验注解

| 注解                | 作用                                  |
| :------------------ | :------------------------------------ |
| `@NotNull`          | 不能为 null                           |
| `@NotEmpty`         | 不能为 null 且长度 > 0（字符串/集合） |
| `@NotBlank`         | 不能为 null 且去掉首尾空格后长度 > 0  |
| `@Size(min, max)`   | 长度/大小在范围内                     |
| `@Min` / `@Max`     | 数值范围                              |
| `@Positive`         | 数值必须大于 0，允许为 null           |
| `@PositiveOrZero`   | 数值必须大于或等于 0，允许为 null     |
| `@Email`            | 邮箱格式                              |
| `@Pattern(regexp)`  | 正则匹配                              |
| `@Past` / `@Future` | 过去/未来时间                         |

```java
public class UserDTO {
    @NotNull(message = "id 不能为空")
    private Long id;

    @NotBlank(message = "姓名不能为空")
    @Size(min = 2, max = 20, message = "姓名长度 2-20")
    private String name;

    @Email(message = "邮箱格式不正确")
    private String email;

    @Min(value = 0, message = "年龄不能为负数")
    @Max(value = 150, message = "年龄不合法")
    private Integer age;
}
```

> `@Positive` 通常用于校验单个数值字段或方法参数

### 提取校验错误

`@Valid @RequestBody` 校验失败时，Spring MVC 会抛出`MethodArgumentNotValidException`。在全局异常处理器中通过`BindingResult` 取得错误：

```java
@ExceptionHandler(MethodArgumentNotValidException.class)
public Result<Void> handleMethodArgumentNotValid(
        MethodArgumentNotValidException e) {

    String message = e.getBindingResult()
            .getFieldErrors()
            .stream()
            .findFirst()
            .map(DefaultMessageSourceResolvable::getDefaultMessage)
            .orElse(ErrorCode.PARAM_ERROR.getMessageKey());

    return Result.fail(
            ErrorCode.PARAM_ERROR.getCode(),
            message);
}
```

### 分组校验

**解决的问题：**同一个 DTO 在不同接口中校验规则不同。比如新增用户时 id 必须为空（由数据库自增），更新用户时 id 不能为空

第一步：定义分组接口（空接口，只做标记）

```java
public interface AddGroup {}
public interface UpdateGroup {}
```

第二步：在 DTO 字段上指定 groups

```java
public class UserDTO {
    // 新增时 id 必须为空，更新时 id 不能为空
    @Null(groups = AddGroup.class, message = "新增时 id 必须为空")
    @NotNull(groups = UpdateGroup.class, message = "更新时 id 不能为空")
    private Long id;

    @NotBlank(groups = {AddGroup.class, UpdateGroup.class}, message = "姓名不能为空")  // 两组都要
    private String name;

    @Email(groups = UpdateGroup.class, message = "邮箱格式不对")  // 只有更新时才校验邮箱
    private String email;
}
```

第三步：在 Controller 上指定用哪个分组

```java
@PostMapping("/add")
public Result add(@Validated(AddGroup.class) @RequestBody UserDTO user) {
    // 只校验加了 groups = AddGroup.class 的字段
    // id → @Null 校验；name → @NotBlank 校验；email → 不校验（没加 AddGroup 分组）
    return Result.ok(userService.add(user));
}

@PostMapping("/update")
public Result update(@Validated(UpdateGroup.class) @RequestBody UserDTO user) {
    // 只校验加了 groups = UpdateGroup.class 的字段
    // id → @NotNull 校验；name → @NotBlank 校验；email → @Email 校验
    return Result.ok(userService.update(user));
}
```

### 嵌套校验

**解决的问题：** 一个 DTO 里嵌套了另一个对象，需要递归校验子对象的字段。

案例一：不分组（简单嵌套）

```java
// 场景：创建订单，订单里有用户信息，都要校验
public class OrderDTO {
    @NotNull(message = "订单号不能为空")
    private String orderNo;

    @NotNull(message = "用户信息不能为空")
    @Valid                         // ← 关键：递归校验 UserInfo 里的字段
    private UserInfo userInfo;
}

public class UserInfo {
    @NotBlank(message = "姓名不能为空")
    private String name;

    @Phone(message = "手机号格式不对")
    private String phone;
}
```

**加 `@Valid`**会递归校验引用数据类型

```java
@PostMapping("/create")
// @Valid 触发校验 → 遇到 @Valid → 递归进入 UserInfo 校验 name 和 phone
public Result create(@Valid @RequestBody OrderDTO order) {
    return Result.ok(orderService.create(order));
}
```

案例二：有分组（嵌套 + 分组校验）

```java
// 场景：新增时所有字段必填，更新时用户信息可选
public interface AddGroup {}
public interface UpdateGroup {}

public class OrderDTO {
    @Null(groups = AddGroup.class, message = "新增时 id 为空")
    @NotNull(groups = UpdateGroup.class, message = "更新时 id 不能为空")
    private Long id;

    @Valid                         // ← 触发嵌套校验，分组会传播进来
    @NotNull(groups = AddGroup.class)
    private UserInfo userInfo;
}

public class UserInfo {
    @NotBlank(groups = AddGroup.class, message = "姓名不能为空")
    @NotBlank(groups = UpdateGroup.class, message = "姓名不能为空")
    private String name;

    @Phone(groups = AddGroup.class, message = "手机号格式不对")  // 新增时才校验手机号
    private String phone;
}
```

`@Validated` 指定的分组会自动传播给 `@Valid` 标记的子对象。但**子对象里的字段也必须加对应的 `groups`**，否则默认是 `Default` 分组，和传入的分组不匹配，会被跳过

```java
@PostMapping("/add")
// @Validated 指定分组 → 传播给 @Valid → 子对象只校验加了 AddGroup 的字段
public Result add(@Validated(AddGroup.class) @RequestBody OrderDTO order) {
    // 校验：id → @Null；userInfo → @NotNull + @Valid 递归
    //      UserInfo.name → @NotBlank；UserInfo.phone → @Phone
    return Result.ok(orderService.add(order));
}

@PostMapping("/update")
public Result update(@Validated(UpdateGroup.class) @RequestBody OrderDTO order) {
    // 校验：id → @NotNull；userInfo → 不校验（没加 UpdateGroup）
    //      UserInfo.name → @NotBlank；UserInfo.phone → 不校验
    return Result.ok(orderService.update(order));
}
```

### 自定义校验注解

第一步：自定义注解

```java
@Target({FIELD})                                           // 贴在字段上
@Retention(RUNTIME)
@Constraint(validatedBy = PhoneValidator.class)            // 指定校验器，由它完成校验逻辑
public @interface Phone {
    String message() default "手机号格式不正确";              // 校验失败时的提示
    Class<?>[] groups() default {};                         // 分组校验，必须加
    Class<? extends Payload>[] payload() default {};        // 元数据，必须加
}
```

第二步：实现校验器

```java
public class PhoneValidator implements ConstraintValidator<Phone, String> {
    @Override
    public boolean isValid(String value, ConstraintValidatorContext context) {
        if (value == null) {
            return true;                     // null 交给 @NotNull 判断，不在这里判空
        }
        return value.matches("^1[3-9]\\d{9}$");  // 校验手机号
    }
}
```

第三步：使用

```java
public class UserDTO {
    @NotBlank(message = "手机号不能为空")
    @Phone(message = "手机号格式不对")        // ← 自定义注解，像内置注解一样用
    private String phone;
}
```

Spring 启动时扫描 `@Constraint` 注解，把校验器注册到 Validator 的映射表中。校验时根据注解类型找到对应的 `ConstraintValidator` 实例，调用 `isValid()` 方法判断。

## 文件上传与下载

### 上传

```java
@PostMapping("/upload")
public Result<String> upload(@RequestParam("file") MultipartFile file) throws IOException {
    // MultipartFile 是 Spring 对上传文件的抽象，底层靠 MultipartResolver 解析 multipart 请求
    String originalName = file.getOriginalFilename(); // 原始文件名
    String ext = originalName.substring(originalName.lastIndexOf(".")); // 后缀
    // 为什么用 UUID 重命名：防止用户上传同名文件互相覆盖，也防止路径穿越
    String newName = UUID.randomUUID().toString() + ext;
    file.transferTo(new File("E:/upload/" + newName)); // 落盘
    return Result.ok("/files/" + newName);
}
```


## 异步请求

### Callable异步线程

业务在线程池里执行，返回 Callable后容器线程立刻释放，完成后由框架再写响应

```java
@GetMapping("/callable")
public Callable<String> callable() {
    // 返回 Callable：容器线程立刻释放，业务在线程池里执行，完成后由框架再写响应
    return () -> {
        TimeUnit.SECONDS.sleep(2); // 模拟耗时操作
        return "处理完成";
    };
}
```

### DeferredResult跨线程回写

```java
@GetMapping("/deferred")
public DeferredResult<String> deferred() {
    DeferredResult<String> result = new DeferredResult<>(5000L); // 超时 5 秒
    // 把 result 交给另一个线程/消息队列，稍后 setResult 写回响应
    executor.submit(() -> {
        String data = remoteService.slowCall();
        result.setResult(data); // 完成时才写响应，线程早已释放
    });
    return result;
}
```

### SSE服务端推送

```java
@GetMapping(value = "/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public SseEmitter stream() {
    SseEmitter emitter = new SseEmitter();
    executor.execute(() -> {
        try {
            for (int i = 0; i < 10; i++) {
                emitter.send("消息 " + i); // 每次 send 推一条给前端
                TimeUnit.SECONDS.sleep(1);
            }
            emitter.complete();
        } catch (Exception e) {
            emitter.completeWithError(e);
        }
    });
    return emitter;
}
```

> 💡 面试题：Spring MVC 是同步还是异步模型？
> 结论：**默认同步阻塞**。它是基于 Servlet 规范的，每个请求占用一个 Tomcat 线程直到处理完成。需要异步时，可以返回 `Callable` / `DeferredResult` / `SseEmitter`，让容器线程先释放、业务在别处执行，从而提高吞吐。真正全异步（事件驱动、非阻塞 IO）是 Spring WebFlux 的活，不是 Spring MVC 的主场。

## 原理

1. 加载配置：HttpServletBean读取 Servlet init-param
2. 封装配置等为上下文：FrameworkServlet创建/初始化 WebApplicationContext
3. 做请求分发：DispatcherServlet调用doDispatch
   - `getHanler` ： 根据请求路径和方法找到`handler`(`controller`类中的方法)，同时得到拦截器
   - 正序调用拦截器 `preHandle()`
   - 参数解析 → 调用 `Controller` → 处理返回值
   - 逆序调用 `postHandle()`
