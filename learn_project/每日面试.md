## 第1天 · 项目搭建（Maven 多模块 + 统一返回 + 全局异常）

### Q1：`@RestControllerAdvice` 和 `@ControllerAdvice` 有什么区别？为什么能捕获到所有 Controller 抛出的异常？

**答：**

`@RestControllerAdvice` = `@ControllerAdvice` + `@ResponseBody`，返回值直接序列化成 JSON 而不是走视图解析器。

它捕获异常的精确机制不是"传统 AOP 通知（@Around/@AfterThrowing）"，而是 **Spring MVC 的 `HandlerExceptionResolver` 链**：

1. Controller 抛出异常 → `DispatcherServlet` 捕获
2. 调用 `HandlerExceptionResolver` 链 → 匹配到 `ExceptionHandlerExceptionResolver`
3. 这个 Resolver 扫描所有 `@ControllerAdvice` 类，按 `@ExceptionHandler` 声明的异常类型匹配
4. 匹配到就调用对应处理方法，返回包装好的 Result

**项目代码：** `GlobalExceptionHandler.java` 的 `@ExceptionHandler(BizException.class)` 精确匹配业务异常，`@ExceptionHandler(Exception.class)` 兜底 500。

**对比传统 try-catch：** 不用每个接口自己 try-catch，异常出口统一，代码不重复。

### Q2：`BizException` 为什么继承 `RuntimeException` 而不是 `Exception`？

**答：**

继承 `RuntimeException` = 非受检异常，编译器不强制处理。原因：

1. **不污染方法签名**——Service 里直接 `throw new BizException(PARAM_ERROR)`，不需要加 `throws`
2. **让全局异常处理器兜底**——`@RestControllerAdvice` 统一捕获，Controller 不需要 try-catch

```java
// 如果继承 Exception，每个方法都要 throws：
public Order getOrder(Long id) throws BizException {  // 污染签名
    if (id == null) throw new BizException(PARAM_ERROR);
}
```

```java
// 继承 RuntimeException，可以这样：
public Order getOrder(Long id) {
    if (id == null) throw new BizException(PARAM_ERROR);
    // 直接 throw，全局异常处理器统一处理
}
```

**总结：** 业务异常永远继承 `RuntimeException`，这是业界约定俗成的最佳实践。

### Q3：受检异常（Checked）和非受检异常（Unchecked）有什么区别？

**答：**

核心区别：**编译器管不管**。

| | 受检异常 | 非受检异常 |
|---|---|---|
| 编译器强制处理？ | 是（try-catch 或 throws，否则编译报错） | 否 |
| 代表 | `IOException`、`SQLException`、`FileNotFoundException` | `NullPointerException`、`IllegalArgumentException`、`BizException` |
| 典型场景 | 外部风险（文件不存在、网络断开、数据库连不上） | 程序 bug 或业务异常（空指针、参数不合法、订单不存在） |

**一句话：** 受检异常是"调用者必须意识到的外部风险"；非受检异常是"编译器不强制你处理的内部异常"（包括 bug 和业务异常）。

### Q4：`Result<T>` 为什么要设计成泛型？不用泛型用 `Object` 会怎样？

**答：**

核心原因两点：

**① 编译期类型安全，调用方不用强转：**

```java
// 不用泛型 → 必须强转，容易 ClassCastException
Result obj = userService.getUser(1L);
User user = (User) obj.getData();  // 类型不安全

// 用泛型 → 编译器保证类型匹配
Result<User> obj = userService.getUser(1L);
User user = obj.getData();  // 不需要强转
```

**② 方法签名本身就是文档：**

```java
Result<User> getUser(Long id);           // 一看就知道返回 User
Result<List<Order>> getOrders(Long userId); // 一看就知道返回订单列表
```

**项目代码：** `HealthController.java` 返回 `Result<Map<String, Object>>`，调用 `Result.ok(info)` 时编译器从实参类型推断出 T。

### Q5：聚合（`<modules>`）和继承（`<parent>`）有什么区别？

**答：**

| | 聚合（modules） | 继承（parent） |
|---|---|---|
| 方向 | 父→子（父知道子） | 子→父（子认父） |
| 本质 | 便捷构建 | 复用配置 |
| 没有会怎样？ | 每个模块单独 `mvn install` | 子模块各自写版本号 |

**项目代码：**

```xml
<!-- 父工程：聚合（爸爸叫儿子吃饭） -->
<modules>
    <module>mall-common</module>
    <module>mall-user</module>
</modules>

<!-- 子模块：继承（儿子认爸爸） -->
<parent>
    <groupId>com.mall</groupId>
    <artifactId>course-mall</artifactId>
    <version>1.0.0</version>
</parent>
```

**一句话：** 聚合是"爸爸叫儿子吃饭"，继承是"儿子认爸爸"——两回事，但通常一起出现。

### Q6：`parent` 继承父工程，具体继承了哪些内容？

**答：**

继承 `spring-boot-starter-parent` 主要得到：

| 继承内容 | 说明 |

| `dependencyManagement` | 所有 Spring Boot starter 版本号锁定（不用写 version） |

**本质：** Maven 继承就是把父 pom 的配置合并到子 pom 里，同名的子模块覆盖父工程。

### Q7：`dependencyManagement` 和 `dependencies` 有什么区别？

**答：**

| | `dependencyManagement` | `dependencies` |
|---|---|---|

```xml
</dependency>
```

### Q8：`@SpringBootApplication(scanBasePackages = "com.mall")` 不写会怎样？

**答：**

`@SpringBootApplication` = `@Configuration` + `@EnableAutoConfiguration` + `@ComponentScan`。

`@ComponentScan` 默认只扫启动类所在包（`com.mall.user`）及其子包。

如果不写 `scanBasePackages = "com.mall"`，就扫不到 `com.mall.common` 下的 `GlobalExceptionHandler`，导致：
- Controller 抛异常时不会走统一异常处理，返回默认白页/堆栈而非统一 JSON
- 所有 `com.mall.common` 包下的 Bean 都注册不上

**项目代码：** `MallUserApplication.java` 显式设置 `scanBasePackages = "com.mall"` 扩大扫描范围。

### Q9：`Result.ok(info)` 的泛型类型是怎么推断出来的？Java 有类似 `typeof` 的机制吗？

**答：**

Java 没有 `typeof`，这里用的是 **类型推断（Type Inference）**。

```java
public static <T> Result<T> ok(T data) { ... }

// 调用
Map<String, Object> info = new HashMap<>();
return Result.ok(info);  // 编译器从 info 的类型推断出 T = Map<String, Object>
```

编译器看实参 `info` 是 `Map<String, Object>`，方法签名是 `T data`，所以 T 自动推断为 `Map<String, Object>`。等价于显式写法 `Result.<Map<String, Object>>ok(info)`，但不需要写出来。

### Q10：为什么 `mall-common` 的 pom 里要显式加 `slf4j-api` 依赖？

**答：**

`GlobalExceptionHandler` 用了 `@Slf4j` 注解，Lombok 编译时会生成 `private static final Logger log = LoggerFactory.getLogger(...)`。

`spring-web` 依赖**不传递** `slf4j-api`，所以必须显式引入：

```xml
<dependency>
    <groupId>org.slf4j</groupId>
    <artifactId>slf4j-api</artifactId>
</dependency>
```

如果不加，编译报错：**"程序包org.slf4j不存在"**。这是 Day01 实际踩过的坑。

## 第2天 · 数据库设计（建表 SQL + 索引设计）

### Q1：订单为什么拆 `orders`（主表）+ `order_item`（明细表）？`order_item` 为什么存快照？

**答：**

一个订单可能买多门课，明细表承载「这个订单买了哪些、每件多少钱」。拆开后，订单状态（支付/取消）和商品快照各归各的表。

`order_item` 存的是**快照**（`course_title` + `price`），不是 `course_id` 然后 JOIN 查。原因是：**历史订单数据不可变**。下单那一刻的标题和价格固化下来，之后课程改名/改价不影响历史订单。如果 JOIN 查，课程改名后老订单上显示的是新名字，财务对账就乱了。

---

### Q2：为什么用 RBAC 角色-权限模型，而不是直接给用户分配权限？

**答：**

没有角色层时，N 个用户每人绑 M 条权限，管理成本是 O(N×M)。新增用户要重复绑、权限变更要逐个改。

引入角色做中间层后：**角色是权限的集合，用户只关联角色**。新增用户只要选角色，权限变更只改角色——管理成本降到 O(N+M)。

实现上需要三张关联表：
- `user_role`：用户 ↔ 角色（多对多）
- `role_permission`：角色 ↔ 权限（多对多）
- `role_menu`：角色 ↔ 菜单（多对多）

---

### Q3：`uk_user_activity (user_id, activity_id)` 联合唯一索引为什么能实现秒杀限购？

**答：**

联合唯一索引保证了同一 `(user_id, activity_id)` 组合只能插入一行。第一个人秒杀成功，第二个人再下单时 INSERT 会因唯一索引冲突**直接报错**，数据库层天然拒绝重复下单。

比「先 SELECT 查是否已买，再 INSERT」更可靠，因为**唯一索引的约束在数据库层，并发下也不会漏**——两个请求同时 Select 都查到"没买"，然后同时 Insert，唯一索引会让其中一个失败，而先查再插两个都会成功。

### Q4：金额字段为什么用 `DECIMAL(10,2)` 不用 `float`/`double`？

**答：**

`float`/`double` 是二进制浮点数，`0.1` 在二进制里是无限循环小数（和十进制 1/3 一样），截断后精度丢失。`0.1 + 0.2` 在 `double` 里等于 `0.30000000000000004`。

金额场景必须精确到分，`DECIMAL` 是定点数，按字符串存储，每一步计算都精确。

**补充：** `DECIMAL(10,2)` = 总共 10 位，小数点后 2 位，范围 `-99999999.99 ~ 99999999.99`。

### Q5：为什么不建物理外键（FOREIGN KEY）？

**答：**

四个原因：

1. **级联风险**——`ON DELETE CASCADE` 可能删掉你不知道的数据
2. **锁竞争**——插入子表时，InnoDB 会在父表对应行上加共享锁，高并发下互相阻塞
3. **分库分表后失效**——微服务拆分后，`order_item.user_id` 要指向 `mall-user` 库的 `user.id`，跨库 MySQL 不支持外键
4. **运维成本**——数据迁移、归档、备份恢复全被外键绑死

**数据一致性怎么保证？** 靠业务代码 + 事务 + 逻辑外键（字段上保留关联 ID，代码里做校验），这是大厂主流做法。

---

### Q6：主键为什么用 `BIGINT` 自增？分库分表后自增会有什么问题？

**答：**

`BIGINT`（8 字节）支持 2^63 条记录，足够用户上亿场景。

**分库分表后的问题：** 自增 ID 是每个数据库各自维护的计数器，互不通气：

```
db0：user 表自增 → 1, 2, 3, 4...
db1：user 表自增 → 1, 2, 3, 4...  ← 和 db0 冲突了
```

**解决方案：** 雪花算法生成分布式 ID（趋势递增、全局唯一）。MyBatis-Plus 的 `@TableId(type = IdType.ASSIGN_ID)` 自动生成雪花 ID。

---

### Q7：`deleted`（TINYINT）和 `deleted_at`（DATETIME）两种逻辑删除方案，各有什么优缺点？

**答：**

| | `deleted TINYINT` | `deleted_at DATETIME` |
|---|---|---|
| 知道删除时间？ | ❌ 不知道 | ✅ 知道 |
| 误删恢复 | 改回 0 | 改回 NULL |
| 查询 | `WHERE deleted = 0` | `WHERE deleted_at IS NULL` |
| 定期清理 | 不知道删了多久 | `WHERE deleted_at < '2025-01-01'` |
| 索引大小 | 1 字节 | 8 字节（可忽略） |

**为什么项目用 `deleted_at` 更好？** 能知道什么时候删的，方便定期清理过期数据。MyBatis-Plus 的 `@TableLogic` 注解支持时间戳模式，配置 `@TableLogic(value = "null", delval = "now()")` 即可。

### Q8：`created_by` / `updated_by` 审计字段解决了什么问题？

**答：**

记录「谁创建了这个记录」「谁最后修改的」，方便审计和责任追溯。`created_by` 在建表时写入，`updated_by` 在每次修改时更新。

**注意事项：** `created_by` 是历史审计字段，查询时不应该过滤 `deleted_at IS NULL`，因为用户后来被删了不影响"创建时是谁做的"这个历史事实。

**哪些表加？** 业务实体表（`category`、`teacher`、`course`、`chapter`、`lesson`、`seckill_activity`、`menu`、`role`、`permission`）加 `created_by` + `updated_by`。`user` 表只加 `updated_by`（用户自己注册，`created_by` 无意义）。

### Q9：菜单表 `type` 字段（0目录 1菜单 2按钮）有什么用？权限标识 `course:create` 是什么设计思想？

**答：**

`type` 控制三级粒度：

| type | 层级 | 含义 | 权限标识示例 |
|---|---|---|---|
| 0 | 目录 | 模块分组，不配具体权限 | 无 |
| 1 | 菜单 | 功能页面 | `user:list`、`course:list` |
| 2 | 按钮 | 页面内操作 | `user:add`、`course:create` |

`course:create` 的冒号结构 = `资源:操作`，是 RESTful 风格的权限模型。好处：
- 后端 `@PreAuthorize("hasAuthority('course:create')")` 和代码一一对应
- 支持通配符匹配（`course:*` 匹配所有课程权限）
- 前端按冒号前的资源分组渲染树形菜单

### Q10：`WITH RECURSIVE` 递归 CTE 怎么查分类树？

**答：**

`WITH RECURSIVE` 是 MySQL 8.0+ 的标准 SQL 语法，适合查树形结构（分类、菜单）。

```sql
WITH RECURSIVE cte AS (
    -- ① 起点：找到根节点
    SELECT id, parent_id, name FROM category WHERE id = 1
    UNION ALL
    -- ② 递归：查子分类，每次 JOIN 上一轮结果
    SELECT c.id, c.parent_id, c.name
    FROM category c JOIN cte ON c.parent_id = cte.id
)
SELECT * FROM cte;
```

**执行过程：** 第一轮查出根节点 → 第二轮查子节点 → 第三轮查孙子节点 → 直到没有子节点为止。不用写死 JOIN 层数。拿到所有子分类 ID 后，就可以 `WHERE category_id IN (SELECT id FROM cte)` 查课程了。

## 第3~4天 · 用户服务与安全（注册登录 + BCrypt + JWT 认证授权）

### Q1：注册接口已经「先 SELECT 查重」了，为什么还要捕获 `DuplicateKeyException`？

**答：**

先查再插之间存在**竞态窗口**：两个并发请求都查到「用户名不存在」，然后都 INSERT。查库只是**体验层的快速失败**，数据库唯一索引 + catch 兜底才是**正确性保证**。

反过来只留 catch 也能跑，但用户名/邮箱两个唯一键冲突时无法区分该提示哪个字段，双击重复提交也直接撞 409，体验差。所以两层都留：**查询管体验，catch 管正确性**。

---

### Q2：BCrypt 怎么比对明文和密文？盐存在哪？为什么数据库没有 salt 列？

**答：**

BCrypt 密文是**自包含格式**，盐就打包在密文字符串里：

```text
$2a$10$N9qo8uLOickgx2ZMRZoMyeXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX
 │  │  └────22位盐────┘└─────────31位哈希─────────────────┘
 │  └ cost：2^10 轮（每 +1 耗时翻倍，慢是故意的，拖垮暴力破解）
 └ 算法版本
```

- `encode()`：每次**现场随机生成新盐** → 同一密码两次结果不同 → 彩虹表（预计算的「密码→哈希」对照表）整体失效
- `matches()`：**从老密文里解出盐和 cost，用同样的盐重算一遍**再比较——不是「再随机加密一次看相等」（那样永远不等）
- 盐自动跟密文走，天然不需要 salt 列，也不会出现盐列和密文对不上的事故

`{bcrypt}` 前缀由 `DelegatingPasswordEncoder` 解析后分发给 BCryptPasswordEncoder——多算法并存，老系统可平滑迁移。

### Q3：JWT 里已有身份，为什么 JwtAuthFilter 还要每个请求都查一次库？怎么优化？

**答：**

查库换来三样东西：**权限实时生效**（降权立即起作用）、**账号状态实时**（封禁/注销下一请求即失效）、**不用把角色塞进 JWT**（否则降权用户拿旧 token 横行到过期）。本质是花一条主键点查（~1ms）买回实时正确性和可吊销性。

优化阶梯（先确认 L0 是不是真瓶颈，别过早优化）：

| 层级 | 方案 | 适用 |
|---|---|---|
| L0 | 不优化 | 主键点查，中小流量无压力 |
| L1 | Caffeine 本地缓存 | 单实例 |
| L2 | Redis 权限快照 | 多实例（本地缓存跨实例不一致） |

Redis 方案要点（Cache-Aside 模式）：读——miss 查库回填（TTL ≤ token 有效期）；写（改权限）——**先 UPDATE 库，再 DEL 缓存 key**。删除是幂等的，不会并发覆盖；回填由下次读请求惰性完成。缓存值只存 userId/username/status/authorities，**别把 BCrypt 密文一起塞进去**。

### Q4：JwtAuthFilter 加 `@Component` 会怎样？为什么恰好是执行两次而不是报错？

**答：**

两个注册源同时生效：`@Component` 让 Spring Boot 的 `ServletContextInitializerBeans` 把 Filter Bean 自动注册进 Tomcat 容器链；`addFilterBefore(new ...)` 又把另一个实例挂进安全链：

```text
Tomcat 容器链
├─ DelegatingFilterProxy ──→ FilterChainProxy（springSecurityFilterChain）
│                              └─ 安全链内：… → JwtAuthFilter 实例② → …
└─ JwtAuthFilter 实例①        ← 自动注册的 Bean，又跑一遍
```

不报错的原因：两条链互不知情，Servlet 规范没禁止同类逻辑跑两遍。症状是静默的——**token 解析×2、查库×2、日志×2**，数据库压力直接翻倍。

记住两个名字：**DelegatingFilterProxy**（桥，把容器请求转交给 Spring Bean）包着 **FilterChainProxy**（安全链本体）。解法就是现状：不加 `@Component`，在 SecurityConfig 手动 new 传参。

### Q5：JWT 项目为什么必须显式声明 `STATELESS`？

**答：**

1. **防冗余 Session**：默认策略下 Spring 会把 ThreadLocal 里的认证上下文写进 HttpSession，每个活跃用户在堆里驻留一份没人读的身份副本 + 发一个没用的 JSESSIONID
2. **为扩容兜底**：Session 是单机对象，多实例下 A 建的 B 看不见；不声明就可能悄悄依赖它，扩容时翻车
3. **是 `csrf.disable()` 的前提契约**：CSRF 能成立靠浏览器自动带 Cookie；只有「身份永远在手动携带的 token 头里」这个约束被 STATELESS 钉死，关 CSRF 才安全

一句话：一行管安全（关 CSRF），一行守前提（STATELESS），必须成对出现。

### Q6：JwtAuthFilter 验签失败后，错误响应是怎么一步步写出来的？为什么不当时直接处理？

**答：**

接力链：

```text
① JwtAuthFilter catch → setAttribute(JWT_ERROR_ATTRIBUTE) → 不设身份，继续放行（匿名前进）
② AuthorizationFilter：anyRequest().authenticated() → 匿名被拒 → 抛 AccessDeniedException
③ ExceptionTranslationFilter 接住，按身份分流：
     匿名 / RememberMe → entryPoint.commence()        → 401 家族
     已认证但权限不够   → accessDeniedHandler.handle() → 403 家族
④ entryPoint 读 JWT_ERROR_ATTRIBUTE（TOKEN_EXPIRED 等）→ SecurityJsonWriter 统一写出
```

为什么不在 Filter 里当场处理：

| 方案 | 结局 |
|---|---|
| 抛 AuthenticationException | ExceptionTranslationFilter 只包它**之后**的过滤器，JwtAuthFilter 在它前面，抛了没人接 → 穿到 Tomcat 变 500 |
| 当场写 response | 能用，但 401/403 各写一份重复代码，还跳过 HeaderWriterFilter 等补安全响应头的过滤器 |
| **setAttribute + 继续放行** | 制造一次标准化「未认证状态」，让框架统一出口收尾，全项目只有一个写响应的地方 |

关键认知：401/403 的分流裁判是 ExceptionTranslationFilter，依据是**身份可信度**（是否匿名），不是异常类型——两种情况抛的都是同一个 `AccessDeniedException`。

### Q7：白名单为什么拆「硬编码常量 + yml 配置」两段？把 `anyRequest()` 挪到最前面会怎样？

**答：**

matcher 链**从上往下逐条尝试，第一条命中的规则说了算**（first-match-wins）。`anyRequest()` 匹配一切，相当于 switch 的 default——挪到最前面就吞掉一切请求，登录接口也要求「已认证」→ 拿不到 token 就永远进不了登录接口 → **鸡生蛋死锁**。规则型系统（nginx location、iptables）同款法则：顺序即逻辑。

两段白名单是 fail-safe 设计的两面：

| | 登录/注册（硬编码） | Swagger 路径（yml + 默认空列表） |
|---|---|---|
| 事故方式 | 配置误删 → 自己把自己锁门外 | 生产忘删 → 文档全网裸奔 |
| 失败性质 | 响亮失败（立刻发现） | 静默失败（漏洞无声存在） |
| 对策 | 编译期钉死删不掉 | 不配置 = 自动关闭 |

底层同一条哲学：**不指望人不犯错，让每种犯错的默认结局都落在安全一侧。**

### Q8：MapStruct 的 `ignore` / `expression` / `default` 三者怎么分工？

**答：**

判断轴心：**ignore 问「这值从哪来」，expression/default 问「这值能不能当场算出来」**。

| 字段 | 方案 | 理由 |
|---|---|---|
| id | ignore | DB 自增给；且不能信客户端传的 id（改包越权风险） |
| password | ignore + Service 层显式 encode() | 要注入 PasswordEncoder（接口 default 方法注入不了）；加密是业务规则不是格式转换 |
| createTime/updateTime | 最优：MyBatis-Plus MetaObjectHandler 自动填充；converter 内做则 `expression="java(LocalDateTime.now())"` | 审计时间是全表统一约定，放 converter 会漏（绕过 converter 的插入路径就没时间了） |

### Q9：接口里 `default String encodePassword(...)` 这种写法有什么隐患？

**答：**

`@Mapper` 接口里的 default 方法不是私有工具，而是登记成**按类型生效的转换器**，全接口所有转换方法共享同一个候选池。只要字段「源 String → 目标 String」对上，MapStruct 就自动插入调用——当初只为注册写的 encodePassword，会波及后来新增方法里的昵称、手机号（全被 BCrypt 加密），编译零报错、主流程还正常，直到发现用户昵称是一串 `$2a$10$...`。

三道防线：

1. 带业务语义的转换收进抽象类显式调用
2. 必须共用时 `@Named("encodePassword")` + `@Mapping(qualifiedByName=...)` 从「按类型撒网」改成「按名点火」
3. `unmappedTargetPolicy=ERROR` 防「漏」不防「误伤」，是互补不是重复保险

### Q10：取语言为什么 SecurityJsonWriter 用 `localeResolver.resolveLocale(request)`，业务代码用 `LocaleContextHolder`？

**答：**

`LocaleContextHolder` 是 DispatcherServlet 开始处理请求时（FrameworkServlet.processRequest）才绑定进 ThreadLocal 的，值来自 AcceptHeaderLocaleResolver 解析的 **Accept-Language** 头。SecurityJsonWriter 工作在 Filter 阶段——MVC 管线还没开跑，拿不到绑定。

此时 `LocaleContextHolder.getLocale()` 不报错，而是**静默回退到 JVM 默认语言**：中文开发机 zh_CN 恰好掩盖 bug，部署到英文服务器后所有用户无论 Accept-Language 是什么都收到英文文案——环境相关静默 bug。所以安全链路必须显式 `localeResolver.resolveLocale(request)`。

### Q11：`UsernamePasswordAuthenticationToken` 本质是匿名 token 吗？

**答：**

不是。匿名有专属类 **AnonymousAuthenticationToken**（由链尾的 AnonymousAuthenticationFilter 兜底塞入）。UsernamePasswordAuthenticationToken 是**同一个类的两种状态**：

| 构造方式 | 状态 | 谁创建 |
|---|---|---|
| 两参 `(principal, credentials)` | 未认证，`isAuthenticated()==false`，认证申请单 | 登录入口，交给 AuthenticationManager |
| 三参 `(principal, null, authorities)` | 已认证，真实生效身份 | Provider 比对通过后 / JwtAuthFilter 验签后 |

三参版把 credentials 擦成 null，防明文密码滞留内存。`isAnonymous()` 底层就是 `instanceof AnonymousAuthenticationToken`。

### 附：快问快答（自测卷 9 题补正）

**① `@RestController` vs `@Controller`？`@ResponseBody` 做了什么？**

复合注解 = `@Controller` + `@ResponseBody`，返回一律走数据管道不走视图名。@ResponseBody **不是 AOP**：是 DispatcherServlet 的返回值处理器策略（`RequestResponseBodyMethodProcessor`）拿返回值交给 `HttpMessageConverter`（Jackson）序列化写响应体，全程无代理无织入。

**② `@Valid` vs `@Validated`？**

@Valid 是标准注解，支持级联（嵌套对象递归校验）但没有 groups 属性；@Validated 是 Spring 的，支持分组如 `@Validated(Create.class)`（典型：插入无 id、更新必须有 id）。实战两者共存：入口选分组用 @Validated，嵌套递归在字段上标 @Valid。

**③ `@NotBlank` / `@NotEmpty` / `@NotNull`？**

强度阶梯：NotNull < NotEmpty < NotBlank。反例 `"   "`（三个空格）：NotNull ✓、NotEmpty ✓（长度 > 0）、NotBlank ✗（trim 后为空）。

**④ 为什么 `@RequestBody` 校验失败抛 `MethodArgumentNotValidException`，表单/Query 抛 `BindException`？**

因为走的是**两套参数解析器**：@RequestBody 走 RequestResponseBodyMethodProcessor（消息转换器反序列化后校验）抛前者；表单/Query 走 ModelAttributeMethodProcessor（WebDataBinder 逐属性绑定）抛后者。Spring 6 起 `MethodArgumentNotValidException extends BindException`，catch BindException 一处兜住两种。Boot 3.2 起单个 `@RequestParam` 校验失败抛新类型 `HandlerMethodValidationException`。

**⑤ JWT 三部分？为什么改 payload 伪装不了？签名防什么？**

`Header.签名算法 + Payload.claims + Signature`，签名 = `HMAC-SHA256(前两段拼接, secret)`。改 payload 后服务端重算 HMAC 对不上 → JwtException；伪造签名需要 secret，而 secret 只在服务器、绝不进 token。注意：第三段叫**签名不是密钥**；签名防篡改不防偷看——Payload 是 Base64URL **编码不是加密**，谁拿到都能解码，严禁放敏感信息。

**⑥ 无状态 vs 有状态核心区别？无状态的代价？**

核心区别：身份住在哪——服务端 Session 对象 vs 客户端自证 token。无状态天然水平扩容（Session 是单机对象，多实例要粘性路由或 Spring Session + Redis）。代价：token 签出去就收不回，主动登出/踢人三方案：① 短有效期 + refresh token；② Redis 黑名单按 jti 拉黑到过期为止；③ 每请求回源查账号状态（本项目方案）。

**⑦ 认证 vs 授权？为什么没登录 401、权限不足 403？**

认证 = 你是谁，授权 = 你能干什么。项目实现：两种情况在授权阶段都抛同一个 `AccessDeniedException`，由 ExceptionTranslationFilter 按是否匿名分流——匿名 → entryPoint（401），已认证但缺权限 → deniedHandler（403）。

**⑧ `hasRole('ADMIN')` 为什么查找的是 `ROLE_ADMIN`？和 `hasAuthority` 的区别？**

hasRole 执行时**字面拼接** `"ROLE_" + "ADMIN"` 再去 authorities 精确匹配；hasAuthority 不加前缀。authorities 集合里角色和权限都只是字符串，ROLE_ 前缀是唯一类型标记。「角色聚合一组权限」来自项目的 RBAC 表设计，Spring Security 运行时全部摊平成 `SimpleGrantedAuthority` 字符串列表。

**⑨ `@PreAuthorize` 从哪里拿权限？为什么查了权限不放进 Authentication 注解就不生效？**

从 `SecurityContextHolder → Authentication.getAuthorities()` 拿（即三参构造器的第三个参数）。表达式引擎只认上下文里这一份，**绝不会替你查数据库**。查了不装进 Authentication = 注解眼里零权限，一律 403。所以 JwtAuthFilter 必须 `userDetails.getAuthorities()` 原样传入三参构造器。
