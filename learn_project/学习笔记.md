## Maven

> **一句话**：Maven 用 GAV 坐标定位依赖，`dependencyManagement` 声明版本号，`dependencies` 才是真正引入。

1. **GAV 三要素**：`groupId` + `artifactId` + `version` 唯一定位一个依赖
2. **dependencyManagement**：父工程声明有哪些依赖及版本号，子模块无需再写 version
3. **dependencies**：子模块真正引入的依赖，不加 version 就找父工程声明的
4. **Spring Boot 做法**：父工程继承 `spring-boot-starter-parent`，它内部用 BOM 锁定了所有常用依赖版本，子模块声明依赖时不用管版本号

## 注解

> **一句话**：注解本质是给类/方法/字段打标签，让编译期或运行期产生副作用，正是注解让框架变成声明式驱动。

### 自定义注解

- 自定义 = 接口前加 `@`，成员是抽象方法（`String value()`）
- 成员类型受限：基本类型、String、Class、枚举、注解、数组
- 只有 `value` 一个成员时可省略名字：`@RequireLogin("xxx")`
- 默认值用 `default`：`int count() default 1;`

### 元注解（标注注解的注解）

| 元注解        | 作用                                |
| ------------- | ----------------------------------- |
| `@Target`     | 决定注解能贴到哪（类/方法/字段...） |
| `@Retention`  | 决定注解保留到什么时候              |
| `@Repeatable` | 是否能在同一位置重复标注多次        |

Spring 支持组合注解，外层注解可以通过元注解复用功能，并通过 @AliasFor 覆盖元注解的属性，同时添加自己的配置。

### @Retention 三种策略

| 策略      | 保留阶段                   | 典型用途                               |
| --------- | -------------------------- | -------------------------------------- |
| `SOURCE`  | 编译时丢弃，字节码里没有   | `@Override`，只给编译器做语法检查      |
| `CLASS`   | 保留到字节码，运行期不可见 | Lombok 的 `@Getter`，编译期处理器用    |
| `RUNTIME` | 一路保留到 JVM，反射可读   | Spring 的 `@Autowired`，运行时反射读取 |

### 注解的原理

```
源码 @Xxx
   │
   ▼ 编译（SOURCE 注解在此被丢弃）
字节码 .class（CLASS 注解保留到这里，运行期丢弃）
   │
   ▼ 运行（RUNTIME 注解一路保留，可反射读）
JVM 运行时
```

### 注解的两种使用方式

1. **编译时处理**：Processor 处理抽象语法树（AST）注入信息，如 Lombok 注入 getter/setter
2. **运行时处理**：反射读取注解信息，如 Spring 扫描 `@Autowired` 做依赖注入

### Spring 中的 @RestController

> 标记类是 Controller，`@RestController` = `@Controller` + `@ResponseBody`

注解本身只是标记，实际是 Spring 容器扫描到后完成三件事：**Bean 注册 + 依赖注入 + 路由映射**

## 异常

> **一句话**：自定义异常携带业务错误码，全局异常处理器统一拦截，避免每个 Controller 写 try-catch。

### 自定义业务异常

```java
// 继承 RuntimeException，带 code（错误码）和 message（错误信息）
public class BizException extends RuntimeException {
    private final Integer code;
    public BizException(Integer code, String message) {
        super(message);
        this.code = code;
    }
}
```

### 全局异常处理器

- 用 `@RestControllerAdvice` 统一拦截所有 Controller 抛出的异常
- 本质是 AOP 切面实现，Spring 把 Controller 封装为代理
- 核心价值：**异常处理与业务逻辑解耦**，前端拿到统一 JSON 结构

## 6. 日志记录

> SLF4J 是门面接口，背后有 Logback（Spring 默认）、Log4j2 等实现

### 日志级别（从低到高）

```
TRACE < DEBUG < INFO < WARN < ERROR
设置 WARN → 只打印 WARN 和 ERROR，TRACE/DEBUG/INFO 被过滤
```

### 关键要点

- **门面模式**：SLF4J 定义接口，业务代码只依赖接口，换实现不用改代码
- **与 Profile 配合**：开发环境 DEBUG，生产环境 WARN
- **日志事件**：`log.info()` 产生 LoggingEvent 对象，发给所有 Appender（观察者模式）
- **Appender 职责链**：每个 Appender 内部有 Filter 链（过滤）→ Encoder（格式化）
- **logback-spring.xml**：当 application.yml 不够用时（如错误日志单独文件、彩色日志），用 XML 做高级控制。必须叫 `logback-spring.xml` 才能用 `<springProfile>` 分环境

## 10. 拦截器与过滤器

### 拦截器和过滤器对比

| 维度                  | 过滤器 Filter                | 拦截器 Interceptor            |
| --------------------- | ---------------------------- | ----------------------------- |
| 归属                  | Servlet 规范                 | Spring MVC                    |
| 作用范围              | 所有请求（含静态资源）       | 进入 Controller 的请求        |
| 能否拿到 Spring Bean  | 不能直接拿（需手动从容器取） | 能（就是 Spring 管理的 Bean） |
| 能否拿到 Handler 方法 | 不能                         | 能（`HandlerMethod`）         |
| 典型场景              | 编码、CORS、日志             | 登录鉴权、权限、性能统计      |

### 配置拦截器

配置拦截器就是编写WebMvcConfigurer类实例配置，SpringMVC启动的时候会加载配置

```java
@Configuration
public class WebConfig implements WebMvcConfigurer {

    private final LoginInterceptor loginInterceptor;
    public WebConfig(LoginInterceptor loginInterceptor) {
        this.loginInterceptor = loginInterceptor;
    }

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(loginInterceptor)
                .addPathPatterns("/**")          // 拦截所有
                .excludePathPatterns("/login", "/register");  // 放行登录注册
    }
}
```

### 跨域及其配置

```java
@Configuration
public class CorsConfig implements WebMvcConfigurer {

    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/**")                    // 允许所有路径
                .allowedOriginPatterns("*")            // 允许所有来源（生产环境要指定具体域名）
                .allowedMethods("GET", "POST", "PUT", "DELETE", "OPTIONS")  // 允许的 HTTP 方法
                .allowedHeaders("*")                   // 允许所有请求头
                .allowCredentials(true)                // 允许携带 Cookie
                .maxAge(3600);                         // 预检请求缓存时间（秒），减少 OPTIONS 请求
    }
}
```

原理

```shell
后端返回的响应头：
HTTP/1.1 200 OK
Access-Control-Allow-Origin: http://localhost:5173    ← 浏览器只看这个
Access-Control-Allow-Credentials: true
Access-Control-Allow-Methods: GET, POST

浏览器检查：
当前请求来源 = http://localhost:5173
         ↓
响应头 Access-Control-Allow-Origin = http://localhost:5173
         ↓
匹配 ✅ → 放行，JS 能拿到响应数据
不匹配 ❌ → 拦截，控制台报 CORS 错误
```

具体流程

```shell
前端（localhost:5173）发请求到后端（localhost:8080）
    ↓
浏览器发现「跨域了」
    ↓
先发 OPTIONS 预检请求（非简单请求时）
    ↓
后端返回 Access-Control-Allow-Origin: http://localhost:5173
    ↓
浏览器检查这个头，和当前页面域名对比
    ↓
匹配 ✅ → 发真实请求，JS 能拿到数据
不匹配 ❌ → 报错：No 'Access-Control-Allow-Origin' header is present
```

为什么 maxAge 重要： 每次真实请求前都发一个 OPTIONS，浪费性能。设置 maxAge(3600) 后，1 小时内不再发预检请求。

## 11. Actuator

SpringBoot提供的监控系统状态的接口

```shell
/health      → 还活着吗？数据库通吗？Redis 通吗？
/metrics     → 内存用了多少？CPU 多少？QPS 多少？
/loggers     → 当前日志级别是多少？能调低看细节吗？
/env         → 当前运行环境变量、配置项是什么？
```

你需要配置暴露或者不暴露哪些监控端点

```yml
management:
  endpoints:
    web:
      exposure:
        include: health,info,metrics,loggers # 暴露哪些端点
        exclude: env,beans # 排除敏感端点
  endpoint:
    health:
      show-details: always # 显示健康详情（组件状态）
  health:
    redis:
      enabled: false # 关闭某个健康检查项
```

常用的端点如下
| 端点 | 作用 |
| ------------------- | ---------------------------- |
| `/actuator/health` | 健康状态（UP/DOWN） |
| `/actuator/info` | 应用信息（版本等） |
| `/actuator/metrics` | 指标列表（内存、线程、HTTP） |
| `/actuator/env` | 环境属性（敏感，慎暴露） |
| `/actuator/loggers` | 动态调整日志级别 |
| `/actuator/beans` | 容器中所有 Bean |

## 12. 事务

事务就是一些列的sql操作，事务只能同时成功或同时失败

### 事务传播

方法 B 调方法 A，A 有事务，B 也有事务——B 是加入 A 的事务，还是挂起 A 自己开一个新的？

```java
@Service
public class OrderService {

    @Transactional
    public void createOrder(Order order) {
        orderMapper.insert(order);          // ① 写订单表
        logService.log("创建订单", order.getId());  // ② 写日志表
    }
}

@Service
public class LogService {
    @Transactional
    public void log(String action, Long bizId) {
        logMapper.insert(new Log(action, bizId));
    }
}
```

问题： log() 也有 @Transactional，它和 createOrder() 的事务是什么关系？

传播行为就是回答这个问题：

```text
场景一：REQUIRED（默认）
createOrder() 开了事务 T1
  └─ log() 发现已经有 T1 了 → 加入 T1，不新建
     ↓
如果 log() 抛异常 → T1 整体回滚 → 订单和日志都回滚

场景二：REQUIRES_NEW
createOrder() 开了事务 T1
  └─ log() 发现已经有 T1 → 挂起 T1，开一个新事务 T2
     ↓
如果 log() 抛异常 → 只有 T2 回滚，T1 不受影响
     → 订单创建成功，只是日志没写进去
```

### 事务隔离级别

你说的大方向对，但精确一下：

| 问题       | 原因                    | 后果                                 |
| ---------- | ----------------------- | ------------------------------------ |
| 脏读       | 读了别人没提交的数据    | 数据是假的，别人回滚你就错了         |
| 不可重复读 | 两次读之间被人改了      | 同一事务两次读同一条数据不一样       |
| 幻读       | 两次读之间被人插了/删了 | 同一事务两次查同一个范围，行数不一样 |

**记忆：** 脏读是数据假的，不可重复读是值变了，幻读是行数变了。

### 声明式事务 vs 编程式事务

编程式事务粒度细一点，可以设置部分成功也算成功

```java
public void batchCreate(List<Order> orders) {
     for (Order order : orders) {
         // 每个订单独立事务，一个失败不影响其他
         transactionTemplate.execute(status -> {
             try {
                 orderMapper.insert(order);
                 stockService.deduct(order.getGoodsId(), order.getNum());
                 return null;
             } catch (Exception e) {
                 status.setRollbackOnly();  // 手动标记回滚
                 log.error("订单处理失败", e);
                 return null;
             }
         });
     }
 }
```

### @Transactional 失效的七种场景

1. 通过this调用内部方法，可以通过注入自身引用来解决
2. @Transcational只对public方法生效，把方法改成public就行
3. 异常被try catch吞掉，解决就是不要吞或者手动调用回滚`TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()`
4. 当是受检异常时，因为默认只回滚未受检异常。解决加 rollbackFor = Exception.class
5. 存储引擎不支持事务
6. 方法被final修饰，因为动态代理无法重写final方法
7. 事务中开启了新线程进行异步操作，解决方法就是等事务结束后才进行异步，比如用 `@TransactionalEventListener` 在事务提交后异步处理

### 事务只读化

一个事务里面既有查询又有修改可以配置查询的时候不加锁,MySQL/ORM 可以做优化

```java
// 查询时加 readOnly = true，告诉数据库不需要加锁，MySQL/ORM 可以做优化
@Transactional(readOnly = true)
public Order getById(Long id) {
    return orderMapper.selectById(id);
}
```

## 15、发布事件

### 发布订阅模式

其实就是发布订阅模式的运用

1. 创建事件对象
2. 调用ApplicationEventPublisher 对象发布事件到消息中心
3. 订阅者订阅对应事件，事件发布会调用订阅者的回调函数

### 四种方式

1. @EventListener 注解（推荐，最简单）
2. 实现接口（需要将 `implements ApplicationListener<OrderCreatedEvent>`的类实例注入容器）
3. 异步监听（不阻塞主流程）
4. 条件监听（只有满足条件才处理）

### 事务监听器

可以监听事务不同阶段

1. AFTER_COMMIT:事务提交后执行（最常用）
2. AFTER_ROLLBACK:事务回滚后执行
3. AFTER_COMPLETION:事务完成（无论提交/回滚）
4. BEFORE_COMMIT:事务提交前执行

```java
@Component
public class OrderEventListeners {

    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)  // 事务提交后才执行
    public void handleAfterCommit(OrderCreatedEvent event) {
        // ① 事务已提交，数据已落库
        // ② 如果监听器抛异常，不会导致业务回滚
        // ③ 适合发 MQ 消息、发邮件等操作
        mqService.send("order.created", event.getOrderId());
    }
}
```

实际上Spring 启动时通过反射读参数类型，就知道这个监听器要监听什么事件。比如OrderCreatedEvent事件

### 使用场景

下单后发短信/送积分/发邮件，不需要在 OrderService 里写一行相关代码，新增功能只需加一个 @EventListener 方法。

# 8.22 SpringSecurity

你这份流程主线没问题，但混用了“默认表单登录”和“前后端分离 JSON 登录”。CourseMall 应该改成下面这版。

### 一、请求总入口

```
Servlet FilterChain
→ DelegatingFilterProxy
→ FilterChainProxy
→ 匹配当前请求的 SecurityFilterChain
→ Spring Security 内部过滤器
→ DispatcherServlet
```

`FilterChainProxy` 会选择第一个匹配的 `SecurityFilterChain`，并负责请求结束后的安全上下文清理。[Spring Security Servlet 架构](https://docs.spring.io/spring-security/reference/servlet/architecture.html)

你的自定义过滤器顺序：

```
http.addFilterBefore(
        jwtAuthFilter,
        UsernamePasswordAuthenticationFilter.class
);
```

这里的 `UsernamePasswordAuthenticationFilter.class` 主要作为排序参照。前后端分离通常关闭 `formLogin`，因此默认登录过滤器可能根本不在链中。

---

### 二、首次登录：JSON 账号密码登录

```
POST /api/user/login
```

流程：

1. 请求进入 Spring Security 过滤器链。
2. `JwtAuthFilter` 没发现 `Bearer Token`，直接放行。
3. `AuthorizationFilter` 发现 `/api/user/login` 配置了 `permitAll()`，允许进入 Controller。
4. `LoginController` 从 JSON 中获取用户名和密码。
5. Controller 创建未认证对象：

```
UsernamePasswordAuthenticationToken.unauthenticated(
        username,
        password
);
```

1. 调用：

```
authenticationManager.authenticate(authenticationToken);
```

1. 实际内部流程：

```
AuthenticationManager
→ ProviderManager
→ DaoAuthenticationProvider
→ UserDetailsService 查询用户
→ PasswordEncoder 校验密码
→ 检查账号是否启用、锁定、过期
```

用户名密码认证使用的是 `DaoAuthenticationProvider`，不存在标准的 `UsernamePasswordAuthenticationProvider`。[DaoAuthenticationProvider 官方说明](https://docs.spring.io/spring-security/reference/6.5/servlet/authentication/passwords/dao-authentication-provider.html)

1. 验证成功后返回一个已认证的 `Authentication`。
2. Controller 从中取得 `LoginUser`，生成 JWT 并返回前端。
3. 无状态模式下，不需要把登录结果长期保存进 `SecurityContextHolder`。

关键点：

```
首次登录不经过 UsernamePasswordAuthenticationFilter
而是 Controller 主动调用 AuthenticationManager
```

### 三、携带 AccessToken 访问业务接口

```
Authorization: Bearer <access-token>
```

流程：

1. 请求进入过滤器链。
2. `JwtAuthFilter` 提取 AccessToken。
3. 校验：

```
签名
过期时间
Token 类型必须为 access
```

1. 从 Token 中读取 `username/userId`。
2. 查询 `UserDetails`，检查用户当前是否禁用、锁定以及最新权限。
3. 创建已认证对象：

```
UsernamePasswordAuthenticationToken auth =
        UsernamePasswordAuthenticationToken.authenticated(
                userDetails,
                null,
                userDetails.getAuthorities()
        );
```

1. 放入当前请求上下文：

```
SecurityContextHolder.getContext().setAuthentication(auth);
```

1. `AuthorizationFilter` 根据 `authorizeHttpRequests` 做 URL 级鉴权：

```
未登录访问受保护接口 → 401
已登录但权限不足 → 403
权限通过 → DispatcherServlet → Controller
```

Spring Security 6 使用 `authorizeHttpRequests` 时，主要是 `AuthorizationFilter`，不是旧资料中的 `FilterSecurityInterceptor`。[请求授权官方说明](https://docs.spring.io/spring-security/reference/6.5/servlet/authorization/authorize-http-requests.html)

1. 如果启用了：

```
@EnableMethodSecurity
```

并使用：

```
@PreAuthorize("hasAuthority('course:delete')")
```

则由 `AuthorizationManagerBeforeMethodInterceptor` 在方法执行前鉴权，而不是旧版名称 `MethodSecurityInterceptor`。[方法级鉴权官方说明](https://docs.spring.io/spring-security/reference/servlet/authorization/method-security.html)

1. 请求结束后清理 `SecurityContextHolder`，下次请求重新根据 JWT 构造 `Authentication`。

### 四、前后端分离双 Token 与“记住我”

推荐设计：

```
AccessToken：10～30 分钟，只访问业务接口
RefreshToken：数天到数周，只能访问刷新接口
```

#### 登录时

`rememberMe=false`：

- AccessToken 仍然保持短有效期。
- RefreshToken 使用较短有效期。
- 浏览器端使用 Session Cookie，关闭浏览器后失效。

`rememberMe=true`：

- AccessToken 有效期不变。
- RefreshToken 使用较长有效期。
- Cookie 配置 `Max-Age`，关闭浏览器后仍保留。

Web 端推荐：

```
AccessToken  → 保存在内存
RefreshToken → Secure + HttpOnly + SameSite Cookie
```

不推荐把 RefreshToken 放进 `localStorage`，因为发生 XSS 时，JavaScript 可以直接读取并盗走它。[OWASP 浏览器存储建议](https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html)

Flutter 移动端则放进系统安全存储，例如 Keychain/Keystore。

#### AccessToken 过期

```
业务接口返回 401
→ 前端调用 /api/auth/refresh
→ 浏览器自动携带 RefreshToken Cookie
→ 后端校验 RefreshToken 和 Redis 会话
→ 返回新 AccessToken
→ 重试原请求
```

刷新接口在 Spring Security 中可以配置 `permitAll()`，但它内部必须自行严格校验 RefreshToken。

#### RefreshToken 轮换

每次刷新时：

```
旧 RefreshToken 作废
→ 生成新 AccessToken
→ 生成新 RefreshToken
→ 原子更新 Redis
```

RefreshToken 轮换可以检测旧令牌被重复使用，是当前推荐做法。[OAuth 2.0 Security BCP](https://www.rfc-editor.org/info/rfc9700/)

Redis 建议存：

```
sessionId / jti
userId
RefreshToken 摘要
设备信息
过期时间
状态
```

不要直接存明文 RefreshToken。

#### 退出登录与踢下线

```
删除或作废 Redis 中的 RefreshToken 会话
→ 清除 RefreshToken Cookie
→ 无法继续刷新
```

但要注意：

> 删除 RefreshToken 并不会让已经签发的 AccessToken 立即失效。

AccessToken 默认还能使用到自然过期。想立即踢下线，需要额外选择一种方案：

- AccessToken 黑名单
- 用户 `tokenVersion`
- 每次请求检查 Redis 登录会话
- 使用很短的 AccessToken 有效期接受短暂延迟

### 最终记忆

```
FilterChain        = 安全处理流水线
Authentication     = 当前用户是谁、凭证和权限
SecurityContext    = 保存 Authentication
SecurityContextHolder = 保存当前请求的 SecurityContext
AuthenticationManager = 组织认证
DaoAuthenticationProvider = 校验用户名密码
AuthorizationFilter = URL 鉴权
@PreAuthorize      = 方法鉴权
```

你原文最需要改的三处就是：

1. 前后端分离登录由 Controller 调用 `AuthenticationManager`，不是默认登录过滤器处理。
2. Spring Security 6 的 URL 鉴权主要写 `AuthorizationFilter`。
3. RefreshToken 不应直接放 `localStorage`，删除它也不能立即废除已有 AccessToken。

### SpringSecurity登录认证

1. UserDetailsService：用户自己实现这个接口决定如何获取UserDetails和权限，这个方法返回标准的UserDetails

2. Authentication：认证对象。UsernamePasswordAuthenticationToken是其实现，但是只是根据前端传来的信息封装成的Authentication对象你可以认为是AuthenticionDto，其中有三个重要属性

   | 参数          | 含义               | 代码中的值                     |
   | ------------- | ------------------ | ------------------------------ |
   | `principal`   | 当前用户是谁       | `userDetails`                  |
   | `credentials` | 用户凭什么证明身份 | `null`，因为 JWT 已验证完成    |
   | `authorities` | 用户拥有哪些权限   | `userDetails.getAuthorities()` |

3. AuthenticationManager：authenticate方法内部会调用UserDetailsService这个方法来查询UserDetail和UsernamePasswordAuthenticationToken的password进行比对，比对后生成Authentication对象，这个对象是认证后的Authentication对象和UsernamePasswordAuthenticationToken有所区别。然后将Authentication对象保存到SpringSecurityContextHolder中

4. SpringSecurityContextHolder：保存Authentication上下文，后续基于认证信息来授权

## i8n

各个类的职责：

1. `MessageSource` 是 Spring 的消息源。Spring Boot 根据
   `spring.messages.basename` 加载 `messages*.properties`，并将
   `MessageSource` 注册成 Bean。
2. `MessageKeys` 只是保存消息 key 常量，避免到处手写字符串，不是 Spring 必需组件。
3. `I18nMessageService` 是对 `MessageSource` 的项目级封装，统一处理当前 Locale、参数和默认值；它类似工具类，但作为 Bean 使用。
4. `LocaleResolver` 负责从 `Accept-Language` 解析 Locale；Spring MVC 再把结果绑定到 `LocaleContextHolder`，供当前请求使用。
5. `LocalValidatorFactoryBean` 负责创建并适配 Validator，使
   `@Valid`、`@Validated`、`@NotBlank` 等校验能够使用
   `MessageSource` 中的国际化提示。Spring Boot 通常已经自动配置，只有需要定制时才显式声明。
6. `ErrorCode` 保存稳定的业务码和 messageKey；`BizException` 携带错误码、messageKey 和占位参数，不直接保存某一种语言。
7. `GlobalExceptionHandler` 只负责把各种异常转换成统一的 `Result`。当然可以在
   `handleBiz()` 中翻译，但那只能覆盖业务异常，其他异常和正常响应还要重复处理。
8. `ResultMessageAdvice` 会在 Controller 或异常处理器执行完成后、Jackson 写出 JSON 前拦截所有 `Result`，因此适合作为统一翻译出口。

## openAPI 和 knif4j以及swagger

```text
Springdoc 扫描 Controller、DTO 和注解
        ↓
生成 OpenAPI 接口描述
        ↓
Knife4j / Apifox 读取描述
```

- 具体测试数据、断言和测试流程仍需要自己配置。
