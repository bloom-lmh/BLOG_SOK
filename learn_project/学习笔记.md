## Maven

> **一句话**：Maven 用 GAV 坐标定位依赖，`dependencyManagement` 声明版本号，`dependencies` 才是真正引入。

1. **GAV 三要素**：`groupId` + `artifactId` + `version` 唯一定位一个依赖
2. **dependencyManagement**：父工程声明有哪些依赖及版本号，子模块无需再写 version
3. **dependencies**：子模块真正引入的依赖，不加 version 就找父工程声明的
4. **Spring Boot 做法**：父工程继承 `spring-boot-starter-parent`，它内部用 BOM 锁定了所有常用依赖版本，子模块声明依赖时不用管版本号

## 注解

> **一句话**：注解本质是给类/方法/字段打标签，让编译期或运行期产生副作用，正是注解让框架变成声明式驱动。

### 自定义注解

- 自定义 = 接口前加 `@`，成员是抽象方法（`String value()`）
- 成员类型受限：基本类型、String、Class、枚举、注解、数组
- 只有 `value` 一个成员时可省略名字：`@RequireLogin("xxx")`
- 默认值用 `default`：`int count() default 1;`

### 元注解（标注注解的注解）

| 元注解        | 作用                                |
| ------------- | ----------------------------------- |
| `@Target`     | 决定注解能贴到哪（类/方法/字段...） |
| `@Retention`  | 决定注解保留到什么时候              |
| `@Repeatable` | 是否能在同一位置重复标注多次        |

Spring 支持组合注解，外层注解可以通过元注解复用功能，并通过 @AliasFor 覆盖元注解的属性，同时添加自己的配置。

### @Retention 三种策略

| 策略      | 保留阶段                   | 典型用途                               |
| --------- | -------------------------- | -------------------------------------- |
| `SOURCE`  | 编译时丢弃，字节码里没有   | `@Override`，只给编译器做语法检查      |
| `CLASS`   | 保留到字节码，运行期不可见 | Lombok 的 `@Getter`，编译期处理器用    |
| `RUNTIME` | 一路保留到 JVM，反射可读   | Spring 的 `@Autowired`，运行时反射读取 |

### 注解的原理

```
源码 @Xxx
   │
   ▼ 编译（SOURCE 注解在此被丢弃）
字节码 .class（CLASS 注解保留到这里，运行期丢弃）
   │
   ▼ 运行（RUNTIME 注解一路保留，可反射读）
JVM 运行时
```

### 注解的两种使用方式

1. **编译时处理**：Processor 处理抽象语法树（AST）注入信息，如 Lombok 注入 getter/setter
2. **运行时处理**：反射读取注解信息，如 Spring 扫描 `@Autowired` 做依赖注入

### Spring 中的 @RestController

> 标记类是 Controller，`@RestController` = `@Controller` + `@ResponseBody`

注解本身只是标记，实际是 Spring 容器扫描到后完成三件事：**Bean 注册 + 依赖注入 + 路由映射**

## 异常

> **一句话**：自定义异常携带业务错误码，全局异常处理器统一拦截，避免每个 Controller 写 try-catch。

### 自定义业务异常

```java
// 继承 RuntimeException，带 code（错误码）和 message（错误信息）
public class BizException extends RuntimeException {
    private final Integer code;
    public BizException(Integer code, String message) {
        super(message);
        this.code = code;
    }
}
```

### 全局异常处理器

- 用 `@RestControllerAdvice` 统一拦截所有 Controller 抛出的异常
- 本质是 AOP 切面实现，Spring 把 Controller 封装为代理
- 核心价值：**异常处理与业务逻辑解耦**，前端拿到统一 JSON 结构

## 1. Spring Boot 本质

> Spring Boot 就是简化依赖、配置和部署的工具

## 6. 日志记录

> SLF4J 是门面接口，背后有 Logback（Spring 默认）、Log4j2 等实现

### 日志级别（从低到高）

```
TRACE < DEBUG < INFO < WARN < ERROR
设置 WARN → 只打印 WARN 和 ERROR，TRACE/DEBUG/INFO 被过滤
```

### 关键要点

- **门面模式**：SLF4J 定义接口，业务代码只依赖接口，换实现不用改代码
- **与 Profile 配合**：开发环境 DEBUG，生产环境 WARN
- **日志事件**：`log.info()` 产生 LoggingEvent 对象，发给所有 Appender（观察者模式）
- **Appender 职责链**：每个 Appender 内部有 Filter 链（过滤）→ Encoder（格式化）
- **logback-spring.xml**：当 application.yml 不够用时（如错误日志单独文件、彩色日志），用 XML 做高级控制。必须叫 `logback-spring.xml` 才能用 `<springProfile>` 分环境

## 10. 拦截器与过滤器

### 拦截器和过滤器对比

| 维度                  | 过滤器 Filter                | 拦截器 Interceptor            |
| --------------------- | ---------------------------- | ----------------------------- |
| 归属                  | Servlet 规范                 | Spring MVC                    |
| 作用范围              | 所有请求（含静态资源）       | 进入 Controller 的请求        |
| 能否拿到 Spring Bean  | 不能直接拿（需手动从容器取） | 能（就是 Spring 管理的 Bean） |
| 能否拿到 Handler 方法 | 不能                         | 能（`HandlerMethod`）         |
| 典型场景              | 编码、CORS、日志             | 登录鉴权、权限、性能统计      |

### 配置拦截器

配置拦截器就是编写WebMvcConfigurer类实例配置，SpringMVC启动的时候会加载配置

```java
@Configuration
public class WebConfig implements WebMvcConfigurer {

    private final LoginInterceptor loginInterceptor;
    public WebConfig(LoginInterceptor loginInterceptor) {
        this.loginInterceptor = loginInterceptor;
    }

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(loginInterceptor)
                .addPathPatterns("/**")          // 拦截所有
                .excludePathPatterns("/login", "/register");  // 放行登录注册
    }
}
```

### 跨域及其配置

```java
@Configuration
public class CorsConfig implements WebMvcConfigurer {

    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/**")                    // 允许所有路径
                .allowedOriginPatterns("*")            // 允许所有来源（生产环境要指定具体域名）
                .allowedMethods("GET", "POST", "PUT", "DELETE", "OPTIONS")  // 允许的 HTTP 方法
                .allowedHeaders("*")                   // 允许所有请求头
                .allowCredentials(true)                // 允许携带 Cookie
                .maxAge(3600);                         // 预检请求缓存时间（秒），减少 OPTIONS 请求
    }
}
```

原理

```shell
后端返回的响应头：
HTTP/1.1 200 OK
Access-Control-Allow-Origin: http://localhost:5173    ← 浏览器只看这个
Access-Control-Allow-Credentials: true
Access-Control-Allow-Methods: GET, POST

浏览器检查：
当前请求来源 = http://localhost:5173
         ↓
响应头 Access-Control-Allow-Origin = http://localhost:5173
         ↓
匹配 ✅ → 放行，JS 能拿到响应数据
不匹配 ❌ → 拦截，控制台报 CORS 错误
```

具体流程

```shell
前端（localhost:5173）发请求到后端（localhost:8080）
    ↓
浏览器发现「跨域了」
    ↓
先发 OPTIONS 预检请求（非简单请求时）
    ↓
后端返回 Access-Control-Allow-Origin: http://localhost:5173
    ↓
浏览器检查这个头，和当前页面域名对比
    ↓
匹配 ✅ → 发真实请求，JS 能拿到数据
不匹配 ❌ → 报错：No 'Access-Control-Allow-Origin' header is present
```

为什么 maxAge 重要： 每次真实请求前都发一个 OPTIONS，浪费性能。设置 maxAge(3600) 后，1 小时内不再发预检请求。

## 11. Actuator

SpringBoot提供的监控系统状态的接口

```shell
/health      → 还活着吗？数据库通吗？Redis 通吗？
/metrics     → 内存用了多少？CPU 多少？QPS 多少？
/loggers     → 当前日志级别是多少？能调低看细节吗？
/env         → 当前运行环境变量、配置项是什么？
```

你需要配置暴露或者不暴露哪些监控端点

```yml
management:
  endpoints:
    web:
      exposure:
        include: health,info,metrics,loggers # 暴露哪些端点
        exclude: env,beans # 排除敏感端点
  endpoint:
    health:
      show-details: always # 显示健康详情（组件状态）
  health:
    redis:
      enabled: false # 关闭某个健康检查项
```

常用的端点如下
| 端点 | 作用 |
| ------------------- | ---------------------------- |
| `/actuator/health` | 健康状态（UP/DOWN） |
| `/actuator/info` | 应用信息（版本等） |
| `/actuator/metrics` | 指标列表（内存、线程、HTTP） |
| `/actuator/env` | 环境属性（敏感，慎暴露） |
| `/actuator/loggers` | 动态调整日志级别 |
| `/actuator/beans` | 容器中所有 Bean |

## 12. 事务

事务就是一些列的sql操作，事务只能同时成功或同时失败

### 事务传播

方法 B 调方法 A，A 有事务，B 也有事务——B 是加入 A 的事务，还是挂起 A 自己开一个新的？

```java
@Service
public class OrderService {

    @Transactional
    public void createOrder(Order order) {
        orderMapper.insert(order);          // ① 写订单表
        logService.log("创建订单", order.getId());  // ② 写日志表
    }
}

@Service
public class LogService {
    @Transactional
    public void log(String action, Long bizId) {
        logMapper.insert(new Log(action, bizId));
    }
}
```

问题： log() 也有 @Transactional，它和 createOrder() 的事务是什么关系？

传播行为就是回答这个问题：

```text
场景一：REQUIRED（默认）
createOrder() 开了事务 T1
  └─ log() 发现已经有 T1 了 → 加入 T1，不新建
     ↓
如果 log() 抛异常 → T1 整体回滚 → 订单和日志都回滚

场景二：REQUIRES_NEW
createOrder() 开了事务 T1
  └─ log() 发现已经有 T1 → 挂起 T1，开一个新事务 T2
     ↓
如果 log() 抛异常 → 只有 T2 回滚，T1 不受影响
     → 订单创建成功，只是日志没写进去
```

### 事务隔离级别

你说的大方向对，但精确一下：

| 问题       | 原因                    | 后果                                 |
| ---------- | ----------------------- | ------------------------------------ |
| 脏读       | 读了别人没提交的数据    | 数据是假的，别人回滚你就错了         |
| 不可重复读 | 两次读之间被人改了      | 同一事务两次读同一条数据不一样       |
| 幻读       | 两次读之间被人插了/删了 | 同一事务两次查同一个范围，行数不一样 |

**记忆：** 脏读是数据假的，不可重复读是值变了，幻读是行数变了。

### 声明式事务 vs 编程式事务

编程式事务粒度细一点，可以设置部分成功也算成功

```java
public void batchCreate(List<Order> orders) {
     for (Order order : orders) {
         // 每个订单独立事务，一个失败不影响其他
         transactionTemplate.execute(status -> {
             try {
                 orderMapper.insert(order);
                 stockService.deduct(order.getGoodsId(), order.getNum());
                 return null;
             } catch (Exception e) {
                 status.setRollbackOnly();  // 手动标记回滚
                 log.error("订单处理失败", e);
                 return null;
             }
         });
     }
 }
```

### @Transactional 失效的七种场景

1. 通过this调用内部方法，可以通过注入自身引用来解决
2. @Transcational只对public方法生效，把方法改成public就行
3. 异常被try catch吞掉，解决就是不要吞或者手动调用回滚`TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()`
4. 当是受检异常时，因为默认只回滚未受检异常。解决加 rollbackFor = Exception.class
5. 存储引擎不支持事务
6. 方法被final修饰，因为动态代理无法重写final方法
7. 事务中开启了新线程进行异步操作，解决方法就是等事务结束后才进行异步，比如用 `@TransactionalEventListener` 在事务提交后异步处理

### 事务只读化

一个事务里面既有查询又有修改可以配置查询的时候不加锁,MySQL/ORM 可以做优化

```java
// 查询时加 readOnly = true，告诉数据库不需要加锁，MySQL/ORM 可以做优化
@Transactional(readOnly = true)
public Order getById(Long id) {
    return orderMapper.selectById(id);
}
```

## 15、发布事件

### 发布订阅模式

其实就是发布订阅模式的运用

1. 创建事件对象
2. 调用ApplicationEventPublisher 对象发布事件到消息中心
3. 订阅者订阅对应事件，事件发布会调用订阅者的回调函数

### 四种方式

1. @EventListener 注解（推荐，最简单）
2. 实现接口（需要将 `implements ApplicationListener<OrderCreatedEvent>`的类实例注入容器）
3. 异步监听（不阻塞主流程）
4. 条件监听（只有满足条件才处理）

### 事务监听器

可以监听事务不同阶段

1. AFTER_COMMIT:事务提交后执行（最常用）
2. AFTER_ROLLBACK:事务回滚后执行
3. AFTER_COMPLETION:事务完成（无论提交/回滚）
4. BEFORE_COMMIT:事务提交前执行

```java
@Component
public class OrderEventListeners {

    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)  // 事务提交后才执行
    public void handleAfterCommit(OrderCreatedEvent event) {
        // ① 事务已提交，数据已落库
        // ② 如果监听器抛异常，不会导致业务回滚
        // ③ 适合发 MQ 消息、发邮件等操作
        mqService.send("order.created", event.getOrderId());
    }
}
```

实际上Spring 启动时通过反射读参数类型，就知道这个监听器要监听什么事件。比如OrderCreatedEvent事件

### 使用场景

下单后发短信/送积分/发邮件，不需要在 OrderService 里写一行相关代码，新增功能只需加一个 @EventListener 方法。

# 8.22 SpringSecurity

## 介绍

Spring Security是用一串 Servlet 过滤器链统一解决 Web 应用的认证（Authentication，你是谁）、授权（Authorization，你能干什么）两大安全问题，同时内置了密码加密、CSRF 防护、会话管理、方法级权限的框架

## 几个重要的角色

| 组件                     | 类型   | 作用                                                                          |
| ------------------------ | ------ | ----------------------------------------------------------------------------- |
| `SecurityContext`        | 接口   | 安全上下文容器，保存当前登录用户的 `Authentication`                           |
| `SecurityContextHolder`  | 工具类 | 持有 `SecurityContext`，**默认用 `ThreadLocal` 存储**，保证线程隔离           |
| `Authentication`         | 接口   | 认证对象，封装**身份（principal）+ 凭证（credentials）+ 权限（authorities）** |
| `UserDetails`            | 接口   | 框架认识的标准用户模型，从数据库查出的用户要转成它                            |
| `UserDetailsService`     | 接口   | 只做一件事：**根据用户名加载用户**，认证时被调用                              |
| `AuthenticationManager`  | 接口   | 认证入口，真正干活的是它的实现 `ProviderManager`                              |
| `AuthenticationProvider` | 接口   | 具体认证策略，如 `DaoAuthenticationProvider`（查库认证）                      |
| `PasswordEncoder`        | 接口   | 密码加密与比对（`encode` / `matches`）                                        |
| `GrantedAuthority`       | 接口   | 权限项，如 `ROLE_ADMIN`、`order:read`                                         |
| `FilterChainProxy`       | 类     | 安全过滤器链的**总入口**，把多个 `SecurityFilterChain` 串起来                 |
| `SecurityFilterChain`    | 接口   | 一条具体的过滤器链（可配置多条，如 API 链 + 页面链）                          |

它们之间的「三角关系」如下：

```
UserDetailsService（查用户）
        │  返回
        ▼
UserDetails（用户名/密码/权限）  <── 数据库 User 实体转换而来
        │
        │ 交给
        ▼
DaoAuthenticationProvider（认证提供者）
        │  1. 调 UserDetailsService 查用户
        │  2. 调 PasswordEncoder.matches 比对密码
        │  3. 成功则组装 Authentication
        ▼
Authentication（认证对象）
        │  放入
        ▼
SecurityContext ──> SecurityContextHolder（ThreadLocal）
        │  授权时从这里取
        ▼
FilterSecurityInterceptor / AuthorizationFilter（授权判断）
```

也就是如下流程：

1. 用户信息如何获取：你实现UserDetailsService来定义具体获取用户信息的行为，并返回标准用户模型
2. 有了用户信息，具体如何做认证：你需要实现DaoAuthenticationProvider，具体去做认证
